# Слои

Одинаковы для любого бэкенд-стека. Как они выглядят в коде — `stacks/go/structure.md` (Go + Go SDK) и `stacks/php/structure.md` (Laravel + mps/core).

---

## Пять слоёв

| Слой | Отвечает за | Не знает про |
|---|---|---|
| **Domain** | бизнес-правила одного домена: сущность/DTO, интерфейс репозитория, сервис, Command/Query | HTTP, БД, очереди, другие контексты, другие домены |
| **Workflow** *(опционально)* | агрегатная логика между доменами | HTTP, транспорт, детали БД |
| **Entrypoint** | вход извне: HTTP по контекстам (admin/client/mobile/integration), consumers, консоль, cron | бизнес-правила, хранилища |
| **Infrastructure** | реализация репозиториев: Postgres, Redis, HTTP-клиенты внешних сервисов, брокер | бизнес-решения |
| **Common** *(общий бизнес-словарь)* | значения и понятия, нужные двум и более доменам: enum, value-объекты, чистые функции над ними — без зависимостей, ввода-вывода и DI | все остальные слои |
| **Bootstrap / App** | сборка: DI, регистрация модулей, маршрутов, consumers | — |

## Направление зависимостей

```
Entrypoint     → Workflow, Domain
Workflow       → Domain
Infrastructure → Domain          (реализует интерфейсы домена)
Bootstrap      → все слои
все слои       → Common          (Common → ни от чего, кроме языка и библиотек дат)
```

Запрещено (= **[ОШИБКА]** на ревью): `Domain → Infrastructure | Entrypoint | Workflow`, `Workflow → Entrypoint`, `Infrastructure → Entrypoint`, `Entrypoint → Bootstrap`, `Context A → Context B`.

> **Исключение PHP-стека (решение P-4):** интерфейс репозитория в домене возвращает Eloquent-модель из `Infrastructure/Postgres/…/Models` — так устроено ядро `mps/core` (`CRUDRepositoryInterface`). Это единственное разрешённое направление `Domain → Infrastructure` в PHP; остальные запреты действуют. В Go запрет без исключений.

## Правила слоёв, общие для стеков

Как это выглядит на классах — `stacks/<stack>/conventions.md`; здесь само правило, одно место (O-12).

- **Хранилища — только через репозитории.** К БД, кэшу, брокеру, файлам и внешним HTTP ходит только Infrastructure. Сервис, Command/Query, workflow, хендлер и consumer работают с интерфейсом репозитория; прямой запрос (`DB::`, `Model::where`, `gorm.`, клиент Redis) в них — **[ОШИБКА]**, тег `service-direct-db-query` (один для всех слоёв). Нужен запрос — метод в репозитории того домена, чья таблица. Проверяется механически grep-ом (`stacks/<stack>/review-checks.md`, п. 0).
- **Контракт репозитория.** Репозиторий только читает и пишет: формирует запрос, маппит строку в сущность/модель, возвращает результат. Не решает по значениям (`if status == …`), не трансформирует данные под потребителя (`keyBy`, скидки, форматирование), не вызывает другие репозитории и сервисы, не бросает бизнес-исключений. «Не найдено» — `null`/`nil, nil`, не ошибка: что с этим делать, решает вызывающий; методов `*OrFail` нет ни в репозитории, ни в сервисе (**[ВНИМАНИЕ]**, `service-thin-wrapper`). Совмещённых решений `FindOrCreate`/`CreateOrUpdate` нет — два метода, выбор в сервисе; пакетный `upsert` одним SQL без решений в коде допустим. Запись принимает типизированные данные — DTO или аргументы, не карту колонок (`core/style.md`, «Данные между слоями»). Каждый запрос — с таймаутом (`approaches/patterns/performance.md`).
- **Тонкая точка входа.** Хендлер/контроллер/consumer: биндинг и проверка формата → маппинг в DTO → один вызов сервиса, Command или workflow → ответ. Без бизнес-ветвлений, запросов к хранилищам и сборки массивов; перевод результата в протокол (`null` → 404, исключение → код ответа) — его единственная логика. Обёртку ответа (`success`/`data`) даёт middleware стека (Go — `FormattedResponseMiddleware` + `response.*`, PHP — `ApiResponseMiddleware`), в коде она не собирается (`regulations/rest-api.md`, «Формат ответа»).
- **DI — только в сборке.** Контейнер используется в Bootstrap (`app.go`/фабрики, `definitions.php`/провайдеры); в домен, workflow, инфраструктуру и точки входа зависимости приходят через конструктор как интерфейсы. Резолв из контейнера внутри бизнес-кода (`di.Resolve`, `app()`, `resolve()`) — **[ОШИБКА]**. Конструктор отдаёт конкретный тип; интерфейс объявляет потребитель (`regulations/contracts.md`).
- **Метод репозитория — один запрос** (**[ОШИБКА]**, тег `repository-multi-query`; по запросу пользователя, mobile-api-rewrite: «две выборки — это бизнес-логика, функция репы — один запрос»). Публичный метод репозитория выполняет ровно один запрос к хранилищу: один `SELECT`, `UPDATE`, `DELETE`, `INSERT` или `upsert`. Цепочка «выбрать → по результату записать» — бизнес-логика, даже если её шаги тривиальны: заблокировать строки и удалить их, прочитать модель и сохранить её, удалить и вставить, вставить и перечитать. Каждый шаг — свой метод репозитория; порядок шагов и транзакция — в сервисе, Command или workflow (`approaches/patterns/transactions.md`). Блокировка `FOR UPDATE` имеет смысл только внутри транзакции вызывающего, поэтому метод `lock…` без неё не вызывается. Почему: что делать между двумя запросами и где граница транзакции — решение, а репозиторий, который выполняет два запроса, прячет это решение и транзакцию от читателя сервиса.
  - Обновление — одним `UPDATE … WHERE`, а не «прочитать модель → изменить → сохранить». Нужен результат записи — `RETURNING` в том же запросе; нужно знать, нашлась ли строка, — число изменённых строк.
  - Постраничная выборка (`count` + страница внутри одного вызова пагинатора) считается одним запросом. Пакетный `upsert` или `INSERT` многих строк одним SQL — тоже один запрос.
  Синтаксис — `stacks/php/conventions.md` п. 2b, `stacks/go/conventions.md` п. 15b.
- **Запрос виден целиком** (**[ВНИМАНИЕ]**; по запросу пользователя, mobile-api-rewrite MR !3773). Метод репозитория собирает свой запрос в одном месте сверху вниз: источник → условия → подзапросы на месте → сортировка → колонки → маппинг. Кусков запроса в отдельных функциях/методах (`activeQuery()`, `applyFilter(builder)`, общий `baseSelect`), списка колонок константой, скоупов модели нет — колонки пишутся явно в каждом запросе (Go/GORM: запрос без `Select` — все колонки модели — допустим, `stacks/go/conventions.md` п. 15a). Фильтры списка — подряд в том же методе. Почему: запрос, собранный из пяти кусков, не проверить глазами на скоуп и индексы.
  - Повтор **подзапроса** (`EXISTS`, подзапрос в `SELECT`/`FROM`/`JOIN`/`IN`) в двух-трёх методах допустим; в четырёх и более — нужен другой метод с другим смыслом или другая выборка, а не хелпер. Join и простые условия (владелец, активность по датам, получатель, «с удалёнными») под лимит не попадают: повторяются в каждом методе, где нужны, и не выносятся. Почему: простое условие читается на месте за один взгляд, а четыре одинаковых подзапроса — признак, что данные надо брать иначе.
  - Запрос не помещается на экран (ориентир ~40 строк) или нужны три и более подзапроса по таблицам других модулей — запрос делится на несколько методов репозиториев (каждый — по таблицам своего модуля); сервис или workflow вызывает их через интерфейсы и собирает **готовые результаты** пачкой по id. Сам запрос в сервисе/workflow не пишется и не достраивается — ни SQL, ни билдер, ни переданный из репозитория кусок условия (**[ОШИБКА]**, `service-direct-db-query`).
  - Приватный помощник, который собирает **значения** для записи (поля `SET` из DTO), — не кусок запроса и допустим.
  Синтаксис — `stacks/php/conventions.md` п. 2a, `stacks/go/conventions.md` п. 15a.
- **Модель/сущность без поведения инфраструктуры.** Сущность домена и модель БД не содержат запросов, скоупов, статических «найти», побочных эффектов в хуках; бизнес-правило про объект — метод сущности или сервис (`regulations/entity.md`), выборка — репозиторий.

## Домен и модуль

- **Домен** — предметная область (`billing`, `catalog`, `session`). **Модуль** — сущность/подобласть внутри домена (`tariff`, `parking`).
- Путь во всех слоях — `{domain}/{module}`. Мелкий проект без доменов — только `{module}`; решение принимается один раз на проект.
- Связь модулей **внутри одного домена** — Command/Query в домене; связь **разных доменов** — workflow (см. `cross-domain.md`). Command/Query, которому нужны несколько модулей своего домена, лежит в **модуле-владельце результата** и получает остальные модули через интерфейсы (решение O-6): `fiscalize_receipt_command.go` → `domains/billing/fiscal_receipt/`.

## Контекст (аудитория)

- Контекст точки входа — для кого API: `admin`, `client`/`mobile`, `integration`, `internal`, `partner`.
- Контексты — разные продукты: если логика для двух контекстов различается, это разные реализации, а не `if` по роли.
- Один эндпойнт для двух аудиторий — две директории.

## Валидация, доступ и фильтр данных — три разные ответственности (O-11)

| Что | Где | Отвечает на вопрос | Ответ при нарушении |
|---|---|---|---|
| **Валидация входа** | Request / DTO-биндинг точки входа | данные в правильном формате? (типы, обязательность, границы, enum) | 422 |
| **Доступ** | middleware (interceptor) своего контекста | этому пользователю можно? (аутентификация; роль/право на операцию; принадлежность здания/организации/записи из заголовка **и** из параметров запроса) | 401 / 403 |
| **Фильтр данных** | сервис → репозиторий | какие записи вернуть/изменить в разрешённых границах | чужая запись по id — 404 |

- **Проверка доступа в валидации — [ОШИБКА].** Валидатор не ходит в хранилище за правами и не дублирует middleware; правило «здание доступно пользователю» в Request — ошибка, даже если «удобно».
- **Middleware кладёт готовый контекст** (разрешённые здания, организация) в контекст запроса, а не в данные запроса: PHP — `$request->attributes`, Go — `context.Context`. Клиент его не подменит, поля тела не перезаписываются.
- **Сервис получает контекст как обычный фильтр** (`buildingIds`, null — без ограничения), применяет его в запросе к хранилищу и про пользователей и права не знает.
- Чтение контекста без middleware на маршруте — ошибка конфигурации (исключение), а не «без ограничения».
- **Роли и права на операцию — middleware на маршруте, до контроллера** (**[ОШИБКА]** иначе). «Может ли пользователь с этой ролью/правом вызвать эту операцию» навешивается на роут (группу роутов) именованной middleware с именем права; контроллер/хендлер, сервис, Command, workflow, репозиторий ролей и прав не проверяют и про них не знают. Причины: правило доступа видно в одном месте — в маршрутах; домен не зависит от модели пользователей и переиспользуется из консоли/очереди; запрос без права отсекается до валидации и запросов в БД.
  ```
  // плохо — в контроллере/хендлере или сервисе
  if (!$user->hasPermission('tariffs.update')) { throw ... }      if !admin.HasPermission("tariffs.update") { ... }
  // хорошо — на маршруте
  Route::put(...)->middleware('permission:tariffs.update')         group.PUT(..., middleware.RequirePermission("parking.admin.tariffs.update"), h.Update)
  ```
  Не путать с соседними случаями:
  - **Логика различается по роли/аудитории** (админ видит больше полей, может то, чего не может клиент) — это не проверка прав, а разные контексты: отдельный эндпойнт и `{Context}{Entity}Service` (см. «Контекст» выше), не `if ($user->isAdmin())` в сервисе.
  - **Доступ к конкретной записи** (своё здание/организация) — middleware кладёт границы в контекст, сервис применяет их фильтром, чужая запись — 404 (пункты выше).
  - **Консоль, крон, consumer** — внутренние точки входа, проверки ролей нет; если сообщение несёт действие пользователя — право проверено там, где оно принято (HTTP-вход продюсера).
  - **Машинный вызов** (подпись интеграции, служебный токен) — своя middleware аутентификации; права пользователя к нему не применяются, пропуск — явно в middleware прав (как `IsMachineCaller` в `parking-session-service`).

### Меры по слоям

Любая мера из `threats.md`, `design.md` и кода лежит в своём слое по этой таблице, а не по образцу легаси (`approaches/process/legacy-refactor.md`, «Что переносится»). Мера не в своём слое — находка того же уровня, что и в коде. Синтаксис стека и примеры — `stacks/<stack>/security.md`, «Меры по слоям».

| Мера | Слой |
|---|---|
| Формат: типы, обязательность, границы, enum, форма вложенных коллекций | валидация точки входа (Request / биндинг) — без запросов к хранилищу |
| Роль/право на операцию; здание/организация из заголовка и параметров | middleware контекста → контекст запроса |
| Существование связанной записи | сервис/workflow через репозиторий; сущность чужого домена — workflow через репозиторий того домена (O-7) |
| Принадлежность записи скоупу актора | фильтр в запросе репозитория; скоуп — обязательный аргумент, `null` передаётся явно (`scope-param-defaults-unrestricted`) |
| Уникальность | уникальный индекс + перехват нарушения → 422; проверка в сервисе — для понятного сообщения, не как защита (`approaches/patterns/concurrency.md`) |
| Доменные инварианты DTO (без данных из БД) | `{E}DtoValidator` / `{entity}_validator.go` (O-18) |

Повод — ревью AINA-2628 (`superapp-api`): «валидация входных данных не место для проверки доступов», «проверка прав не совсем зона сервиса». Как в коде — `stacks/php/conventions.md` (п. 9, 19a), Go — `stacks/go/conventions.md` (п. 7).

## Service, Command/Query, Workflow

Это разные вещи, не ступени одного и того же:

| | Что это | Где живёт | Границы |
|---|---|---|---|
| **Service** | операции модуля (CRUD и простая бизнес-логика) | домен/модуль | один домен |
| **Command / Query** | **тот же сервис**, вынесенный в отдельный класс, когда операция слишком большая, чтобы перегружать сервис: Command — изменение, Query — чтение. Один класс — одна операция | домен/модуль, рядом с сервисом | один домен |
| **Workflow** | агрегатная **междоменная** логика: сценарий, которому нужны 2+ домена | слой workflow | несколько доменов |
| **Validator** | доменные инварианты DTO (`{E}DtoValidator`): чистая проверка значений DTO между собой, возвращает ошибки по полям. **Не сервис** — без зависимостей, хранилища, репозиториев и DI; бросает исключение вызывающий | домен/модуль: PHP — папка `Validators/`, Go — файл `{entity}_validator.go` в пакете модуля (отдельный пакет дал бы цикл импортов с DTO) | один DTO |

Как выбирать:

1. Операция в рамках одного домена, небольшая → метод сервиса модуля.
2. Операция в рамках одного домена, большая (много шагов, зависимостей, ветвлений) → Command (изменение) / Query (чтение) в том же модуле.
3. Сценарий затрагивает 2+ домена → Workflow. Не потому что «большой», а потому что междоменный.

Валидатор вызывают сервис, Command и workflow — там, где DTO пишется. Проверки, которым нужны данные (существование, уникальность, принадлежность скоупу), — не в валидаторе, а в сервисе/workflow через репозиторий (`stacks/<stack>/security.md`, «Меры по слоям»).

Зависимости (решение O-7):
- **Workflow** — агрегат над доменами: может брать **репозитории и сервисы любых доменов напрямую** через конструктор. Агрегат транзакционен по умолчанию (O-8, `approaches/patterns/transactions.md`).
- **Command/Query и Service** живут в домене: берут только репозитории **своего** домена; чужой домен им недоступен ни через репозиторий, ни через сервис — такой сценарий переезжает в workflow. Модули своего домена — через интерфейсы (O-6).

- **Общий бизнес-словарь — `Common`, не импорт и не копия.** Домен не импортирует ничего из чужого домена — ни сервис, ни репозиторий, ни сущность, ни enum. Понятие, которое нужно второму домену (тип услуги, единицы времени, деньги, период), переезжает в слой **Common** (PHP — `{подпроект}/Common/`, Go — `internal/common/`) и оттуда импортируется всеми. Пока понятие нужно одному домену — живёт в нём. В Common — только enum, value-объекты (неизменяемые, с самопроверкой, без идентичности), чистые функции над ними и их исключения; без зависимостей (кроме языка, библиотеки дат и базового трейта enum ядра), ввода-вывода, DI и состояния. Сервисы, репозитории, сущности с идентичностью, Command/Query, процессы, DTO сценариев — не в Common: правило, нужное двум доменам, — workflow. Копия понятия в другом домене (тот же набор значений под другим именем) — **[ОШИБКА]**, тег `duplicated-enum`; логика с зависимостями в Common — **[ОШИБКА]**, тег `common-with-logic`. Границы Common закрепляются архитектурным тестом (`approaches/process/testing.md`; ставится в волну 0 задачи, где `Common` появляется в проекте впервые). Почему: `Core` — техника (транзакции, пагинация), бизнес-словарь в нём размывает слой; копии в каждом домене расходятся при новом значении (mobile-api-rewrite: три копии единиц времени, копия типов услуг); `Domains/Shared` с логикой запрещён (P-11) — Common ограничен словарём, чтобы не стать им.

Ошибки: междоменная логика в Command/Query или в сервисе домена, в т.ч. репозиторий/сервис чужого домена в их конструкторе — **[ОШИБКА]**; однодоменная операция, вынесенная в workflow, — **[ВНИМАНИЕ]** (место — Command/Query домена).

Новый слой, новый тип компонента, которого нет в этой таблице и в `stacks/*/structure.md`, — не создаётся молча: вопрос пользователю и строка в `rules-log.md` задачи.

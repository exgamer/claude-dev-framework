# Интерфейсы и контракты

Выжимка из `INTERFACE-AND-CONTRACT-REGULATION.md`.

---

## Интерфейс нужен, если хотя бы одно

1. Больше одной реализации (есть или реально планируется).
2. Граница слоя (домен ↔ инфраструктура, сервис ↔ внешний API).
3. Зависимость от внешнего мира (БД, сеть, очередь, время, UUID).
4. Нужна подмена в тестах бизнес-логики.

Примеры: Repository, HTTP/gRPC-клиент, Publisher, Cache, TxManager, Clock.

## Интерфейс не нужен

- Одна реализация, меняться не будет.
- Внутренняя бизнес-логика (Service, UseCase). **По умолчанию сервисы без интерфейса** — конструктор возвращает конкретный тип.
- «На всякий случай».

Исключение — порт внешней системы: интерфейс объявляет домен-потребитель, реализует адаптер в Infrastructure (`architecture/integrations.md`). На чужой домен домен интерфейсов не объявляет — такой сценарий в workflow, он берёт интерфейсы доменов напрямую (O-7, `architecture/cross-domain.md`).

## Форма

- Интерфейс объявляет **потребитель**, а не реализация. Минимум методов — только то, что реально вызывается.
- 1–5 методов — норма, 6–10 — пересмотреть, 10+ — декомпозировать.
- Не протекают детали реализации: ORM-типы, HTTP-модели, флаги поведения.

## Что фиксирует контракт

Назначение · входные данные (обязательные/опциональные) · выходные данные · ошибки · гарантии (идемпотентность, порядок, консистентность) · нефункциональное (таймауты, ретраи, лимиты).

## Внешние интеграции

- Контракт описан (OpenAPI / AsyncAPI / JSON Schema).
- DTO внешнего API не смешиваются с доменными моделями — маппер обязателен.
- Изменение контракта — с версионированием.

## Моки в тестах

Мокаем: Repository, внешние клиенты, шину сообщений, Clock/UUID. Не мокаем: бизнес-сервисы, UseCase, мапперы.

# Git: ветки, коммиты, MR

Выжимка из `BRANCH-NAMING-CONVENTION.md`, `COMMIT-NAMING-CONVENTION.md`, `GITFLOW.md`, `CODE-REVIEW-REGULATIONS.md`.

> Модель никогда не делает `commit`/`push` без явного подтверждения на каждый раз.

---

## Ветки

- Имя ветки = ключ задачи, строго `PROJECTKEY-номер`: `AINA-722`.
- Запрещено: `feature/AINA-722`, `AINA-722-fix`, `AINA_722`, `aina-722`, `AINA722`.
- Рабочая ветка создаётся от `release`; hotfix — от `production`.
- Поток: ветка задачи → MR → `stage` (тест) → `release` → `production`. Править прямо в `stage` нельзя.

## Коммиты

```
тип: описание #КЛЮЧ-задачи
```

| Тип | Когда |
|---|---|
| `feat` | новая функциональность |
| `fix` | исправление бага без новой функциональности |
| `refactor` | рефакторинг без изменения поведения |
| `perf` | оптимизация производительности |
| `conf` | конфиги, CI, env, yaml |

- Описание по-русски, с маленькой буквы, без точки, до 70 символов.
- Одна логическая задача — один коммит (squash перед merge при необходимости).

```
feat: добавлен расчёт долга по тарифу #AINA-722
fix: исправлено кэширование ошибок шлюза kassa24 #AINA-801
```

## MR — условия приёма на ревью

1. Проект собирается, линтер/статанализ без ошибок, тесты проходят (если CI нет — прогон на авторе).
2. Self-review: нет отладочного кода, закомментированных блоков, лишних логов.
3. Описание: что сделано, зачем, какой функционал затронут, ссылка на задачу. «Готово»/«фиксы» — недопустимо.
4. Документация обновлена (Swagger при изменении API, доки при изменении схемы/конфига).
5. Скоуп MR = задача, посторонних изменений нет.
6. Ветка и коммиты по конвенции.

## Замечания на ревью (Conventional Comments)

- `blocking:` — баг, нарушение регламента, безопасность. Блокирует merge, требует ссылки на пункт правила.
- `suggestion:` / `nit:` — не блокирует.
- `question:` — нужен ответ.
- `praise:` — удачное решение.

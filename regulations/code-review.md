# Code review: приём MR, замечания, разногласия

Выжимка из `CODE-REVIEW-REGULATIONS.md` (`backend-regulation/docs/`). Ролевая модель — кто вправе ревьюить и апрувить, сколько апрувов, критичные зоны — в `CODE-REVIEW-APPROVAL-AUTHORITY.md`; во фреймворк не перенесена, при необходимости читать там.

Ветки, коммиты, Git Flow — `git.md`.

---

## Принципы

- Ревьюится каждое изменение: в `production` код попадает только через MR и ревью. Self-approve запрещён, включая тимлида.
- Ревьюится изменение, а не автор. Замечания — к коду, по существу.
- Маленькие MR; крупная задача — под-MR в агрегирующую ветку (ниже).
- Крупное архитектурное изменение — согласование подхода до кода (design-doc или обсуждение в задаче). Во фреймворке это `design.md`.
- Draft/WIP MR для раннего фидбэка — норма.
- Продвижение MR — ответственность автора (напомнить, если никто не взял). Апрув не снимает с автора ответственности за качество.

## Условия приёма MR на ревью (gate)

Не выполнено хотя бы одно — ревьюер вправе вернуть MR без проверки.

1. Локально: проект собирается, линтер/статанализ без ошибок, автотесты проходят (нет CI на MR — прогон на авторе).
2. Self-review: нет отладочного кода, закомментированных блоков, лишних логов; к неочевидным местам — пояснения.
3. Описание MR: что сделано, зачем, какой функционал затронут, ссылка на задачу. «Готово»/«фиксы» — недопустимо.
4. Документация обновлена: Swagger при изменении API, доки при изменении схемы/конфига/процессов. Без неё задача не завершена.
5. Скоуп MR = задача: номер, описание и состав изменений совпадают, посторонних изменений нет.
6. Ветка и коммиты — по конвенциям (`git.md`).

## Апрувы

После значимых правок по итогам ревью ранее полученные апрувы сбрасываются — повторное ревью.

## Агрегирующий MR

Подзадачи — отдельные небольшие под-MR в агрегирующую ветку; **всё ревью кода — в под-MR**. Напрямую в ветку не коммитят: конфликты и склейка — тоже под-MR. Финальный MR в релизную ветку нового кода не содержит и по договорённости команды мержится без ревью, если: все под-MR смержены с апрувами; мимо под-MR не коммитили; сливается без конфликтов и правок; сборка и тесты зелёные. Иначе лишнее — в отдельный под-MR.

## Замечания на ревью (Conventional Comments)

Каждое замечание ревьюер помечает префиксом:

| Префикс | Что это | Merge |
|---|---|---|
| `blocking:` | баг, нарушение регламента, риск безопасности или стабильности; **обязательна ссылка на дефект или пункт регламента** | блокирует до исправления или явного согласования |
| `suggestion:` / `nit:` | стиль, вкусовые улучшения, мелкие предложения | не блокирует, автор решает сам |
| `question:` | нужен ответ автора, правка не обязательна | — |
| `praise:` | удачное решение | — |

Правила обработки:

- **Автор отвечает на каждое замечание**: исправляет либо обосновывает отказ. Молчание — не ответ.
- **Тред закрывает открывший** (или автор после исправления — по договорённости команды). Чужие треды не резолвить.
- **Кто заблокировал — тот и апрувит**: ревьюер с `blocking:` после правок возвращается, перепроверяет и ставит апрув; не договорились — эскалация.
- **LGTM with comments**: остались только `suggestion`/`nit` — апрув ставится сразу, без второго круга; автор применяет по своему решению.

### Соответствие уровням фреймворка

Находки ревью во фреймворке (`approaches/process/review.md`) и префиксы регламента — одно и то же с двух сторон:

| Фреймворк | Префикс | Примечание |
|---|---|---|
| [БЕЗОПАСНОСТЬ], [ОШИБКА] | `blocking:` | ссылка на правило — тег и файл правил (`checklist.md`, `security.md`, `review-findings.md`, регламент) |
| [ВНИМАНИЕ] | `suggestion:` | |
| [ИНФО] | `nit:` | |
| «Не покрыто правилами», известный спор (`core/decisions.md`) | `question:` | не находка: правила нет — спрашиваем, а не блокируем |
| — | `praise:` | удачный паттерн, которого нет в правилах, — кандидат в `review-findings.md`/эталон |

Обратно: `blocking:` ревьюера без ссылки на правило — повод найти правило во фреймворке или зафиксировать пробел (`core/rules-evolution.md`), а не повод игнорировать. Разбор тредов MR — `approaches/process/mr-threads.md` (`/dev-mr`).

## Разногласия

1. Автор и ревьюер договариваются в треде по существу.
2. Нет консенсуса — эскалация руководителю (тимлид / руководитель отдела по ролевой модели). Его решение финальное.
3. **Спор по стилю, не закрытый правилом, текущий MR не блокирует** — фиксируется и выносится в обновление регламентов/линтеров. Во фреймворке — строка в `rules-log.md` и `/dev-rule`.

## Роли вне ролевой модели

- QA проверяет наличие апрувов и без них задачу в тестирование не берёт.
- Автор агрегирующего MR отвечает за то, что в ветку смержены только отревьюенные под-MR.

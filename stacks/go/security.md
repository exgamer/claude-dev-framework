# Безопасность (Go): чеклист ревью

Из `go-reviewer` (раздел 5.1). Теги — для колонки «Уязвимость» в отчёте и статистики повторяющихся ошибок (`approaches/process/review.md`, «Теги»). Каталог тегов (тег — суть, общий для стеков) — `approaches/process/security.md`, «Каталог тегов безопасности»; здесь — признаки в коде Go. Тег из каталога без строки здесь — искать по его сути.

Проверяй независимо от типа компонента — это чек-лист уязвимостей, а не архитектурное правило. Каждая подтверждённая находка помечается **[БЕЗОПАСНОСТЬ]**, выносится в отдельный раздел отчёта (см. `approaches/process/review.md`, «Отчёт») и **всегда** переводит вердикт ревью в **КРИТИЧНО**, независимо от количества остальных находок.

| Уязвимость | Тег | Признаки в коде |
|---|---|---|
| SQL Injection | `sql-injection` | `fmt.Sprintf`/конкатенация строк в SQL, переданном в `db.Raw(...)`, `db.Exec(...)`, `Where(...)` строкой — вместо параметризованных плейсхолдеров `?` / gorm-биндингов |
| Command Injection | `command-injection` | `exec.Command`/`exec.CommandContext` собирается из пользовательского ввода (конкатенация, `sh -c "..."`) без allowlist |
| SSRF | `ssrf` | HTTP-запрос (`gosdk-http-request-builder`, `http.Client.Do`) на URL/host, пришедший от пользователя, без валидации схемы/домена |
| Path Traversal | `path-traversal` | `os.Open`/`os.ReadFile`/`filepath.Join` с пользовательским именем файла без `filepath.Clean` + проверки, что путь не выходит за пределы базовой директории |
| Небезопасная десериализация | `insecure-deserialization` | `json.Unmarshal`/`gob.Decode` в `interface{}`/`any` от недоверенного источника с последующим `reflect`-based динамическим вызовом |
| Захардкоженные секреты | `hardcoded-secret` | API-ключ, пароль, JWT secret, connection string — литералом в коде вместо конфига/env/vault |
| Слабая криптография | `weak-crypto` | `md5`/`sha1` для хеширования паролей вместо `bcrypt`/`argon2`; `math/rand` для генерации токена/сессии/пароля вместо `crypto/rand` |
| Broken Access Control / IDOR | `broken-access-control` | Handler получает/меняет ресурс по ID из path/body без проверки, что ресурс принадлежит текущему пользователю/тенанту (схема — `architecture/layers.md`, «Принадлежность записи скоупу — два случая»: id владельца из запроса — 403 в middleware, по ID записи — скоуп из `context.Context` аргументом сервиса и условие в запросе репозитория, чужая — 404, кэш по ID — сверка после чтения; эталон — `examples/tariff`). Проверять **каждый** handler ресурса по отдельности — типично, что `list`/`get` скоупят по владельцу правильно, а `update`/`cancel`/`destroy` того же ресурса полагаются только на факт валидного ID |
| Отсутствие мульти-тенантного скоупа | `tenant-scope-missing` | `list`/`search`-хендлер принимает id сущности-владельца (`tenant_id`/`company_id`/`parking_id`/`department_id`/любой аналог — название разное в каждом сервисе, важна роль «то, чем ограничен текущий актор», а не буква поля) как **необязательный** query/body-параметр вместо обязательного скоупа, выводимого сервером из прав текущего актора (найти, как в конкретном сервисе выражается «какими сущностями он управляет», и сверять с этим). Без параметра — отдаёт данные ВСЕХ сущностей; с чужим id — отдаёт чужую. Отдельный случай от строки выше: там — единичный ресурс по ID, здесь — списочный/агрегирующий эндпоинт, который выдаёт чужие данные не из-за угадывания ID, а из-за отсутствия обязательного фильтра |
| Ссылка на чужой ресурс по id во входе | `cross-scope-reference` | DTO создания/изменения несёт id другой записи или ресурса (`ImageIDs []uint`, `FileID`, `ParentID`, связанный объект), и сервис пишет привязку без поиска этих id в скоупе актора — чужой файл привязывается к своей записи и затем отдаётся в её ответе. Хорошо: сервис/workflow ищет набор одним запросом со скоупом (`WHERE id IN (…) AND owner/parking IN (…)`), найдено меньше, чем передано, — 422 по полю, один текст для «нет» и «чужой» |
| Отсутствие auth-middleware | `missing-auth-middleware` | Новый route/handler зарегистрирован без auth middleware там, где домен/паттерн соседних ручек требует авторизации. Отдельно: если по названию/summary ручки видно, что это административное действие (`cancel`, `force-*`, `refund` и т.п.), а зарегистрирована она в client-группе без единого auth-middleware, — не вопрос «осознанно?», а прямая находка [БЕЗОПАСНОСТЬ] (`review-findings.md`) |
| Fail-open авторизация | `fail-open-authorization` | Middleware/сервис прав по умолчанию **разрешает** запрос, если запись о праве/роли для маршрута не найдена (`if permission == nil { return next() }` вместо явного `Forbidden`). Отдельно проверять генератор/сидер прав: если имя роута не попадает под его конвенцию — для такого роута право никогда не будет создано, и fail-open становится постоянным, а не временным |
| Webhook/callback без проверки подписи | `unverified-webhook` | Хендлер колбэка платёжного шлюза или другой внешней системы доверяет статусу/сумме из тела запроса и меняет состояние платежа/сессии (`MarkPaid`, `Complete`, ...) без проверки HMAC/подписи/секрета по протоколу конкретного шлюза. Смотреть каждый шлюз провайдера (`internal/entrypoints/**/http/{provider}`) по отдельности — проверка подписи в одном шлюзе не гарантирует её наличие в другом (см. эвристику «сверить с соседним шлюзом» в `review-findings.md`) |
| Некорректная проверка JWT | `jwt-validation-weak` | `jwt.Parse` без проверки алгоритма (допускает `alg: none`) или без проверки подписи/`exp` |
| Перебор без лимита | `missing-rate-limiting` | Хендлер проверяет угадываемое значение (логин, OTP, сброс пароля, промокод, купон, код подтверждения, инвайт, короткий токен) без middleware лимита частоты по пользователю/номеру и IP; неудачная попытка не увеличивает счётчик (Redis `INCR` с TTL) |
| Перечисление пользователей | `user-enumeration` | Логин, сброс пароля или регистрация отвечают по-разному на существующий и несуществующий аккаунт: разный код (`404` против `200`), разный `message`, ранний возврат без хеширования пароля или отправки (разница во времени). Хорошо: один ответ «код или письмо отправлены», для несуществующего — та же работа по времени |
| Rate limit обходится подменой IP | `spoofable-rate-limit` | Rate-limit/lockout ключуется по IP клиента (`c.ClientIP()` в gin), при этом доверенные прокси не ограничены (`gin.Engine.SetTrustedProxies` не вызван / вызван с широким диапазоном) — `c.ClientIP()` в этом случае читает `X-Forwarded-For` от любого клиента, лимит обходится подменой заголовка на каждый запрос |
| Динамическая запись без allowlist полей | `dynamic-mass-assignment` | `db.Model(&entity).Updates(requestMap)` / `Updates(rawJSONMap)` — весь декодированный из запроса `map[string]interface{}`/DTO пишется в БД без allowlist разрешённых колонок; клиент может передать лишние поля (статус, флаг доступа, баланс), которых в его DTO по контракту быть не должно, и они всё равно применятся |
| Утечка чувствительных данных в логи | `sensitive-data-in-logs` | `logger.Info/Error(...)` логирует полное тело запроса, пароль, токен, номер карты |
| Утечка внутренних деталей в ответе | `internal-details-leak` | HTTP-хендлер возвращает клиенту `err.Error()` / stack trace вместо обобщённого сообщения. Отдельный случай — техническая ошибка (драйвер Postgres/Redis) текстом в `message` через `response.ErrorResponse(c, err)` SDK — уровень этого случая в каталоге (`approaches/process/security.md`, сверка 2026-10-20), не [БЕЗОПАСНОСТЬ]; закрыть ли и как (обёртка на границе хендлера или как есть) — выбор разработчика (`go-sdk/exceptions.md`, «Техническая ошибка в ответе»). Текст паники и стек, которые отдаёт recovery SDK из `InitRouter`, — не находка сервиса; сама паника в коде сервиса — находка по памятке, как обычно (`go-sdk/exceptions.md`, «Паника в обработчике») |
| Небезопасная загрузка файлов | `insecure-file-upload` | `c.SaveUploadedFile(file, filepath.Join(dir, file.Filename))` — имя и расширение от клиента; тип из `file.Header.Get("Content-Type")` (заявлен клиентом) вместо `http.DetectContentType` по первым 512 байтам против allowlist; принимается HTML/JS/XML; SVG отдаётся `c.File(path)` inline с домена приложения (с `nosniff` или без — он SVG не обезвреживает), другой файл — без `X-Content-Type-Options: nosniff` (хорошо — `c.FileAttachment` или отдельный домен/хранилище) |
| Документация API на проде | `api-docs-exposed` | Маршрут Swagger ставит SDK (`InitRouter`, `go-sdk/capabilities.md`, «Swagger UI и схема») — до `router.Use`, middleware сервиса на него не действует. http-core ≥ v1.1.0 (GitLab и GitHub): `SWAGGER_ENABLED` включён (`true`/`1` без учёта регистра) в конфиге прода — values, манифест, переменные CI прода, `ENV` в Dockerfile или compose прод-образа. http-core < v1.1.0 — маршрут есть всегда: проверять в диффе с новым сервисом или деплой-конфигом прода. В обоих случаях: в диффе конфиг ingress/gateway без закрытия `/<префикс>/*` аутентификацией — находка; конфига в диффе нет — неподтверждённая находка (уровень — `approaches/process/security.md`, шапка каталога) с вопросом в MR, закрыт ли путь на проде. Свой маршрут Swagger без явной настройки, выключенной по умолчанию, и без auth-middleware группы — тоже |
| Open Redirect | `open-redirect` | Redirect на URL, взятый из query/body, без проверки что это относительный/allowlisted путь |
| Секрет в артефакте сборки | `secret-in-build-artifact` | CI кладёт реальный секрет (registry-токен, `.netrc`, приватный SSH-ключ для приватных Go-модулей) в файл сборочного контекста без последующего исключения — `Dockerfile` без `.dockerignore` копирует его в слой образа (`COPY . .` после генерации секрета) |

Если находка не подтверждена однозначно (нет прямого пользовательского ввода в опасном месте) — не флагай, чтобы не плодить false positive; при сомнении отметь как **[ВНИМАНИЕ]** с пояснением риска, а не как **[БЕЗОПАСНОСТЬ]**.

## Меры по слоям

Таблица слоёв общая — `architecture/layers.md`, «Меры по слоям». В Go: формат — тег `binding` в хендлере без запросов к хранилищу (`conventions.md` п. 7); доступ — middleware контекста → `context.Context`; уникальность — индекс + перехват `23505` → 422 (`checklist.md` п. 25); значения входа DTO — `{entity}_validator.go` (O-18), правила состояния — методы сущности (`regulations/entity.md`, O-26).

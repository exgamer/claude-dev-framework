# Безопасность (Go): чеклист ревью

Из `go-reviewer` (раздел 5.1). Теги — для колонки «Уязвимость» в отчёте и статистики повторяющихся ошибок (`approaches/process/review.md`, «Теги»); у PHP-аналогов те же теги.

Проверяй независимо от типа компонента — это pentest-ориентированный чек-лист, а не архитектурное правило. Каждая подтверждённая находка помечается **[БЕЗОПАСНОСТЬ]**, выносится в отдельный раздел отчёта (см. `approaches/process/review.md`, «Отчёт») и **всегда** переводит вердикт ревью в **КРИТИЧНО**, независимо от количества остальных находок.

| Уязвимость | Тег | Признаки в коде |
|---|---|---|
| SQL Injection | `sql-injection` | `fmt.Sprintf`/конкатенация строк в SQL, переданном в `db.Raw(...)`, `db.Exec(...)`, `Where(...)` строкой — вместо параметризованных плейсхолдеров `?` / gorm-биндингов |
| Command Injection | `command-injection` | `exec.Command`/`exec.CommandContext` собирается из пользовательского ввода (конкатенация, `sh -c "..."`) без allowlist |
| SSRF | `ssrf` | HTTP-запрос (`gosdk-http-request-builder`, `http.Client.Do`) на URL/host, пришедший от пользователя, без валидации схемы/домена |
| Path Traversal | `path-traversal` | `os.Open`/`os.ReadFile`/`filepath.Join` с пользовательским именем файла без `filepath.Clean` + проверки, что путь не выходит за пределы базовой директории |
| Небезопасная десериализация | `insecure-deserialization` | `json.Unmarshal`/`gob.Decode` в `interface{}`/`any` от недоверенного источника с последующим `reflect`-based динамическим вызовом |
| Захардкоженные секреты | `hardcoded-secret` | API-ключ, пароль, JWT secret, connection string — литералом в коде вместо конфига/env/vault |
| Слабая криптография | `weak-crypto` | `md5`/`sha1` для хеширования паролей вместо `bcrypt`/`argon2`; `math/rand` для генерации токена/сессии/пароля вместо `crypto/rand` |
| Broken Access Control / IDOR | `broken-access-control` | Handler получает/меняет ресурс по ID из path/body без проверки, что ресурс принадлежит текущему пользователю/тенанту. Проверять **каждый** handler ресурса по отдельности — типично, что `list`/`get` скоупят по владельцу правильно, а `update`/`cancel`/`destroy` того же ресурса полагаются только на факт валидного ID |
| Отсутствие мульти-тенантного скоупа | `tenant-scope-missing` | `list`/`search`-хендлер принимает id сущности-владельца (`tenant_id`/`company_id`/`parking_id`/`department_id`/любой аналог — название разное в каждом сервисе, важна роль «то, чем ограничен текущий актор», а не буква поля) как **необязательный** query/body-параметр вместо обязательного скоупа, выводимого сервером из прав текущего актора (найти, как в конкретном сервисе выражается «какими сущностями он управляет», и сверять с этим). Без параметра — отдаёт данные ВСЕХ сущностей; с чужим id — отдаёт чужую. Отдельный случай от строки выше: там — единичный ресурс по ID, здесь — списочный/агрегирующий эндпоинт, который выдаёт чужие данные не из-за угадывания ID, а из-за отсутствия обязательного фильтра |
| Отсутствие auth-middleware | `missing-auth-middleware` | Новый route/handler зарегистрирован без auth middleware там, где домен/паттерн соседних ручек требует авторизации. Отдельно — не путать с «межсервисный эндпоинт по умолчанию без auth» (см. `review-findings.md`): если по названию/summary ручки видно, что это административное действие (`cancel`, `force-*`, `refund` и т.п.), а зарегистрирована она в client-группе без единого auth-middleware — это не «осознанный межсервисный паттерн», а прямая находка [БЕЗОПАСНОСТЬ] |
| Fail-open авторизация | `fail-open-authorization` | Middleware/сервис прав по умолчанию **разрешает** запрос, если запись о праве/роли для маршрута не найдена (`if permission == nil { return next() }` вместо явного `Forbidden`). Отдельно проверять генератор/сидер прав: если имя роута не попадает под его конвенцию — для такого роута право никогда не будет создано, и fail-open становится постоянным, а не временным |
| Webhook/callback без проверки подписи | `unverified-webhook` | Хендлер колбэка платёжного шлюза (`kaspi`, `halyk`, `kassa24`, ...) или другой внешней системы доверяет статусу/сумме из тела запроса и меняет состояние платежа/сессии (`MarkPaid`, `Complete`, ...) без проверки HMAC/подписи/секрета по протоколу конкретного шлюза. Смотреть каждый шлюз в `internal/entrypoints/**/http/{kaspi,halyk,kassa24,...}` по отдельности — проверка подписи в одном шлюзе не гарантирует её наличие в другом (см. эвристику «сверить с соседним шлюзом» в `review-findings.md`) |
| Некорректная проверка JWT | `jwt-validation-weak` | `jwt.Parse` без проверки алгоритма (допускает `alg: none`) или без проверки подписи/`exp` |
| Rate limit обходится подменой IP | `spoofable-rate-limit` | Rate-limit/lockout ключуется по IP клиента (`c.ClientIP()` в gin), при этом доверенные прокси не ограничены (`gin.Engine.SetTrustedProxies` не вызван / вызван с широким диапазоном) — `c.ClientIP()` в этом случае читает `X-Forwarded-For` от любого клиента, лимит обходится подменой заголовка на каждый запрос |
| Динамическая запись без allowlist полей | `dynamic-mass-assignment` | `db.Model(&entity).Updates(requestMap)` / `Updates(rawJSONMap)` — весь декодированный из запроса `map[string]interface{}`/DTO пишется в БД без allowlist разрешённых колонок; клиент может передать лишние поля (статус, флаг доступа, баланс), которых в его DTO по контракту быть не должно, и они всё равно применятся |
| Утечка чувствительных данных в логи | `sensitive-data-in-logs` | `logger.Info/Error(...)` логирует полное тело запроса, пароль, токен, номер карты |
| Утечка внутренних деталей в ответе | `internal-details-leak` | HTTP-хендлер возвращает клиенту `err.Error()` / stack trace вместо обобщённого сообщения |
| Open Redirect | `open-redirect` | Redirect на URL, взятый из query/body, без проверки что это относительный/allowlisted путь |
| Секрет в артефакте сборки | `secret-in-build-artifact` | CI кладёт реальный секрет (registry-токен, `.netrc`, приватный SSH-ключ для приватных Go-модулей) в файл сборочного контекста без последующего исключения — `Dockerfile` без `.dockerignore` копирует его в слой образа (`COPY . .` после генерации секрета) |

Если находка не подтверждена однозначно (нет прямого пользовательского ввода в опасном месте) — не флагай, чтобы не плодить false positive; при сомнении отметь как **[ВНИМАНИЕ]** с пояснением риска, а не как **[БЕЗОПАСНОСТЬ]**.

## Меры по слоям

Мера в `threats.md`, `design.md` и в коде — в слое по правилам стека, не по образцу легаси (`approaches/process/legacy-refactor.md`, «Что переносится»); мера не в своём слое — находка того же уровня, что в коде. Как в PHP (`stacks/php/security.md`, «Меры по слоям»):

| Мера | Слой |
|---|---|
| Формат: теги биндинга/`validate` (типы, обязательность, границы, enum) | хендлер — без запросов к хранилищу (`conventions.md` п. 7, O-11) |
| Роль/право; здание/организация из заголовка и параметров | middleware контекста → `context.Context` |
| Существование связанной записи | сервис/workflow через репозиторий; чужой домен — workflow (O-7) |
| Принадлежность скоупу | фильтр в запросе репозитория, скоуп — обязательный аргумент |
| Уникальность | уникальный индекс + перехват `23505` → 422 (`checklist.md` п. 25) |

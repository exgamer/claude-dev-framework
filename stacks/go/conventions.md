# Правила написания кода

Обязательные правила при написании и ревью кода. Нарушение = ошибка ревью.

---

## Общие правила

1. **Контекст** — `ctx context.Context` первым параметром во все методы; контекст передаётся по цепочке вызовов из app-контекста; `context.Background()` и `context.TODO()` внутри бизнес-логики, хендлеров, сервисов, репозиториев и workflow запрещены — создание нового корневого контекста разрывает цепочку и теряет данные (trace ID, request ID, deadline, values)
2. **Контекст не хранится в структуре** — `context.Context` запрещено принимать в конструкторе (`NewService(ctx context.Context, ...)`) и сохранять как поле структуры (`type Service struct { ctx context.Context }`); контекст передаётся явно первым параметром в каждый метод, выполняющий операцию, а не привязывается к экземпляру при создании — иначе значение контекста (deadline, trace ID) "замораживается" на момент конструирования и не отражает контекст конкретного вызова
    ```go
    // неправильно
    type Service struct {
        ctx  context.Context
        repo Repository
    }

    func NewService(ctx context.Context, repo Repository) *Service {
        return &Service{ctx: ctx, repo: repo}
    }

    func (s *Service) GetByID(id uint) (*Product, error) {
        return s.repo.GetByID(s.ctx, id)
    }

    // правильно
    type Service struct {
        repo Repository
    }

    func NewService(repo Repository) *Service {
        return &Service{repo: repo}
    }

    func (s *Service) GetByID(ctx context.Context, id uint) (*Product, error) {
        return s.repo.GetByID(ctx, id)
    }
    ```
3. **DI** — использовать только на уровне app и module, в остальном только явно
4. **Все запросы к внешним хранилищам** (БД, Redis, HTTP, файлы) — только через репозитории в `internal/infrastructure`; прямые вызовы из сервисов, хендлеров или workflow запрещены (`architecture/layers.md`, «Правила слоёв», тег `service-direct-db-query`)
5. **Все исходящие HTTP запросы** — только через `gosdk-http-request-builder`; `http.Get`, `http.Post` и прочие прямые вызовы запрещены
6. **Вся бизнес-логика** — только в сервисах, Command/Query домена и workflow; хендлеры, репозитории и маперы бизнес-логики не содержат
7. **Тонкий хендлер** — только валидация, маппинг и вызов сервиса/workflow; никакой бизнес-логики и запросов к хранилищам. Валидация (теги биндинга, `validate`) — только формат; доступ (роль/право на операцию — `RequirePermissionMiddleware(...)` на маршруте; принадлежность здания/организации из заголовка и параметров) — middleware контекста, результат — в `context.Context`, сервис получает его фильтром; проверок ролей/прав в хендлере и домене нет (`architecture/layers.md`, «Валидация, доступ и фильтр данных», O-11)
7a. **Скоуп — тип, чьё нулевое значение — «ни одной записи»** (**[ОШИБКА]**, правило — `architecture/layers.md`, «Меры по слоям», `scope-param-defaults-unrestricted`): `[]uint` с `nil` = «все» — умолчание «без ограничения» (забыл заполнить — видны все). Форма — `type ParkingScope struct{ All bool; IDs []uint }`: «без ограничения» — явный `All: true` (super-admin, consumer, консоль, integration), пустой `IDs` без `All` — ничего не находит; список — поле фильтра этого типа (`Search.Scope ParkingScope`), чтение и запись по ID — аргумент этого типа (`GetByID(ctx, id, scope)`); репозиторий при `All` условие не добавляет, иначе `parking_id IN (…)`. **Где объявлен тип:** пока скоуп нужен одному домену — в нём (эталон — `domains/billing/tariff/dto.go`); нужен 2+ доменам (второй домен с тем же скоупом в задаче) — тип переезжает в `internal/common/` и импортируется всеми, включая admin-middleware (`architecture/layers.md`, «Общий бизнес-словарь»); импорт чужого домена ради типа — [ОШИБКА] (памятка п. 3), копия — `duplicated-enum`. Перенос задевает файлы первого домена и middleware — архитектор ставит его отдельной задачей плана (волна 0)
8. **Ошибки не игнорируются** — присваивание `_ = ...` для возвращаемой ошибки запрещено (исключение — `errorreporter.CaptureSoft`: она возвращает ту же, уже отправленную ошибку, вызывается отдельной строкой без `_ =`, п. 19); каждая ошибка обрабатывается или пробрасывается выше
9. **`panic()` запрещён** в production коде; допустим только при инициализации приложения (некорректный конфиг) — никогда внутри хендлеров, сервисов, репозиториев
10. **Конструкторы возвращают конкретный тип, не интерфейс** — `func NewService(...) *Service`, не `ServiceInterface`
11. **Интерфейс объявляется у потребителя** — интерфейс определяется в пакете, который его использует, а не в пакете провайдера; провайдер реализует его неявно и не знает о существовании интерфейса. Это о месте объявления, не о разрешённых зависимостях: домен объявляет интерфейсы только своих репозиториев, транзакций, модулей своего домена (O-6), портов внешних систем и системных зависимостей (п. 12); чужой домен — только в workflow (O-7)
12. **Интерфейсы-зависимости — в своих файлах, не инлайном** — объявлять интерфейс в `service.go`, `workflow.go`, `*_command.go` и т.п. запрещено. **Модуль домена** (`internal/domains/{domain}/{module}/`) и **workflow** (`internal/workflows/…`, условия — `go-sdk/workflow.md`) кладут интерфейсы-зависимости в файлы **по группам — по роли зависимости** (G-6): `repository.go` — данные: то, через что модуль читает или хранит данные (`Repository`, `CacheRepository`, `PresenceRepository`, порт внешней системы или легаси как источник данных — Postgres, Redis, HTTP-репозиторий, `architecture/cross-domain.md`); `modules.go` — соседние модули своего домена (O-6: `TemplateReader`, `ScreenRegistry`, `Deliverer` — реализуют сервисы других модулей, связывает `bootstrap`); `system.go` — технические сервисы без данных домена: время, ID, отправка событий и сообщений, планирование (`Clock`, `IDGenerator`, `ChangeNotifier`, шина, публикатор, отправка SMS/пушей, планировщик — даже если реализация ходит в Redis или внешний HTTP). Спорный случай — по тому, что модуль получает: данные в ответ (прочитать, сохранить, проверить) — `repository.go`; только «отправлено», время или ID — `system.go`. Один файл на группу; нет интерфейсов группы — нет файла. **Интерфейсы транзакций (`TxManager`) — всегда в `tx_manager.go`** — в модуле домена и в workflow, все менеджеры пакета в одном файле. Интерфейс группы в другом файле или файл по имени одного интерфейса (`clock.go`, `template_reader.go`) в модуле домена или workflow — **[ВНИМАНИЕ]** `interface-file-group`. Почему: по файлам групп видно, от чего зависит модуль — от хранилища, от транзакций, от соседей по домену или от системного; файлы по одному интерфейсу в 6–10 строк дробили модуль на десятки файлов (2026-10-20, `screen-gateway`: 34 таких файла в 7 модулях). У workflow `modules.go` нет — сервисы и репозитории доменов он берёт напрямую (O-7). **Остальные пакеты** (точки входа, инфраструктура) — файл по имени интерфейса: `publisher.go`, `retry_scheduler.go`. Общий hexagonal-термин в названии файла (`ports.go`, `interfaces.go`, `dependencies.go`) — **[ОШИБКА]**: не отражает, что объявлено; имена групп выше — не такой термин, а закреплённый список
13. **Общие объявления выносятся в отдельный файл** — константы, типы, структуры и переменные пакетного уровня, используемые более чем в одном файле пакета, выносятся в отдельный файл: константы-перечисления домена — `{name}_enum.go` по смыслу (`status_enum.go`, `discount_type_enum.go`, см. `go-sdk/domain.md`), DTO — `dto.go`, сущности — `entity.go`, интерфейсы — по п. 12 (в модуле домена и workflow — файлы групп `repository.go`/`tx_manager.go`/`modules.go`/`system.go` (у workflow без `modules.go`), в остальных пакетах — файл по имени интерфейса); файл, названный по абстракции (`types.go`, `const.go`, `utils.go`), — **[ВНИМАНИЕ]** (`core/style.md`, «Имена»; G-5); имена-абстракции для файлов интерфейсов (`ports.go`, `interfaces.go`, `dependencies.go`) — п. 12, **[ОШИБКА]**; оставлять инлайном допустимо только если используются исключительно в одном файле
14. **Репозиторий не называется client** — структура, реализующая доменный интерфейс репозитория, именуется `Repository` (HTTP-адаптер источника данных — `HTTPRepository` в `repository.go`; адаптер порта отправки — `HTTPNotifier` в `notifier.go`; имена по роли — `architecture/integrations.md`, `go-sdk/infra/http.md`), не `Client`, `HttpClient` и т.п.; имя `Client` подразумевает транспортный примитив, а не бизнес-абстракцию
15. **Репозиторий содержит только запросы, клиент инжектируется** — репозиторий содержит только логику формирования и выполнения запросов; HTTP-клиент (или любой другой транспортный клиент) не создаётся внутри репозитория, а получается через конструктор из DI в модуле (`module.go`). `gosdk-http-request-builder` создаёт `http.Client` сам на каждый запрос — для HTTP-адаптера на нём инжектируются адрес и таймаут (через конструктор из конфига модуля), `go-sdk/infra/http.md`, «repository.go»
15a. **Запрос виден целиком** (**[ВНИМАНИЕ]**, тег `query-split-into-pieces`; правило, лимиты и «почему» — `architecture/layers.md`, «Правила слоёв»; здесь — GORM): цепочка `r.client.WithContext(ctx).Where(...)…First/Find` — целиком в методе репозитория. Кусков запроса нет: `Scopes(...)` и функций-скоупов `func(db *gorm.DB) *gorm.DB` (`activeScope`, `byOwner(userID)`), общего начала запроса в методе (`r.baseQuery(ctx)`), списка колонок переменной или константой (`var tariffColumns = []string{...}` в `Select`). `Select` не обязателен — без него GORM выбирает все колонки таблицы модели (`db.Model(&tariff{})`, как в `examples/tariff`); выбираешь часть колонок — строкой в этом же запросе, не переменной; `Select("*")` не пишется. Фильтры списка — подряд в том же методе. Подзапрос (`Where("EXISTS (?)", sub)`, `Where("id IN (?)", sub)`, `Joins("JOIN (?) AS …", sub)`) допустимо повторить в 2–3 методах; `Joins` по таблице и простые `Where` (`deleted_at IS NULL`, владелец, даты) — в каждом методе без лимита.

    ```go
    // плохо: условие вынесено в скоуп
    func notDeleted(db *gorm.DB) *gorm.DB {
        return db.Where("deleted_at IS NULL")
    }

    result := r.client.WithContext(ctx).Scopes(notDeleted).Where("id = ?", id).First(&model)

    // хорошо: условия повторены в каждом методе, запрос виден целиком
    query := r.client.WithContext(ctx).
        Where("parking_id = ?", f.ParkingID).
        Where("deleted_at IS NULL")

    if f.Status != nil {
        query = query.Where("status = ?", *f.Status)
    }
    ```
15b. **Метод репозитория — один запрос** (**[ОШИБКА]**, тег `repository-multi-query`; правило и «почему» — `architecture/layers.md`, «Правила слоёв»; здесь — GORM): одна завершающая операция на метод (`First`/`Find`/`Count`/`Pluck`/`Updates`/`Delete`/`Create`/`Exec`). «Заблокировать и удалить», «прочитать и сохранить», «удалить и вставить» — два метода репозитория, порядок и транзакция — в сервисе, Command или workflow через `txManager.Exec` (`go-sdk/infra/postgres.md`, «Транзакции»). Обновление — `Model(&M{}).Where(...).Updates(...)` с проверкой `RowsAffected`, не `First` → изменить → `Save`.
16. **Нестандартные пути и имена файлов** — пути и имена файлов должны строго соответствовать структуре, описанной в structure.md (таблица "Структура путей", диаграмма директорий и Checklist нового модуля); любое отклонение является ошибкой
17. **Атомарность операций записи** — транзакция в workflow, Command и Service — когда сценарий делает больше одного модифицирующего запроса (в разные таблицы или в одну); один модифицирующий запрос — без транзакции (кроме транзакции ради блокировки `FOR UPDATE`/`FOR SHARE` — основание «Конкурентность» `design.md`); проверки перед записью в неё не тянутся; внутри `txManager.Exec` только репозитории из аргументов. Правило — `approaches/patterns/transactions.md` (O-8), механика — `go-sdk/infra/postgres.md`, «Транзакции»
18. **Горутина создаётся на уровне принятия решения об асинхронности** — `go` запускается там, где принимается решение, что операция должна выполняться асинхронно (workflow, runner, entrypoint), а не внутри вызываемого сервиса, если асинхронность не является частью его контракта; сервис отвечает за выполнение операции, вызывающий код — за способ её запуска и lifecycle (когда стартовать, как дождаться завершения, как остановить, куда пробросить ошибку/панику). Скрытый `go` внутри сервиса лишает вызывающий код контроля над этим lifecycle и делает асинхронность неявной побочной особенностью реализации
    ```go
    // неправильно — асинхронность спрятана внутри сервиса
    func (s *Service) Notify(ctx context.Context, order Order) error {
        go func() {
            _ = s.repo.Send(context.Background(), order)
        }()

        return nil
    }

    // правильно — сервис синхронный, решение об асинхронности и lifecycle — на вызывающей стороне
    func (s *Service) Notify(ctx context.Context, order Order) error {
        return s.repo.Send(ctx, order)
    }

    func (w *Workflow) Exec(ctx context.Context, order Order) {
        go func() {
            if err := w.service.Notify(ctx, order); err != nil {
                w.logger.Error(ctx, err)
            }
        }()
    }
    ```
19. **Незначимая ошибка репортится через `errorreporter`, не только логируется** — если ошибка намеренно не пробрасывается наверх (fallback есть, поток не должен прерываться — например, не удалось инвалидировать кеш или синхронизировать с внешним сервисом, а запись уже сохранена), одного `logger.Warning`/`logger.Error` недостаточно: обычный лог никто не мониторит в реальном времени, ошибка тихо теряется. Использовать `errorreporter.CaptureSoft(ctx, err, tags)` (уровень warning, поток продолжается) или `errorreporter.CaptureError(ctx, err, tags)` (уровень error) из `gosdk-core/pkg/errorreporter` — они уходят в Sentry/систему трекинга и одновременно дедуплицируют повторную отправку одной и той же ошибки через несколько слоёв (`WasReported`). Просто `logger.Warning(...)` / `logger.Error(...)` без `errorreporter` в таком месте — **[ВНИМАНИЕ]**
    ```go
    // недостаточно — ошибка попадёт только в текстовый лог
    if err := s.cache.Invalidate(ctx, key); err != nil {
        logger.Warning(ctx, fmt.Sprintf("failed to invalidate cache: %v", err))
    }

    // правильно — ошибка ещё и долетает до Sentry/трекинга
    if err := s.cache.Invalidate(ctx, key); err != nil {
        errorreporter.CaptureSoft(ctx, err, map[string]string{"component": "tariff_cache"})
    }
    ```
20. **Имя функции/типа/поля обязано отражать фактическое поведение** — название не должно обещать то, чего код не делает. Частый случай: имя из терминологии очередей/асинхронности (`Enqueue`, `dispatch`, `Schedule*`; `*TxManager` по операции — норма, `go-sdk/infra/postgres.md`, «Транзакции») присвоено операции, которая на самом деле синхронно пишет в БД или делает прямой вызов без какой-либо очереди. Несовпадение имени и поведения — **[ВНИМАНИЕ]**, при явно вводящем в заблуждение имени (например `Enqueue`, за которым нет ни очереди, ни асинхронности, а просто `repository.Create` в транзакции) — **[ОШИБКА]**
21. **`nil` не передаётся как обязательная зависимость в конструктор** — если конструктор принимает интерфейс/коллаборатора, который используется где-то в реализации, вызывающий код не должен подставлять `nil` под предлогом "на этом пути всё равно не используется". Это оставляет мину: любой другой/будущий вызов упадёт с nil pointer panic без единого намёка на этапе компиляции. Если зависимость на части путей действительно не нужна — сделать её явно опциональной (nil-check внутри метода перед использованием и осмысленная деградация) либо разделить конструктор/сервис на две сущности, а не тихо инжектить `nil` — **[ОШИБКА]**
    ```go
    // неправильно — паника при первом же вызове метода, которому нужен publisher
    tariffdomain.NewService(repos.TariffRepository, nil)

    // правильно — зависимость опциональна и это видно по сигнатуре/поведению,
    // либо вообще не создавать этот сервис на путях, где Publisher не нужен
    ```
22. **Не-бизнесовая функциональность не реализуется дважды независимо** — если проблема не относится ни к какому домену (транспорт, сериализация, шифрование, сборка connection string, ретраи, парсинг формата) и в проекте уже есть код, который её решает — новый код обязан переиспользовать существующий, а не писать параллельную реализацию. Разные пакеты/домены НЕ являются оправданием для дублирования: то, что код нужен и `session`-домену, и `billing`-домену — повод вынести общую реализацию в shared-место (`pkg/`, общий инфра-пакет или сам SDK, если проблема not specific to this service), а не размножить её. Проверяется поиском по признаку проблемы (не по имени функции — реализации почти всегда называются и написаны по-разному): одинаковый workaround для одной и той же сторонней библиотеки/формата в двух файлах — **[ОШИБКА]**, даже если оба явно закомментированы и работают корректно по отдельности
    - Пример (происхождение — MR!151): два consumer'а независимо чинят одну и ту же проблему `watermill-amqp.DefaultMarshaler` с нестроковыми AMQP-заголовками (`x-death` от Dead Letter Exchange) — каждый своим marshaler-ом, разными способами, с разным покрытием edge case; обе копии молчаливо разъедутся при следующем фиксе одной из них. Правильно — одна реализация в SDK (`DeathTolerantMarshaler`, эталон `stacks/go/examples/tariff`, `consumer_registry.go`)
    - Признаки при ревью: (а) doc-комментарий объясняет проблему сторонней библиотеки/протокола, а не бизнес-правило; (б) тип/функция не принимает и не возвращает ничего доменного (`entity`, `DTO`) — только транспортные примитивы (`amqp.Delivery`, `[]byte`, `io.Reader`, connection string и т.п.); если такое уже встречалось в другом файле проекта — это не совпадение, а дублирование
    - Что делать: искать по всему проекту (`grep`/`Explore`) прежде чем писать новый инфраструктурный workaround; если уже есть похожий в другом домене — вынести в общий пакет (`pkg/`, `internal/infrastructure/{type}/shared` или аналог) либо в SDK, если проблема не специфична для этого сервиса (см. `go-sdk/entrypoint/rabbit.md`, раздел «Кастомный Marshaler» — конкретный кейс, где решение уехало в SDK)

---
23. **Источник и версия Go SDK — определяются в начале задачи и запоминаются** (решение O-4) — SDK есть в двух источниках: `git.mpinnovations.kz/mps/go-packages/gosdk-*` (GitLab) и `github.com/exgamer/gosdk-*` (GitHub). **Проект уже на SDK** (`go.mod` с `gosdk-*`) — источник и версии пакетов берутся из `go.mod`, пользователю показываются одной строкой, без вопроса. **Спросить пользователя** (источник и версии): новый проект (нет `go.mod` или в нём нет `gosdk-*`); задача меняет источник или версию SDK; задаче нужен пакет `gosdk-*`, которого в `go.mod` ещё нет (например `gosdk-http-request-builder`, `gosdk-sentry-core`); в `go.mod` пакеты из обоих источников (GitLab и GitHub). Результат записывается в `docs/tasks/<ключ>/design.md` (раздел «SDK») один раз на задачу; дальше все роли берут его оттуда — не переопределяют и не переспрашивают. API SDK сверять с исходниками именно этой версии (`go/pkg/mod/…@<версия>`), а не с примерами из `go-sdk/*.md`: пути импортов там (`github.com/exgamer/…`) — иллюстрация. Код на SDK без записанного «SDK» в `design.md` — **[ВНИМАНИЕ]**

## Предупреждения

- **Отсутствие документации на модели и сущности** — если структура является доменной сущностью (`entity.go`) или инфраструктурной моделью (`model.go`) и не имеет doc-комментария на саму структуру или описания у неочевидного поля (единицы, формат, nullable со смыслом, связь) — предупреждение; у очевидных полей (`ID`, `CreatedAt`, `Name`) описание не пишется (`core/style.md`, «Комментарии»; для линтера — `style.md`)
- **Дублирование скелета обработчика между похожими сценариями/типами/статусами** — несколько Command/Workflow/consumer-обработчиков (обычно по одному на тип/статус) почти дословно повторяют один и тот же порядок шагов (например: idempotency-check → вызов специфичного действия → запись лога), отличаясь только вызовом 1-2 специфичных методов внутри; правка сквозного шага (обработка ошибок, логирование) требует ручной синхронизации во всех копиях — риск забыть одну при следующем изменении. Не [ОШИБКА] — предупреждение с предложением вынести общий скелет в переиспользуемую абстракцию (State Machine / Strategy: общая функция с шагами `idempotencyCheck → action → writeLog`, где `action` — специфичное поведение, передаваемое через интерфейс или `map`/`switch` по типу). Не находка: повторённые шаги разных workflow — их повтор правило разрешает (`architecture/layers.md`, «Зависимости»; `core/style.md`, «Форма кода»)

## Рекомендации

- Один бизнес-контекст — один модуль
- Регистрировать маршруты только в `bootstrap/{module}/module.go` / `bootstrap/{domain}/{module}/module.go`
- Не использовать глобальные переменные
- Не создавать HTTP server вручную — только через `HttpKernel`

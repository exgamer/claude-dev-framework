# Правила написания кода

Обязательные правила при написании и ревью кода. Нарушение = ошибка ревью.

---

## Общие правила

1. **Контекст** — `ctx context.Context` первым параметром во все методы; контекст передаётся по цепочке вызовов из app-контекста; `context.Background()` и `context.TODO()` внутри бизнес-логики, хендлеров, сервисов, репозиториев и workflow запрещены — создание нового корневого контекста разрывает цепочку и теряет данные (trace ID, request ID, deadline, values)
2. **Контекст не хранится в структуре** — `context.Context` запрещено принимать в конструкторе (`NewService(ctx context.Context, ...)`) и сохранять как поле структуры (`type Service struct { ctx context.Context }`); контекст передаётся явно первым параметром в каждый метод, выполняющий операцию, а не привязывается к экземпляру при создании — иначе значение контекста (deadline, trace ID) "замораживается" на момент конструирования и не отражает контекст конкретного вызова
    ```go
    // неправильно
    type Service struct {
        ctx  context.Context
        repo Repository
    }

    func NewService(ctx context.Context, repo Repository) *Service {
        return &Service{ctx: ctx, repo: repo}
    }

    func (s *Service) GetById(id uint) (*Product, error) {
        return s.repo.GetById(s.ctx, id)
    }

    // правильно
    type Service struct {
        repo Repository
    }

    func NewService(repo Repository) *Service {
        return &Service{repo: repo}
    }

    func (s *Service) GetById(ctx context.Context, id uint) (*Product, error) {
        return s.repo.GetById(ctx, id)
    }
    ```
3. **DI** — использовать только на уровне app и module, в остальном только явно
4. **Все запросы к внешним хранилищам** (БД, Redis, HTTP, файлы) — только через репозитории в `internal/infrastructure`; прямые вызовы из сервисов, хендлеров или workflow запрещены
5. **Все исходящие HTTP запросы** — только через `gosdk-http-request-builder`; `http.Get`, `http.Post` и прочие прямые вызовы запрещены
6. **Вся бизнес-логика** — только в сервисах и workflow; хендлеры, репозитории и маперы бизнес-логики не содержат
7. **Тонкий хендлер** — только валидация, маппинг и вызов сервиса/workflow; никакой бизнес-логики и запросов к хранилищам
8. **Ошибки не игнорируются** — присваивание `_ = ...` для возвращаемой ошибки запрещено; каждая ошибка обрабатывается или пробрасывается выше
9. **`panic()` запрещён** в production коде; допустим только при инициализации приложения (некорректный конфиг) — никогда внутри хендлеров, сервисов, репозиториев
10. **Конструкторы возвращают конкретный тип, не интерфейс** — `func NewService(...) *Service`, не `ServiceInterface`
11. **Интерфейс объявляется у потребителя** — интерфейс определяется в пакете, который его использует, а не в пакете провайдера; провайдер реализует его неявно и не знает о существовании интерфейса
12. **Интерфейсы-зависимости выносятся в отдельный файл** — объявлять интерфейс инлайном в `service.go`, `workflow.go` и т.п. запрещено; интерфейс выносится в отдельный файл того же пакета, названный по имени объявляемого интерфейса (`repository.go` для `Repository`, `retry_scheduler.go` для `RetryScheduler`, `publisher.go` для `Publisher`). Общий hexagonal-термин в названии файла (`ports.go`) — **[ОШИБКА]**: не отражает, что конкретно объявлено, и не соответствует названиям файлов, принятым в проекте
13. **Общие объявления выносятся в отдельный файл** — константы, типы, структуры и переменные пакетного уровня, используемые более чем в одном файле пакета, выносятся в отдельный файл (`const.go`, `types.go` и т.п.); оставлять инлайном допустимо только если используются исключительно в одном файле
14. **Репозиторий не называется client** — структура, реализующая доменный интерфейс репозитория, именуется `Repository`, не `Client`, `HttpClient` и т.п.; имя `Client` подразумевает транспортный примитив, а не бизнес-абстракцию
15. **Репозиторий содержит только запросы, клиент инжектируется** — репозиторий содержит только логику формирования и выполнения запросов; HTTP-клиент (или любой другой транспортный клиент) не создаётся внутри репозитория, а получается через конструктор из DI в модуле (`module.go`)
16. **Нестандартные пути и имена файлов** — пути и имена файлов должны строго соответствовать структуре, описанной в structure.md (таблица "Структура путей", диаграмма директорий и Checklist нового модуля); любое отклонение является ошибкой
17. **Атомарность операций записи** — если сценарий (Command, Service, Workflow) выполняет несколько операций записи (в одном или нескольких репозиториях), и частичное выполнение недопустимо (например создание записи + обновление связанной сущности) — операции оборачиваются в транзакцию (см. `go-sdk/infra/postgres.md`); отсутствие транзакции в таком сценарии — ошибка ревью. Один самостоятельный `Create`/`Update`/`Delete` отдельной транзакции не требует
18. **Горутина создаётся на уровне принятия решения об асинхронности** — `go` запускается там, где принимается решение, что операция должна выполняться асинхронно (workflow, runner, entrypoint), а не внутри вызываемого сервиса, если асинхронность не является частью его контракта; сервис отвечает за выполнение операции, вызывающий код — за способ её запуска и lifecycle (когда стартовать, как дождаться завершения, как остановить, куда пробросить ошибку/панику). Скрытый `go` внутри сервиса лишает вызывающий код контроля над этим lifecycle и делает асинхронность неявной побочной особенностью реализации
    ```go
    // неправильно — асинхронность спрятана внутри сервиса
    func (s *Service) Notify(ctx context.Context, order Order) error {
        go func() {
            _ = s.repo.Send(context.Background(), order)
        }()

        return nil
    }

    // правильно — сервис синхронный, решение об асинхронности и lifecycle — на вызывающей стороне
    func (s *Service) Notify(ctx context.Context, order Order) error {
        return s.repo.Send(ctx, order)
    }

    func (w *Workflow) Run(ctx context.Context, order Order) {
        go func() {
            if err := w.service.Notify(ctx, order); err != nil {
                w.logger.Error(ctx, err)
            }
        }()
    }
    ```
19. **Незначимая ошибка репортится через `errorreporter`, не только логируется** — если ошибка намеренно не пробрасывается наверх (fallback есть, поток не должен прерываться — например, не удалось инвалидировать кеш или синхронизировать с внешним сервисом, а запись уже сохранена), одного `logger.Warning`/`logger.Error` недостаточно: обычный лог никто не мониторит в реальном времени, ошибка тихо теряется. Использовать `errorreporter.CaptureSoft(ctx, err, tags)` (уровень warning, поток продолжается) или `errorreporter.CaptureError(ctx, err, tags)` (уровень error) из `gosdk-core/pkg/errorreporter` — они уходят в Sentry/систему трекинга и одновременно дедуплицируют повторную отправку одной и той же ошибки через несколько слоёв (`WasReported`). Просто `logger.Warning(...)` / `logger.Error(...)` без `errorreporter` в таком месте — **[ВНИМАНИЕ]**
    ```go
    // недостаточно — ошибка попадёт только в текстовый лог
    if err := s.cache.Invalidate(ctx, key); err != nil {
        logger.Warning(ctx, fmt.Sprintf("failed to invalidate cache: %v", err))
    }

    // правильно — ошибка ещё и долетает до Sentry/трекинга
    if err := s.cache.Invalidate(ctx, key); err != nil {
        _ = errorreporter.CaptureSoft(ctx, err, map[string]string{"component": "session_cache"})
    }
    ```
20. **Имя функции/типа/поля обязано отражать фактическое поведение** — название не должно обещать то, чего код не делает. Частый случай: имя из терминологии очередей/асинхронности (`Enqueue`, `dispatch`, `*TxManager`, `Schedule*`) присвоено операции, которая на самом деле синхронно пишет в БД или делает прямой вызов без какой-либо очереди. Несовпадение имени и поведения — **[ВНИМАНИЕ]**, при явно вводящем в заблуждение имени (например `Enqueue`, за которым нет ни очереди, ни асинхронности, а просто `repository.Create` в транзакции) — **[ОШИБКА]**
21. **`nil` не передаётся как обязательная зависимость в конструктор** — если конструктор принимает интерфейс/коллаборатора, который используется где-то в реализации, вызывающий код не должен подставлять `nil` под предлогом "на этом пути всё равно не используется". Это оставляет мину: любой другой/будущий вызов упадёт с nil pointer panic без единого намёка на этапе компиляции. Если зависимость на части путей действительно не нужна — сделать её явно опциональной (nil-check внутри метода перед использованием и осмысленная деградация) либо разделить конструктор/сервис на две сущности, а не тихо инжектить `nil` — **[ОШИБКА]**
    ```go
    // неправильно — паника при первом же вызове CreateAndPublish в этом инстансе
    fiscalreceiptdomain.NewService(repos.FiscalReceiptRepository, nil)

    // правильно — зависимость опциональна и это видно по сигнатуре/поведению,
    // либо вообще не создавать этот сервис на путях, где Publisher не нужен
    ```
22. **Не-бизнесовая функциональность не реализуется дважды независимо** — если проблема не относится ни к какому домену (транспорт, сериализация, шифрование, сборка connection string, ретраи, парсинг формата) и в проекте уже есть код, который её решает — новый код обязан переиспользовать существующий, а не писать параллельную реализацию. Разные пакеты/домены НЕ являются оправданием для дублирования: то, что код нужен и `session`-домену, и `billing`-домену — повод вынести общую реализацию в shared-место (`pkg/`, общий инфра-пакет или сам SDK, если проблема not specific to this service), а не размножить её. Проверяется поиском по признаку проблемы (не по имени функции — реализации почти всегда называются и написаны по-разному): одинаковый workaround для одной и той же сторонней библиотеки/формата в двух файлах — **[ОШИБКА]**, даже если оба явно закомментированы и работают корректно по отдельности
    - Пример из практики (MR!151): `session_event/marshaler.go` (`deathTolerantMarshaler`) и `fiscalization/marshaler.go` (`dlxMarshaler`) — два разных consumer'а независимо чинят одну и ту же проблему `watermill-amqp.DefaultMarshaler` с нестроковыми AMQP-заголовками (`x-death` от Dead Letter Exchange), разными способами, с разным покрытием edge case — обе копии молчаливо разъедутся при следующем фиксе одной из них
    - Признаки при ревью: (а) doc-комментарий объясняет проблему сторонней библиотеки/протокола, а не бизнес-правило; (б) тип/функция не принимает и не возвращает ничего доменного (`entity`, `DTO`) — только транспортные примитивы (`amqp.Delivery`, `[]byte`, `io.Reader`, connection string и т.п.); если такое уже встречалось в другом файле проекта — это не совпадение, а дублирование
    - Что делать: искать по всему проекту (`grep`/`Explore`) прежде чем писать новый инфраструктурный workaround; если уже есть похожий в другом домене — вынести в общий пакет (`pkg/`, `internal/infrastructure/{type}/shared` или аналог) либо в SDK, если проблема не специфична для этого сервиса (см. `go-sdk/entrypoint/rabbit.md`, раздел «Кастомный Marshaler» — конкретный кейс, где решение уехало в SDK)

23. **Версию Go SDK всегда уточнять у пользователя** (решение O-4) — до первой строки кода, которая опирается на SDK, спросить: какой источник (`git.mpinnovations.kz/mps/go-packages/gosdk-*` или `github.com/exgamer/gosdk-*`) и какие версии пакетов. Что сейчас в `go.mod` — показать как контекст, но не считать ответом. Спрашивается один раз на задачу, ответ записывается в `docs/tasks/<ключ>/design.md` (раздел «SDK»); дальше по задаче — по нему. API SDK сверять с исходниками именно этой версии (`go/pkg/mod/…@<версия>`), а не с примерами из `go-sdk/*.md`: пути импортов там (`github.com/exgamer/…`) — иллюстрация. Код на SDK без подтверждённой версии — **[ВНИМАНИЕ]**

## Предупреждения

- **Отсутствие документации на модели и сущности** — если структура является доменной сущностью (`entity.go`) или инфраструктурной моделью (`model.go`) и не имеет doc-комментария на саму структуру и/или комментариев на поля — предупреждение; без описания контекст структуры и назначение полей непонятны новым разработчикам
- **Дублирование скелета обработчика между похожими сценариями/типами/статусами** — несколько Command/Workflow/consumer-обработчиков (обычно по одному на тип/статус) почти дословно повторяют один и тот же порядок шагов (например: idempotency-check → вызов специфичного действия → запись лога), отличаясь только вызовом 1-2 специфичных методов внутри; правка сквозного шага (обработка ошибок, логирование) требует ручной синхронизации во всех копиях — риск забыть одну при следующем изменении. Не [ОШИБКА] — предупреждение с предложением вынести общий скелет в переиспользуемую абстракцию (State Machine / Strategy: общая функция с шагами `idempotencyCheck → action → writeLog`, где `action` — специфичное поведение, передаваемое через интерфейс или `map`/`switch` по типу)

## Рекомендации

- Один бизнес-контекст — один модуль
- Регистрировать маршруты только в `bootstrap/{module}/module.go` / `bootstrap/{domain}/{module}/module.go`
- Не использовать глобальные переменные
- Не создавать HTTP server вручную — только через `HttpKernel`

# Замечания из реальных MR-тредов и прод-инцидентов (Go)

Эмпирический слой поверх `architecture.md` / `conventions.md` / `style.md`. Источник — прод-инциденты Sentry
и треды MR в `parking-session-service` (!93, !99, !100, !103 — выгрузка 2026-08; !151 — выгрузка 2026-09), полное
ревью `gateway` (2026-09, тестирование AINA-2773).
Каждый класс бага ниже **уже стрелял** — при ревью это не «best practice», а повтор известного инцидента.

Формат: `что смотреть → почему`.

## Платёжные хендлеры и workflow (`internal/workflows/**/payment/*`, `internal/entrypoints/**/http/{kaspi,halyk,kassa24,...}`)

- **Идемпотентность pay** по `(payment_system, payment_system_txn_id)`. Если unique-констрейнта в таблице транзакций нет — повторный или параллельный запрос от шлюза = двойное списание. Новый путь записи транзакции → показать, где дедупликация.
- **Платёж без сессии** → `session_id = 0` → FK violation и 500 (класс Kaspi FK). Новые пути записи проверять на nullable / валидацию `session_id` до INSERT.
- **Кэш ответов шлюза** (`payment_system_logs`, `CachedBytes` в mapper) — **ошибки кэшировать нельзя**, иначе шлюз вечно получает закэшированный фейл. Эталонный паттерн — mapper kassa24; новый шлюз сверять с ним.
- **Проверка подписи колбэка** — каждый платёжный вебхук-хендлер (`kaspi`/`halyk`/`kassa24`/...) обязан проверять HMAC/подпись/секрет согласно протоколу именно этого шлюза **до** изменения статуса платежа/сессии. Это не общее правило «на будущее» — проверять по каждому шлюзу отдельно и явно писать в отчёт результат (есть/нет), даже когда нарушений не найдено: один шлюз может проверять подпись корректно, а следующий, скопированный по его образцу, — забыть про этот шаг (тот же класс расхождения, что и с кэшированием ошибок выше).
- **Горутина после INSERT** (`go func(...)` после записи платежа) — fire-and-forget: упал под → ЛПМ не узнал об оплате, чека нет. Ревьюер снимает каждую («зачем тут горутина?» ×4 в !93). Побочные эффекты — через outbox-таблицу и отдельный обработчик, не через горутину.
- **Новый статус** (`StatusAwaitingRetry` и подобные) — если в сервисе нет планировщика, статус без обработчика = тупик навсегда. У каждого нового статуса должен быть потребитель (cron/consumer/переход), показать его в MR.

## Контекст, таймауты, ошибки

- `context.WithoutCancel` и вызовы БД без таймаута — «если БД зависнет, конект останется навсегда, проверить везде» (!93). В репозиториях — `context.WithTimeout(ctx, 10*time.Second)` или аналог; `context.Background()` внутри бизнес-логики запрещён (`conventions.md`, п. 1).
- Проглоченные ошибки — «игнорируется ошибка при сериализации» (!93): `json.Marshal` / `strconv` / `Close()` с `_` — реджект (`conventions.md`, п. 8).
- Ошибки → в Sentry через hub из контекста, не только в лог. Оборачивать `errors.Wrap` / `fmt.Errorf("...: %w", err)`, чтобы цепочка не терялась.
- **Таймаут на вызов Redis есть, но не действует** (gateway 2026-09: зависший Redis держал запрос 10–15 с при `context.WithTimeout` на каждом вызове) — go-redis не прерывает чтение из сокета по дедлайну контекста, пока в клиенте не включён `ContextTimeoutEnabled`: вызов ждёт `ReadTimeout` × повторы. С `gosdk-redis-core` ≥ v1.0.3 — `REDIS_CONTEXT_TIMEOUT_ENABLED=true` в конфиге окружения. Проверять не только наличие `WithTimeout`, но и этот флаг; лучше — проверка на старте, что он включён.
- **`logger.Warning`/`logger.Error` вместо `errorreporter`** для намеренно не пробрасываемых ошибок (MR!151, многократно: "сокрытие ошибки. Использовать errorreporter sdk", "тут и везде где такое") — `gosdk-core/pkg/errorreporter.CaptureSoft`/`CaptureError(ctx, err, tags)` уходит в Sentry и дедуплицирует повтор через слои; голый `logger.*` — нет. См. `conventions.md`, п. 19.

## Конфиг

- Viper с динамическими ключами (`PARKING_HOST_<id>`): опечатка в имени env молча даёт пустой host. Новый динамический ключ → валидация на старте (пустое значение = fail при init, `conventions.md`, п. 9 допускает panic только здесь).
- Хвостовой `/` или `/api/` в хостах даёт двойной слеш в URL (класс smartpoint `/api//parking/payment`). Нормализовать через `strings.TrimSuffix` / `url.JoinPath` при чтении конфига, не в каждом вызове.

## HTTP-роуты

- Межсервисные endpoint'ы исторически без auth. Новый роут без middleware — спросить, осознанно ли; ответ фиксировать в MR.
- Изменились роуты или DTO → swagger в `docs/` перегенерирован (`swag init ...`). Спрашивают прямо (!99).
- **`http.MaxBytesReader` поверх `http.NoBody`** (gateway 2026-09, F16: ретрай GET молча не работал) — обёртка лимита тела над запросом без тела превращает `NoBody` в «тело есть», и код, решающий по `Body != http.NoBody` (ретраи, дедлайны чтения), ломается. Оборачивать только при `Body != nil && Body != http.NoBody`.
- **Admin-действие в client-контексте без auth** (MR!151: `POST /sessions/{id}/cancel`, "Ручная отмена... администратором", зарегистрирован в `client`-группе, где вообще нет ни одного auth-middleware) — это не "межсервисный эндпойнт по умолчанию без auth" (тот случай выше), а конкретный Broken Access Control/IDOR: по summary/описанию ручки видно, что она для административного действия, но её просто положили не в тот контекст. Не путать эти два случая — здесь не "спросить, осознанно ли", а прямая находка [БЕЗОПАСНОСТЬ].

## Безопасность (эмпирические кейсы, дополнение к чек-листу 5.1)

- **Проверять каждый handler ресурса по отдельности, не домен целиком.** Типичный паттерн: `list`/`get`
  скоупят по владельцу/тенанту правильно, а `update`/`cancel`/`delete` того же ресурса — нет, потому что
  их добавили позже и по памяти скопировали не с того соседа. Один подтверждённый скоуп на domain не
  означает, что весь domain безопасен.
- **Сверять с соседней реализацией, не считать её образцовым эталоном молча.** Тот же принцип, что уже
  применяется к mapper'ам платёжных шлюзов (kassa24 — эталон кэширования ошибок, см. выше): если в
  проекте несколько похожих интеграций/хендлеров (несколько шлюзов, несколько consumer'ов одного типа
  события) — сверять их друг с другом явно. Расхождение почти всегда баг копирования (скопировали
  раньше, чем добавили проверку подписи/скоуп/rate-limit), а не осознанное решение.
- **`LoggerMiddleware` SDK на DEBUG пишет тело запроса целиком** (gateway 2026-09: пароли логина/смены пароля и HMAC-секреты в логах stage) — на группе с ручками, принимающими пароли/секреты/токены, при `LOG_LEVEL=DEBUG` это утечка. Смотреть, на какие группы повешен `LoggerMiddleware` и какой уровень логов на окружениях; такие ручки исключать из логирования тела.
- **Секреты в общем кэше Redis** (gateway 2026-09: HMAC-ключи JWT-политик лежали открытым JSON в `…:jwtpolicy:active`) — кэширование сущности целиком уносит в Redis и её секреты; доступ к Redis = подделка токенов. Секреты не кэшировать в общем Redis: читать из БД в in-process кэш или хранить зашифрованными.
- **Fail-open как постоянная, а не временная дыра.** Если авторизация/права строятся через
  генератор/сидер (роль → список разрешённых маршрутов), проверять, что реальные имена/пути роутов
  вообще попадают под его конвенцию генерации. Несовпадение конвенции = право физически невозможно
  выдать, и запасной путь («нет записи — разрешаем») работает всегда, а не только до первого деплоя
  сидера.

## RabbitMQ

- Очереди/exchange объявляются при старте (`declareRetryQueue` и подобные), не лениво в consumer.
- Новый consumer переживает недоступность rabbit на старте: ретрай подключения, не молчаливый пропуск регистрации.
- **Своё `amqp.Dial` для декларации топологии без consumer-а** (MR!151, kulzhambekov.o: "пересмотреть полностью. реализация является антипаттерном. создается еще одно соединение внутри outboxrabbit.DeclareTopology") — лишнее соединение в обход kernel-а. С `gosdk-rabbit-core >= v1.0.5` — `rabbitDi.GetRabbitConnection` + `rabbitmq.DeclareTopology`; сама функция — bootstrap-код (kulzhambekov.o: "это bootstrap слой"), не infra. См. `go-sdk/entrypoint/rabbit.md`.
- **Две независимые реализации одного и того же transport-фикса** (MR!151: `session_event/marshaler.go` vs `fiscalization/marshaler.go` — обработка `x-death`, "одно и тоже разными способами") — частный случай общего правила о недопустимости дублирования не-бизнесовой логики, см. `conventions.md` п. 22 и `go-sdk/entrypoint/rabbit.md`.
- **`Publisher` оборачивает `Publisher`** (MR!151: `type Publisher struct { publisher *rabbitmq.Publisher }` в `fiscal_receipt/publisher.go`; "шедулер по сути просто паблишер, зачем обертка в обертке это нечитабельно") — доменный интерфейс, инфра-структура и SDK-тип с одним именем. Называть инфра-адаптер иначе (`RabbitPublisher`/с префиксом домена).

## Структура и стиль (что ревьюеры пишут построчно)

- **Много аргументов функции** (4+) → структура `Params`/`Input` (!93; автор так и починил).
- **DTO / константы / типы не в файле сервиса** — отдельные `dto.go`, `const.go`, `enum.go` (!93 «почему в сервисе лежат и ДТО и константы и типы?»); файл называется по содержимому — `dto.go` / `entity.go`, а не `types.go` для всего подряд (!99). См. `conventions.md`, п. 13.
- **Mapper только маппит** — «это не маппер», «этому не место в маппере, лишняя обёртка» (!93). Условия, запросы, форматирование бизнес-смысла — в сервис/workflow.
- **Доменный слой без HTTP-типов** (!99 «В доменном слое Http») — `gin`, `http.Request`, request/response-структуры entrypoint'а в `internal/domains` не импортируются.
- **Workflow самодостаточен** — общие хелперы дублируются в каждый workflow, не шарятся между файлами workflow-слоя (!103, повторено дважды). Это осознанная позиция команды: workflow читается сверху вниз без прыжков.
- **Транзакции на workflow** — «транзакция надо как будто» (!100, !103): workflow с записью без транзакции — ждать вопроса; теперь правило строже — workflow транзакционен по умолчанию (O-8). Вызов сервиса домена внутри `txManager.Exec` — запись мимо транзакции. См. `conventions.md`, п. 17.
- **`gofmt` обязателен** — по отступам придираются построчно (!93).
- **Имя не отражает поведение** (MR!151, серия комментариев подряд в одном файле: "почему функция называется положить в очередь а по факту создает запись в БД?", "почему менеджер называется положить в очередь а по факту транзакция?", "почему функция которая просто создает записи называется dispatch?") — `Enqueue`/`EnqueueTxManager`/`dispatch` присвоены синхронной записи в БД и прямому вызову без какой-либо очереди. См. `conventions.md`, п. 20.
- **Название файла интерфейса слишком абстрактное** (MR!151: `ports.go` вместо `publisher.go`/`repository.go` — "что за название файла? название слишком абстрактное") — файл называется по объявляемому интерфейсу, не hexagonal-термином. См. `conventions.md`, п. 12.
- **«ИИ-шные» комментарии** (MR!151, kulzhambekov.o дословно: "убери эти ИИшиные коменты, бессмысленные, если надо напиши чтобы было понятно (тут и везде)") — длинные комментарии, пересказывающие код построчно вместо одной мысли о неочевидном. См. `style.md`, раздел «Комментарии».
- **`nil` как обязательная зависимость в конструктор** (MR!151: "ты в фабрике создаешь сервис с publisher = nil эта функция потенциально выкинет ошибку. так нельзя делать") — мина для любого будущего вызова через этот инстанс. См. `conventions.md`, п. 21.
- **Домен собирает `map[string]any` с именами колонок** (gateway 2026-09, по образцу parking-session-service) — `Repository.Update(ctx, id, map[string]any{"path_pattern": …})` значит, что домен знает схему БД, а опечатка в ключе ловится только SQL-ошибкой. Частичное обновление — через DTO из `dto.go` (`Patch` с указателями), `map` с колонками строится только в infra (`mapper.go`). [ОШИБКА], архитектура.
- **Проверка «такого ещё нет» без перехвата unique violation** (gateway 2026-09: 20 параллельных создания → 14 упёрлись в constraint и получили 500) — `ExistsBy…` + `Create` не атомарны. Unique-констрейнт в БД плюс перехват SQLSTATE `23505` в репозитории → 422 (как для FK — `23503`); хелпер разбора кодов один на сервис.
- **Значения, которые ломаются только на трафике** (gateway 2026-09) — проверять на записи (422), а не ждать отказа при запросе: CSV IP/CIDR (опечатка → список не совпадает ни с кем → отказ всем), URL без схемы (`billing:8080` парсится как схема `billing`), лимит `0` при включённом rate limit (→ 429 на всё), CIDR или IPv6 в другом регистре там, где сравнение точное по строке.
- **Цепочка builder-вызовов в одну строку** (MR!151, дважды на один файл: "Цепочку вызовов лучше разбить по одному вызову на строку") — 3+ метода подряд сливаются в нечитаемую строку. См. `style.md`.

## Тесты

- Тесты живые и разложены по шлюзам (`tests/<шлюз>/`). Новый платёжный сценарий без теста — законное замечание.
- `tests/*` — e2e, требуют `APP_URL` запущенного сервиса. Их падение «unsupported protocol scheme» локально — не сигнал. Локальный гейт — юнит-тесты пакетов (`go test ./internal/...`).

## Известные споры (фиксировать как спор, не как свежую находку)

- Сборка workflow в `services_factory` (!99 «Почему workflow собирается в services_factory?») — **[ВНИМАНИЕ]**, собирать в `workflows_factory.go` (решение O-2). Существующий parking написан по-старому: в новом коде — по правилу, массово старое не переписывать без задачи.
- Файл `*_command.go` / `*_query.go` в `internal/workflows/` — **[ВНИМАНИЕ]** (решение G-1): если сценарий междоменный — переименовать в `*_workflow.go` (`sync_outbox_event_command.go`: handbook + session); если однодоменный — это Command/Query домена, перенести в модуль-владелец результата в `internal/domains/` (`fiscalize_receipt_command.go` → `domains/billing/fiscal_receipt/`, решение O-6).
- Инфра-адаптер внешней системы не по имени провайдера (`http/fiscalization/webkassa` → `http/webkassa`) или внешняя система под нашим доменом (`http/billing/payment` для Kaspi) — **[ВНИМАНИЕ]** (решение G-2, `go-sdk/infra.md`). В parking `http/kaspi/kaspiautopay` по форме уже верно.
- Расположение тестов (!103) — решено (O-3): unit рядом с кодом, e2e в `tests/`, см. `structure.md`, «Тесты».

## За пределами файла

- **Разъезд `const`-блоков статусов**: новое значение → `grep` по `switch` и `map` по этому типу, по swagger `enums:` в DTO.
- **Данные под миграцию поведения**: новый NOT NULL / новое значение enum — что лежит в колонке на stage/prod; локальной базы в репо может не быть — тогда явно поручать автору.
- **CI без гейтов**: если pipeline — только containerize + deploy (ни lint, ни test stage), локальный `go build ./... && go vet ./... && go test ./... && gofmt -l internal pkg` — единственный гейт; его результат писать в отчёт явно.
- **`go.sum` вместе с `go.mod`**, нет неиспользуемых импортов.
- **Коммиты** по регламенту: `feat|perf|conf|fix|refactor: описание #номер`.

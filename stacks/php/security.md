# Безопасность (PHP): чеклист ревью

Из `php-reviewer` (раздел 5.1). Теги — для отчёта и статистики повторяющихся ошибок (`approaches/process/review.md`, «Теги»).

Проверяй независимо от типа компонента — это pentest-ориентированный чек-лист, а не архитектурное правило. Каждая подтверждённая находка помечается **[БЕЗОПАСНОСТЬ]**, выносится в отдельный раздел отчёта (см. `approaches/process/review.md`, «Отчёт») и **всегда** переводит вердикт ревью в **КРИТИЧНО**, независимо от количества остальных находок.

| Уязвимость | Тег (для отчёта, отчёт) | Признаки в коде |
|---|---|---|
| SQL Injection | `sql-injection` | `DB::select/statement/raw(...)`, `whereRaw(...)` с конкатенацией/интерполяцией пользовательского ввода вместо биндингов (`?`, именованные плейсхолдеры) |
| Mass Assignment | `mass-assignment` | `Model::create($request->all())` / `->fill($request->all())` / `->update($request->except('avatar'))` (в обход `$request->validated()`) без строгого `$fillable`; или `$fillable` включает чувствительное поле (`is_admin`, `role`, `balance`, `is_banned`, `otp_verified`). Отдельно проверять базовую/ядровую модель проекта — `protected $guarded = false;` на общем предке отключает защиту сразу для всех моделей, которые не задали свой `$fillable` явно. В mps/core так и есть: `MPS\Core\Models\Model::$guarded = false`; `CRUDRepository::update()`/`updateById()` пишут query builder-ом — мимо `$fillable` и `$casts` (отсекаются только несуществующие колонки): поэтому запись — методами репозитория с DTO и явным списком колонок, модель с casts — `fill()->save()` (`conventions.md` п. 11a, тег `write-array-instead-of-dto`) (AINA-2978) |
| Синхронизация связей вне скоупа актора | `cross-scope-relation-sync` | sync many-to-many («удалить все привязки, вставить набор», как `BelongsToMany::sync`) при операции актора со скоупом удаляет/меняет привязки к сущностям **вне** его скоупа: админ здания A отвязывает организацию от здания B. Хорошо: при скоупе `!== null` удаляются и обновляются только привязки внутри скоупа, остальные не трогаются (AINA-2978) |
| PUT сбрасывает/выдаёт флаг прав | `put-resets-privileged-flag` | Флаг доступа (`has_employee_access`, `is_admin`, `can_*`) в DTO общего `create/update` с умолчанием `false`: любое сохранение молча отзывает выданное, а точка входа на общий `update` выставляет `true` в обход отдельной операции с проверкой роли. Хорошо: флага нет в DTO и колонках записи общего `update`, нет в `$fillable`; пишет отдельный метод под своим правом (AINA-2978) |
| Мягко удалённое членство даёт доступ | `soft-deleted-membership-grants-access` | Принадлежность (сотрудник организации, участник) проверяется `join`/`EXISTS` к таблице с `SoftDeletes` без `deleted_at IS NULL` — query builder глобальный скоуп модели не применяет; уволенный сохраняет доступ (AINA-2978) |
| Ссылка на чужую/несуществующую запись | `cross-scope-reference` | `parent_id`/`*_id` другой записи пишется без проверки существования и скоупа актора: привязка к чужой (через неё — раскрытие в чужих выборках) или удалённой записи; у иерархий — циклы. Хорошо: в сервисе/workflow — поиск по id в скоупе актора, нет — `ValidationAppException` по полю (один текст для «нет» и «чужая»), иерархия — проверка цикла (AINA-2978) |
| Динамическая запись произвольного поля/модели | `dynamic-mass-assignment` | Generic-эндпоинт вида `PATCH /{model}/{id}/field`, где имя модели и/или имя колонки берутся из route/body (`'App\\Models\\'.ucfirst($model)`, `$record->update([$attribute => $value])`) без allowlist моделей и полей — фактически mass assignment через рефлексию, обходит `$fillable` целиком |
| XSS | `xss` | Blade `{!! $var !!}` выводит данные из API/пользовательского ввода без санитизации (`{{ }}` не заменён на `{!! !!}` без явной причины) |
| CSRF | `csrf` | Route, меняющий состояние, исключён из `VerifyCsrfToken::$except` без обоснования |
| Broken Access Control / IDOR | `broken-access-control` | Controller получает/меняет ресурс по `{id}` из route без Policy/Gate или явной проверки владельца (`$resource->user_id === auth()->id()`) |
| Отсутствие мульти-тенантного скоупа | `tenant-scope-missing` | `index`/`search`/дашборд-эндпоинт принимает id сущности-владельца (`building_id`/`organization_id`/`company_id`/`tenant_id`/`department_id`/`client_id`/`project_id`/`warehouse_id` — **название разное в каждом проекте**, важна не буква поля, а роль: «то, чем ограничен текущий актор») как **необязательный** клиентский параметр вместо обязательного скоупа, выводимого сервером из прав/принадлежности текущего пользователя (`auth()->user()->getBuildingIds()` или любой её аналог в проекте — сначала найти, как в конкретном проекте вообще выражается «какими сущностями владеет текущий актор», и сверять с ним). Без параметра — отдаёт данные ВСЕХ сущностей; с чужим id — отдаёт чужую. Отдельно проверять `show/update/destroy` того же ресурса: `index()` часто скоупят правильно, а соседние `show/update/destroy` того же контроллера — нет (implicit route-model binding без довеска). Самый частый паттерн в мульти-тенантных Laravel-проектах команды — искать в первую очередь, независимо от того, как называется сущность-владелец в этом конкретном проекте. Тот же fail-open внутри кода: параметр скоупа в сигнатуре сервиса/репозитория с умолчанием `?array $buildingIds = null` («без ограничения») — вызов, забывший аргумент, получает всё; скоуп — обязательный аргумент, `null` супер-админа передаётся явно (без ввода — [ВНИМАНИЕ], тег `scope-param-defaults-unrestricted`, AINA-2978) |
| Отсутствие auth-middleware | `missing-auth-middleware` | Новый route зарегистрирован вне `auth`/`auth:api` группы там, где соседние ручки домена требуют авторизации; отдельно проверять группы вида `['someApiMiddleware','locale']`, где `someApiMiddleware` форматирует ответ, а не аутентифицирует — легко спутать с реальным auth-guard'ом |
| Fail-open авторизация | `fail-open-authorization` | Permission/RBAC-middleware по умолчанию **разрешает** запрос, если для route name нет зарегистрированной записи прав (`if (!$permission) return true;` вместо `return false;`). Отдельно проверять: сихронизатор/сидер прав (`PermissionSync`, `RolePermissionSeeder` и т.п.) — если regex/конвенция генерации имени права не покрывает имя нового route, для него **никогда** не будет создана запись — fail-open становится не временным, а постоянным. Особенно критично для роутов оплаты/возврата/списания |
| Webhook/callback без проверки подлинности | `unverified-webhook` | Контроллер, принимающий колбэк от внешней системы (платёжный шлюз, СКУД, партнёрский вебхук), доверяет полю статуса/суммы из тела запроса (`$request->all()`/`$payload['status']`) без проверки HMAC/подписи/секрета согласно протоколу провайдера. Особо опасно, если результат меняет финансовое состояние (`markAsPaid()`, `markSuccess()`) — эквивалент IDOR/broken-auth, но на входящей интеграции, а не на пользовательском ресурсе |
| Небезопасная десериализация | `insecure-deserialization` | `unserialize(...)` на пользовательском вводе вместо `json_decode` |
| Command Injection | `command-injection` | `exec()`, `shell_exec()`, `system()`, `passthru()` вызван с неэкранированным пользовательским вводом |
| Path Traversal | `path-traversal` | Путь к файлу (чтение/запись/скачивание) собирается из пользовательского ввода (`Storage::get($request->path)`) без валидации против выхода за пределы базовой директории. Имя записи архива или файла — тоже ввод: отказ на `..`, `.`, пустые сегменты, абсолютный путь, `\0` и управляющие символы, разбор по `/` и `\`; итоговый путь — внутри `realpath` базы (ближайшего существующего предка). `realpath`/`mkdir` бросают `\ValueError` на `\0` — проверять до вызова ФС. `fopen($p, 'x')` разыменовывает висящий симлинк — перед записью проверять `is_link()` и `file_exists()` у цели. Одни правила имени для упаковки и распаковки — один валидатор (AINA-2744) |
| SSRF | `ssrf` | Исходящий HTTP-запрос (`Http::get($request->url)` и т.п.) на URL, пришедший от пользователя, без валидации схемы/домена |
| Небезопасная загрузка файлов | `insecure-file-upload` | Файл сохраняется под оригинальным именем/расширением от клиента без валидации (риск RCE через `.php`) — минуя `UploadManager` |
| Слабая криптография | `weak-crypto` | `md5()`/`sha1()` для хеширования паролей вместо `Hash::make()` (bcrypt/argon2) |
| Захардкоженные секреты | `hardcoded-secret` | API-ключ, пароль, токен, приватный ключ (`-----BEGIN PRIVATE KEY-----`) — литералом в конфиге/коде вместо `.env`/env-переменной или secret-хранилища. Отдельно проверять `config/*.php` с heredoc/литеральными ключами (частый случай — Passport/JWT ключи, сгенерированные один раз и закоммиченные) |
| Секрет утекает в артефакт сборки | `secret-in-build-artifact` | CI кладёт реальный секрет в файл сборочного контекста (например `auth.json` из `$COMPOSER_AUTH`) без последующего `.dockerignore`/`rm` — `COPY . .` в Dockerfile запекает его в слой образа, даже если сам секрет не в git |
| Тестовый/отладочный обход аутентификации | `test-auth-backdoor` | Список тестовых телефонов/логинов/фиксированный OTP-код (`'7777'`) или аналогичный bypass без проверки `app()->environment('local','testing')` — активен и в проде |
| Rate limit обходится подменой IP | `spoofable-rate-limit` | `throttle`/кастомный rate-limiter ключуется по `$request->ip()`, при этом `trustProxies(at: '*')` (или аналог) доверяет `X-Forwarded-For`/`X-Real-IP` от любого клиента — лимит тривиально обходится сменой заголовка на каждый запрос. Также проверять, что кастомный limiter реально инкрементирует счётчик (`RateLimiter::hit()`), а не только читает его (`tooManyAttempts()` без `hit()` — лимитер никогда не сработает) |
| Утечка чувствительных данных в логи | `sensitive-data-in-logs` | `Log::info(...)` логирует полное тело запроса, пароль, токен, номер карты, фото/биометрию (base64 в поле запроса к внешней СКУД/интеграции, сохранённое в БД-таблицу логов без маскирования). Полезная проверка: если рядом есть похожий сервис/интеграция для другого провайдера — сравнить, маскирует ли он то же поле перед логированием (несовпадение соседних реализаций — сильный сигнал). Секрет в аргументе функции попадает в трейс исключения → лог/Sentry: параметры с паролем/токеном — `#[\SensitiveParameter]` (AINA-2744) |
| Утечка внутренних деталей в ответе | `internal-details-leak` | Exception handler возвращает клиенту `$e->getMessage()`/trace вместо обобщённого сообщения. В mps/core `AppException::render` отдаёт клиенту текст и `details` для кодов < 500 — в них нельзя абсолютные пути, имена temp-файлов, секреты; `DataObject::toArray()` включает private-поля — секрет в DTO маскировать в `toArray`. Под Laravel `E_WARNING` функций ФС становится `\ErrorException` с абсолютным путём — предпроверки, локальный `set_error_handler`, перевод в своё исключение без пути (AINA-2744) |
| Распаковка без ограничения объёма (zip-бомба) | `decompression-bomb` | Лимит сравнивается с объявленным в каталоге архива размером (`statIndex()['size']`, размер архива) — подменённый `size` его обходит; `ZipArchive::extractTo`/`getFromName` не ограничивают вывод и не проверяют CRC; `getFromName($n, 0)` — без лимита. Хорошо: чтение потоком (`getStreamIndex`) кусками со своим счётчиком фактической длины, `crc32b` и суммой за операцию; лимиты (число записей, сумма, одна запись в память) по умолчанию конечные и > 0; число записей — до построения списка; читать до пустого куска, а не до `feof()` (libzip проверяет CRC/HMAC на чтении после конца) (AINA-2744) |
| Обход симлинков при упаковке/распаковке | `symlink-following` | Обход директории для архивации идёт по симлинкам (`RecursiveDirectoryIterator` с `FOLLOW_SYMLINKS`, `is_file()` на симлинке) — в архив попадает чужой файл (`/etc/...`); при распаковке запись-симлинк (unix mode в `external attributes`, независимо от `opsys`) не отклоняется (AINA-2744) |
| Отсутствие rate limiting | `missing-rate-limiting` | Login/сброс пароля/регистрация/OTP без `throttle` middleware — см. также `spoofable-rate-limit`, если throttle формально есть, но обходится |

Если находка не подтверждена однозначно (нет прямого пользовательского ввода в опасном месте) — не флагай, чтобы не плодить false positive; при сомнении отметь как **[ВНИМАНИЕ]** с пояснением риска, а не как **[БЕЗОПАСНОСТЬ]**.

## Меры по слоям

Мера в `threats.md`, `design.md` и в коде — в слое по правилам стека, не по образцу легаси (`approaches/process/legacy-refactor.md`, «Что переносится»). Мера не в своём слое — находка того же уровня, что в коде.

| Мера | Слой |
|---|---|
| Формат: типы, обязательность, `integer\|gt:0`, `max:`, `Rule::enum()`; вложенная коллекция DTO — `list` + `{поле}.*: array` (иначе ядро соберёт пустую коллекцию = «отвязать всё», `mps-core/data-objects.md`) | Request — без SQL (P-17, `conventions.md` п. 9a) |
| Роль/право на операцию; здание/организация из заголовка и параметров | middleware контекста (`conventions.md` п. 19a) |
| Существование связанной записи | сервис/workflow через репозиторий; сущность другого домена — в workflow через репозиторий (интерфейс) того домена |
| Принадлежность записи скоупу | фильтр в запросе репозитория, скоуп — обязательный аргумент |
| Уникальность | уникальный индекс + проверка в сервисе через репозиторий для понятной ошибки |
| Доменные инварианты (значения DTO без данных из БД) | `{E}DtoValidator` в `Validators/` модуля (P-8) |

```php
// плохо: мера легаси в Request
'user_id' => ['required', 'exists:users,id'],

// хорошо: Request — формат, существование — workflow через репозиторий домена User
'user_id' => ['required', 'integer', 'gt:0'],

if (! $this->userRepository->oneById($dto->getUserId())) {
    throw new ValidationAppException('VALIDATION ERROR', ['user_id' => ['Пользователь не найден']]);
}
```

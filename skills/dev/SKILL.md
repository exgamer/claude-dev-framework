# /dev

`{DF}` — корень фреймворка: `.claude/dev-framework` в проекте, если есть, иначе `~/.claude/dev-framework`.

```
/dev <задача>            # авто: уточнить всё сразу → сделать до результата
/dev --step <задача>     # пошагово: стоп и «ок» после каждой роли
```

Цель авто-режима: пользователь отвечает на вопросы **один раз в начале** и получает готовый результат. Всё, что можно выяснить из кода, правил и истории проекта, — выясняется самостоятельно, а не спрашивается.

## Фаза 0 — Контекст

Прочитай `{DF}/core/principles.md`, `{DF}/approaches/process/role-chain.md` (разделы «Авто-режим» и «Контекст ролей»). Больше правил сам не загружаешь: роли читают свои правила в своём контексте. `.claude/dev-rules.md` проекта главнее фреймворка.

**Ты координатор, а не исполнитель.** Каждая роль (аналитик, архитектор, безопасник, QA, каждая задача разработки, ревью) — отдельный субагент со свежим контекстом: агенты `df-analyst`, `df-architect`, `df-security`, `df-qa`, `df-go`, `df-php`, `df-review` (Agent, `subagent_type` = имя). Роль, ограничения и правила субагента у них уже прописаны (`{DF}/agents/`, `{DF}/approaches/process/subagent.md`). Так правила роли не теряются при сжатии твоего контекста. Ты держишь только: ответы пользователя, политику новых вопросов, статусы `plan.md` и краткие итоги ролей. Код и правила стека сам не читаешь — кроме сборки изменений после волны и прогона команд.

Поручение агенту — короткое, по шаблону `role-chain.md`, «Контекст ролей»: ключ задачи и готовые артефакты, режим, своя задача и файлы (разработчику), ответы пользователя, политика новых вопросов. Что читать и как себя вести, агент знает сам — не пересказывай.

Стек: `go.mod` с `gosdk-*` → Go (`/dev-go`); `composer.json` с `mps/core` → PHP (`/dev-php`); фронт без фреймворка — роль отложена, сказать пользователю. Перенос — оба стека.

Тип: фича · рефактор легаси (`{DF}/approaches/process/legacy-refactor.md`) · перенос стека (`stack-migration.md`) — для двух последних в список вопросов **всегда** входит «сохраняем ли контракты API старого проекта» со списком найденных контрактов · аудит безопасности (сразу `/dev-security audit`, не цепочка).

Ключ задачи — номер из трекера в запросе или короткий slug; артефакты — `docs/tasks/<ключ>/`. Есть артефакты от прошлой сессии — продолжай с них, не начинай заново.

## Фаза 1 — Разведка (без вопросов пользователю)

Шаги 1–4 — субагенты по очереди (следующий читает артефакт предыдущего).

1. **Требования** — `df-analyst` → `requirements.md` (участники, сценарии, правила R*, критерии приёмки AC*, границы). Неясности — в «Открытые вопросы», сам не спрашиваешь.
2. **Дизайн и план** — `df-architect`, по `requirements.md` (режим `feature` / `refactor` / `migrate` по типу задачи) → `design.md`, `plan.md`. Шаг 5 архитектора — по правилу авто-режима: вопросы не задаёшь, копишь в «Открытые вопросы». Карта связей (`{DF}/approaches/process/impact-analysis.md`) — обязательна для любой задачи, задевающей существующий код. Код до этого не пишется ни строки.
3. **Модель угроз** — если в `design.md` отмечены чувствительные зоны: `df-security` → `threats.md`, меры — в `plan.md`. Вопросы — туда же.
4. **Тест-кейсы** — `df-qa`, режим `cases`: по AC* и негативным сценариям `requirements.md`, связям и `threats.md` → `qa.md` (до кода — разработчики пишут unit-тесты по ним).
5. **Предпроверка окружения** — есть ли чем собрать и прогнать тесты (Go: `go`; PHP: `php`/`composer` или контейнер проекта; общая БД/Redis — уже поднятые, `docker ps`). Нет — это вопрос, а не молчаливое «не запускал» в конце. Понадобится прогон миграций, тесты с пересозданием схемы, сиды или массовые правки данных — вопрос с указанием БД, без «да» не выполнять (`{DF}/core/principles.md`, «Действия с БД»).
6. Пройди чеклист «Что выяснить до старта» из `role-chain.md`. Каждый пункт — либо закрыт по артефактам и итогам ролей (записать, откуда), либо вопрос. Вопросы, которые вернули субагенты, и «Открытые вопросы» артефактов — в общий список.

## Фаза 2 — Один список вопросов

Одним сообщением, обычным текстом, пронумеровано:
- коротко: что понял из задачи, что будет сделано (срез), что отложено;
- вопросы — каждый с вариантами и **рекомендацией**, чтобы можно было ответить «1 — да, 2 — Б, остальное по рекомендации»;
- рабочая ветка: «создам `<КЛЮЧ-N>` от `release` — ок?» (если сейчас не она);
- последним пунктом: «Если по ходу всплывёт новый вопрос: (а) по рекомендации с записью в `rules-log.md` и в отчёт — **по умолчанию**, или (б) отложить этот кусок и спросить в конце?»

Вопросов нет — сразу Фаза 3, сказав, что уточнять нечего и что будет сделано.

## Фаза 3 — Фиксация ответов

Ответы → в `requirements.md` / `design.md` / `threats.md` / `qa.md` / `plan.md` (ответ, меняющий требование, меняет и кейсы, и план). Всё, что касается правил (пробел, спор, «сделано, но нет в регламенте», решение не по правилам), → строки в `docs/tasks/<ключ>/rules-log.md` (`{DF}/core/rules-evolution.md`, «Лог отклонений по задаче»); правила не правятся до разбора в Фазе 8. Дальше пользователь не нужен до результата.

## Фаза 4 — Разработка с unit-тестами (без остановок)

Перед первой волной — рабочая ветка по ответу из Фазы 2 (`{DF}/regulations/git.md`: имя = ключ задачи, от `release`); дерево должно быть чистым — иначе это вопрос, а не `stash`. Создание ветки — не коммит, подтверждения не требует.

По волнам `plan.md` (статус задачи в `plan.md` обновляется после каждой: `в работе` → `готово`; так работу можно продолжить в новой сессии):
- **каждая задача — агент `df-go` / `df-php`**, даже мелкая (мелкие задачи одной волны можно отдать одному субагенту); сам код не пишешь;
- одна задача в волне — субагент прямо в рабочей ветке; 2–3 независимые — параллельные агенты (`isolation: "worktree"` от рабочей ветки), **не больше 3**. Каждому в поручении: id задачи и **список его файлов**, ключ задачи, ответы пользователя из Фазы 2, политика новых вопросов;
- задача готова только с **unit-тестами** на свою логику (правила R*, ветки ошибок, кейсы из `qa.md`, относящиеся к ней) — тесты пишет разработчик вместе с кодом;
- предыдущие волны не закоммичены → worktree их не увидит: параллельные агенты — в одном рабочем дереве, без `isolation`, по правилу `planning.md` (AINA-2744);
- после волны: свести изменения **без коммитов** — субагенты в worktree не коммитят; их правки переносятся в рабочую ветку диффом (`git -C <worktree> diff` + новые файлы → `git apply` / копирование), затем worktree удаляется; проверить, что файлы задач не пересеклись; сборка/линтер/тесты. Красное — чинить до следующей волны.

**Новый вопрос по ходу** (не предусмотренный в Фазе 2) — по выбранной политике: (а) решение по рекомендации, строка в `rules-log.md` и в отчёт; (б) этот кусок отложить, остальное доделать, вопрос — в итог. Не останавливать всю работу.

## Фаза 5 — QA: интеграционные и e2e тесты

`df-qa`, режим `tests`: по кейсам `qa.md` — интеграционные/e2e автотесты (unit уже написаны разработчиками), регрессия по связям «сохраняется»; прогнать всё. Красное из-за кода — исправить (разработчиком на задачу) до ревью; не сходится за 3 попытки — остановиться и показать.

## Фаза 6 — Независимое ревью и исправления

Ревью — агент **`df-review`** (без контекста разработки, код не правит; в поручении — базовая ветка), по изменениям относительно базовой ветки, включая незакоммиченное (`git diff release` + новые файлы; код **и** тесты), и артефактам задачи → `review.md`. Автор кода сам себя не ревьюит.

[БЕЗОПАСНОСТЬ] и [ОШИБКА] — исправить агентом `df-go` / `df-php` (поручение: «исправить находки `review.md` №…», файлы находок), прогнать сборку и **все** тесты, повторить ревью. **Не больше 3 кругов**; не сошлось — остановиться и показать, что осталось и почему. [ВНИМАНИЕ] — исправить, если в пределах задачи; иначе — в отчёт.

## Фаза 7 — Результат

Проверить «Готово» (`{DF}/approaches/process/role-chain.md`, «Definition of Done») — каждый пункт: выполнен / нет и почему. Затем одним сообщением (и копия в `docs/tasks/<ключ>/result.md`):
- что сделано — по требованиям (R*, AC* → чем покрыто), список файлов;
- как проверено — команды и их результат (сборка, линтер, тесты, проверка зависимостей); что **не** проверено и почему;
- меры безопасности из `threats.md` — реализованы / нет; связи из «Связи» — учтены;
- вердикт ревью;
- **выкатка**: миграции и их порядок, новые env/конфиг, совместимость со старыми клиентами, флаги, как откатить (из `design.md`, «Выкатка»);
- решения, принятые по ходу, и сколько строк в `rules-log.md`;
- отложено и открытые вопросы;
- готово к коммиту: ветка и сообщения коммитов по `{DF}/regulations/git.md` (одна логическая задача — один коммит) и черновик описания MR по его условиям. **Коммит и пуш — только после явного «да»**; MR, миграции на окружениях, деплой — не делаются; массовые операции, очистка и изменение схемы локальной БД — только по явному «да» на каждую.

## Фаза 8 — Разбор лога отклонений

Если `rules-log.md` не пуст: показать его одной таблицей, сгруппировав по предложению (фреймворк / проект / оставить), с рекомендацией по каждой строке. По ответу пользователя (можно «всё по рекомендации»): (Ф) — правки в источнике истины фреймворка по процессу `/dev-rule` + `core/decisions.md`; (П) — `.claude/dev-rules.md` проекта; (О) — ничего. Статусы — в лог. Можно отложить разбор («потом») — тогда лог остаётся с открытыми строками, и решения из него действуют только в этой задаче.

## Режим `--step`

Те же роли и те же субагенты, но после требований, дизайна, модели угроз, каждой волны, QA и ревью — показать результат и ждать «ок»; вопросы задаются по мере появления. Любой шаг можно запустить отдельно своей ролью (`/dev-analyst`, `/dev-architect`, `/dev-security`, `/dev-qa`, `/dev-go`, `/dev-php`, `/dev-review`) по готовым артефактам.

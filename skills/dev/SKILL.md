# /dev

`{DF}` — корень фреймворка: `.claude/dev-framework` в проекте, если есть, иначе `~/.claude/dev-framework`.

```
/dev <задача>            # авто: уточнить всё сразу → сделать до результата
/dev --step <задача>     # пошагово: стоп и «ок» после каждой роли
```

Цель авто-режима: пользователь отвечает на вопросы **один раз в начале** и получает готовый результат. Всё, что можно выяснить из кода, правил и истории проекта, — выясняется самостоятельно, а не спрашивается.

## Фаза 0 — Контекст

Прочитай `{DF}/core/principles.md`, `{DF}/core/decisions.md`, `{DF}/approaches/process/role-chain.md` (раздел «Авто-режим»), `{DF}/approaches/process/planning.md`, `{DF}/approaches/process/security.md` («Чувствительные зоны»). `.claude/dev-rules.md` проекта главнее фреймворка.

Стек: `go.mod` с `gosdk-*` → Go (`/dev-go`); `composer.json` с `mps/core` → PHP (`/dev-php`); фронт без фреймворка — роль отложена, сказать пользователю. Перенос — оба стека.

Тип: фича · рефактор легаси (`{DF}/approaches/process/legacy-refactor.md`) · перенос стека (`stack-migration.md`) — для двух последних в список вопросов **всегда** входит «сохраняем ли контракты API старого проекта» со списком найденных контрактов · аудит безопасности (сразу `/dev-security audit`, не цепочка).

Ключ задачи — номер из трекера в запросе или короткий slug; артефакты — `docs/tasks/<ключ>/`. Есть артефакты от прошлой сессии — продолжай с них, не начинай заново.

## Фаза 1 — Разведка (без вопросов пользователю)

1. **Дизайн и план** — по правилам `/dev-architect` → `design.md`, `plan.md`. Вопросы не задаёшь — копишь в «Открытые вопросы».
2. **Модель угроз** — если в `design.md` есть чувствительные зоны: по правилам `/dev-security design` → `threats.md`, меры — в `plan.md`. Вопросы — туда же.
3. **Предпроверка окружения** — есть ли чем собрать и прогнать тесты (Go: `go`; PHP: `php`/`composer` или контейнер проекта; общая БД/Redis — уже поднятые, `docker ps`). Нет — это вопрос, а не молчаливое «не запускал» в конце.
4. Пройди чеклист «Что выяснить до старта» из `role-chain.md`. Каждый пункт — либо закрыт по коду/правилам (записать, откуда), либо вопрос.

## Фаза 2 — Один список вопросов

Одним сообщением, обычным текстом, пронумеровано:
- коротко: что понял из задачи, что будет сделано (срез), что отложено;
- вопросы — каждый с вариантами и **рекомендацией**, чтобы можно было ответить «1 — да, 2 — Б, остальное по рекомендации»;
- последним пунктом: «Если по ходу всплывёт новый вопрос: (а) по рекомендации с записью в правила и в отчёт — **по умолчанию**, или (б) отложить этот кусок и спросить в конце?»

Вопросов нет — сразу Фаза 3, сказав, что уточнять нечего и что будет сделано.

## Фаза 3 — Фиксация ответов

Ответы → в `design.md` / `threats.md` / `plan.md`. Ответы, которые меняют правила (пробел, спор, «сделано, но нет в регламенте»), → правки по процессу `/dev-rule` (в источнике истины фреймворка) + строка в `core/decisions.md`. Дальше пользователь не нужен до результата.

## Фаза 4 — Разработка (без остановок)

По волнам `plan.md`:
- волна из мелких задач — сам, по правилам `/dev-go` / `/dev-php`;
- 2–3 независимые задачи заметного объёма — параллельные субагенты (Agent, `isolation: "worktree"`), **не больше 3**. Каждому: пути к `design.md`, `plan.md`, `threats.md`, id задачи, **список его файлов**, правила стека (`{DF}/skills/dev-go/SKILL.md` или `dev-php`), ответы пользователя из Фазы 2 и политика новых вопросов;
- после волны: свести изменения, проверить непересечение файлов, сборка/линтер/тесты. Красное — чинить до следующей волны.

**Новый вопрос по ходу** (не предусмотренный в Фазе 2) — по выбранной политике: (а) решение по рекомендации, запись в правила и в отчёт; (б) этот кусок отложить, остальное доделать, вопрос — в итог. Не останавливать всю работу.

## Фаза 5 — Ревью и исправления

`/dev-review` по изменениям → `review.md`. [БЕЗОПАСНОСТЬ] и [ОШИБКА] — исправить (сам или субагентом на задачу) и повторить ревью. **Не больше 3 кругов**; не сошлось — остановиться и показать, что осталось и почему. [ВНИМАНИЕ] — исправить, если в пределах задачи; иначе — в отчёт.

## Фаза 6 — QA

`/dev-qa` → `qa.md` и автотесты; прогнать. Красные тесты из-за кода — назад в Фазу 5 (в пределах тех же 3 кругов).

## Фаза 7 — Результат

Одним сообщением (и копия в `docs/tasks/<ключ>/result.md`):
- что сделано — по пунктам задачи, список файлов;
- как проверено — команды и их результат (сборка, линтер, тесты); что **не** проверено и почему;
- меры безопасности из `threats.md` — реализованы / нет;
- вердикт ревью, тесты QA;
- решения, принятые по ходу (по рекомендации), и правки правил фреймворка;
- отложено и открытые вопросы;
- готово к коммиту: имя ветки и сообщения коммитов по `{DF}/regulations/git.md`. **Коммит и пуш — только после явного «да»**; MR, миграции на окружениях, деплой — не делаются.

## Режим `--step`

Те же роли, но после дизайна, модели угроз, каждой волны, ревью и QA — показать результат и ждать «ок»; вопросы задаются по мере появления. Любой шаг можно запустить отдельно своей ролью (`/dev-architect`, `/dev-security`, `/dev-go`, `/dev-php`, `/dev-review`, `/dev-qa`) по готовым артефактам.

# /dev

`{DF}` — корень фреймворка: `.claude/dev-framework` в проекте, если есть, иначе `~/.claude/dev-framework`.

```
/dev <задача>            # авто: уточнить всё сразу → сделать до результата
/dev --step <задача>     # пошагово: стоп и «ок» после каждой роли
/dev                     # без задачи: продолжить незаконченную (Фаза 0, «Метка продолжения»)
```

Цель авто-режима: пользователь отвечает на вопросы **один раз в начале** и получает готовый результат. Всё, что можно выяснить из кода, правил и истории проекта, — выясняется самостоятельно, а не спрашивается.

## Фаза 0 — Контекст

Прочитай `{DF}/core/principles.md`, `{DF}/approaches/process/role-chain.md` (разделы «Авто-режим» и «Контекст ролей»). Больше правил сам не загружаешь: роли читают свои правила в своём контексте. `.claude/dev-rules.md` проекта главнее фреймворка.

**Ты координатор, а не исполнитель.** Каждая роль (аналитик, архитектор, безопасник, QA, каждая задача разработки, ревью) — отдельный субагент со свежим контекстом: агенты `df-analyst`, `df-architect`, `df-security`, `df-qa`, `df-go`, `df-php`, `df-review` (Agent, `subagent_type` = имя). Роль, ограничения и правила субагента у них уже прописаны (`{DF}/agents/`, `{DF}/approaches/process/subagent.md`). Так правила роли не теряются при сжатии твоего контекста. Ты держишь только: ответы пользователя, политику новых вопросов, статусы `plan.md` и краткие итоги ролей — и всё это в файлах, не в памяти: ответы и пожелания пользователя, сказанные по ходу разговора («git веду сам», «на устройстве — подтверждать»), сразу записываешь в `docs/tasks/<ключ>/answers.md` (разделы «Решения» и «Пожелания»), чтобы они пережили перезапуск сессии (ниже). Код и правила стека сам не читаешь — кроме сборки изменений после волны и прогона команд. Артефакты задачи — только нужные строки (`grep` по id задачи, разделу, статусу), не файлы целиком. Работающего агента не опрашиваешь — ни его транскрипт, ни файл вывода: итог придёт уведомлением, пока ждёшь — делай другое или ничего.

Подпись каждого запуска — «Роль Имя: задача» по таблице имён `role-chain.md`, «Контекст ролей» (пулы QA и разработчиков — случайное свободное имя, закреплённое за задачей; имя — в статус `plan.md` / шапку `qa.md`, в поручение не идёт, в код и git не попадает). Поручение агенту — короткое, по шаблону `role-chain.md`, «Контекст ролей»: ключ задачи и готовые артефакты, режим, своя задача и файлы (разработчику), ответы пользователя, политика новых вопросов. Что читать и как себя вести, агент знает сам — не пересказывай.

Стек: `go.mod` с `gosdk-*` → Go (`/dev-go`); `composer.json` с `mps/core` → PHP (`/dev-php`); фронт без фреймворка — роль отложена, сказать пользователю. Перенос — оба стека.

Тип: фича · рефактор легаси (`{DF}/approaches/process/legacy-refactor.md`) · перенос стека (`stack-migration.md`) — для двух последних в список вопросов **всегда** входит «сохраняем контракт или делаем по правилам (новой версией)» со списком найденных контрактов (O-19, без флагов) · аудит безопасности (сразу `/dev-security audit`, не цепочка) · баг в пределах контракта (сразу `/dev-fix`, `{DF}/approaches/process/bugfix.md`, «Границы»).

**Навигация по коду:** проверь доступ к IDE и при недоступности предложи включить — `{DF}/approaches/process/code-navigation.md`, «Проверка при старте»; работу это не останавливает, пункт — в список Фазы 2, перед Фазой 4 — повторная проверка.

Ключ задачи — номер из трекера в запросе или короткий slug; артефакты — `docs/tasks/<ключ>/`. Есть артефакты от прошлой сессии — продолжай с них, не начинай заново: с шага из строки «Сейчас» в шапке `plan.md`; ответы и пожелания — `answers.md`, статусы — `plan.md`, отклонения — `rules-log.md`. Строки «Сейчас» нет (задача начата до этого правила или строку не записали) — не бери первый раздел сверху: найди самый свежий по дате раздел состояния во **всём** `plan.md` (разделов нет — определи шаг по статусам задач `plan.md` и готовым артефактам), сверь его с `git log` ветки и последними ответами `answers.md` (закрытый вопрос не выдавай за открытый), запиши строку «Сейчас», старые разделы состояния пометь историей — и только потом продолжай или спрашивай пользователя. Почему: без строки «Сейчас» разделы состояния копятся, верхний устаревает, а актуальный оказывается в конце файла.

**Метка продолжения.** Ключ определён и задача остаётся в `/dev` (ушла в `/dev-fix` или `/dev-security audit` — метку не ставь) — `python3 {DF}/tools/resume/resume.py set dev <ключ>` (с `--step` — ещё `--flags "--step"`): после `/clear` или в новой сессии хук (`install.sh <проект>`) предложит продолжить — пользователю хватит «дальше». Снимается в конце задачи (Фаза 8). Каждый вызов `resume.py` (`set`, `done`, `list`) — с `--project <корень проекта>`: после `/dev-rule` посреди задачи текущая папка — репозиторий фреймворка, и без него метка ставится и ищется не там. `/dev` без задачи — `resume.py list`: одна незаконченная команда — продолжай её (не `/dev` — вызови её скилл), несколько — спроси какую, ни одной — спроси задачу.

**Перезапуск сессии.** Твой контекст растёт: каждый твой шаг перечитывает его целиком (оркестратор — 22–36% расхода задачи, замер D-3), а при сжатии правила и ответы остаются только пересказом. Поэтому на границе — после Фазы 3, после каждой волны Фазы 4, после Фазы 5 и каждого круга ревью — проверь размер: `python3 {DF}/tools/usage/usage.py --project <корень проекта> --context` (берёт самую свежую сессию проекта; в проекте открыта ещё одна — `--session <ID своей сессии>`); контекст больше ~250 тыс. токенов, или уже сжимался, или подходит к пределу: проверь, что всё записано (`answers.md` — в том числе всё, что пользователь сказал в чате по ходу; статусы `plan.md`, `rules-log.md`, итоги ролей — в их артефактах; в сообщении о перезапуске — одна строка, что записано в `answers.md` с прошлого перезапуска), что ни один агент не работает, запиши в шапку `plan.md` строку «Сейчас: Фаза N, следующий шаг — …» — она одна и **заменяет** прежнюю (не дописывай новую ниже и не заводи свободных разделов «Состояние на …»; подробности — в статусах задач и артефактах ролей) — и напиши пользователю, почему нужен перезапуск, а не только что момент удобный — по причине: сжатие — «Контекст уже сжимался (или скоро сожмётся) — после сжатия инструкции фреймворка остаются у меня только пересказом, и я могу ошибиться в правилах. Нужен перезапуск, чтобы загрузить их заново целиком.»; порог — «Мой контекст — <N> тыс. токенов: каждый мой шаг перечитывает его целиком, и дальше задача дорожает. Перезапуск сбросит его до ~50 тыс.». Затем: «Всё записано, агенты не работают: `/clear` (или новая сессия) и «дальше» (без хука продолжения — `/dev <ключ>`) — продолжу с шага «Сейчас» в `plan.md`». Сжатие уже случилось посреди фазы — новых агентов не запускай, дождись работающих, запиши их итоги и предложи перезапуск. Новая сессия проходит Фазу 0 заново: правила читаются целиком, а не пересказом.

## Фаза 1 — Разведка (без вопросов пользователю)

Шаги 1–4 — субагенты по очереди (следующий читает артефакт предыдущего).

1. **Требования** — `df-analyst` (есть `bug.md` от `/dev-fix` — он вход аналитику, в поручении; в поручении аналитику — критерий «баг не воспроизводится», архитектору — файлы теста бага из «Тест» в задачу модуля исправления, `bugfix.md`, «Границы») → `requirements.md` (участники, сценарии, правила R*, критерии приёмки AC*, границы). Неясности — в раздел «Неясности», сам не спрашиваешь.
2. **Дизайн и план** — `df-architect`, по `requirements.md` (режим `feature` / `refactor` / `migrate` по типу задачи) → `design.md`, `plan.md`. Шаг 5 архитектора — по правилу авто-режима: вопросы не задаёшь, копишь в «Открытые вопросы». Карта связей (`{DF}/approaches/process/impact-analysis.md`) — обязательна для любой задачи, задевающей существующий код. Код до этого не пишется ни строки.
3. **Модель угроз** — если в `design.md` отмечены чувствительные зоны: `df-security` → `threats.md`, меры — в `plan.md`; задачу без файлов (механизм волны 0 — мера задаёт только слой) — снова `df-architect`, в поручении «повторный вызов: файлы задачам T…». Вопросы — туда же.
4. **Тест-кейсы** — `df-qa`, режим `cases`: по AC* и негативным сценариям `requirements.md`, связям и `threats.md` → `qa.md` (до кода — разработчики пишут unit-тесты по ним).
5. **Предпроверка окружения** — есть ли чем собрать и прогнать тесты (Go: `go`; PHP: `php`/`composer` или контейнер проекта; общая БД/Redis — уже поднятые, `docker ps`). Нет — это вопрос, а не молчаливое «не запускал» в конце. Понадобится прогон миграций, тесты с пересозданием схемы, сиды или массовые правки данных — вопрос с указанием БД, без «да» не выполнять (`{DF}/core/principles.md`, «Действия с БД»).
6. Пройди чеклист «Что выяснить до старта» из `role-chain.md`. Каждый пункт — либо закрыт по артефактам и итогам ролей (записать, откуда), либо вопрос. Вопросы, которые вернули субагенты, «Неясности» `requirements.md` и «Открытые вопросы» `design.md` — в общий список.

## Фаза 2 — Один список вопросов

Одним сообщением, обычным текстом, пронумеровано:
- коротко: что понял из задачи, что будет сделано (срез), что отложено;
- вопросы — каждый с вариантами и **рекомендацией**, чтобы можно было ответить «1 — да, 2 — Б, остальное по рекомендации»;
- рабочая ветка: «создам `<КЛЮЧ-N>` от `release` — ок?» (если сейчас не она; пакет библиотеки — от `main`, `regulations/git.md`, «Ветки»);
- **обратная совместимость** — задача меняет существующее: изменённые контракты и потребители вне сервиса из «Открытых вопросов» `design.md` — отдельным пунктом, списком, с вариантами «сохранить / ломать с согласованием» и рекомендацией; изменение контракта — всегда, даже без найденных потребителей (`{DF}/approaches/process/impact-analysis.md`, «Обратная совместимость», O-29); у рефактора и переноса это вопрос O-19 выше;
- **схема БД** — есть раздел «Схема БД» в `design.md`: отдельным пунктом, таблицей целиком (`regulations/technical-approval.md`, «Схема БД»), вопрос «согласовано?»; без «да» задачи с миграциями не стартуют;
- Go: строка «SDK: <источник>, <пакеты и версии> — из `go.mod`» как информация (пользователь может поправить), а в случаях вопроса по `stacks/go/conventions.md` п. 23 — вопрос; итог — раздел «SDK» в `design.md` (O-4);
- PHP, задача с новым списком: вопрос формы пагинации, итог — раздел «Список» в `design.md` (`stacks/php/conventions.md` п. 2c, P-19);
- IDE недоступна или проект в ней не открыт — «включить до разработки? Рекомендация: да», с шагами (`code-navigation.md`, «Проверка при старте»);
- последним пунктом: «Если по ходу всплывёт новый вопрос: (а) по рекомендации с записью в `rules-log.md` и в отчёт — **по умолчанию**, или (б) отложить этот кусок и спросить в конце?»

Вопросов нет — сразу Фаза 3, сказав, что уточнять нечего и что будет сделано.

## Фаза 3 — Фиксация ответов

Ответы — сначала дословно в `answers.md`, затем → в `requirements.md` / `design.md` / `threats.md` / `qa.md` / `plan.md` (ответ, меняющий требование, меняет и кейсы, и план). Всё, что касается правил (пробел, спор, «сделано, но нет в регламенте», решение не по правилам), → строки в `docs/tasks/<ключ>/rules-log.md` (`{DF}/core/rules-evolution.md`, «Лог отклонений по задаче»); правила не правятся до разбора в Фазе 8. Дальше пользователь не нужен до результата — кроме перезапуска сессии, если твой контекст вырос больше ~250 тыс. токенов или сжимался (Фаза 0).

## Фаза 4 — Разработка с unit-тестами (без остановок)

Перед первой волной — рабочая ветка по ответу из Фазы 2 (`{DF}/regulations/git.md`: имя = ключ задачи, от `release`, пакет библиотеки — от `main`); дерево должно быть чистым (кроме файлов теста бага из `bug.md`, «Тест», — `bugfix.md`, «Границы») — иначе это вопрос, а не `stash`. Создание ветки — не коммит, подтверждения не требует.

По `plan.md`, **запуск по готовности** (`planning.md`, «Команда»; статус задачи в `plan.md` обновляется после каждой: `в работе` → `готово`; так работу можно продолжить в новой сессии):
- перед первой задачей — повторная проверка IDE, если в Фазе 0 она была недоступна и пользователь не ответил «без IDE» (`code-navigation.md`);
- задачу с миграцией — только при «да» на «Схему БД» в `answers.md`; миграция пишется по «Схеме БД» `design.md`, разработчику понадобилось другое поле или таблица — вопрос, не правка (`regulations/technical-approval.md`);
- перед запуском — сверка плана: у каждой задачи есть файлы и «контекст», нет задачи явно больше предела (`planning.md`, «Размер задачи»); не так — вернуть архитектору, сам не режешь;
- **каждая задача — свой свежий агент `df-go` / `df-php`**, даже мелкая; закончившегося агента новой задачей и правками ревью не продолжать — только доводка в 1–3 шага сразу после его итога, не позже 5 минут (`planning.md`, «Команда»); несколько задач одному агенту — только правки в пару строк одного слоя; сам код не пишешь;
- задача стартует, как только готовы все её зависимости, не дожидаясь остальных задач волны; одновременно **не больше 3** агентов (`refactor`/`migrate` — до 5, `planning.md`, «Команда») **в одном рабочем дереве** (без `isolation`: коммитов по ходу задачи нет, worktree от ветки не увидел бы предыдущие волны). Регистрация (волна 3) — только когда готовы все задачи реализации. Каждому в поручении: id задачи и **список его файлов**, ключ задачи, ответы пользователя из Фазы 2, политика новых вопросов;
- задача готова только с **unit-тестами** на свою логику (правила R*, ветки ошибок, кейсы из `qa.md`, относящиеся к ней) — тесты пишет разработчик вместе с кодом;
- после каждой задачи: файлы — только из её списка (`git status`), сборка и тесты её пакетов/тестов; **полный прогон** сборки/линтера/всех тестов — когда никто не работает: перед регистрацией и после неё. Красное — чинить до задач, которые от этого зависят. Коммитов нет — только по «да» в конце;
- агент вернул «задача больше предела, разрез T3 → T3a/T3b» или «в контракте не хватает метода» — сделанное оставить, план поправить агентом `df-architect` (разрез / «Контракты слоёв»), остаток — новыми задачами.

**Новый вопрос по ходу** (не предусмотренный в Фазе 2) — по выбранной политике: (а) решение по рекомендации, строка в `rules-log.md` и в отчёт; (б) этот кусок отложить, остальное доделать, вопрос — в итог. Не останавливать всю работу. Исключения — согласование до кода, смена внешнего контракта (ломающая, `{DF}/approaches/process/impact-analysis.md`, «Обратная совместимость»; кусок откладывается до ответа при любой политике) и действие с БД (стоп до «да») — `role-chain.md`, «Новые вопросы по ходу».

## Фаза 5 — QA: интеграционные и e2e тесты

`df-qa`, режим `tests`: по кейсам `qa.md` — интеграционные/e2e автотесты (unit уже написаны разработчиками), регрессия по связям «сохраняется»; прогнать всё. Красное из-за кода — исправить (разработчиком на задачу) до ревью; не сходится за 3 попытки — остановиться и показать.

## Фаза 6 — Независимое ревью и исправления

Ревью — агент **`df-review`** (без контекста разработки, код не правит; в поручении — базовая ветка), по изменениям относительно базовой ветки, включая незакоммиченное (`git diff release`, пакет библиотеки — `git diff main`, + новые файлы; код **и** тесты), и артефактам задачи → `review.md`. Автор кода сам себя не ревьюит. Строки для `rules-log.md` из итога ревьюера («Не покрыто правилами», новый класс замечаний) переносишь в лог сам.

[БЕЗОПАСНОСТЬ] и [ОШИБКА] — исправить свежим агентом `df-go` / `df-php` (поручение: «исправить находки `review.md` №…», файлы находок), прогнать сборку и **все** тесты, повторить ревью. Повторный круг — **по дельте**: в поручении `df-review` указать «круг N», номера находок прошлого круга и список файлов, изменённых после него (`git diff --name-only` от зафиксированного состояния, напр. `git stash create` / список из итога разработчика) — ревьюер проверяет закрытие находок и только эти файлы; правила — памятка, `security.md` и каталоги тегов (общий и стека) всегда, остальное — по слоям изменённых файлов (`skills/dev-review/SKILL.md`, «Повторный круг»). **Не больше 3 кругов**; не сошлось — остановиться и показать, что осталось и почему. [ВНИМАНИЕ] — исправить, если в пределах задачи, кроме помеченных «унаследовано» (`approaches/process/review.md` п. 3a: попутно не исправляются — в отчёт и строкой в `rules-log.md`); иначе — в отчёт.

## Фаза 7 — Результат

Проверить «Готово» (`{DF}/approaches/process/role-chain.md`, «Definition of Done») — каждый пункт: выполнен / нет и почему. Затем одним сообщением (и копия в `docs/tasks/<ключ>/result.md`):
- что сделано — по требованиям (R*, AC* → чем покрыто), список файлов;
- как проверено — команды и их результат (сборка, линтер, тесты, проверка зависимостей); что **не** проверено и почему;
- меры безопасности из `threats.md` — реализованы / нет; связи из «Связи» — учтены;
- вердикт ревью;
- **выкатка**: миграции и их порядок, новые env/конфиг, совместимость со старыми клиентами, флаги (только у новой функциональности, не в рефакторе — O-19), как откатить (из `design.md`, «Выкатка и эксплуатация»);
- решения, принятые по ходу, и сколько строк в `rules-log.md`;
- **расход**: перед отчётом — `python3 {DF}/tools/usage/usage.py --project <корень проекта> --task <ключ> --write` → `docs/tasks/<ключ>/usage.md` (каждый агент: роль, поручение, задача плана, модель, время, токены; итоги по ролям и оркестратору); в отчёт — одна строка: агентов, токенов всего, стоимость (ед. цены входа) и доля оркестратора, тройка ролей по доле стоимости. Выход в транскрипте занижен — так и писать («не меньше»);
- отложено и открытые вопросы;
- готово к коммиту: ветка и сообщения коммитов по `{DF}/regulations/git.md` (одна логическая задача — один коммит) и черновик описания MR по его условиям — без `Co-Authored-By: Claude`, `Claude-Session` и «Generated with Claude Code» (`{DF}/core/principles.md`, «Git»). **Коммит и пуш — только после явного «да»**; MR, миграции на окружениях, деплой — не делаются; массовые операции, очистка и изменение схемы локальной БД — только по явному «да» на каждую.

## Фаза 8 — Разбор лога отклонений

Метка продолжения (Фаза 0) снимается после решения пользователя по коммиту — `resume.py done dev <ключ>`, пуст лог или нет.

В новой сессии: разбор лога и правки фреймворка — отдельная работа, в контексте задачи они только дорожают (каждый шаг перечитывает всю задачу). `rules-log.md` пуст — разбирать нечего, Фаза 8 закончена. Иначе после Фазы 7 и решения пользователя по коммиту (черновики коммита и MR — в `result.md`, не только в чате) — предложи `/clear` и `/dev-rule docs/tasks/<ключ>/rules-log.md`; всё нужное — в файлах задачи. Предложил разбор в новой сессии — `resume.py set dev-rule docs/tasks/<ключ>/rules-log.md` (тогда после `/clear` хватит «дальше»). Так же замечания ревьюеров в MR — `/dev-mr` в новой сессии, не в этой. Пользователь хочет разобрать здесь же — разбирай здесь.

Прочитай `{DF}/skills/dev-rule/SKILL.md` и выполняй по нему (режим разбора лога задачи, включая Шаг 3а — проверку каждой правки). Если `rules-log.md` не пуст: показать его одной таблицей по `{DF}/core/rules-evolution.md`, «Разбор в конце задачи» (группы, рекомендация, у (Ф) — почему правило общее). По ответу пользователя (можно «всё по рекомендации»): (Ф) — правки в источнике истины фреймворка по процессу `/dev-rule` + строка в `core/decisions-log.md`; (П) — `.claude/dev-rules.md` проекта; (О) — ничего. Статусы — в лог. Можно отложить разбор («потом») — тогда лог остаётся с открытыми строками, и решения из него действуют только в этой задаче.

## Режим `--step`

Те же роли и те же субагенты, но после требований, дизайна, модели угроз, каждой волны (здесь волна — барьер: следующая не стартует до «ок»), QA и ревью — показать результат и ждать «ок»; вопросы задаются по мере появления. Любой шаг можно запустить отдельно своей ролью (`/dev-analyst`, `/dev-architect`, `/dev-security`, `/dev-qa`, `/dev-go`, `/dev-php`, `/dev-review`) по готовым артефактам.

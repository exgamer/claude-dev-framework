# /dev-intro

```
/dev-intro            # тур целиком, под цель пользователя
/dev-intro <тема>     # одна тема: «команды», «режимы», «продолжение», «расход», «анализаторы», «правила» …
```

`{DF}` — корень фреймворка: `.claude/dev-framework` в проекте, если есть, иначе `~/.claude/dev-framework`.

Тур только рассказывает: файлы и git не меняет, агентов и других команд не запускает, метку продолжения не ставит. Подсказку о туре в первой сессии проекта даёт хук (`{DF}/tools/resume/resume.py`), тур её не трогает.

## Источник — `README.md`, не своя копия

Перед туром прочитай `{DF}/README.md` целиком: команды, сценарии, режимы и инструменты бери только оттуда, своими словами и коротко. Так тур не расходится с фреймворком. Чего в README нет — так и скажи и дай ссылку на `{DF}/skills/<команда>/SKILL.md`, не додумывай. README противоречит скиллу команды (`{DF}/skills/<команда>/SKILL.md`) — об этой команде говори по её скиллу и предложи `/dev-rule`: README отстал.

## Шаг 1 — Цель

Стек определи сам, как `/dev` (`go.mod` с `gosdk-*` — Go, `composer.json` с `mps/core` — PHP), не спрашивай; не нашёл (фронт, другой стек, папка не проект) — так и скажи, тур — без примеров стека. Одним сообщением: что такое фреймворк (2–3 строки по началу README), найденный стек и один вопрос — с чего хочет начать: новая фича · баг · ревью чужого MR · замечания ревьюеров в своём MR · рефактор или перенос легаси · аудит безопасности · просто посмотреть. Ответ можно не ждать дословно: «баг» или «фича» хватит.

## Шаг 2 — Тур

Части по одной, каждая — 5–10 строк, с файлом, где подробнее; в конце части — «дальше / вопрос / хватит». «Хватит» — сразу Шаг 3. Порядок и упор — по цели из Шага 1: команду под цель — первой и подробнее, остальные — строкой.

1. **Команды и сценарии** — таблица «Роли» и «Сценарии» README: какую команду когда брать; мелкая правка — сразу `/dev-go` / `/dev-php`.
2. **Как идёт задача** — «Как выглядит работа»: разведка → один список вопросов («1 — да, 2 — Б, остальное по рекомендации») → код волнами → QA → независимое ревью → результат → разбор лога. Пользователь нужен трижды: ответы, лог, «да» на коммит. Коммит и пуш — только по его «да».
3. **Режимы** — `--step` (стоп после каждой роли — для первой задачи), `--hotfix` у `/dev-fix`, рефактор и перенос стека (вопрос «контракт или по правилам»), `/dev-review --mr`, `/dev-security audit`.
4. **Артефакты и продолжение** — `docs/tasks/<ключ>/` (что в каких файлах), после `/clear` или в новом окне хватит «дальше», без хука — `/dev` без задачи; длинная задача сама попросит перезапуск сессии.
5. **Расход и анализаторы** — `tools/usage/usage.py` (`usage.md` задачи), `tools/lint/lint.py` (запускают разработчик и ревью; что не ловит — список «проверить глазами»).
6. **Правила** — приоритет `.claude/dev-rules.md` проекта над фреймворком; не согласен с правилом — `/dev-rule`, а не обход; разбор лога отклонений в конце задачи.

`/dev-intro <тема>` — стек из Шага 1 (сам, без вопроса), эта часть и Шаг 3; цель не названа — в Шаге 3 вариант «посмотреть».

## Шаг 3 — Первая задача

Под цель — готовая строка команды: фича — `/dev --step <задача>`, баг — `/dev-fix --step <баг>`, MR — `/dev-review --mr <id>` или `/dev-mr <id>`, рефактор — `/dev --step отрефактори <модуль>`, перенос — `/dev --step перенеси <модуль> из php в go`, аудит — `/dev-security audit`, «посмотреть» — эталон `{DF}/stacks/<стек>/examples/` (стек не найден — оба эталона, `stacks/go/examples/` и `stacks/php/examples/`) и `/dev --step` на маленькой задаче. Сам не запускай — пользователь пришлёт задачу.

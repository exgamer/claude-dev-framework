# /dev-security

`{DF}` — `.claude/dev-framework` в проекте, если есть, иначе `~/.claude/dev-framework`.

```
/dev-security design [<ключ задачи>]   # модель угроз по design.md → docs/tasks/<ключ>/threats.md
/dev-security audit [path]             # глубокий аудит репозитория/пути → review_result/{datetime}_security-audit.md
```

Режим не указан: есть `docs/tasks/<ключ>/design.md` без `threats.md` → `design`; просьба «проверить сервис на дыры/уязвимости», аудит для безопасников → `audit`; иначе спроси одним вопросом.

## Шаг 1 — Процедура и правила

Прочитай `{DF}/approaches/process/security.md` — чувствительные зоны, таблица вопросов модели угроз, формат `threats.md`, процедура аудита. Затем `{DF}/core/principles.md`, `{DF}/stacks/<stack>/security.md`, `{DF}/architecture/integrations.md`, `{DF}/approaches/patterns/idempotency.md`, `outbox.md`, при зоне «деньги» — `payments.md`; готовые механизмы — `{DF}/stacks/go/go-sdk/capabilities.md` или `{DF}/stacks/php/mps-core/capabilities.md`. В режиме `audit` — ещё `{DF}/stacks/<stack>/review-findings.md` (разделы про платежи, роуты, данные); в режиме `design` он не нужен. Стек: `go.mod` с `gosdk-*` → Go, `composer.json` с `mps/core` → PHP.

## Шаг 2a — `design`

1. Прочитай `requirements.md` (участники, права, ограничения), `design.md` (и `plan.md`, если есть). Зон из списка нет — скажи, что модель угроз не нужна, и остановись.
2. Найди в проекте, как то же решено у соседей (auth-middleware, скоуп по тенанту, проверка подписи у другого шлюза, маскирование в логах) — меры повторяют их форму.
3. Пройди каждый эндпойнт/консьюмер/сценарий по таблице вопросов → `docs/tasks/<ключ>/threats.md` в формате из `security.md` процедуры: угроза (`Th1…`, не `S*`), тег, конкретная мера, слой (без файла, функции и пакета — их выбирает архитектор), тест. Слой каждой меры — по «Меры по слоям» `{DF}/stacks/<stack>/security.md` (PHP: мера в Request сверяется с P-17); мера легаси или соседа — не образец (`{DF}/approaches/process/legacy-refactor.md`, «Что переносится»). Мера, которая меняет данные или ответ относительно легаси при сохранённом контракте, — не мера по умолчанию, а вопрос пользователю: вариант в разделе «Контракты» `design.md` с рекомендацией (`legacy-refactor.md`, «Правила»: отличие от легаси по данным или ответам).
4. Мера, которой нет ни в правилах, ни в SDK/ядре, ни в проекте, — пробел: вопрос пользователю обычным текстом (варианты + рекомендация); в цепочке `/dev` — не спрашивай сам, верни вопрос в список (см. п. 6). Продуктовые решения — в раздел «Решения, которые нужны».
5. Обнови `plan.md` (`{DF}/approaches/process/security.md`, «Режим `design` — модель угроз»: меры — часть задач): каждая мера — в задачу разработчика, чей слой и модуль она задевает: в колонку «контекст» — `threats: Th…` (разработчик выполняет её как критерий готовности); общий механизм (middleware, проверка подписи) — новой задачей волны 0 с контекстом, без файлов: файлы ставит архитектор по составу слоя (`/dev` возвращает ему план — у задачи нет файлов). Состав, файлы, зависимости и статусы чужих задач не меняешь.
6. Покажи пользователю кратко: зоны, главные угрозы, меры, открытые вопросы; задачи механизма без файлов (Шаг 2a, п. 5) вне цепочки `/dev` — пользователю: запустить `/dev-architect`, он поставит им файлы. Код не пишешь. В цепочке `/dev` (авто-режим) — не спрашивай сам: верни `threats.md` и открытые вопросы (варианты + рекомендация) оркестратору.

## Шаг 2b — `audit`

Выполни раздел «Режим `audit`» из `{DF}/approaches/process/security.md`: периметр → контекст → 4–8 параллельных read-only агентов (`Explore`) одним сообщением с прицельными брифами → сведение (дедупликация, теги, приоритет) → отчёт `review_result/{YYYY-MM-DD_HH-MM}_security-audit.md` (формат — `{DF}/approaches/process/review.md`; таблица/Excel — по просьбе). Исправления не предлагай «скопом»: часть находок — продуктовые решения.

## Шаг 3 — Итог

Угрозы и меры, которых нет в `security.md` стека, и решения не по правилам — строки в `docs/tasks/<ключ>/rules-log.md` (тип `пробел`/`ревью`, предложение — «фреймворк: `security.md`»; формат строк — `{DF}/core/rules-evolution.md`, «Лог отклонений по задаче»).


Путь к `threats.md` или отчёту, главное по приоритету, открытые вопросы. Новые классы уязвимостей — в `rules-log.md` (см. выше), не правь `security.md` сам. Код в режиме `design` и `audit` не меняешь; коммит/пуш — только по явному подтверждению.

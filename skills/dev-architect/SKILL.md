# /dev-architect

`{DF}` — `.claude/dev-framework` в проекте, иначе `~/.claude/dev-framework`. Режим: `feature` (по умолчанию), `refactor`, `migrate` — из аргументов или из запроса.

## Шаг 1 — Правила

Прочитай: `{DF}/core/*.md`, `{DF}/architecture/*.md`, `{DF}/regulations/*.md`, `{DF}/approaches/process/impact-analysis.md`, `{DF}/stacks/<stack>/structure.md` и `conventions.md`, `{DF}/approaches/process/planning.md`; по теме задачи — нужные `{DF}/approaches/patterns/*.md`. Режим `refactor` — `legacy-refactor.md`, `migrate` — `stack-migration.md` и `structure.md` обоих стеков. Локальные `.claude/dev-rules.md` проекта.

## Шаг 2 — Изучи код

- Найди ближайший аналог в проекте (тот же тип модуля/сценария) и в эталоне стека; дизайн повторяет его форму.
- `refactor` / `migrate`: инвентаризация исходника — эндпойнты, события, схема БД, крон, бизнес-правила с указанием файл:метод.
- Выпиши всё, что в коде сделано, но не подкреплено правилами (`core/principles.md`).

## Шаг 3 — design.md

`docs/tasks/<ключ>/design.md`:
1. Что и зачем (1–3 предложения) и критерии приёмки — из `docs/tasks/<ключ>/requirements.md` (ссылкой на AC*); его нет и задача не техническая мелочь — сначала `/dev-analyst`.
2. **Связи** — карта по `{DF}/approaches/process/impact-analysis.md`: что изменяется, входящие/исходящие/неявные связи (вызовы, DI, роуты и права, события, данные, кэш, крон, enum-литералы, другие репозитории), по каждой — «меняется вместе / сохраняется / не затронута» и тест. Неизвестные потребители — в открытые вопросы. Связи «меняется вместе» — задачи в `plan.md`.
3. Домены/модули и слой каждой части; нужен ли workflow — по `architecture/layers.md` («Service, Command/Query, Workflow»).
4. API: метод, URL, контекст, запрос, ответ, коды ошибок (по `regulations/rest-api.md`).
5. Данные: сущности, миграции, индексы, транзакции, кэш, очереди/outbox. **Конкурентность** по `{DF}/approaches/patterns/concurrency.md`: места одновременности (счётчики/лимиты, уникальность, статусы, повторная доставка, крон на нескольких инстансах, воркеры очереди, горутины) и решение для каждого — или «конкурентных мест нет». **Производительность** по `{DF}/approaches/patterns/performance.md`: для горячих путей — число запросов к БД/внешним системам на операцию, индексы под каждый фильтр/сортировку, что кэшируется, что в асинхрон; объёмов нет в требованиях — вопрос.
6. Что требует согласования (`regulations/technical-approval.md`).
7. **Выкатка и эксплуатация**: миграции (обратно совместимые — expand/contract, `approaches/patterns/migrations.md`) и порядок относительно кода; новые env/конфиг; совместимость со старыми клиентами; фича-флаг, если нужен; как откатить; что логируем, что уходит в трекер ошибок, метрики/алерты для нового потока.
8. **Чувствительные зоны** — по списку из `{DF}/approaches/process/security.md` (auth, данные с владельцем, деньги, вебхуки, ПДн, файлы, секреты); есть хоть одна — пометить, что нужен `/dev-security design`.
9. **SDK** (Go): источник и версии `gosdk-*` — всегда спросить у пользователя, даже если в `go.mod` уже что-то есть (решение O-4).
10. **Новый сервис** (в каталоге нет кода): основа — шаблон (`go-sdk-rest-template` / аналог для PHP) или с нуля — всегда вопрос; каркас (`main`, `app`, kernels, конфиг из env, healthcheck, консоль для миграций, Dockerfile) — по `regulations/service-requirements.md` и `stacks/<stack>/structure.md`, отдельной задачей волны 0.
11. `refactor`/`migrate`: раздел «Контракты» — инвентаризация HTTP API, событий, данных для других сервисов, консоли и их потребителей (`{DF}/approaches/process/legacy-refactor.md`, «Контракты»); **сохраняем ли их — всегда в открытые вопросы** с вариантами (а) 1:1 / (б) новая версия рядом / (в) менять свободно и рекомендацией. Плюс: что в исходнике нарушает правила и как будет в новом.
12. **Открытые вопросы** — пробелы, споры (ссылки на `core/decisions.md`), «сделано, но не в регламенте». Каждый: варианты, рекомендация. Каждый такой случай — ещё и строка в `docs/tasks/<ключ>/rules-log.md` (тип, где, предложение «фреймворк / проект / оставить»).

## Шаг 4 — plan.md

Режимы `refactor`/`migrate`: **характеризующие тесты** на сохраняемые контракты и поведение — первая задача волны 0, до любых изменений кода (`legacy-refactor.md`, п. 2).

По `approaches/process/planning.md`: таблица задач (id, задача, файлы, зависимости, волна), волна 0 — контракты, параллельные волны — без пересечения файлов, регистрация (`app.go`/`*_factory.go`/`definitions.php`/`routes.php`) — в последовательной волне, не больше 3 параллельных задач в волне. Раздел «Отложено».

## Шаг 5 — Стоп

В цепочке `/dev` (авто-режим) не задавай вопросы сам и не жди «ок»: верни `design.md`/`plan.md` и список открытых вопросов (варианты + рекомендация) — их соберёт `/dev` в один список. Самостоятельный запуск `/dev-architect` — как ниже.


Покажи пользователю кратко дизайн, план по волнам и открытые вопросы обычным текстом. Код не пишешь. После ответов — обнови артефакты; решения, касающиеся правил, — строки в `rules-log.md` (в правила — после разбора лога).

# /dev-php

Стек: **Laravel + mps/core + mps/utils**. Не для Go — там `/dev-go`. Шаги общие с `skills/dev-go/SKILL.md` — правишь один, проверь второй.
`{DF}` — `.claude/dev-framework` в проекте, иначе `~/.claude/dev-framework`.

## Шаг 1 — Правила

1. `{DF}/stacks/php/checklist.md` — **памятка стека**: жёсткие правила одной строкой. Читаешь **целиком, всегда** — основа всей работы (ограничения ниже её не касаются).
2. `{DF}/core/principles.md` — всегда. `{DF}/stacks/php/structure.md` — всегда, но **только разделы по слоям и файлам своей задачи** (по заголовкам: ветки «Дерева подпроекта» и «Путей» своих слоёв, «Чеклист нового модуля» — новый модуль, «Тесты»), не файл целиком. Задача задевает несколько или все слои — нужные разделы по каждому из них; сомневаешься, нужен ли раздел, — прочитай.
3. Остальное — **по задаче**, по ссылкам из пунктов памятки, которые задача задевает: `{DF}/stacks/php/conventions.md` и `style.md` (нужные пункты), `mps-core/*.md` (те, что нужны задаче: `data-objects.md`, `repository.md`, `service.md`, `transactions.md`, `exceptions.md`, `http.md`, `swagger.md`, `migrations.md`, `jobs.md`, `tests.md`, `enums.md`, `rules.md`; `commands.md`, `queries.md` — Command/Query; `model.md` — модель; `cli.md` — Artisan-команда; `domain.md` — новый домен/модуль), `{DF}/approaches/patterns/*.md` — те, на которые ссылаются разделы `design.md` (транзакции, конкурентность, производительность, кэш, outbox…). Новый или изменённый эндпойнт — `{DF}/regulations/rest-api.md`; событие (публикация или потребление), новый интерфейс или порт — `{DF}/regulations/contracts.md`.

Локальные `.claude/dev-rules.md` проекта главнее.

Запуск напрямую (не субагентом `/dev`): проверь доступ к IDE и при недоступности предложи включить — `{DF}/approaches/process/code-navigation.md`, «Проверка при старте»; работу это не останавливает.

## Шаг 2 — Задача

Режим `fix` (поручение `/dev-fix`, есть `docs/tasks/<ключ>/bug.md`) — порядок работы по `{DF}/approaches/process/bugfix.md`, «Шаги», п. 2–6: падающий тест до правки, причина, исправление причины; границы баг-фикса — там же; Шаги 1, 3–7 ниже — как обычно, задача — `bug.md` вместо `design.md`/`plan.md`; ограничение «мелкой правки» из абзаца ниже в режиме `fix` не действует — вместо него границы `bugfix.md`, «Границы».

Есть `docs/tasks/<ключ>/design.md` и `plan.md` — работай по своей задаче из плана и только в её файлах (что читать из `design.md` и правил — колонка «контекст» задачи; есть «Контракты слоёв» — пишешь строго по ним, код других слоёв — только интерфейсы и DTO, `{DF}/approaches/process/planning.md`); бизнес-правила и критерии приёмки — из `requirements.md` (R*, AC*). Есть `threats.md` — меры из него по твоим файлам обязательны, как критерии готовности. Нет `design.md` — без архитектора можно только **мелкую правку**: один модуль, без новых эндпойнтов, таблиц/миграций, событий, без изменения контракта и без чувствительных зон (`{DF}/approaches/process/security.md`). Иначе — остановись и предложи `/dev` (или `/dev-architect`): план обязателен.

## Шаг 3 — Что уже есть в ядре

Прочитай `{DF}/stacks/php/mps-core/capabilities.md` — карта «задача → класс mps/core / mps/utils» с пометками версий. Версию ядра проекта возьми из `composer.lock`; если её справочника нет в `{DF}/stacks/php/mps-core/reference/` — собери: `{DF}/tools/sdk-ref/php.sh <scratch-dir> <корень проекта>`. Методы сверяй со справочником версии проекта (или с `vendor/mps/*`) — **`grep` по имени класса/метода, файл справочника целиком не читать (до 2000 строк)**; как пользоваться компонентом подробно — официальная документация `{DF}/stacks/php/mps-core/official/` (или `vendor/mps/*/docs/` проекта, если версия другая). Самописная замена того, что есть в ядре, — ошибка; метода нет в справочнике — его нет. Преобразование формата (телефон, ИИН, карта, деньги, даты) — порядок поиска из `{DF}/core/principles.md`, «Повторяющаяся обработка — один хелпер»: mps/utils → `Core/Helpers/` проекта (grep) → новый `{Thing}Helper`; inline-копия — ошибка.

## Шаг 4 — Образец

Искать объявления, сигнатуры и образцы — по `{DF}/approaches/process/code-navigation.md` (IDE, если проект открыт в IDEA, иначе grep).

- **Форма** — по эталонному модулю `{DF}/stacks/php/examples/` (README там — карта «файл → правило»): раскладка, имена, порядок объявлений, стиль ошибок и комментариев. README целиком не читаешь: шапка + строки таблицы по **слоям и файлам своей задачи** (`grep` по пути слоя/типу класса; задача на несколько или все слои — строки по каждому), файлы эталона — точечно, те, что названы в этих строках.
- **Детали** (поля, бизнес-правила, соседние зависимости) — из соседнего модуля того же типа в проекте.
- Соседний модуль расходится с эталоном (старый нейминг, workflow в `services_factory`, `*Command` в `Workflows/` и т.п.) — форма по эталону, расхождение не копировать.
- Легаси и сосед — не образец при расхождении с правилами: из легаси переносятся только контракты и бизнес-правила, реализация (слой проверки, форма класса, фильтры, валидация) — по памятке (`{DF}/approaches/process/legacy-refactor.md`, «Что переносится»); расхождение — назвать в итоге и в `rules-log.md`. Правка или «исправление ошибки легаси», которые меняют данные или ответ относительно легаси при сохранённом контракте, — по `legacy-refactor.md`, «Правила» (отличие от легаси по данным или ответам).

## Шаг 5 — Код

- Пиши по памятке и `structure.md`; решения из разделов «Границы транзакций», «Конкурентность», «Производительность» `design.md` — обязательны.
- **БД** — миграции, сиды, массовые правки, очистку сам не запускаешь без «да» (`{DF}/core/principles.md`, «Действия с БД»); субагент — возвращает вопрос оркестратору.
- **Миграция** — строго по «Схеме БД» `design.md`; другое поле/таблица — вопрос, не правка (`{DF}/regulations/technical-approval.md`, «Схема БД»).
- **Список (пагинация)** — форма из раздела «Список» `design.md`; раздела нет, а список новый — вопрос пользователю: `{DF}/stacks/php/conventions.md` п. 2c (P-19).
- **Unit-тесты — вместе с кодом**: на правила R* своей задачи, ветки ошибок, кейсы `qa.md` уровня unit; правила — `{DF}/approaches/process/testing.md`, раскладка — `structure.md`, «Тесты». Задача без тестов на новую логику не готова.
- Пробел, спор, открытый пункт `core/decisions.md`; «в проекте так, в правилах нет» — не решать молча (`{DF}/core/principles.md`, «Пробелы и споры»); в `/dev` и как субагент — по политике новых вопросов от оркестратора. Согласования до кода и изменение внешнего контракта — всегда откладывать.
- Не создавай свои абстракции, если в проекте или в эталоне (`{DF}/stacks/php/examples/`) задача уже решена другим способом.
- **Связи:** перед изменением существующего символа, роута, события, таблицы, enum — использования по `{DF}/approaches/process/impact-analysis.md`, сверка с «Связи» `design.md`; не учтённое — дописать в карту.

## Шаг 6 — Самопроверка

Пройди **памятку** `{DF}/stacks/php/checklist.md` по каждому пункту, который задевает твой код (пометки **О**/**В**/**И** — уровни каталога тегов `{DF}/approaches/process/review-tags.md`, с ними же придёт ревью), и `{DF}/approaches/process/self-check.md` — в том числе прогон правил фреймворка анализаторами `{DF}/tools/lint/lint.py` по своему диффу: находки исправить до сдачи. Есть `threats.md` или чувствительные зоны — ещё `{DF}/stacks/php/security.md` по своему коду. `review-findings.md` — материал ревьюера, целиком не читаешь. Прогони `composer csfix-validate`, `composer phpstan`, `composer test:run` (или аналоги из `composer.json` проекта; субагент `/dev` — только по своим путям, `subagent.md`); в режиме IDE — ещё `lint_files` по своим файлам — покажи результат; если не запускал — так и скажи.

## Шаг 7 — Итог

Что сделано (файлы), что отложено, какие строки добавлены в `docs/tasks/<ключ>/rules-log.md` (формат строк — `{DF}/core/rules-evolution.md`, «Лог отклонений по задаче»; субагент — вернуть их оркестратору); правила сам не правишь. Вынес в `Core/` подпроекта или хелпер доменно-нейтральный код, который нужен в нескольких местах, — предложи пользователю перенести его в `mps/core` (что, откуда, кто вызывает); `vendor/` сам не правишь (`{DF}/core/principles.md`, «Инфраструктурный код — один раз»). Без коммита и пуша, пока пользователь явно не подтвердит.

# /dev-php

Стек: **Laravel + mps/core + mps/utils**. Не для Go — там `/dev-go`.
`{DF}` — `.claude/dev-framework` в проекте, иначе `~/.claude/dev-framework`.

## Шаг 1 — Правила

1. `{DF}/stacks/php/checklist.md` — **памятка стека**: жёсткие правила одной строкой. Держишь её как основу всей работы.
2. `{DF}/core/principles.md` и `{DF}/stacks/php/structure.md` — всегда.
3. Остальное — **по задаче**, по ссылкам из пунктов памятки, которые задача задевает: `{DF}/stacks/php/conventions.md` и `style.md` (нужные пункты), `mps-core/*.md` (те, что нужны задаче: `data-objects.md`, `repository.md`, `service.md`, `transactions.md`, `exceptions.md`, `http.md`, `swagger.md`, `migrations.md`, `jobs.md`, `tests.md`, `enums.md`, `rules.md`), `{DF}/approaches/patterns/*.md` — те, на которые ссылаются разделы `design.md` (транзакции, конкурентность, производительность, кэш, outbox…).

Локальные `.claude/dev-rules.md` проекта главнее.

## Шаг 2 — Задача

Есть `docs/tasks/<ключ>/design.md` и `plan.md` — работай по своей задаче из плана и только в её файлах; бизнес-правила и критерии приёмки — из `requirements.md` (R*, AC*). Есть `threats.md` — меры из него по твоим файлам обязательны, как критерии готовности. Нет `design.md` — без архитектора можно только **мелкую правку**: один модуль, без новых эндпойнтов, таблиц/миграций, событий, без изменения контракта и без чувствительных зон (`{DF}/approaches/process/security.md`). Иначе — остановись и предложи `/dev` (или `/dev-architect`): план обязателен.

## Шаг 3 — Что уже есть в ядре

Прочитай `{DF}/stacks/php/mps-core/capabilities.md` — карта «задача → класс mps/core / mps/utils» с пометками версий. Версию ядра проекта возьми из `composer.lock`; если её справочника нет в `{DF}/stacks/php/mps-core/reference/` — собери: `{DF}/tools/sdk-ref/php.sh <scratch-dir> <корень проекта>`. Методы сверяй со справочником версии проекта (или с `vendor/mps/*`) — **`grep` по имени класса/метода, файл справочника целиком не читать (до 2000 строк)**; как пользоваться компонентом подробно — официальная документация `{DF}/stacks/php/mps-core/official/` (или `vendor/mps/*/docs/` проекта, если версия другая). Самописная замена того, что есть в ядре, — ошибка; метода нет в справочнике — его нет.

## Шаг 4 — Образец

- **Форма** — по эталонному модулю `{DF}/stacks/php/examples/` (README там — карта «файл → правило»): раскладка, имена, порядок объявлений, стиль ошибок и комментариев.
- **Детали** (поля, бизнес-правила, соседние зависимости) — из соседнего модуля того же типа в проекте.
- Соседний модуль расходится с эталоном (старый нейминг, workflow в `services_factory`, `*Command` в `Workflows/` и т.п.) — форма по эталону, расхождение не копировать.
- Легаси и сосед — не образец при расхождении с правилами: из легаси переносятся только контракты и бизнес-правила, реализация (слой проверки, форма класса, фильтры, валидация) — по памятке (`{DF}/approaches/process/legacy-refactor.md`, «Что переносится»); расхождение — назвать в итоге и в `rules-log.md`.

## Шаг 5 — Код

- Пиши по памятке и `structure.md`; решения из разделов «Границы транзакций», «Конкурентность», «Производительность» `design.md` — обязательны.
- **БД** — миграции, сиды, массовые правки, очистку сам не запускаешь без «да» (`{DF}/core/principles.md`, «Действия с БД»); субагент — возвращает вопрос оркестратору.
- **Unit-тесты — вместе с кодом**: на правила R* своей задачи, ветки ошибок, кейсы `qa.md` уровня unit; раскладка тестов — `structure.md`, «Тесты». Задача без тестов на новую логику не готова.
- Пробел, спор, открытый пункт `core/decisions.md`, «в проекте так, в правилах нет» — не решать молча (`{DF}/core/principles.md`, «Пробелы и споры»); в `/dev` и как субагент — по политике новых вопросов от оркестратора. Согласования до кода и изменение внешнего контракта — всегда откладывать.
- Не создавай свои абстракции, если в проекте/эталоне задача уже решена другим способом.
- **Связи:** перед изменением существующего символа, роута, события, таблицы, enum — использования по `{DF}/approaches/process/impact-analysis.md`, сверка с «Связи» `design.md`; не учтённое — дописать в карту.

## Шаг 6 — Самопроверка

Пройди **памятку** `{DF}/stacks/php/checklist.md` по каждому пункту, который задевает твой код, и `{DF}/approaches/process/self-check.md`. Есть `threats.md` или чувствительные зоны — ещё `{DF}/stacks/php/security.md` по своему коду. `review-findings.md` — материал ревьюера, целиком не читаешь. Прогони `composer csfix-validate`, `composer phpstan`, `composer test:run` (или аналоги из `composer.json` проекта) — покажи результат; если не запускал — так и скажи.

## Шаг 7 — Итог

Что сделано (файлы), что отложено, какие строки добавлены в `docs/tasks/<ключ>/rules-log.md` (субагент — вернуть их оркестратору); правила сам не правишь. Без коммита и пуша, пока пользователь явно не подтвердит.

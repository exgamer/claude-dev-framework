# /dev-fix

`{DF}` — корень фреймворка: `.claude/dev-framework` в проекте, если есть, иначе `~/.claude/dev-framework`.

```
/dev-fix <баг или ключ задачи>            # авто: разбор → тест → причина → исправление → ревью → итог
/dev-fix --step <баг или ключ задачи>     # стоп и «ок» после причины и после исправления
/dev-fix --hotfix <баг или ключ задачи>   # ветка от production
```

Порядок, границы, `bug.md`, проверка «тест падал до правки» — `{DF}/approaches/process/bugfix.md`; здесь — кто и когда.

## Фаза 0 — Контекст

Прочитай `{DF}/core/principles.md`, `{DF}/approaches/process/bugfix.md`, `{DF}/approaches/process/role-chain.md` (раздел «Контекст ролей»). Ты координатор, как в `/dev` (`{DF}/skills/dev/SKILL.md`, Фаза 0): разработку и ревью делают свежие агенты `df-go`/`df-php` и `df-review`, код ты не пишешь; подписи запусков и имена — по таблице `role-chain.md`. Стек, ключ задачи (номер из трекера или slug), артефакты прошлой сессии (`docs/tasks/<ключ>/`, продолжить с них), навигация по коду, метка продолжения (`resume.py set dev-fix <ключ>`; каждый вызов `resume.py` — с `--project <корень проекта>`; флаги — `--flags "--step --hotfix"`, какие заданы) — как в `/dev`, Фаза 0. Ответы пользователя по ходу — сразу в `docs/tasks/<ключ>/answers.md`.

**Перезапуск сессии** — как в `/dev`, Фаза 0, «Перезапуск сессии» (проверка `usage.py --context`, порог, тексты причины). Граница — после Фазы 3 (итог разработчика и проверка «тест падал до правки»), после каждого круга ревью Фазы 4, после Фазы 5 до разбора `rules-log.md`. Строка «Сейчас: Фаза N, следующий шаг — …» — в шапку `bug.md` (одна, заменяет прежнюю); продолжение в новой сессии — с неё.

## Фаза 1 — Разбор (без вопросов пользователю)

1. `bugfix.md`, «Шаги», п. 1 — сам: симптом, ожидаемое и откуда оно, воспроизведение — из запроса, трекера, логов, кода (`grep` по тексту ошибки, роуту, имени) → раздел «Симптом» `bug.md`. Читаешь только то, что нужно, чтобы описать симптом и проверить границы, — причину ищет разработчик.
2. Границы (`bugfix.md`, «Границы»): уже видно, что нужна миграция, новый контракт или несколько модулей, — стоп, предложить `/dev <ключ>` с `bug.md` и снять метку (`resume.py done dev-fix <ключ>`).
3. Предпроверка окружения — есть чем собрать и прогнать тесты (как в `/dev`, Фаза 1, п. 5).

## Фаза 2 — Вопросы

Одним сообщением, только то, без чего нельзя: неясно ожидаемое поведение, нет данных для воспроизведения, окружение. Каждый — с вариантами и рекомендацией. Рабочая ветка: «создам `<КЛЮЧ-N>` от `release` (с `--hotfix` — от `production`; пакет SDK — от `main`) — ок?» (`{DF}/regulations/git.md`, «Ветки»). Последним пунктом — политика новых вопросов, как в `/dev`, Фаза 2. Вопросов нет — сразу Фаза 3, сказав, что будет сделано.

## Фаза 3 — Исправление

Ветка по ответу; дерево чистое — нет изменённых отслеживаемых файлов и посторонних неотслеживаемых вне `docs/tasks/<ключ>/`, иначе вопрос (проверка до правки берёт код из `HEAD`). Свежий агент `df-go` / `df-php`, поручение по шаблону `role-chain.md`, «Контекст ролей», с режимом `fix`:

```
Задача: <ключ>; артефакты: docs/tasks/<ключ>/bug.md (+ answers.md).
Режим: fix — {DF}/approaches/process/bugfix.md, «Шаги», п. 2–7.
Ответы пользователя: <…>. Политика новых вопросов: <а/б>. Разрешения: БД — <…>.
```

Итог разработчика — по `bugfix.md`: «Тест», «Причина», «Исправление», «Испорченные данные», «Вне границ» записаны в `bug.md`; вернул «не воспроизводится» или «за границами» — стоп, показать пользователю (`bugfix.md`) — код без «да» не правится; пользователь уходит в `/dev` или бросает баг — снять метку (`resume.py done dev-fix <ключ>`).

После итога:
1. `git status` — изменены только файлы, названные в `bug.md`; полный прогон стека (`{DF}/approaches/process/self-check.md`).
2. **Проверка «тест падал до правки»** — сам, по `bugfix.md`, «Проверка до правки»; результат — в `bug.md`, «Тест». Тест на копии до правки проходит или падает не с симптомом — тому же разработчику (`SendMessage`, исключение — `bugfix.md`, «Тот же разработчик») вернуться к `bugfix.md`, «Шаги», п. 2; второй раз — стоп, показать.

`--step` — стоп и «ок» после «Причины» (разработчик возвращает её до правки кода: в поручении — «остановиться после причины, п. 4»; после «ок» продолжает тот же агент через `SendMessage`) и после исправления.

## Фаза 4 — Ревью

`df-review`, поручение с режимом `fix` и базовой веткой (`release`, с `--hotfix` — `production`, пакет SDK — `main`) → `review.md`: обычное ревью диффа + `bugfix.md`, «Ревью баг-фикса». Исправления и повторные круги — как в `/dev`, Фаза 6 (свежий разработчик на находки, круги по дельте, не больше 3); поручение исправления — с `Режим: fix` и номерами находок, разработчик обновляет «Исправление» и, если находка о них, «Испорченные данные» в `bug.md`; изменился тест бага — проверку до правки повторить.

## Фаза 5 — Итог

Одним сообщением и копией в `docs/tasks/<ключ>/result.md`:
- симптом и причина — по строке; где исправлено (файлы);
- тест бага: путь и имя; проверка на копии до правки — падает / не запускалась (почему); полный прогон — результат;
- тот же дефект в соседних местах — исправлен / за границами; связи — что прогнано;
- испорченные данные — что баг мог записать, как найти, чем вернуть (`bug.md`, «Испорченные данные»): на stage/prod — готовая команда для человека, локально — вопрос «выполнить?», по «да» выполняешь сам, на каждую операцию отдельно (`bugfix.md`, «Шаги», п. 7);
- вердикт ревью; вне границ — что предложено отдельно;
- `--hotfix` — строка «правку перенести в `release`» (ветка от `production`, поток — `{DF}/regulations/git.md`, «Ветки»); у пакета SDK нет `production` и `release` — `--hotfix` не применяется, ветка от `main`;
- расход — `python3 {DF}/tools/usage/usage.py --project <корень проекта> --task <ключ> --write`, строка в итог;
- готово к коммиту: ветка и сообщение по `{DF}/regulations/git.md`, без подписей Claude/ИИ (`{DF}/core/principles.md`, «Git»). **Коммит и пуш — только после явного «да».**

Затем — разбор `rules-log.md`, как в `/dev`, Фаза 8 (метка — `resume.py done dev-fix <ключ>`, при разборе в новой сессии — `set dev-rule …`). Баг, класс которого можно поймать правилом, — строка в `rules-log.md` с предложением «фреймворк: `review-findings.md` стека» (`{DF}/core/rules-evolution.md`, «Когда дополнять»).

# /dev-qa

```
/dev-qa cases   # до кода: тест-кейсы по требованиям → qa.md (Шаги 1–2)
/dev-qa tests   # после кода: интеграционные/e2e автотесты по qa.md + прогон всего (Шаги 3–4)
/dev-qa         # оба режима подряд
```

Unit-тесты на логику пишет разработчик вместе с кодом; QA проектирует кейсы до кода и пишет интеграционные/e2e тесты и регрессию по связям.

`{DF}` — `.claude/dev-framework` в проекте, иначе `~/.claude/dev-framework`.

## Шаг 1 — Источник

`docs/tasks/<ключ>/requirements.md` (критерии приёмки AC* → кейсы один к одному, негативные сценарии S*.a, правила R*), `design.md` (API, связи), `threats.md` (колонка «Тест» — негативные кейсы безопасности обязательны) или описание задачи от пользователя. Нет критериев — спроси, не выдумывай.

## Шаг 2 — Тест-кейсы (режим `cases`)

`docs/tasks/<ключ>/qa.md`: на каждый критерий — позитивный сценарий, негативные (валидация, нет доступа, нет записи, чужой контекст), граничные (пустые списки, лимиты, повторный запрос/идемпотентность, параллельный запрос). Формат: id, связь (AC*/R*/S*/T*/C*), предусловия, шаги, ожидаемый результат, приоритет, уровень (unit / интеграционный / e2e).

Конкурентные места из раздела «Конкурентность» `design.md` — кейсы с параллельными запросами / повторной доставкой (уровень — интеграционный, на реальной БД).

Связи «сохраняется» из раздела «Связи» `design.md` — регрессионные кейсы (что не сломалось); «меняется вместе» — кейсы на новое поведение.

## Шаг 3 — Автотесты (режим `tests`)

Сначала проверь, что unit-тесты разработчиков покрывают кейсы `qa.md`, отмеченные как unit; пробелы — список в итог (дописывает разработчик). Сам пишешь интеграционные/e2e и регрессию. Прогон тестов, которые пересоздают схему (`RefreshDatabase`, `migrate:fresh`), запускают миграции или пишут в общую БД разработки, — только по явному «да» (`{DF}/core/principles.md`, «Действия с БД»).

- Go: раскладка — `{DF}/stacks/go/structure.md`, раздел «Тесты» (unit рядом, интеграционные с тегом `integration`, e2e в `tests/`); fakes по интерфейсам, `testify` assert/require.
- PHP: раскладка — `{DF}/stacks/php/structure.md`, раздел «Тесты» (`tests/Unit|Feature/{Подпроект}/…`); как писать — `{DF}/stacks/php/mps-core/tests.md`.
- UI: Python + Playwright + pytest (POM) по `{DF}/stacks/qa-playwright/conventions.md`.
- Живая инфраструктура — только уже поднятые общие контейнеры (`docker ps`), тестовые данные удаляются после прогона.

## Шаг 4 — Итог

Не удалось написать тест по правилам (нет образца, правило мешает, нужна инфраструктура, которой нет) — строка в `docs/tasks/<ключ>/rules-log.md`.


Что покрыто автотестами, что только кейсами, результат прогона (или «не запускал»). Найденные баги — отдельным списком с шагами воспроизведения.

# /dev-review

`{DF}` — `.claude/dev-framework` в проекте, если есть, иначе `~/.claude/dev-framework`.

```
/dev-review                         # изменённые файлы (git diff HEAD)
/dev-review --staged | <path> | --module <name> | --all
/dev-review --mr <id-or-url>        # MR через glab, с открытыми тредами ревьюеров
/dev-review --security-audit [path] # синоним /dev-security audit — выполняй по {DF}/skills/dev-security/SKILL.md
```

## Шаг 1 — Процедура и стек

Прочитай `{DF}/approaches/process/review.md` — там цели ревью (в т.ч. `--mr`), порядок проверок, уровни, теги, формат отчёта, сохранение. Выполняй его по шагам. `--security-audit` — это роль `/dev-security`, режим `audit`.

Стек: `go.mod` с `gosdk-*` → Go, `composer.json` с `mps/core` → PHP. Смешанный дифф — каждый стек по своим файлам.

Запуск напрямую (не субагентом `/dev`): проверь доступ к IDE и при недоступности предложи включить — `{DF}/approaches/process/code-navigation.md`, «Проверка при старте»; работу это не останавливает.

## Шаг 2 — Правила стека

Правила грузятся по задетым слоям, как у разработчика, — не всё сразу (контекст ревьюера иначе 100k+ токенов).

**Всегда** (`<stack>` = `go` | `php`): `{DF}/stacks/<stack>/checklist.md` (первой — памятка, по ней идёт основная проверка), `security.md`, `review-checks.md`, `{DF}/core/principles.md`, `{DF}/core/style.md`, `{DF}/core/decisions.md` (открытые споры и ключевые решения), `{DF}/stacks/<stack>/go-sdk/capabilities.md` / `mps-core/capabilities.md`; локальные `.claude/dev-rules.md` проекта главнее. Каталоги тегов с уровнями — целиком: общий `{DF}/approaches/process/review-tags.md` и стековый `{DF}/stacks/<stack>/review-tags.md`; теги безопасности — `{DF}/approaches/process/security.md`, «Каталог тегов безопасности». Уровень находки с тегом — только оттуда (O-24: новый код — уровень каталога, унаследованное — [ВНИМАНИЕ], `review.md` п. 3a); тег того же паттерна переиспользуется, не заводится новый (`review.md`, «Теги»). `--mr` — ещё `{DF}/regulations/code-review.md` (префиксы тредов, «Соответствие уровням фреймворка»).

**По задетому в диффе** — нужные разделы (по заголовкам, не файл целиком; дифф задевает несколько или все слои — по каждому):
- расположение/новые файлы → `structure.md`, разделы по задетым слоям;
- пункт памятки, который код задевает, → раздел `conventions.md` / `style.md` по ссылке из пункта;
- слой/пакет SDK или ядра → `go-sdk/<слой>.md` / `mps-core/<тема>.md`; дифф в самом пакете SDK (`gosdk-*`, `go-sdk-*-core`) → `stacks/go/conventions.md` п. 24;
- платежи, HTTP-роуты, статусы/enum, транзакции, данные → соответствующие разделы `review-findings.md` (платёжные пути в Go — раздел «Платёжные хендлеры» обязательно);
- API/контракт, миграции, git-гигиена → `{DF}/regulations/{rest-api,entity,contracts,git}.md`; миграции — ещё `{DF}/regulations/technical-approval.md`, «Схема БД», и «да» на схему в `docs/tasks/<ключ>/answers.md` (проверка `schema-not-approved`, `review.md`, «За пределами дифа», п. 4a);
- граница доменов, workflow, интеграция → `{DF}/architecture/*.md`;
- задет код с записью в хранилище или запросами к БД/внешним системам → `{DF}/approaches/patterns/{transactions,concurrency,performance}.md` всегда (`review.md`, «Порядок», п. 6a–6b), есть `design.md` или нет; кэш, outbox и другие паттерны → `{DF}/approaches/patterns/*.md`, на которые ссылается `design.md` или которые задеты в диффе; платёжный путь → `payments.md` всегда; тесты в диффе → `{DF}/approaches/process/testing.md`;
- подозрение на расхождение формы с эталоном → строки README эталона `{DF}/stacks/<stack>/examples/` по задетым слоям и файлам (`grep`, README целиком не читать) и названный в них файл эталона, не весь модуль.

API сверять со справочником версии проекта (`reference/`; Go — версии из `go.mod`, PHP — из `composer.lock`) — **поиском по имени класса/функции (`grep`), файл целиком не читать**; справочника нужной версии нет — пересобрать `{DF}/tools/sdk-ref/`.

Навигация по коду (сигнатуры, объявления, проверки за пределами дифа) — по `{DF}/approaches/process/code-navigation.md`: IDE, если проект открыт в IDEA, иначе grep; использования и строковые связи — всегда grep. В режиме IDE `lint_files` по изменённым файлам — материал для находок, не замена правилам.

**Повторный круг** (в цепочке `/dev`, круг 2+): ревьюер — свежий агент, правила прошлого круга у него не в контексте. Загрузка: памятка стека, `security.md` и каталоги тегов (общий и стековый) — всегда; остальное из списков выше — только по слоям и темам изменённых файлов; находки прошлого круга — из `review.md`. Проверяются (1) каждая находка прошлого круга — закрыта или нет, (2) только изменённый с прошлого круга код (`git diff` от состояния прошлого круга — оркестратор даёт список файлов) по тем же правилам, (3) изменённые `threats.md`/`design.md` — по правилам слоёв (Шаг 3). Отчёт — дописывается в тот же `review.md` разделом «Круг N».

## Шаг 3 — Ревью, отчёт, сохранение

По `review.md`. Обязательно:
- **анализаторы** — `{DF}/tools/lint/lint.py … --no-install` по диффу (`review.md` п. 6): находки — с тегом их правила из списка «Остаток» в конце вывода; по правилам этого списка глазами только их остаток (таблицу `RULES.md` не открывать), остальная памятка — целиком; строка «прогон шёл без тестов» — тесты задачи по этим правилам глазами целиком; не запустился — так и написать, памятка целиком;
- **[БЕЗОПАСНОСТЬ]** по `security.md` стека — всегда КРИТИЧНО; есть `docs/tasks/<ключ>/threats.md` — каждая мера реализована (не реализована — [БЕЗОПАСНОСТЬ] с тегом угрозы);
- **артефакты** `threats.md` и `design.md` (включая меры «к следующим задачам») — на соответствие правилам слоёв (`security.md`, «Меры по слоям»; `legacy-refactor.md`, «Что переносится»): в первом круге и в круге, где артефакт изменён; находка того же тега и уровня, что в коде (мера `exists:` в Request — `request-queries-db`), перенос легаси вопреки правилу — тег `legacy-pattern-copied`; правка, меняющая данные или ответ относительно легаси при сохранённом контракте, — по `{DF}/approaches/process/legacy-refactor.md`, «Правила» (вопрос пользователю, не исправление по рекомендации);
- **баг-фикс** (режим `fix` в поручении `/dev-fix`, есть `docs/tasks/<ключ>/bug.md`) — ещё `{DF}/approaches/process/bugfix.md`, «Ревью баг-фикса», каждый пункт;
- блок «Не покрыто правилами» — темы для обсуждения, не ошибки автора; каждая — строка в `docs/tasks/<ключ>/rules-log.md` (если ревью вне задачи — в `docs/tasks/<дата>-review/rules-log.md`);
- известные споры (`{DF}/core/decisions.md`) — как спор, не как находку;
- колонка категории в сохранённом отчёте — kebab-case тег паттерна (по нему считаются повторяющиеся ошибки);
- отчёт — `review_result/{YYYY-MM-DD_HH-MM}_{type}.md` (или `docs/tasks/<ключ>/review.md` в цепочке `/dev`).

## Шаг 4 — Итог

Путь к отчёту, вердикт (ПРОЙДЕНО / НУЖНЫ ПРАВКИ / КРИТИЧНО), предложение исправить [ОШИБКИ]. Новый повторяющийся класс замечаний — строка `ревью` в `rules-log.md` с предложением «фреймворк: `review-findings.md`»; решение — на разборе лога. Коммит/пуш — только по явному подтверждению.

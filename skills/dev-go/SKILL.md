# /dev-go

Стек: **Go + Go SDK (gosdk-*)**. Не для PHP — там `/dev-php`.
`{DF}` — `.claude/dev-framework` в проекте, иначе `~/.claude/dev-framework`.

## Шаг 1 — Правила

Прочитай `{DF}/core/principles.md`, `{DF}/core/style.md`, `{DF}/architecture/layers.md`, `{DF}/stacks/go/structure.md`, `{DF}/stacks/go/conventions.md`, `{DF}/stacks/go/style.md`, `{DF}/stacks/go/go-sdk/*.md` (те, что нужны задаче: `module.md`, `domain.md`, `workflow.md`, `infra/*.md`, `entrypoint/*.md`, `exceptions.md`, `di.md`), по теме — `{DF}/approaches/patterns/*.md`. Локальные `.claude/dev-rules.md` проекта главнее.

## Шаг 2 — Задача

Есть `docs/tasks/<ключ>/design.md` и `plan.md` — работай по своей задаче из плана и только в её файлах; бизнес-правила и критерии приёмки — из `requirements.md` (R*, AC*). Есть `threats.md` — меры из него по твоим файлам обязательны, как критерии готовности. Нет `design.md` — без архитектора можно только **мелкую правку**: один модуль, без новых эндпойнтов, таблиц/миграций, событий, без изменения контракта и без чувствительных зон (`{DF}/approaches/process/security.md`). Иначе — остановись и предложи `/dev` (или `/dev-architect`): план обязателен.

## Шаг 3 — Что уже есть в SDK

Прочитай `{DF}/stacks/go/go-sdk/capabilities.md` — карта «задача → пакет SDK». Нужный вызов ищи в `{DF}/stacks/go/go-sdk/reference/<модуль>.md` (полный список функций и типов из исходников); как пользоваться модулем подробно — README модулей в `{DF}/stacks/go/go-sdk/official/`. Своё решение того, что есть в SDK, — ошибка. Чего нет в справочнике — того в SDK нет, не выдумывай.

## Шаг 4 — Версия SDK

Если в `design.md` задачи нет раздела «SDK» — спроси пользователя (ты субагент — верни вопрос оркестратору, сам не выбирай), какой Go SDK используем (источник `git.mpinnovations.kz/mps/go-packages` или `github.com/exgamer`, версии пакетов), показав, что сейчас в `go.mod`. Не начинай код на SDK без ответа. Ответ запиши в `design.md`. Если версии отличаются от тех, по которым собран `reference/` (указаны в шапке файлов), — пересобери справочник под проект: `{DF}/tools/sdk-ref/go.sh <scratch-dir> --gomod <go.mod проекта>` и работай по нему.

## Шаг 5 — Образец

- **Форма** — по эталонному модулю `{DF}/stacks/go/examples/tariff/` (README там — карта «файл → правило»): раскладка, имена, порядок объявлений, стиль ошибок и комментариев.
- **Детали** (поля, бизнес-правила, соседние зависимости) — из соседнего модуля того же типа в проекте.
- Соседний модуль расходится с эталоном (старый нейминг, workflow в `services_factory`, `*Command` в `Workflows/` и т.п.) — форма по эталону, расхождение не копировать.

## Шаг 6 — Код

- Пиши по `structure.md` / `conventions.md` / `style.md` стека.
- **Конкурентность** — решения из раздела «Конкурентность» `design.md` по `{DF}/approaches/patterns/concurrency.md` (атомарные апдейты, уникальные индексы, условная смена статуса, идемпотентность, блокировки крона, без data race: mutex/atomic/каналы, `go test -race`).
- **БД** — миграции, сиды, массовые правки данных, очистку и пересоздание схемы сам не запускаешь: только по явному «да» пользователя на каждую, с показом команды, БД и числа строк (`{DF}/core/principles.md`, «Действия с БД»). Ты субагент — верни вопрос оркестратору.
- **Транзакции** — по «Границам транзакций» `design.md` и `{DF}/approaches/patterns/transactions.md`: workflow с записью — проверки и записи в одном `txManager.Exec`, внутри `fn` только репозитории из аргументов (сервисы доменов пишут мимо транзакции); побочные эффекты и сброс кэша — после коммита.
- **Производительность** — по `{DF}/approaches/patterns/performance.md`: без N+1, с пагинацией, индексом под запрос, таймаутами, пачками для массовых операций, атомарными счётчиками; новый тяжёлый запрос — `EXPLAIN`.
- **Unit-тесты — вместе с кодом**: на правила R* своей задачи, ветки ошибок, кейсы `qa.md` уровня unit; раскладка тестов — `structure.md`, «Тесты». Задача без тестов на новую логику не готова.
- Пробел, спор, открытый пункт из `core/decisions.md` или «в проекте так сделано, но в правилах нет» — **стоп на этом месте**, вопрос пользователю обычным текстом (варианты + рекомендация), случай — строка в `rules-log.md`. Остальную однозначную работу можно продолжать. Если ты субагент или работаешь в авто-режиме `/dev` — действуй по политике новых вопросов, которую передал оркестратор: (а) решение по рекомендации, строка в `rules-log.md` задачи; (б) отложить затронутый кусок и вернуть вопрос. Согласования до кода и изменения внешнего контракта — всегда откладывать.
- Не создавай свои абстракции, если в проекте/эталоне задача уже решена другим способом.
- **Связи:** перед изменением существующего символа, роута, события, таблицы или значения enum — найди все использования (по имени и по строковому литералу, `{DF}/approaches/process/impact-analysis.md`) и сверь с разделом «Связи» `design.md`; нашлось не учтённое — допиши в карту и учти в коде или в итоге.

## Шаг 7 — Самопроверка

Пройди `{DF}/approaches/process/self-check.md`, `{DF}/stacks/go/security.md` (чеклист безопасности — по своему коду), `{DF}/stacks/go/review-checks.md` (разъезд статусов/enum, данные под миграцию, гигиена) и `{DF}/stacks/go/review-findings.md`. Прогони `go build ./... && go vet ./... && go test ./... && gofmt -l internal pkg` — покажи результат; если не запускал — так и скажи.

## Шаг 8 — Итог

Что сделано (файлы), что отложено, какие строки добавлены в `docs/tasks/<ключ>/rules-log.md` (субагент — вернуть их оркестратору); правила сам не правишь. Без коммита и пуша, пока пользователь явно не подтвердит.

# /dev-go

Стек: **Go + Go SDK (gosdk-*)**. Не для PHP — там `/dev-php`. Шаги общие с `skills/dev-php/SKILL.md` — правишь один, проверь второй.
`{DF}` — `.claude/dev-framework` в проекте, иначе `~/.claude/dev-framework`.

## Шаг 1 — Правила

1. `{DF}/stacks/go/checklist.md` — **памятка стека**: жёсткие правила одной строкой. Читаешь **целиком, всегда** — основа всей работы (ограничения ниже её не касаются).
2. `{DF}/core/principles.md` — всегда. `{DF}/stacks/go/structure.md` — всегда, но **только разделы по слоям и файлам своей задачи** (по заголовкам: «Слои и зависимости», нужные слои из «Ответственность слоёв», ветки «Структуры директорий» и «Структуры путей», «Checklist нового модуля» — новый модуль, «Тесты»), не файл целиком. Задача задевает несколько или все слои — нужные разделы по каждому из них; сомневаешься, нужен ли раздел, — прочитай.
3. Остальное — **по задаче**, по ссылкам из пунктов памятки, которые задача задевает: `{DF}/stacks/go/conventions.md` и `style.md` (нужные пункты), `go-sdk/*.md` (те, что нужны задаче: `module.md`, `domain.md`, `workflow.md`, `infra.md` и `infra/*.md` — слой Infrastructure (`infra.md` — раскладка и nil-check в маппере), `entrypoint/*.md`, `exceptions.md`, `di.md`; `app.md` — новый модуль или сервис; `main.md` — новый сервис), `{DF}/approaches/patterns/*.md` — те, на которые ссылаются разделы `design.md` (транзакции, конкурентность, производительность, кэш, outbox…). Новый или изменённый эндпойнт — `{DF}/regulations/rest-api.md`; событие (публикация или потребление), новый интерфейс или порт — `{DF}/regulations/contracts.md`.

Локальные `.claude/dev-rules.md` проекта главнее.

Запуск напрямую (не субагентом `/dev`): проверь доступ к IDE и при недоступности предложи включить — `{DF}/approaches/process/code-navigation.md`, «Проверка при старте»; работу это не останавливает.

## Шаг 2 — Задача

Режим `fix` (поручение `/dev-fix`, есть `docs/tasks/<ключ>/bug.md`) — порядок работы по `{DF}/approaches/process/bugfix.md`, «Шаги», п. 2–7: падающий тест до правки, причина, исправление причины, испорченные данные (только предложение); границы баг-фикса — там же; Шаги 1, 3–7 ниже — как обычно, задача — `bug.md` вместо `design.md`/`plan.md`; ограничение «мелкой правки» из абзаца ниже в режиме `fix` не действует — вместо него границы `bugfix.md`, «Границы».

Есть `docs/tasks/<ключ>/design.md` и `plan.md` — работай по своей задаче из плана и только в её файлах (что читать из `design.md` и правил — колонка «контекст» задачи; есть «Контракты слоёв» — пишешь строго по ним, код других слоёв — только интерфейсы и DTO, `{DF}/approaches/process/planning.md`); бизнес-правила и критерии приёмки — из `requirements.md` (R*, AC*). Есть `threats.md` — меры из него по твоим файлам обязательны, как критерии готовности. Нет `design.md` — без архитектора можно только **мелкую правку**: один модуль, без новых эндпойнтов, таблиц/миграций, событий, без изменения контракта и без чувствительных зон (`{DF}/approaches/process/security.md`). Иначе — остановись и предложи `/dev` (или `/dev-architect`): план обязателен.

## Шаг 3 — Что уже есть в SDK

Сначала источник и версия SDK — от них зависит, какой справочник `reference/` читать; затем поиск в нём.

1. **Источник и версия.** Источник и версии пакетов — из раздела «SDK» `design.md`. Если в `design.md` задачи нет раздела «SDK» — определи источник (`git.mpinnovations.kz/mps/go-packages` или `github.com/exgamer`) и версии пакетов из `go.mod` и запиши в `design.md` (`{DF}/stacks/go/conventions.md` п. 23; субагентом `/dev` — не в `design.md`, а в итог оркестратору: с `design.md` работают параллельные разработчики); в случаях из п. 23 — спроси пользователя (ты субагент — верни вопрос оркестратору, сам не выбирай). Не начинай код на SDK, пока «SDK» не записан; субагент записи в `design.md` не ждёт — источник и версии из `go.mod` пишет в итог и продолжает по `go.mod` (вопрос из п. 23 — код на SDK не начинает). Если версии отличаются от тех, по которым собран `reference/` (указаны в шапке файлов), — пересобери справочник под проект: `{DF}/tools/sdk-ref/go.sh <scratch-dir> --gomod <go.mod проекта>` и работай по нему.
2. **Что уже есть.** Прочитай `{DF}/stacks/go/go-sdk/capabilities.md` — карта «задача → пакет SDK». Преобразование формата (телефон, ИИН, карта, деньги, даты) — порядок из `{DF}/core/principles.md`, «Повторяющаяся обработка — один хелпер»: SDK (`validation.NormalizePhoneNumber`…) → `pkg/` проекта (grep) → новый пакет в `pkg/`; inline-копия — ошибка. Нужный вызов ищи в `{DF}/stacks/go/go-sdk/reference/{gitlab|github}/<модуль>.md` (по источнику из п. 1) (полный список функций и типов из исходников) — **`grep` по имени пакета/функции, файл целиком не читать**; как пользоваться модулем подробно — README модулей в `{DF}/stacks/go/go-sdk/official/`. Своё решение того, что есть в SDK, — ошибка. Чего нет в справочнике — того в SDK нет, не выдумывай.

## Шаг 4 — Образец

Искать объявления, сигнатуры и образцы — по `{DF}/approaches/process/code-navigation.md` (IDE, если проект открыт в IDEA, иначе grep).

- **Форма** — по эталонному модулю `{DF}/stacks/go/examples/tariff/` (README там — карта «файл → правило»): раскладка, имена, порядок объявлений, стиль ошибок и комментариев. README целиком не читаешь: шапка + строки таблицы по **слоям и файлам своей задачи** (`grep` по пути слоя/типу файла; задача на несколько или все слои — строки по каждому), файлы эталона — точечно, те, что названы в этих строках.
- **Детали** (поля, бизнес-правила, соседние зависимости) — из соседнего модуля того же типа в проекте.
- Соседний модуль расходится с эталоном (старый нейминг, workflow в `services_factory`, `*Command` в `Workflows/` и т.п.) — форма по эталону, расхождение не копировать.
- Легаси и сосед — не образец при расхождении с правилами: из легаси переносятся только контракты и бизнес-правила, реализация (слой проверки, форма типов, фильтры, валидация) — по памятке (`{DF}/approaches/process/legacy-refactor.md`, «Что переносится»); расхождение — назвать в итоге и в `rules-log.md`. Правка или «исправление ошибки легаси», которые меняют данные или ответ относительно легаси при сохранённом контракте, — по `legacy-refactor.md`, «Правила» (отличие от легаси по данным или ответам).

## Шаг 5 — Код

- Пиши по памятке и `structure.md`; решения из разделов «Границы транзакций», «Конкурентность», «Производительность» `design.md` — обязательны.
- **БД** — миграции, сиды, массовые правки, очистку сам не запускаешь без «да» (`{DF}/core/principles.md`, «Действия с БД»); субагент — возвращает вопрос оркестратору.
- **Миграция** — строго по «Схеме БД» `design.md`; другое поле/таблица — вопрос, не правка (`{DF}/regulations/technical-approval.md`, «Схема БД»).
- **Unit-тесты — вместе с кодом**: на правила R* своей задачи, ветки ошибок, кейсы `qa.md` уровня unit; правила — `{DF}/approaches/process/testing.md`, раскладка — `structure.md`, «Тесты». Задача без тестов на новую логику не готова.
- Пробел, спор, открытый пункт `core/decisions.md`; «в проекте так, в правилах нет» — не решать молча (`{DF}/core/principles.md`, «Пробелы и споры»); в `/dev` и как субагент — по политике новых вопросов от оркестратора. Согласования до кода и изменение внешнего контракта — всегда откладывать.
- Не создавай свои абстракции, если в проекте или в эталоне (`{DF}/stacks/go/examples/`) задача уже решена другим способом.
- **Связи:** перед изменением существующего символа, роута, события, таблицы, enum — использования по `{DF}/approaches/process/impact-analysis.md`, сверка с «Связи» `design.md`; не учтённое — дописать в карту.

## Шаг 6 — Самопроверка

Пройди **памятку** `{DF}/stacks/go/checklist.md` по каждому пункту, который задевает твой код (пометки **О**/**В**/**И** — уровни каталога тегов `{DF}/approaches/process/review-tags.md`, с ними же придёт ревью), и `{DF}/approaches/process/self-check.md` — в том числе прогон правил фреймворка анализаторами `{DF}/tools/lint/lint.py` по своему диффу: находки исправить до сдачи. Есть `threats.md` или чувствительные зоны — ещё `{DF}/stacks/go/security.md` по своему коду. `review-findings.md` — материал ревьюера, целиком не читаешь. Прогони команды Go из `self-check.md` (субагент `/dev` — только по своим пакетам, `subagent.md`); в режиме IDE — ещё `lint_files` по своим файлам — покажи результат; если не запускал — так и скажи.

## Шаг 7 — Итог

Что сделано (файлы), что отложено, какие строки добавлены в `docs/tasks/<ключ>/rules-log.md` (формат строк — `{DF}/core/rules-evolution.md`, «Лог отклонений по задаче»; субагент — вернуть их оркестратору); правила сам не правишь. Вынес в `pkg/` доменно-нейтральный код, который нужен в нескольких местах, — предложи пользователю перенести его в Go SDK (что, откуда, кто вызывает); SDK сам не правишь (`{DF}/core/principles.md`, «Инфраструктурный код — один раз»). Без коммита и пуша, пока пользователь явно не подтвердит.

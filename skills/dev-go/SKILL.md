# /dev-go

Стек: **Go + Go SDK (gosdk-*)**. Не для PHP — там `/dev-php`.
`{DF}` — `.claude/dev-framework` в проекте, иначе `~/.claude/dev-framework`.

## Шаг 1 — Правила

1. `{DF}/stacks/go/checklist.md` — **памятка стека**: жёсткие правила одной строкой. Держишь её как основу всей работы.
2. `{DF}/core/principles.md` и `{DF}/stacks/go/structure.md` — всегда.
3. Остальное — **по задаче**, по ссылкам из пунктов памятки, которые задача задевает: `{DF}/stacks/go/conventions.md` и `style.md` (нужные пункты), `go-sdk/*.md` (те, что нужны задаче: `module.md`, `domain.md`, `workflow.md`, `infra/*.md`, `entrypoint/*.md`, `exceptions.md`, `di.md`), `{DF}/approaches/patterns/*.md` — те, на которые ссылаются разделы `design.md` (транзакции, конкурентность, производительность, кэш, outbox…).

Локальные `.claude/dev-rules.md` проекта главнее.

## Шаг 2 — Задача

Есть `docs/tasks/<ключ>/design.md` и `plan.md` — работай по своей задаче из плана и только в её файлах; бизнес-правила и критерии приёмки — из `requirements.md` (R*, AC*). Есть `threats.md` — меры из него по твоим файлам обязательны, как критерии готовности. Нет `design.md` — без архитектора можно только **мелкую правку**: один модуль, без новых эндпойнтов, таблиц/миграций, событий, без изменения контракта и без чувствительных зон (`{DF}/approaches/process/security.md`). Иначе — остановись и предложи `/dev` (или `/dev-architect`): план обязателен.

## Шаг 3 — Что уже есть в SDK

Прочитай `{DF}/stacks/go/go-sdk/capabilities.md` — карта «задача → пакет SDK». Нужный вызов ищи в `{DF}/stacks/go/go-sdk/reference/<модуль>.md` (полный список функций и типов из исходников) — **`grep` по имени пакета/функции, файл целиком не читать**; как пользоваться модулем подробно — README модулей в `{DF}/stacks/go/go-sdk/official/`. Своё решение того, что есть в SDK, — ошибка. Чего нет в справочнике — того в SDK нет, не выдумывай.

## Шаг 4 — Версия SDK

Если в `design.md` задачи нет раздела «SDK» — спроси пользователя (ты субагент — верни вопрос оркестратору, сам не выбирай), какой Go SDK используем (источник `git.mpinnovations.kz/mps/go-packages` или `github.com/exgamer`, версии пакетов), показав, что сейчас в `go.mod`. Не начинай код на SDK без ответа. Ответ запиши в `design.md`. Если версии отличаются от тех, по которым собран `reference/` (указаны в шапке файлов), — пересобери справочник под проект: `{DF}/tools/sdk-ref/go.sh <scratch-dir> --gomod <go.mod проекта>` и работай по нему.

## Шаг 5 — Образец

- **Форма** — по эталонному модулю `{DF}/stacks/go/examples/tariff/` (README там — карта «файл → правило»): раскладка, имена, порядок объявлений, стиль ошибок и комментариев.
- **Детали** (поля, бизнес-правила, соседние зависимости) — из соседнего модуля того же типа в проекте.
- Соседний модуль расходится с эталоном (старый нейминг, workflow в `services_factory`, `*Command` в `Workflows/` и т.п.) — форма по эталону, расхождение не копировать.
- Легаси и сосед — не образец при расхождении с правилами: из легаси переносятся только контракты и бизнес-правила, реализация (слой проверки, форма типов, фильтры, валидация) — по памятке (`{DF}/approaches/process/legacy-refactor.md`, «Что переносится»); расхождение — назвать в итоге и в `rules-log.md`.

## Шаг 6 — Код

- Пиши по памятке и `structure.md`; решения из разделов «Границы транзакций», «Конкурентность», «Производительность» `design.md` — обязательны.
- **БД** — миграции, сиды, массовые правки, очистку сам не запускаешь без «да» (`{DF}/core/principles.md`, «Действия с БД»); субагент — возвращает вопрос оркестратору.
- **Unit-тесты — вместе с кодом**: на правила R* своей задачи, ветки ошибок, кейсы `qa.md` уровня unit; раскладка тестов — `structure.md`, «Тесты». Задача без тестов на новую логику не готова.
- Пробел, спор, открытый пункт `core/decisions.md`, «в проекте так, в правилах нет» — не решать молча (`{DF}/core/principles.md`, «Пробелы и споры»); в `/dev` и как субагент — по политике новых вопросов от оркестратора. Согласования до кода и изменение внешнего контракта — всегда откладывать.
- Не создавай свои абстракции, если в проекте/эталоне задача уже решена другим способом.
- **Связи:** перед изменением существующего символа, роута, события, таблицы, enum — использования по `{DF}/approaches/process/impact-analysis.md`, сверка с «Связи» `design.md`; не учтённое — дописать в карту.

## Шаг 7 — Самопроверка

Пройди **памятку** `{DF}/stacks/go/checklist.md` по каждому пункту, который задевает твой код, и `{DF}/approaches/process/self-check.md`. Есть `threats.md` или чувствительные зоны — ещё `{DF}/stacks/go/security.md` по своему коду. `review-findings.md` — материал ревьюера, целиком не читаешь. Прогони `go build ./... && go vet ./... && go test ./... && gofmt -l internal pkg` — покажи результат; если не запускал — так и скажи.

## Шаг 8 — Итог

Что сделано (файлы), что отложено, какие строки добавлены в `docs/tasks/<ключ>/rules-log.md` (субагент — вернуть их оркестратору); правила сам не правишь. Без коммита и пуша, пока пользователь явно не подтвердит.

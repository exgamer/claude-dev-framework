# A/B: поручения агентам

Подставить значения из вывода `python3 tools/ab/ab.py prepare …`: `{DF}` — путь фреймворка версии (`old/` из папки A/B или корень репозитория), `{P}` — проект, `{BASE}` — его базовый коммит; для PHP — `{C}` (контейнер) и `{CP}` (путь проекта в контейнере). Все агенты — `general-purpose`, в фоне, параллельно; «до» и «после» получают одно и то же, кроме `{DF}`, `{P}`, `{BASE}`.

## Разработчик (4: go-old, go-new, php-old, php-new)

```
Ты — разработчик <Go | PHP (Laravel + mps/core)>. `{DF}` = <путь> (фреймворк правил; его файлы не правь). Выполни `{DF}/skills/dev-<go|php>/SKILL.md` (запуск напрямую, не субагентом /dev) в проекте {P} (git, базовый коммит `{BASE}`<, подпроект `parking_app`>). Где путь `~/.claude/dev-framework` — это `{DF}`.
<Go:> Сборка и тесты — с `GOFLAGS=-mod=mod GOPROXY=off GONOSUMDB=git.mpinnovations.kz`, сеть не нужна.
<PHP:> В контейнере `{C}` проект — `{CP}` (vendor стоит): phpunit — `docker exec {C} sh -c 'cd {CP} && php vendor/bin/phpunit'`, phpstan — `… && php -d memory_limit=2G vendor/bin/phpstan analyse`. Composer не запускай.

Задача: T1 из `docs/tasks/archive-tariff/plan.md` проекта (ключ `archive-tariff`; `design.md`, `requirements.md`, `answers.md` — там же, согласования получены). Делай её одну.
Пользователь недоступен: где SKILL велит спросить — выбери рекомендуемый вариант и запиши в итог списком «Решил сам». IDE (MCP) может быть недоступна — Grep/Read. Никаких git commit/push. Вне проекта ничего не меняй. Итог — по последнему шагу SKILL.
```

## Ревью (4 — после своего разработчика, та же версия `{DF}`)

```
Ты — ревьюер. `{DF}` = <путь> (не правь). Выполни `{DF}/skills/dev-review/SKILL.md` (напрямую) для незакоммиченного диффа проекта {P} относительно `{BASE}` (стек <Go | PHP>; задача — T1 из `docs/tasks/archive-tariff/plan.md`, там же design/requirements/answers). <Go: сеть не нужна, GOFLAGS=…> <PHP: контейнер {C}, проект в нём {CP}; composer не запускай.> Где путь `~/.claude/dev-framework` — это `{DF}`. Пользователь недоступен: вопросы — в отчёт. Код не правь, без commit/push; отчёт — по SKILL в каталог проекта. Итог — по SKILL.
```

## Судья (1 — после `ab.py diffs`, не знает, где какая версия)

```
Ты — независимый строгий судья качества кода. Только чтение. Одна задача сделана двумя разработчиками на одинаковом исходном проекте — варианты A и B (Go и PHP отдельно), чьи — не знаешь и не угадывай. Диффы — каталог judge папки A/B: go-A.diff, go-B.diff, php-A.diff, php-B.diff. Задача и решения архитектора: `tools/ab/task/{go,php}/{requirements,design,answers,plan}.md`. Контекст кода — эталоны `stacks/go/examples/tariff`, `stacks/php/examples` (диффы поверх них). Мерило — памятки `stacks/{go,php}/checklist.md` (уровни О/В/И) и требования R1–R4/AC1–AC4.
По стеку и варианту: (1) R/AC выполнены — да/нет/частично с местом; (2) подтверждённые диффом нарушения памятки «пункт — место — уровень»; (3) корректность: гонки, коды, скоуп, транзакции, миграция, тесты; (4) вердикт: явно лучше / немного лучше / равны, 3–5 причин. Отчёт — файл verdict.md в каталоге judge папки A/B; ответ — до 15 строк.
```

## Баг-фикс (`prepare --task fix`)

Те же 4 + 4 + 1, поручения выше с заменами — разработчику вместо строки «Задача: T1 …»:

```
Задача: исправить баг из `docs/tasks/fix-default-tariff/bug.md` проекта (ключ `fix-default-tariff`; там только симптом из поддержки). Миграций и изменения контракта не нужно.
Режим: fix — {DF}/approaches/process/bugfix.md, «Шаги», п. 2–7 (файла нет — работай по SKILL как обычно).
```

ревьюеру — «задача — баг из `docs/tasks/fix-default-tariff/bug.md`, режим fix» вместо T1; после разработчиков, до ревью, ведущий A/B делает в каждом проекте проверку до правки (`bugfix.md`, «Проверка до правки»; на базе `{BASE}` вместо `HEAD`; PHP — в контейнере, `vendor` копией) и пишет результат в `bug.md` проекта, «Тест», — у «до» и «после» одинаково; судье — задача `tools/ab/task-fix/{go,php}/bug.md`, заложенный баг — `bug.patch` там же (судье его можно: он оценивает, найдена ли причина), и пункты (1)–(3) заменяются на: (1) исправлена ли причина из `bug.patch` в её месте или закрыт симптом обходом; (2) есть ли тест бага, падает ли он на коде с `bug.patch` и проходит после правки (по чтению теста; запускать не нужно), проверяет ли он поведение из симптома; (3) попутные правки вне причины, нарушения памятки в диффе; (3a) по `judge/<стек>-<буква>.bug.md` (`ab.py diffs` кладёт их для `--task fix`) — разобраны ли данные, которые баг успел испортить (БД, кэш, события), верно ли по коду, предложено ли, как найти и вернуть.

## Итог

По `mapping.secret.json` — какая буква какая версия. Сравнить: вердикт судьи, находки ревью ([ОШИБКА]/[ВНИМАНИЕ]), выполнение R/AC, токены — `python3 tools/usage/usage.py --session <ID сессии> --since <время старта>` (строки агентов A/B). **Хуже** — судья: «после» явно хуже, или у «после» больше нарушений уровня О, или невыполненное R/AC, которого нет у «до»: правку не принимать, разобрать причину. «Немного хуже» на одном прогоне — повторить A/B один раз (разброс модели того же порядка); подтвердилось — разобрать. Расход «после» больше «до» на 30%+ — в итог отдельной строкой.

## Ревью на реальном MR (`real_review.py`)

Значения — из вывода `python3 tools/ab/real_review.py prepare …`: `{DF}` — фреймворк версии, `{P}` — копия MR (`mr-old` / `mr-new` — ревьюерам, `code/` в папке судьи — судье), `{J}` — папка судьи (в ней нет соответствия букв версиям), стек и подпроект, `<суть MR>` — заголовок MR одной фразой. Все агенты — `general-purpose`, в фоне; оба ревью — параллельно и с одним текстом, кроме `{DF}` и `{P}`; судья — после `real_review.py judge`, до `cleanup`.

### Ревью (2: rr-old, rr-new)

```
Ты — ревьюер. `{DF}` = <путь> (фреймворк правил; не правь). Выполни `{DF}/skills/dev-review/SKILL.md` (напрямую, не субагентом /dev) для незакоммиченного диффа проекта {P} относительно `HEAD` (коммит base). Стек <Go (Go SDK) | PHP (Laravel + mps/core), подпроект `<sub>`>. Это реальный MR (<суть MR>); документов задачи (requirements/design) нет — ревью по коду и правилам. Где путь `~/.claude/dev-framework` — это `{DF}`.
<Go:> Сборка и анализаторы — с `GOFLAGS=-mod=mod GOPROXY=off GONOSUMDB=git.mpinnovations.kz,github.com/exgamer` (хосты SDK из `go.mod` проекта); не запускаются без сети — отметь в отчёте и ревьюй глазами по памятке целиком.
<PHP:> Копия без vendor и вне PHP-контейнера: анализаторы (lint.py, phpstan, phpunit) не запускай — отметь в отчёте и ревьюй глазами по памятке целиком. Composer не запускай.
IDE (MCP) может быть недоступна — Grep/Read. Пользователь недоступен: вопросы — в отчёт. Код не правь, без commit/push; отчёт — по SKILL в каталог этого проекта. Итог — по SKILL, плюс в конце список всех находок одной строкой каждая: «тег — уровень — файл:строка — суть».
```

### Судья (1 — не знает, где какая версия)

```
Ты — независимый строгий судья ревью. Только чтение. Один реальный MR отревьюирован дважды — отчёты A и B (файлы A.md и B.md в каталоге `{J}`; пути копий в них заменены на `{P}` и `{DF}`), чей какой — не знаешь и не угадывай. Код MR — незакоммиченный дифф к HEAD в {P} (`{J}/code`; соседний код — там же; в другие папки не заходи). Мерило — памятка `{DF}/stacks/<stack>/checklist.md` и каталог тегов (`{DF}/approaches/process/review-tags.md`, `{DF}/stacks/<stack>/review-tags.md`, теги безопасности — `{DF}/approaches/process/security.md`), {DF} — текущая версия.
(1) Сопоставь находки A и B по месту и сути (тег может отличаться). (2) Каждую находку, которая есть только у одной стороны, проверь по коду: «настоящая» (файл:строка, почему; по коду, а не по тому, есть ли тег в каталоге — тег одной стороны может быть снят или добавлен правкой), «шум» (почему не дефект — с цитатой кода) или «спорная» (что нужно знать); уровень — по каталогу. (3) Общие находки — выборочно 3–5 самых серьёзных: обе ли стороны верно оценили уровень. (4) Вердикт: A или B явно лучше / немного лучше / равны — по настоящим находкам уровня О и безопасности, затем по шуму, затем по В; 3–5 причин.
Отчёт — файл verdict.md в каталоге `{J}` (таблица находок только одной стороны: сторона, тег, место, вердикт, довод); ответ — до 15 строк.
```

### Итог ревью на реальном MR

По `mapping.secret.json` — какая буква какая версия. **Хуже** — у «после» настоящая находка безопасности или уровня О есть только у «до» и это не разброс, или шум «после» от правленого правила (тег или пункт правки): правку не принимать, разобрать причину — шумное правило сузить, потерянное вернуть. «Немного хуже» на одной паре — повторить пару один раз на свежих копиях (`prepare` заново); подтвердилось — разобрать. Итог — строкой в отчёт пачки: MR (проект, хэш, суть), вердикт судьи, находки правленых правил у «после» (настоящие / шум), токены.

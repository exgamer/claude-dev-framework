# lint — механические правила фреймворка на проекте, без файлов в проекте

Проверяет код проекта правилами фреймворка, которые отданы анализаторам (таблица — `tools/check/lint-proof/RULES.md`). В проекте **ничего не создаётся и не меняется**: конфиг собирается под проект и пишется вне его; свои конфиги проекта (`.golangci.yml`, `phpstan.neon`) не читаются и не трогаются — это отдельный, независимый прогон.

## Go

```bash
python3 tools/lint/lint.py go <проект>              # весь код (легаси тоже)
python3 tools/lint/lint.py go <проект> --base <rev> # только новое относительно ревизии — дифф задачи
python3 tools/lint/lint.py go <проект> --render     # напечатать собранный конфиг
```

- Нужен `golangci-lint` v2 на машине — ставится один раз (`brew install golangci-lint`), не в проект.
- Конфиг — `~/.cache/dev-framework-lint/<проект>/golangci.yml`: модуль из `go.mod`, домены из `internal/domains/*` (по правилу «домен не импортирует другой» на каждый).
- Затем — анализатор фреймворка `tools/lint/gocheck` (Go, только стандартная библиотека, разбор AST): правила, которых нет в golangci-lint, — `SetTimeout` пагинатора с `time.Second`, тег `validate` без `binding` или с другими правилами в `internal/entrypoints/`, файлы `ports.go`/`interfaces.go`/`dependencies.go`/`types.go`/`const.go`/`utils.go`. Собирается в `~/.cache/dev-framework-lint/` один раз на версию исходника (нужен `go`, сеть не нужна); с `--base` — только изменённые и новые `.go`. `ruleguard` (gocritic) не подошёл: требует собранный пакет `dsl` в старом GOPATH.
- Тесты проекта не компилируются — прогон говорит об этом и анализирует без тестов: одна сломанная заглушка не прячет анализ.

## PHP

```bash
python3 tools/lint/lint.py php <проект> --sub parking_app [--container <имя>] [--base <rev>]
```

- Запуск — в PHP-контейнере проекта: нужен `vendor/autoload.php` проекта. Контейнер — `--container`, `PHP_CONTAINER`, запомненный для проекта или единственный запущенный, в который смонтирован проект; иначе спросит в терминале и запомнит (`tools/lint/php_container.py`, `tools/lint/.php-containers.json` у разработчика, в git не попадает; спрашивает и `install.sh`). Имя контейнера в фреймворке не зашито — у каждого разработчика своё. Путь проекта в контейнере — по его монтированиям.
- Инструменты фреймворка — phpstan, `phpat/phpat`, `spaze/phpstan-disallowed-calls` (без зависимостей от Laravel) — ставятся один раз в контейнер в `/tmp/df-lint`, не в проект; публичные пакеты, токен не нужен.
- Правила — под неймспейс подпроекта (`psr-4` из `composer.json`) и его домены (`<sub>/Domains/*`); классы правил (`LayersArchitecture` — phpat, `GenericExceptionRule` — своё правило phpstan на `new \Exception`/`new \RuntimeException`) — в автозагрузке инструментов (`/tmp/df-lint/rules/`).
- Включены **только правила фреймворка** (`customRulesetUsed`) — проверки phpstan по уровням и ошибки собственного phpstan проекта сюда не смешиваются.
- `--base` — анализируются только изменённые PHP-файлы подпроекта.

## Ограничения

- Анализатор покрывает пункты памятки частично: что он ловит точно и что остаётся агенту — колонки «Ловит точно» и «Остаток — агенту» в `tools/check/lint-proof/RULES.md` (например «домен без БД» — импорт `gorm` ловит, `database/sql` — нет). Дошедший до конца прогон печатает в конце список «Остаток — проверить глазами» по правилам стека (из этой таблицы — ревьюеру её открывать не нужно); не дошёл — «остатка нет». Ревьюер по правилам списка проверяет только остаток; разработчик проходит памятку целиком.
- `--base`: перенос файла между слоями (`git mv`) без новых строк не ловится — смотреть глазами; в общем дереве параллельных агентов в дифф попадают чужие правки — свои находки отличаются по файлам задачи; PHP проверяет изменённые файлы целиком — старые нарушения в них «унаследованы».
- `--no-install` (php) — не ставить инструменты (агент ревью без сети): нет — «не запускался», код 2.

## Те же правила, что в эталонах

Конфиги эталонов — вывод этих же генераторов (`lint.py go … --render`, `php_rules.py`); `tools/check/lint-rules.py` сверяет, что эталон и шаблон совпадают, поэтому доказательство на эталоне (`tools/check/lint-proof/go.py`, `php.py`: каждое правило ловит заведомое нарушение) доказывает и прогон на проекте.

Проверено 2026-10-20 на действующих проектах Go и PHP: `git status` проекта до и после прогона одинаков; находки — настоящие нарушения слоёв в существующем коде (workflow вызывает workflow, тип порта из инфраструктуры, домен зависит от другого домена).

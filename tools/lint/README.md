# lint — механические правила фреймворка на проекте, без файлов в проекте

Проверяет код проекта правилами фреймворка, которые отданы анализаторам (таблица — `tools/check/lint-proof/RULES.md`). В проекте **ничего не создаётся и не меняется**: конфиг собирается под проект и пишется вне его; свои конфиги проекта (`.golangci.yml`, `phpstan.neon`) не читаются и не трогаются — это отдельный, независимый прогон.

## Go

```bash
python3 tools/lint/lint.py go <проект>              # весь код (легаси тоже)
python3 tools/lint/lint.py go <проект> --base <rev> # только новое относительно ревизии — дифф задачи
python3 tools/lint/lint.py go <проект> --render     # напечатать собранный конфиг
```

- Нужен `golangci-lint` v2 на машине — ставится один раз (`brew install golangci-lint`), не в проект.
- Конфиг — `~/.cache/dev-framework-lint/<проект>/golangci.yml`: модуль из `go.mod`, домены из `internal/domains/*` (по правилу «домен не импортирует другой» на каждый; `common` и `shared` — общий модуль, не домен).
- Затем — анализатор фреймворка `tools/lint/gocheck` (Go, только стандартная библиотека, разбор AST): правила, которых нет в golangci-lint, — `SetTimeout` пагинатора с `time.Second`, тег `validate` без `binding` или с другими правилами в `internal/entrypoints/`, файлы `ports.go`/`interfaces.go`/`dependencies.go`/`types.go`/`const.go`/`constants.go`/`consts.go`/`utils.go`/`helpers.go`/`common.go`/`misc.go`, ссылки на артефакты задачи в комментариях и строках (`R15:`, `design §`, `docs/tasks/`), контейнер DI вне ядер, `app.go` и `module.go` bootstrap (`di-resolve-in-business-code`). Собирается в `~/.cache/dev-framework-lint/` один раз на версию исходника (нужен `go`, сеть не нужна); с `--base` — только изменённые и новые `.go`. `ruleguard` (gocritic) не подошёл: требует собранный пакет `dsl` в старом GOPATH.
- Тесты проекта не компилируются — прогон говорит об этом и анализирует без тестов: одна сломанная заглушка не прячет анализ.
- Код проекта не компилируется (golangci выдаёт только `typecheck`, остальные правила молча выключены) — строка «код проекта не компилируется: <пакеты> — проблема проекта» и повтор без этих пакетов и пакетов, которые их импортируют (по `go list`, тесты — тоже); остаток печатает их список — код задачи в них глазами целиком.

## PHP

```bash
python3 tools/lint/lint.py php <проект> --sub <подпроект> [--container <имя>] [--base <rev>]
```

- Запуск — в PHP-контейнере проекта: нужен `vendor/autoload.php` проекта. Контейнер — `--container`, `PHP_CONTAINER`, запомненный для проекта или единственный запущенный, в который смонтирован проект; иначе спросит в терминале и запомнит (`tools/lint/php_container.py`, `tools/lint/.php-containers.json` у разработчика, в git не попадает; спрашивает и `install.sh`). Имя контейнера в фреймворке не зашито — у каждого разработчика своё. Путь проекта в контейнере — по его монтированиям.
- Инструменты фреймворка — phpstan, `phpat/phpat`, `spaze/phpstan-disallowed-calls` (без зависимостей от Laravel) — ставятся один раз в контейнер в `/tmp/df-lint`, не в проект; публичные пакеты, токен не нужен.
- Правила — под неймспейс подпроекта (`psr-4` из `composer.json`) и его домены (`<sub>/Domains/*`; `Domains/Common` и `Domains/Shared` — общий модуль, не домен; модули домена — `Modules/*` и `src/Modules/*` при psr-4 `Domains/{Домен}/src` → `…\Domains\{Домен}`); классы правил (`LayersArchitecture` — phpat; свои правила phpstan: `GenericExceptionRule` — `new \Exception`/`new \RuntimeException`, `StatusSetDirectlyRule` — запись `status`/`is_default` мимо перехода, `EloquentRelationRule` — связи в модели) — в автозагрузке инструментов (`/tmp/df-lint/rules/`).
- Маршруты (`<sub>/Entrypoints/**/routes.php`: middleware ответа первым — `api.response`, алиас `ApiResponseMiddleware` или группа из `bootstrap/app.php` проекта; `X::class` при алиасе в `bootstrap/app.php`; id в пути без ограничения, `403` в Swagger у маршрута под `permission:`) — `tools/lint/php_routes.py` на хосте после phpstan, без PHP; с `--base` — только находки, задетые добавленными строками диффа (`git diff -U0`; новый файл — целиком): строка ограничения id, цепочка группы или маршрута, атрибуты метода контроллера; старые строки изменённого `routes.php` — не находка задачи.
- Включены **только правила фреймворка** (`customRulesetUsed`) — проверки phpstan по уровням и ошибки собственного phpstan проекта сюда не смешиваются; `@phpstan-ignore` проекта под его уровень «лишним» не считается (`reportUnmatchedIgnoredErrors: false`). Вывод — строками `файл:строка: сообщение 🪪 identifier`; `use` запрещённого класса при его вызове в том же файле — одна находка (`disallowed.class`).
- `--base` — анализируются только изменённые PHP-файлы подпроекта.

## Глушение проверок в диффе (оба стека)

С `--base` после правил стека `lint.py` запускает `tools/lint/diff_silence.py` (правило — `core/principles.md`, «Честность результата», тег `check-silenced`): в **добавленных строках** диффа и в новых файлах задачи — `//nolint` не в виде `//nolint:<линтер> // причина`, `t.Skip`, `@phpstan-ignore*`, `markTestSkipped`/`markTestIncomplete`, `#[CodeCoverageIgnore]`/`@codeCoverageIgnore` без причины комментарием на той же или предыдущей строке (строка-тег docblock — `* @author …`, `* @return …` — не причина; у пропуска теста причина — и сообщение-строка со словом: `t.Skip("нужен брокер")`, `markTestSkipped('нет ext-intl')`; `t.SkipNow()`, `markTestSkipped()`, `('')` — находка); в `.golangci.yml` — новые записи `disable`, `disabled-checks`, `exclusions`, `exclude*`, `skip-*`, `disable-all: true`/`disabled: true`; в `phpstan*.neon` — понижение `level` относительно ревизии, новые записи `ignoreErrors`, `excludePaths`. Находка — `файл:строка: [check-silenced] …`, итог — строка `silence: файлов: N; находок: M`. С `--sub` (PHP-монорепозиторий) — только файлы подпроекта и `phpstan*.neon*` в корне проекта и подпроекта. Без `--base` не запускается: полный прогон — не дифф, старые заглушки проекта — не находка задачи. Отдельно, без анализаторов: `python3 tools/lint/diff_silence.py <проект> --base <rev> [--sub <подпроект>]`. Доказательство — `tools/check/lint-proof/silence.py` (оба эталона целиком как дифф — 0).

## Прогон на реальных проектах (правка анализаторов)

```bash
python3 tools/lint/real_projects.py add <go|php> <путь> [--sub X] [--container Y]  # запомнить проект
python3 tools/lint/real_projects.py list
python3 tools/lint/real_projects.py run [--range N] [--out <каталог>]
```

Правка, задевающая анализаторы, проверяется не только на эталонах, но и на реальных проектах разработчика (`skills/dev-rule/SKILL.md`, Шаг 3а): эталоны чисты по построению, шум новой проверки видит только чужой код. `run` — по каждому проекту `lint.py` дважды: полный прогон и `--base` на ревизию N коммитов назад (по умолчанию 20, без merge, по пути подпроекта); вывод — число находок по правилу (golangci — по линтеру, revive — по правилу, gocheck, phpstan — по identifier, routes, silence) и путь полного вывода. Только чтение: HEAD, `git status` и дифф рабочего дерева проекта до и после сравниваются — изменились, ошибка; файлы из `.gitignore` проекта (кеш, `vendor/`) сверка не видит. Список — `tools/lint/.real-projects.json` у разработчика (в git не попадает, путей проектов в фреймворке нет); нет списка — в терминале спросит и запомнит, не в терминале — код 2 с подсказкой `add`.

## Ограничения

- Анализатор покрывает пункты памятки частично: что он ловит точно и что остаётся агенту — колонки «Ловит точно» и «Остаток — агенту» в `tools/check/lint-proof/RULES.md` (например «домен без БД» — импорт `gorm` ловит, `database/sql` — нет). Дошедший до конца прогон печатает в конце список «Остаток — проверить глазами» по правилам стека (из этой таблицы — ревьюеру её открывать не нужно); не дошёл — «остатка нет». Ревьюер по правилам списка проверяет только остаток; разработчик проходит памятку целиком.
- `--base`: перенос файла между слоями (`git mv`) без новых строк не ловится — смотреть глазами; в общем дереве параллельных агентов в дифф попадают чужие правки — свои находки отличаются по файлам задачи; PHP проверяет изменённые файлы целиком — старые нарушения в них «унаследованы».
- `--no-install` (php) — не ставить инструменты (агент ревью без сети): нет — «не запускался», код 2.

## Те же правила, что в эталонах

Конфиги эталонов — вывод этих же генераторов (`lint.py go … --render`, `php_rules.py`); `tools/check/lint-rules.py` сверяет, что эталон и шаблон совпадают, поэтому доказательство на эталоне (`tools/check/lint-proof/go.py`, `php.py`: каждое правило ловит заведомое нарушение) доказывает и прогон на проекте.

Проверено 2026-10-20 на действующих проектах Go и PHP: `git status` проекта до и после прогона одинаков; находки — настоящие нарушения слоёв в существующем коде (workflow вызывает workflow, тип порта из инфраструктуры, домен зависит от другого домена).

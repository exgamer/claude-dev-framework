# Журнал решений

Почему правила такие, какие есть. Перед тем как спорить с правилом — посмотреть сюда.
Открытые споры = обязательное обсуждение с пользователем, если задача их задевает (см. `core/principles.md`). Пока спор открыт, в новом коде — как в эталоне фреймворка (`stacks/<stack>/examples/`), и это явно проговаривается пользователю.

Префиксы: `O-` общие, `G-` Go, `P-` PHP.

| O-22 | Граф проекта при анализе: строить граф кода проекта (graphify), чтобы роли не перечитывали код каждый раз и тратили меньше токенов; при старте `/dev` и прямых ролей проверять, установлен ли `graphify`, и предлагать установить (`pip install graphifyy`), работа без него не останавливается. После доработок граф обновлять, чтобы не устаревал. Параллельные разработчики (до 3, refactor/migrate — до 5, одно дерево; плюс другие люди/ветки): кто и когда обновляет граф, чтобы не было гонок и расхождений. Стоит ли вводить | (а) не вводить: хватает IDE (O-21) + grep; (б) граф только по коду (AST, без LLM), строится/обновляется в Фазе 0 по git-хэшу, читают аналитик и архитектор для обзора структуры; использования и строковые связи для карты связей — по-прежнему grep; (в) полный граф (код + docs через LLM-извлечение). Обновление (к б/в): в волне граф только читается, разработчики его не пересобирают; после волны координатор `/dev` один раз обновляет инкрементально по изменённым файлам; граф не коммитится, помечен git-хэшем — при старте сверка с `HEAD` и догрузка изменённого (другая ветка/чужие коммиты → пересборка по diff); сборка во временную папку и атомарная замена, чтобы две сессии не испортили граф | не введено; граф есть только для правил самого фреймворка (`tools/graph/`, `/dev-rule`) |

# Журнал решений

Почему правила такие, какие есть. Перед тем как спорить с правилом — посмотреть сюда.
Открытые споры = обязательное обсуждение с пользователем, если задача их задевает (см. `core/principles.md`). Пока спор открыт, в новом коде — как в эталоне фреймворка (`stacks/<stack>/examples/`; он написан по основным эталонам: Go — `parking-session-service`, PHP — `parking_app`), и это явно проговаривается пользователю.

Префиксы: `O-` общие, `G-` Go, `P-` PHP.

| O-22 | Граф проекта при анализе: строить граф кода проекта (graphify), чтобы роли не перечитывали код каждый раз и тратили меньше токенов; при старте `/dev` и прямых ролей проверять, установлен ли `graphify`, и предлагать установить (`pip install graphifyy`), работа без него не останавливается. После доработок граф обновлять, чтобы не устаревал. Параллельные разработчики (до 3, refactor/migrate — до 5, одно дерево; плюс другие люди/ветки): кто и когда обновляет граф, чтобы не было гонок и расхождений. Стоит ли вводить | (а) не вводить: хватает IDE (O-21) + grep; (б) граф только по коду (AST, без LLM), строится/обновляется в Фазе 0 по git-хэшу, читают аналитик и архитектор для обзора структуры; использования и строковые связи для карты связей — по-прежнему grep; (в) полный граф (код + docs через LLM-извлечение). Обновление (к б/в): в волне граф только читается, разработчики его не пересобирают; после волны координатор `/dev` один раз обновляет инкрементально по изменённым файлам; граф не коммитится, помечен git-хэшем — при старте сверка с `HEAD` и догрузка изменённого (другая ветка/чужие коммиты → пересборка по diff); сборка во временную папку и атомарная замена, чтобы две сессии не испортили граф | не введено; граф есть только для правил самого фреймворка (`tools/graph/`, `/dev-rule`) |

## Ключевые принятые

Коротко — то, что роли задевают почти в каждой задаче. Полная история — `core/decisions-log.md`.

| O-7 | Service/Command/Query — только свой домен; 2+ домена → workflow, он берёт репозитории/сервисы любых доменов напрямую; чужой домен (в т. ч. enum) не импортируется; понятие двух и более доменов — слой `Common` (enum, value-объекты, чистые функции, без DI и I/O), копия — [ОШИБКА] | `architecture/layers.md` |

| O-12 | `/dev` только координирует; каждая роль — субагент со свежим контекстом; памятка `checklist.md` — основа разработчика и ревью; у правила одно основное место | `approaches/process/role-chain.md` |
| O-13 | Роли `/dev` — агенты `agents/df-*` с ограниченными инструментами; общие правила — `approaches/process/subagent.md` | `agents/` |
| O-17 | Рефактор/перенос: из легаси — только контракты (URL, ответ, таблицы и значения БД, morph-типы, теги кэша, события, очереди) и бизнес-правила как требования; реализация легаси и расходящийся с правилами сосед — не образец, слой каждой проверки/меры — по правилам стека; ревью проверяет и `threats.md`/`design.md`; отличие от легаси вне контракта — вопрос, только если меняется видимое поведение | `approaches/process/legacy-refactor.md`, `stacks/{php,go}/security.md` («Меры по слоям»), роли |
| O-18 | Доменные инварианты DTO — `{E}DtoValidator` в папке `Validators/` модуля: не сервис (без зависимостей, хранилища, DI); проверки по данным (существование, уникальность, скоуп) — в сервисе/workflow через репозиторий. Go — файл `{entity}_validator.go` в пакете модуля, возвращает ошибки по полям (`map[string]any`), сервис бросает `exception.NewValidationException` | `architecture/layers.md` |
| O-19 | Рефактор/перенос: по каждому контракту всегда вопрос пользователю — (а) сохранить (реализация на месте, без версии) или (б) по правилам — новой версией (`/v2`, версия события), старая без изменений до удаления отдельной задачей. Переключателей нет: флаги, DI по настройке, процент трафика, shadow/dual-write, новый контракт под старым URL | `approaches/process/legacy-refactor.md`, «Контракт: сохранить или по правилам» |
| O-20 | Размер задачи плана: один модуль, ≤2 соседних слоя, ориентир 8–10 файлов; больше — «модуль × слой» по «Контракты слоёв» `design.md`; колонка «контекст» в `plan.md`; не больше 3 разработчиков (refactor/migrate — до 5), задачи не объединяются ради лимита, каждая задача — свежий агент, больше ~120 шагов — разрез; запуск по готовности зависимостей | `approaches/process/planning.md` |
| O-21 | Навигация по коду: IDE (`idea` MCP, 4 инструмента только на чтение), если проект открыт в IDEA, иначе grep; использования и строковые связи — всегда grep; при старте — проверка и предложение включить | `approaches/process/code-navigation.md` |
| G-6 | Go, модуль домена: интерфейсы-зависимости — по файлу на группу: `repository.go` (данные: хранилища и внешние системы как источник данных), `tx_manager.go` (транзакции — так же в workflow), `modules.go` (соседние модули домена), `system.go` (технические сервисы без данных домена); в остальных пакетах — файл по имени интерфейса | `stacks/go/conventions.md` п. 12 |
| P-18 | Данные на запись — DTO по всей цепочке (контроллер → сервис/workflow → репозиторий), не массив; в репозиторий — DTO или типизированные аргументы (`createFromDto`, `updateFromDto`, `setDefault(int, bool)`), не массив; колонки — внутри репозитория, модель с casts — `fill()->save()` | `stacks/php/conventions.md` п. 11a |
| P-17 | В Laravel Request нет SQL (`exists:`/`unique:`/модели/`DB::`) | `stacks/php/conventions.md` |
| P-19 | Список — как в Go: явный метод репозитория `paginate…({E}FilterDto, Page)`, один метод собирает один запрос целиком (фильтры подряд, явный `orderBy`, колонки явно, без методов-кусков и констант колонок); `CRUDRepository::search()`/`filterSearch()`/`SearchDataObject`/`PaginatedQueryHelper` — старая форма, в новом коде не используются | `stacks/php/conventions.md` п. 2a, 12c, 12d, 19 |
| P-20 | Метод репозитория — один запрос: «выбрать → по результату записать» (заблокировать и удалить, прочитать и сохранить, удалить и вставить) — бизнес-логика; шаги — отдельные методы репозитория, порядок и транзакция — в сервисе/Command/workflow; обновление — одним `UPDATE … WHERE` | `architecture/layers.md` «Правила слоёв»; `stacks/php/conventions.md` п. 2b; `stacks/go/conventions.md` п. 15b |

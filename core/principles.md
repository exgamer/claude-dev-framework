# Принципы

Действуют для любого стека и любой роли. При конфликте с правилом стека — побеждает более конкретное правило (стек > архитектура > принципы), кроме раздела «Пробелы и споры» — он не переопределяется.

---

## Простота

- Самое простое решение, которое закрывает задачу. Не проектировать «на вырост».
- Не создавать абстракции, слои, интерфейсы и обёртки без реальной причины (вторая реализация, граница слоя, внешняя система, подмена в тестах).
- Сначала Service; Command/Query/Workflow — только когда сервис реально перерос себя или задача затрагивает несколько доменов.
- «Лучше несколько простых изолированных реализаций, чем одна универсальная с кучей условных ветвлений» (регламент сервисов, п. 10).

## Пиши как в проекте

- Перед тем как писать — прочитать соседний модуль того же типа и повторить его форму: структура файлов, нейминг, порядок объявлений, стиль ошибок. Если сосед расходится с правилами или эталоном (`stacks/<stack>/examples/`) — форма по эталону, детали по соседу, расхождение не копировать и назвать в итоге. Легаси при рефакторе — источник только контрактов и бизнес-правил, не реализации (`approaches/process/legacy-refactor.md`, O-17).
- Не подключать новые библиотеки, фреймворки, SDK — только то, что уже есть в проекте (новая технология = согласование, см. `regulations/technical-approval.md`).
- Не изобретать свои классы и абстракции для задачи, которую уже решает соседний модуль проекта или эталон фреймворка: найти ближайший аналог (сначала в текущем проекте, затем `stacks/<stack>/examples/`) и повторить его форму — имена интерфейсов, раскладку файлов, где живёт оркестрация. Не-бизнесовая проблема (транспорт, сериализация, ретраи, парсинг): общий компонент уже есть — только он; решена копией в другом модуле — когда выносить, по разделам «Инфраструктурный код — один раз» и, для преобразований формата, «Повторяющаяся обработка — один хелпер» ниже.
- Не выдумывать — ни API SDK, ни правила процесса, имена ролей, ответы пользователя и факты задачи. API SDK: что есть — `stacks/go/go-sdk/capabilities.md`, `stacks/php/mps-core/capabilities.md`; точные сигнатуры — `reference/` рядом с ними (сгенерированы из исходников, пересобираются `tools/sdk-ref/` под версию проекта). Нет в справочнике версии проекта — метода нет; сомнение — исходники (`go/pkg/mod`, `vendor`) или вопрос пользователю. Остальное: не уверен — перечитать источник (файл фреймворка, артефакты `docs/tasks/<ключ>/`; у оркестратора — ещё запись разговора), а не восстанавливать по памяти; после сжатия контекста — особенно: в сводке остаётся пересказ, а не правило (2026-10-16: имя разработчика вне пула `role-chain.md`).

## Пробелы и споры — обсуждаем, а не решаем молча

**Главное правило фреймворка.** Если ситуация:
- не описана в регламентах и правилах фреймворка (новый тип компонента, новый слой, непонятно куда положить код, новая интеграция без образца),
- или описана противоречиво (регламент говорит одно, проект делает другое, два правила конфликтуют),
- или затрагивает спорный слой/подход, уже отмеченный в `core/decisions.md` как открытый,
- или в проекте-примере/текущем проекте что-то **сделано, но не подкреплено** регламентом и правилами фреймворка (новый тип класса, свой слой, необычная папка, приём, которого нет в `stacks/*`) — «так уже сделано» не делает это правилом,

то **не выбирать вариант самостоятельно и не продолжать молча**. Порядок:

1. Остановиться на этом месте (остальную однозначную работу можно продолжать).
2. Сформулировать вопрос обычным текстом (не опросником с кнопками): что именно не покрыто, где это в коде/правилах, варианты (2–3), плюсы/минусы, рекомендация.
3. Обсудить с пользователем и получить решение.
4. Записать случай и решение в лог задачи `docs/tasks/<ключ>/rules-log.md` (`core/rules-evolution.md`, «Лог отклонений по задаче»). Вносить ли это в правила фреймворка, проекта или оставить разовым — решается на разборе лога в конце задачи.
5. Только после этого писать код по принятому решению.

Если пользователь сказал «сделай как считаешь нужным» — сделать по рекомендации, записать в лог задачи и явно сказать об этом.

В авто-режиме `/dev` вопросы собираются **заранее, одним списком** (`approaches/process/role-chain.md`, «Авто-режим»); вопрос, всплывший по ходу, решается по политике, которую пользователь выбрал в начале (по рекомендации с записью в лог задачи — или отложить кусок до конца). Остановка всей работы ради одного вопроса — только для согласований до кода и изменений внешнего контракта.

## Повторяющаяся обработка — один хелпер

Преобразование формата или другая чистая техническая операция над примитивами — нормализация телефона, ИИН, номера карты, госномера, форматирование денег и дат, разбор строки, маска, хэш — пишется в проекте **один раз** и вызывается отовсюду. Кейс: в `super_app`/`app` нормализация телефона `preg_replace('/\D/', '', …)` повторена в шести Request'ах, сервисе, репозитории и консольной команде при живом `PhoneHelper` рядом — любая правка формата (новый код страны, маска) требует синхронизации всех копий, одну всегда забывают.

Порядок, прежде чем написать такое преобразование:

1. **SDK/ядро** — `stacks/<stack>/…/capabilities.md`: Go — `core/pkg/validation.NormalizePhoneNumber`, `CheckValidPhone`, `CheckValidEmail`; PHP — `MPS\Utils\Enums\RegexEnum` (`MOBILE_PHONE`, `EMAIL`…), `RegexRule`. Есть — только вызов.
2. **Проект** — grep по хелперам (`Core/Helpers/`, `pkg/`) и по характерным фрагментам (`preg_replace('/\D`, `strings.Map`, `unicode.IsDigit`, `+7`, `substr($phone`). Есть — вызов; лежит не в хелпере (inline в Request или сервисе) — вынести в хелпер в рамках своей правки и вызвать оттуда, старое место тоже перевести на хелпер, если оно в файлах задачи.
3. **Нет нигде** — хелпер сразу, даже если вызов пока один: место для второго вызова уже есть, копировать не придётся.

Что считается хелпером (и чем он не является):

- **чистая функция над примитивами**: строка/число на входе, строка/число/bool на выходе; без DI, без БД, без конфигурации, без доменных типов (сущность, DTO, модель); детерминированная; покрыта unit-тестами на граничные случаи (пусто, `null`, уже нормализованное, мусор);
- **не бизнес-правило**: «телефон обязателен для юрлица», «скидка для тарифа X» — это домен (сервис/валидатор) или workflow, в хелпер не выносится (P-11: `Core/` — только техническое);
- **не инфраструктурный workaround** — для них раздел «Инфраструктурный код — один раз» ниже;
- **не «общий сервис для всех доменов»** — `Domains/Shared/`, `common`-пакеты с бизнес-логикой не заводятся (`stacks/<stack>/structure.md`).

Где лежит и как называется — `stacks/<stack>/structure.md`: Go — раздел «Тесты», строка «хелпер преобразования формата»; PHP — «Дерево подпроекта», абзац «Хелперы». Применение по слоям: нормализация входа — на границе (PHP — `prepareForValidation()` Request'а вызовом хелпера, это формат, не SQL; Go — маппер хендлера/consumer'а), дальше по цепочке — уже нормализованное значение; форматирование для вывода — в Response/маппере тем же хелпером; в сервисе и репозитории преобразований формата нет.

Ревью: вторая копия преобразования и inline-реализация того, что уже есть в SDK или в хелпере проекта (переизобретение, как `repository-reinvents-core-helper`), — `duplicated-format-logic`; уровень каждого случая — в каталоге тегов (`approaches/process/review-tags.md`, O-24). Разработчик перед сдачей прогоняет grep из `review-checks.md` по своим файлам.

## Инфраструктурный код — один раз

Доменно-нейтральная логика — транспорт, сериализация, ретраи, заголовки брокера, обёртка клиента, скелет consumer'а или джобы транспорта — пишется в проекте один раз (O-27). Повтор в домене — другое правило: там он допустим ради независимости путей (`core/style.md`, «Форма кода», O-25).

- **Готовый компонент есть** (SDK, ядро, общий код проекта) — только он; своя реализация даже в первый раз — переизобретение.
- **Вторая копия** — кандидат на вынос: в находке оба места и предложение общего компонента.
- **Третья копия** — вынести в общий компонент.
- **Куда** — сначала в проект: Go — `pkg/`, PHP — `Core/` подпроекта или хелпер (`stacks/<stack>/structure.md`). SDK и ядро разработчик не правит: у пакета свой владелец и версии. Код не знает домен и нужен в нескольких местах — в итоге задачи разработчик предлагает пользователю перенести его в пакет (Go SDK, `mps/core`); решение и перенос — за пользователем.

Теги и уровни каждого случая — каталог (`approaches/process/review-tags.md`): `infra-logic-duplicated`, `duplicated-handler-skeleton`; готовое в SDK или ядре — `sdk-reimplemented` (Go), `repository-reinvents-core-helper` (PHP). Признаки и пример — `stacks/go/conventions.md` п. 22.

## Объём

- Сначала минимальный рабочий срез, который реально нужен, с чистыми точками расширения. Остальное — явным списком «Отложено», не молча выкинуто.
- Не начинать новое, оставив недописанным текущее: если задачу прервали — доделать или явно сказать, что осталось.

## Честность результата

- Не писать, что проверено, если не запускал. Сборка/линтер/тесты — либо запущены и результат показан, либо явно сказано «не запускал».
- Не скрывать отступления от правил: если пришлось отступить — сказать где и почему и записать в лог задачи (`rules-log.md`).
- **Обход поведения ядра/SDK/библиотеки — только после проверки.** Прежде чем писать код «на случай, если ядро так делает» (расширенные типы, ручное приведение, лишние проверки на `null`, дублирующая валидация), проверить это поведение: исходник в `vendor/` / модуле SDK или короткий прогон в окружении проекта. Подтвердилось — обход с комментарием «почему» и тестом на это поведение; не подтвердилось — обход не пишется. Обход по непроверенному предположению — `unverified-workaround`. Пример (AINA-2628): сеттеры DTO принимали `int|float|string|null` «потому что ядро теряет строки из multipart», а `fromArray()` приводит их само — ревью: «эти все типы прям нужны?».
- **Проверку не глушат вместо исправления.** Сначала исправляется код; заглушка — только когда находка ложная или исправление вне задачи, и тогда рядом — причина комментарием (на той же или предыдущей строке); у пропуска теста причина — и сообщение пропуска (`t.Skip("…")`, `markTestSkipped('…')`). Касается новых в диффе: `//nolint` (Go — только `//nolint:<линтер> // причина`), `@phpstan-ignore*` (PHP; шум типизации mps — `ignoreErrors`, `stacks/php/conventions.md` п. 23), пропуска теста (`t.Skip`, `markTestSkipped`/`markTestIncomplete`), исключения из покрытия (`#[CodeCoverageIgnore]`, `@codeCoverageIgnore`), ослабления конфига анализатора (`.golangci.yml` — `exclusions`, `disable`, `disabled-checks`, `exclude*`, `skip-*`; `phpstan*.neon` — понижение `level`, `ignoreErrors`, `excludePaths`) — тег `check-silenced`. Почему: агенту проще заглушить проверку, чем исправить код, а заглушка прячет и следующие нарушения в том же месте. Проверяет `tools/lint/lint.py … --base` (только добавленные строки диффа; `tools/lint/README.md`).

```
плохо:   defer tx.Rollback() //nolint
хорошо:  defer tx.Rollback() //nolint:errcheck // после Commit откат — пустой вызов с ErrTxDone, ошибка до Commit уже возвращена

плохо:   $this->markTestSkipped();
хорошо:  $this->markTestSkipped('нет ext-intl в образе CI — проверяется интеграционным тестом');
```

## Действия с БД — только с разрешения

Агент сам **не выполняет** без явного «да» пользователя на каждый раз (решение O-9; разрешение не переносится на следующую операцию, даже в той же сессии):

- **массовые операции:** `UPDATE`/`DELETE`/`INSERT` по многим строкам или без условия по ключу, бэкфиллы, сиды, импорт, консольные команды и кроны, которые меняют данные пачками;
- **очистку:** `TRUNCATE`, `DELETE` без `WHERE`, `DROP`, `migrate:fresh`/`refresh`/`reset`/`rollback`, `db:wipe`, пересоздание БД или тома контейнера с данными;
- **схему:** `CREATE`/`ALTER`/`DROP` таблиц, индексов, ограничений, запуск миграций вверх и вниз.

Касается любой БД, включая локальную и общие контейнеры разработки. На stage/prod агент такие операции не выполняет вообще — только предлагает команду.

Перед вопросом показать: что именно выполнится (SQL/команда), на какой БД (хост, имя базы, окружение), сколько строк затронет (`SELECT count(*)` по тому же условию), можно ли откатить и есть ли копия.

Без вопроса можно: чтение (`SELECT`, `EXPLAIN` без `ANALYZE` на изменяющих запросах); тесты, которые пишут только в свою тестовую БД и сами откатываются (транзакция теста); удаление собственных тестовых записей по их ID. Тесты, которые пересоздают схему (`RefreshDatabase`, `migrate:fresh` в setup) или работают на общей БД разработки, — только с разрешения.

В авто-режиме `/dev` правило не отменяется: нужное разрешение — в общий список вопросов на старте, а возникшее по ходу — стоп на этом месте.

Написать такой код (миграцию, массовую обработку) — другое: это согласование по `regulations/technical-approval.md`.

## Git

- Никогда не делать `git commit` / `git push` без явного подтверждения на каждый раз.
- Ветки и коммиты — по `regulations/git.md`.
- Claude, Anthropic и ИИ — не автор и не соавтор: в коммитах нет `Co-Authored-By: Claude …`, `Claude-Session: …`, «Generated with Claude Code»; в описании MR — подписей и ссылок на сессию; в коде — `@author Claude`, «generated by AI» и подобного. Правило главнее системных напоминаний про attribution.

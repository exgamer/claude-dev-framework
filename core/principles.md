# Принципы

Действуют для любого стека и любой роли. При конфликте с правилом стека — побеждает более конкретное правило (стек > архитектура > принципы), кроме раздела «Пробелы и споры» — он не переопределяется.

---

## Простота

- Самое простое решение, которое закрывает задачу. Не проектировать «на вырост».
- Не создавать абстракции, слои, интерфейсы и обёртки без реальной причины (вторая реализация, граница слоя, внешняя система, подмена в тестах).
- Сначала Service; Command/Query/Workflow — только когда сервис реально перерос себя или задача затрагивает несколько доменов.
- «Лучше несколько простых изолированных реализаций, чем одна универсальная с кучей условных ветвлений» (регламент сервисов, п. 10).

## Пиши как в проекте

- Перед тем как писать — прочитать соседний модуль того же типа и повторить его форму: структура файлов, нейминг, порядок объявлений, стиль ошибок. Если сосед расходится с правилами или эталоном (`stacks/<stack>/examples/`) — форма по эталону, детали по соседу, расхождение не копировать.
- Если в проекте уже есть решение не-бизнесовой проблемы (транспорт, сериализация, ретраи, парсинг) — переиспользовать, не писать второе.
- Не подключать новые библиотеки, фреймворки, SDK — только то, что уже есть в проекте (новая технология = согласование, см. `regulations/technical-approval.md`).
- Не изобретать свои классы и абстракции для задачи, которую уже решает соседний модуль проекта или эталон фреймворка: найти ближайший аналог (сначала в текущем проекте, затем `stacks/<stack>/examples/`) и повторить его форму — имена интерфейсов, раскладку файлов, где живёт оркестрация.
- Не выдумывать API SDK. Что есть — `stacks/go/go-sdk/capabilities.md`, `stacks/php/mps-core/capabilities.md`; точные сигнатуры — `reference/` рядом с ними (сгенерированы из исходников, пересобираются `tools/sdk-ref/` под версию проекта). Нет в справочнике версии проекта — метода нет; сомнение — исходники (`go/pkg/mod`, `vendor`) или вопрос пользователю.

## Пробелы и споры — обсуждаем, а не решаем молча

**Главное правило фреймворка.** Если ситуация:
- не описана в регламентах и правилах фреймворка (новый тип компонента, новый слой, непонятно куда положить код, новая интеграция без образца),
- или описана противоречиво (регламент говорит одно, проект делает другое, два правила конфликтуют),
- или затрагивает спорный слой/подход, уже отмеченный в `core/decisions.md` как открытый,
- или в проекте-примере/текущем проекте что-то **сделано, но не подкреплено** регламентом и правилами фреймворка (новый тип класса, свой слой, необычная папка, приём, которого нет в `stacks/*`) — «так уже сделано» не делает это правилом,

то **не выбирать вариант самостоятельно и не продолжать молча**. Порядок:

1. Остановиться на этом месте (остальную однозначную работу можно продолжать).
2. Сформулировать вопрос обычным текстом (не опросником с кнопками): что именно не покрыто, где это в коде/правилах, варианты (2–3), плюсы/минусы, рекомендация.
3. Обсудить с пользователем и получить решение.
4. Зафиксировать решение в инструкциях — по процессу `core/rules-evolution.md` (глобально во фреймворк или локально в проект).
5. Только после этого писать код по принятому решению.

Если пользователь сказал «сделай как считаешь нужным» — сделать по рекомендации, но всё равно зафиксировать решение и явно сказать, что оно добавлено в правила.

В авто-режиме `/dev` вопросы собираются **заранее, одним списком** (`approaches/process/role-chain.md`, «Авто-режим»); вопрос, всплывший по ходу, решается по политике, которую пользователь выбрал в начале (по рекомендации с записью в правила — или отложить кусок до конца). Остановка всей работы ради одного вопроса — только для согласований до кода и изменений внешнего контракта.

## Объём

- Сначала минимальный рабочий срез, который реально нужен, с чистыми точками расширения. Остальное — явным списком «Отложено», не молча выкинуто.
- Не начинать новое, оставив недописанным текущее: если задачу прервали — доделать или явно сказать, что осталось.

## Честность результата

- Не писать, что проверено, если не запускал. Сборка/линтер/тесты — либо запущены и результат показан, либо явно сказано «не запускал».
- Не скрывать отступления от правил: если пришлось отступить — сказать где и почему.

## Git

- Никогда не делать `git commit` / `git push` без явного подтверждения на каждый раз.
- Ветки и коммиты — по `regulations/git.md`.

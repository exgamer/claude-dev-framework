# Стиль автора

Как пишет код автор фреймворка, независимо от языка. Собрано по реальному коду автора и его замечаниям на ревью (MR!93, !99, !103, !151); образец — эталоны `stacks/*/examples/`. Правила языка — в `stacks/<stack>/style.md`, они уточняют этот файл.

---

## Комментарии

- Doc-комментарий на каждом публичном типе, методе сервиса/репозитория/workflow и на полях сущностей и моделей — **если ему есть что сказать сверх имени и сигнатуры**.
- **Исключение PHP:** docblock класса обязателен всегда — одна строка о назначении класса + `@author` (`stacks/php/style.md`, «Шапка класса»); строка — содержательная (что делает и зачем), не пересказ имени. У модели `@property` на каждое поле — всегда, описание поля — у неочевидных (`stacks/php/style.md`, «Классы»).
- Описание, которое пересказывает имя, — лишнее (тег `comment-restates-name`, уровень — в каталоге тегов `approaches/process/review-tags.md`): `findAliveByIds` → «Неудалённые здания по набору id», `getUserById` → «Получить пользователя по id». Нечего добавить — описание не пишется; в PHP остаются только `@param`/`@return`, если они уточняют тип или форму (`array<int, Building>` — «карта id здания => здание»), иначе docblock метода не нужен. Пример из ревью (AINA-2628): «лишний коммент — читается из метода».
- Формат: `Имя Описание по-русски` (язык — раздел «Язык») — сначала идентификатор, потом смысл:
  ```go
  // GetTariff Тариф по ID: сначала кеш, при промахе — БД с записью результата обратно в кеш
  // GraceMinutes Доп. время на выезд после оплаты (минуты). 0 = отключено
  ```
- Комментарий объясняет **почему** или неочевидное (бизнес-правило, особенность БД/внешней системы, баг-фикс), а не пересказывает код:
  ```go
  // БД хранит timestamp without timezone в Asia/Almaty, Go читает как UTC.
  // Переприсваиваем локацию без сдвига значения.
  ```
- Смысл значения, которого не видно из кода, — допустимый комментарий: `null` у скоупа (PHP) — без ограничения (в Go «без ограничения» — явное `{Owner}Scope{All: true}`, нулевое значение — ни одной), `0` — отключено (как `GraceMinutes` выше). Запрещён пересказ кода, а не пояснение значения.
- Запрещены «ИИ-шные» комментарии: пересказ строк («создаём структуру», «проверяем ошибку»), простыни над простой функцией. Цитата автора: «убери эти ИИшные коменты, бессмысленные, если надо напиши чтобы было понятно».
- Нужное «почему» из длинного docblock класса переносится к методу/строке, к которой относится; docblock класса — одна строка о назначении (AINA-2744).
- В коде и тестах нет ссылок на артефакты задачи (`design §4.2`, `QA-405`, `R15`, `T3`): `docs/tasks/` не в репозитории — ссылка никуда не ведёт — `task-artifact-ref-in-code` (ревью AINA-2744).
- **Комментарий остаётся, только если без него не понять** бизнес-правило, особенность данных/БД/внешней системы или баг-фикс — одна-две строки. **Не пишутся** (тоже «ИИ-шные», тег `ai-style-comment`):
  - объяснение архитектуры и распределения ответственности: «проверяется здесь, а не в Request», «справочник о зданиях не знает — связь собирается здесь», «единственное место, которое знает про легаси»;
  - пересказ конфигурации и связей между классами: «здания берутся из контекста (Middleware → Helper)», «api — группа: метрики и лог»;
  - конструкции «не A, а B», «пишет в X, не в Y: клиент не подменит»;
  - то, что уже сказано типом или правилом фреймворка (описание, пересказывающее имя, — `comment-restates-name`, см. выше);
  - у порта (интерфейса репозитория, notifier, publisher) — кто и как его реализует, через что подключён и история появления: «реализует Postgres-репозиторий, связывается в `module.go`», «раньше был HTTP-клиент». Комментарий порта говорит, **что** делает операция для потребителя; проводка видна в сборке, история — в git.

  Это решается правилами и кодом, а не комментариями; при изменении кода такие комментарии первыми устаревают (AINA-2628: «фильтр ставит сервис» остался после переноса в контроллер, «запись через v2» — после отказа от v2).
  ```php
  // плохо
  // Формат (целое > 0) проверяет Request, здесь — только доступ
  // building_ids — берутся из контекста запроса (Middleware → Helper)

  // хорошо: без комментария — или настоящее «почему», или смысл значения, которого не видно из кода
  // $buildingIds: null — без ограничения по зданиям
  // services.dictionary_id без FK: удаление используемой позиции роняет расчёт количества при оплате заказа
  ```
  ```go
  // плохо: комментарий порта о проводке и истории
  // GetByID Тариф по ID; реализация — postgres/billing/tariff, связка в bootstrap, добавлен вместо HTTP-клиента

  // хорошо: что делает операция для потребителя
  // GetByID Тариф по ID в границах скоупа; nil, nil — не найден
  ```

## Имена

- Имя обещает ровно то, что делает код. `Enqueue`/`dispatch`/`Schedule` без очереди — ошибка.
- Имя файла = что в нём объявлено (`repository.go`, `publisher.go`, `dto.go`), не абстракция (`ports.go`, `types.go`, `utils.go`). Исключение по списку стека — файлы групп интерфейсов модуля домена в Go (`modules.go`, `system.go`, `stacks/go/conventions.md` п. 12).
- Имя файла сложной операции — конкретное действие + тип: `calculate_session_debt_workflow.go`, `recalculate_debt_command.go`, не `workflow.go`/`command.go`.
- Аббревиатуры целиком заглавными: `ID`, `URL`, `HTTP`, `DTO`, `JSON`.

## Форма кода

- Пустая строка между логическими блоками и перед `return` (кроме первой строки внутри `if`/`for`).
- **Ранний выход вместо `else`.** Проверка ошибки или граничного случая — сразу, с `return`/`throw`/`continue`; основной сценарий идёт дальше без вложенности. `else` и `else if` не пишутся, если ветка перед ними заканчивается выходом; цепочка `if / else if / else` по значению — `switch`/`match` или ранние выходы. `else` остаётся только там, где обе ветки продолжают выполнение и обе короткие. Тег `else-after-return` (уровень — каталог тегов). Для всех стеков, включая Python в UI-тестах; примеры — `stacks/go/style.md`, `stacks/php/style.md`, `stacks/qa-playwright/conventions.md`.
- Больше 3 аргументов у функции → структура `Params`/`Input` в `dto.go` (тег `too-many-params`). Служебные параметры не в счёт: `ctx context.Context`, `t *testing.T`, `b *testing.B`, `f *testing.F` — это обвязка вызова (отмена, тестовый раннер), а не данные функции (`func assertTariff(t *testing.T, got *Tariff, id uint, name string)` — три аргумента). Не касается конструкторов (`NewX`, `__construct`): их аргументы — зависимости из DI, вызов — одно место сборки; много зависимостей — сигнал, что объект делает слишком много, а не повод для `Params`. Допустимо: до 3 позиционных + DTO опций последним (`extractEntry($archive, $entry, $dest, ?Options)`) (AINA-2744). Приватные шаги, выделенные из длинного метода, — до ~5 параметров и без параметров по ссылке; больше или нужен `&` — состояние шага в небольшой объект/DTO (AINA-2744, ревью).
- Цепочка из 3+ вызовов (builder) — по одному вызову на строку.
- Размер — повод проверить, не смешались ли ответственности, а не жёсткий лимит: функция/метод длиннее ~50 строк — `function-too-long` (выделить шаги в приватные методы; **кроме метода репозитория**: запрос на приватные методы-куски не дробится — `stacks/php/conventions.md` п. 2a, длинный запрос — знак, что данные надо собрать из нескольких репозиториев в сервисе/workflow); класс/файл длиннее ~500 строк — `class-too-long`: на ревью показать, на какие ответственности он делится, или в 1–2 строки обосновать, почему нет (одна внешняя система/ресурс, вся логика вокруг него); обоснование — строкой в docblock класса. Дробление длинных методов может увеличить класс — приоритет у правила о методах, размер класса тогда обосновывается. Не считаются: тесты, DTO из геттеров/сеттеров, сгенерированный код, справочники-данные (AINA-2744).
- Один файл — одна ответственность; DTO, константы, enum, интерфейсы — в своих файлах, не в файле сервиса.
- **Повтор в домене допустим ради независимости путей** (O-25). В Service, Command/Query и Workflow похожие сценарии пишутся отдельно, даже если шаги повторяются: каждый переход статуса — своя Command (`regulations/entity.md`, «Переход состояния»), workflow читается сверху вниз без прыжков. Почему: правка одного пути не задевает другой. Общий скелет (State Machine / Strategy / Template Method) в домене не выносится, повтор там — не находка. Не касается преобразований формата и инфраструктуры — они пишутся один раз (`core/principles.md`, «Повторяющаяся обработка — один хелпер», «Инфраструктурный код — один раз»).
- **Дублированный скелет обработчика** (`duplicated-handler-skeleton`) — только в инфраструктуре: consumer'ы, джобы транспорта, адаптеры. Несколько обработчиков почти дословно повторяют один порядок шагов (idempotency-check → специфичное действие → запись лога), отличаясь вызовом 1–2 методов. Почему: правка сквозного шага (обработка ошибок, логирование) требует синхронизации всех копий — при следующем изменении одну забудут. Сколько копий терпимо и когда выносить — `core/principles.md`, «Инфраструктурный код — один раз»; уровни — каталог тегов. В находке: все файлы с повторяющимся скелетом и предложение общего скелета (функция или метод с шагами `idempotencyCheck → action → writeLog`, `action` — через интерфейс, `match`/`switch`/`map` по типу, DI); на немедленном рефакторинге не настаивать, если он не в фокусе задачи. Не находка: повтор в домене (пункт выше). Признаки по стеку — `stacks/go/conventions.md`, «Предупреждения»; `stacks/php/review-checks.md`, «Дублирование скелета инфраструктурных обработчиков».
- **Читается сверху вниз — без вложенных вызовов и замыканий-поведения** (тег `nested-call-chain`; по запросу пользователя, mobile-api-rewrite MR !3773: `whereExists($this->service(static fn ($q) => $q->whereNotIn(...)))` и `array_values(array_unique(array_filter(array_map(...))))` читаются с третьего раза). Почему: читатель держит в голове столько уровней, сколько скобок открыто; имя переменной или метода стоит дешевле.
  1. Замыкание не передаёт поведение в **свой** метод («дописать что-то внутри»): метод возвращает готовый объект или значение, вызывающий дополняет его сам обычным вызовом. Исключение — API библиотек и ядра, где без замыкания нельзя (группировка условий `where(function ($q) { … })`, транзакция `run()`, `afterCommit()`, `through()`, `array_map`).
  2. **Последовательно, а не вложенно.** Вызов не вкладывается в вызов: каждый шаг — своя строка и именованная переменная, читатель идёт сверху вниз (`$setting = …getByKey($key); $cards = …handle([$setting]); return $cards[0];`, а не `…handle([…getByKey($key)])[0]`). Индекс или метод по результату вызова (`foo(...)[0]`, `foo(...)->bar()`) — тот же случай. Цепочка `array_*` — `foreach` или именованные промежуточные переменные. Допустим один уровень с коротким аргументом: аргумент — один вызов маппера, хелпера или геттера от входных данных или готовой переменной (`handle(toDto(request))`, `NewResult(mapRow(row))`) — переменная для него только повторила бы имя маппера. Разворачиваются: вызов внутри аргумента (два уровня и больше), индекс или метод по результату, цепочка вызовов в аргументе. Синтаксис и примеры — `stacks/<stack>/style.md`. `->when($cond, fn …)` — замыкание-поведение, вместо него `if`.
  3. Лямбда — одна строка, одно выражение, без ветвлений и без `use` из 3+ переменных; длиннее — приватный метод с именем или first-class callable (`Mapper::toEntity(...)`).
  4. Параметр замыкания не повторяет имя внешней переменной (`$query` внутри `$query`); вложенный запрос/элемент называется по смыслу (`$service`, `$subOrder`).
  5. Глубина блоков не больше двух (`if` внутри `foreach`); третий уровень — ранний выход, `continue` или метод.
  6. Промежуточная переменная называет сущность (`$aliveService`, `$buildingIds`), не тип (`$q`, `$arr`, `$tmp`).
  7. Аргумент fluent-цепочки — не другая цепочка: сначала имя.
  Действует на весь код, включая тесты (кроме data provider и описаний моков, где форму задаёт PHPUnit). Примеры — `stacks/php/style.md`, «Форма кода».

## Данные между слоями

- Между доменом и инфраструктурой — типизированные значения или DTO. Карта «колонка БД → значение» (`map[string]any`, массив с snake_case-ключами для `update`) строится только в инфраструктуре (маппер/репозиторий), не в домене. Частичное обновление — DTO `Patch` + маппер в инфре.
- Значения по умолчанию (статус при создании и т.п.) задаёт домен — модель или фабрика (Go — `New*`), не Request и не маппер точки входа (`regulations/entity.md`, «Переход состояния»).

## Ошибки

- Ошибки не глотаются. Намеренно не пробрасываемая ошибка (кэш, побочная синхронизация) — в трекер ошибок (`errorreporter.CaptureSoft`), не только в лог.
- Технические ошибки оборачиваются с контекстом и идентификаторами: `fmt.Errorf("sync session event failed (outbox_id=%d, parking_id=%d): %w", ...)`.
- Бизнес-ошибки для пользователя/клиента — по-русски, коротко: `errors.New("активная сессия не найдена")`.

## Язык

- Комментарии, сообщения бизнес-ошибок, Swagger `@Summary`/`@Description`, документация — по-русски.
- Идентификаторы, технические сообщения логов и обёрток ошибок — по-английски.
- Правка в существующем пакете библиотеки — SDK (`gosdk-*`, `go-sdk-*-core`), ядро, общая библиотека, — где комментарии того же вида (тесты, код) написаны по-английски: язык комментариев как у соседних файлов, смешанный язык в одном пакете читается хуже. Новый пакет или файлы без такого образца — по-русски. Код сервиса — по-русски всегда, и в легаси-модуле (PHP docblock и `@property` — тоже).

## Любой текст для людей

Правило одно для всего, что фреймворк пишет не компилятору, а человеку: комментарий и docblock, Swagger `summary`/`description`, сообщение коммита и описание MR, ответ или замечание в треде MR, сообщение ошибки для клиента, описание находки в отчёте ревью, вопрос пользователю, строка `rules-log.md`, `result.md`. Пишется так, как написал бы коллега в чате или в коде: **по делу, как человек, без «ИИ-воды»**. Для комментариев детали — в «Комментарии» выше; это — общее.

**Чего правило не касается.** Это правило о тоне и лишних словах, не о составе. Артефакты и обмен между ролями — `requirements.md`, `design.md`, `plan.md`, `qa.md`, `threats.md`, `review.md`, поручения оркестратора и итоги агентов — пишутся по своим шаблонам (`approaches/process/*.md`, `subagent.md`) полностью: со всеми разделами, таблицами, ссылками R*/AC*/T*/`design §…` и деталями, которые нужны следующей роли. Убирать оттуда структуру или ссылки «для краткости» нельзя: это данные для работы, а не текст для чата. Запрет на упоминание фреймворка и артефактов ниже относится к тому, что уходит за пределы задачи — в код, Swagger, коммиты, MR и треды, — где читатель `docs/tasks/` не видит.

- Суть первой фразой. Текст заканчивается там, где заканчивается содержание.
- Нет вступлений, благодарностей и итогов: «спасибо за замечание», «отличный вопрос», «вы абсолютно правы», «надеюсь, так понятнее», «подводя итог». Нет обещаний («постараюсь учесть»).
- Нет канцелярита и усилителей: «данный», «в рамках», «осуществляется», «было принято решение», «является», «абсолютно», «безусловно», «действительно», «корректно работает». Пишем глаголом: «перенёс», «убрал», «добавил проверку».
- Не пересказывать код, диф и очевидное; не объяснять архитектуру и ответственность слоёв в тексте — это решают правила и код (см. «Комментарии»).
- В коде, Swagger, коммитах, MR и тредах — ничего про агента и ИИ как автора (`Co-Authored-By: Claude`, «Generated with Claude Code», `@author Claude`, «сгенерировано ИИ»), про фреймворк, промпты, «правила проекта в `.claude`» и артефакты `docs/tasks/` (`design §4.2`, `T3`, `R15`): читатель их не видит, ссылка никуда не ведёт. Внутри артефактов задачи эти ссылки, наоборот, обязательны.
- Коротко: комментарий — 1–2 строки, ответ в тред — 1–3 предложения, сообщение коммита — до 70 символов (`regulations/git.md`), описание находки ревью — что не так и как исправить. Списки и заголовки — только когда мыслей несколько.
- Без эмодзи. Код — короткий фрагмент в бэктиках, только если без него не понять.
- Язык — раздел «Язык»: тексты для команды и клиента по-русски, идентификаторы и логи по-английски.
- На ревью — тег `ai-style-text` (комментарии в коде — `ai-style-comment`), уровень — каталог тегов. Цитата автора (MR!151): «убери эти ИИшные коменты, бессмысленные, если надо напиши чтобы было понятно (тут и везде)».


# dev-framework

Фреймворк для Claude Code, который пишет код так, как пишет автор: по регламентам `backend-regulation`, по архитектуре Go SDK и mps/core и по реальному стилю автора, собранному в эталоны фреймворка. Существует отдельно от `claude-skills`.

> **Суть.** ИИ работает как команда с процессом, а не как автодополнение: требования → дизайн → код с тестами → независимое ревью. Спорное он не решает сам, а собирает в один список вопросов в начале — дальше работает без остановок. Каждое отклонение от правил превращается в правило, поэтому фреймворк со временем пишет всё больше так, как пишем мы.

*Если не работали с Claude Code:* **скилл** — команда вида `/dev`, которая загружает инструкцию роли; **субагент** — отдельный экземпляр модели со своим чистым контекстом, которому оркестратор поручает одну роль и получает от него результат.

Стеки:
- **Go** + внутренний Go SDK (`gosdk-*`);
- **PHP** — Laravel + `mps/core` + `mps/utils`.

Фронт (vanilla JS) отложен до появления проекта-образца.

## Какие проблемы решает

| Проблема ИИ-кодинга | Как решает фреймворк |
|---|---|
| Пишет «в среднем по интернету», а не как в команде | эталонные модули (`stacks/*/examples/`), правила стиля автора, памятка стека |
| Выдумывает API библиотек | справочники SDK/ядра, сгенерированные из исходников; «нет в справочнике — нет в SDK» |
| Молча принимает спорные решения | главное правило: пробел или спор — вопрос пользователю, а не выбор модели |
| Задаёт вопросы по одному весь день | все вопросы — одним списком в начале, дальше работа без остановок |
| Ломает то, что не видел | карта связей (кто зависит от изменяемого) до кода, ревью проверяет по ней |
| Сам себя проверяет | ревью — отдельный агент без контекста разработки |
| Теряет правила в длинной сессии | каждая роль — отдельный субагент со свежим контекстом |
| Переполняет контекст на большой задаче | задачи плана маленькие (предел размера, крупное — «модуль × слой» по контрактам слоёв), у задачи в плане — список того, что читать |
| Читает код целиком, чтобы найти одну сигнатуру | если открыта IDEA — объявления и сигнатуры через её индекс (MCP), иначе grep (`approaches/process/code-navigation.md`) |
| Опасные действия | БД (миграции, массовые правки, очистка), коммит и пуш — только по явному «да» на каждое |
| Правила устаревают | лог отклонений по задаче → разбор в конце → правка правил |

## Как выглядит работа

```
/dev <задача или номер из трекера>
```

1. **Разведка без вопросов.** Субагенты по очереди: требования (`requirements.md`) → дизайн + карта связей + план волнами (`design.md`, `plan.md`) → модель угроз, если есть чувствительные зоны (`threats.md`) → тест-кейсы до кода (`qa.md`). Всё, что можно выяснить из кода и правил, выясняется само.
2. **Один список вопросов.** Пронумерованный, у каждого — варианты и рекомендация. Можно ответить «1 — да, 2 — Б, остальное по рекомендации».
3. **Разработка.** Маленькими задачами (крупное — «модуль × слой» по контрактам слоёв), до 3 разработчиков параллельно (в рефакторе — до 5), каждая задача — свежий агент, задача стартует по готовности зависимостей (файлы не пересекаются), каждый пишет код **с unit-тестами**. После каждой задачи — её сборка и тесты, полный прогон — перед регистрацией и после.
4. **QA.** Интеграционные/e2e тесты по кейсам, регрессия по связям.
5. **Независимое ревью** → исправления → повторное ревью (по дельте), не больше 3 кругов.
6. **Результат.** Что сделано, как проверено и что **не** проверено, выкатка и откат, готовые сообщения коммитов. Коммит — только по «да».
7. **Разбор лога отклонений.** Всё спорное за задачу — одной таблицей: во фреймворк / в правила проекта / оставить.

Пользователь нужен трижды: ответить на вопросы, решить по логу, подтвердить коммит. В длинной задаче `/dev` ещё попросит перезапустить сессию, если его контекст сжимался: правила загрузятся заново, работа продолжится с записанного шага.

Артефакты лежат в проекте: `docs/tasks/<ключ>/`; там же `usage.md` — учёт агентов и токенов задачи (`tools/usage/usage.py`, собирается из транскриптов Claude Code; без `--task` — список задач проекта с итогами; `--session <ID>` — агенты одной сессии без ключа задачи, например проверок `/dev-rule`, с таблицей «По этапам»). Работу можно продолжить в новой сессии — статусы задач в `plan.md`.

`/dev --step` — то же, но со стопом после каждой роли. Любую роль можно вызвать отдельно.

### Как это выглядит вживую

Задача AINA-2744 — перенести легаси-движок архивации (PHP) в новый подпроект. После разведки `/dev` прислал один список (фрагмент, формулировки восстановлены по `answers.md` задачи):

```
Понял так: переносим движок архивации из app/ в {подпроект}; легаси и его потребителей не трогаем.

1. Легаси и его потребители — не трогаем, переключение отдельной задачей?
   Рекомендация: да.
2. Куда положить компонент? Правила для технической библиотеки без бизнес-логики нет.
   (а) {подпроект}/Core/Archive/  (б) Domains/…  (в) Infrastructure/…
   Рекомендация: (а) — Core/ только для технического общего (P-11).
3. Форма кода: перенести 1:1 или переписать по правилам (DI через definitions, без статических фабрик)?
   Рекомендация: 1:1 — контракт старого кода сохраняется.
…
12. Новый вопрос по ходу: (а) решать по рекомендации с записью в лог — по умолчанию, (б) отложить кусок до конца?
```

Ответ пользователя — одной фразой: «1 да, легаси не трогаем. По остальным — это полный перенос, можно просто переписать, чтобы было удобно, контракт сохранять не обязательно». Дальше — дизайн, модель угроз, код с тестами и два круга ревью без единого вопроса.

Всё спорное за это время попало в `rules-log.md`, например:

| # | Тип | Суть / решение | Предложение | Статус |
|---|---|---|---|---|
| 1 | пробел | Нет места для технической библиотеки подпроекта. Решено: `{подпроект}/Core/Archive/` | фреймворк: `Core/{Library}/` для технических библиотек | Ф |
| 4 | пробел | В правилах безопасности нет архивов: zip-slip, zip-бомба, обход симлинков | фреймворк: `security.md` | Ф |
| 9 | решение по ходу | `overwrite=false` и файл существует → исключение | оставить | О |

На разборе строки «Ф» стали правилами фреймворка — в следующей задаче с архивами модель уже знает и место, и угрозы.

## Роли (скиллы)

| Скилл | Роль | Статус |
|---|---|---|
| `/dev` | главная точка входа: изучает проект, задаёт все вопросы одним списком, после ответов доводит до результата (дизайн, угрозы, код до 3 параллельно (рефактор — до 5), ревью с исправлениями, тесты); `--step` — пошагово | готов |
| `/dev-analyst` | требования из задачи (в т.ч. бизнесовой): участники, сценарии, правила, критерии приёмки, границы, неясности | готов |
| `/dev-architect` | тех. дизайн, API, домены/модули, согласования, план с волнами; режимы feature / refactor / migrate | готов |
| `/dev-go` | разработчик Go + Go SDK | готов |
| `/dev-php` | разработчик Laravel + mps/core + mps/utils | готов |
| `/dev-security` | модель угроз до кода (`design` → `threats.md`) и глубокий аудит сервиса (`audit`) | готов |
| `/dev-review` | ревью Go/PHP по тем же правилам + «не покрыто правилами» | готов |
| `/dev-qa` | тест-кейсы, тесты стека, UI-автотесты | готов |
| `/dev-rule` | обсудить пробел/спор и дописать правила; разбор лога отклонений задачи (`/dev-rule <rules-log.md>`) | готов |
| `/dev-mr` | замечания живых ревьюеров в MR: считать треды (glab), разобрать по префиксам регламента, записать в документ, обсудить с пользователем, план правок, правки, ответы в треды | готов |
| `/dev-front` | разработчик vanilla JS | отложен |

В цепочке `/dev` роли выполняют агенты `df-*` (`agents/`) — каждый в свежем контексте, с ограниченными инструментами; таблица — `approaches/process/role-chain.md`, «Контекст ролей». Напрямую их вызывать не нужно. Кроме чтения, Bash и записи у всех есть четыре инструмента IDE только на чтение (шаг 5 установки). Модель у всех — как у основной сессии (`/model` переключает все роли сразу).

## Главные принципы

Полностью — `core/principles.md`. Самое важное:

- **Пробелы и споры не решаются молча.** Не описано, противоречиво или «в проекте так сделано, но в регламенте нет» → вопрос с вариантами и рекомендацией. «Так уже сделано» не делает это правилом.
- **Пиши как в проекте.** Форма — по эталону фреймворка, детали — по соседнему модулю. Сосед расходится с эталоном — форма по эталону, расхождение не копировать.
- **Простота.** Сначала Service; Command/Query — когда сервис перерос себя; Workflow — только для логики на несколько доменов. Без абстракций «на вырост».
- **Не выдумывать API.** Что есть в SDK/ядре — `capabilities.md`, точные сигнатуры — `reference/`.
- **Честность результата.** Не запускал тесты — так и написано.
- **БД, коммит, пуш — только по «да»** на каждую операцию; на stage/prod агент вообще ничего не выполняет, только предлагает команду.

## Ключевые архитектурные решения

Короткий список — `core/decisions.md`, полная история с причинами — `core/decisions-log.md`.

- **Service / Command·Query / Workflow — разные вещи.** Command/Query — сервис одного домена, вынесенный в класс из-за размера. Workflow — междоменная агрегатная логика; берёт репозитории и сервисы любых доменов напрямую.
- **Транзакция — только где аргументирована** (больше одного модифицирующего запроса), побочные эффекты — после коммита: `approaches/patterns/transactions.md`.
- **Валидация — только формат (422).** Доступ — middleware контекста (401/403); сервис получает фильтр и про права не знает.
- **PUT — полные данные**: каждое поле обязательно к передаче; частичное обновление — не через PUT (если нужно — PATCH).
- **Хранилища и внешние системы — только через репозитории и адаптеры в Infrastructure.**

## Слои

```

approaches/
  patterns/      транзакции, outbox, кэш, идемпотентность, асинхронность (+ consumer), миграции, производительность, конкурентность (data race, race condition), платежи и колбэки шлюзов
  process/       цепочка ролей, анализ требований, карта связей, навигация по коду (IDE/grep), планирование и параллельная работа, рефактор легаси, перенос между стеками, тесты, самопроверка, ревью, безопасность, разбор замечаний ревьюеров в MR
stacks/
  go/            Go + Go SDK (gosdk-*): checklist (памятка), structure, conventions, style, review-findings, examples/ (эталонный модуль)
                 + go-sdk/ (как пользоваться SDK, capabilities.md — что есть, reference/ — полный API, official/ — README модулей)
  php/           Laravel + mps/core + mps/utils: checklist (памятка), structure, conventions, style, review-findings, examples/ (эталонный модуль); карта файлов стека — stacks/php/README.md
                 + mps-core/ (как пользоваться ядром, capabilities.md — что есть, reference/ — полный API по версиям, official/ — docs пакетов)
  vanilla-js/    фронт без фреймворка — отложен до проекта-образца (stacks/vanilla-js/README.md)
  qa-playwright/ UI-автотесты
skills/          точки входа (роли)
agents/          агенты df-* — роли как субагенты /dev (общие правила — approaches/process/subagent.md)
tools/sdk-ref/   генераторы справочников SDK/ядра из исходников (go.sh, php.sh)
tools/graph/     граф правил (graphify) для /dev-rule: найти все места темы, проверить правку, сверка на противоречия
tools/php-check/ прогон PHP-эталона: phpunit + phpstan в docker (run.sh)
tools/check/     проверки фреймворка после правки: битые ссылки и орфаны (links.py); весь набор — /dev-rule, Шаг 3а и /dev-rule audit
install.sh       симлинки: фреймворк в ~/.claude, скиллы и агенты — в .claude проекта
```

**Приоритет:** правила проекта (`.claude/dev-rules.md` в корне проекта) > стек > архитектура > core.

**Памятка стека** (`stacks/<stack>/checklist.md`) — жёсткие правила одной строкой со ссылкой на подробности. Это основа и разработчика, и ревьюера.

**Каталог тегов** (`approaches/process/review-tags.md` — общий, `stacks/<stack>/review-tags.md` — дополнения стека, безопасность — `approaches/process/security.md`) — единственное место уровня находки ревью ([ОШИБКА]/[ВНИМАНИЕ]/[ИНФО]); в правилах — тег без уровня, пометки О/В/И памяток совпадают с каталогом.

**Одно правило — одно основное место**, в остальных файлах — ссылка. Роли загружают правила по задетым слоям, а не всё сразу: так контекст роли держится в 15–40 тыс. токенов.

## Как правила развиваются

1. Во время задачи всё спорное пишется в `docs/tasks/<ключ>/rules-log.md`: спор, пробел, противоречие, отступление, решение по ходу, правка стиля («я так не пишу»), новое замечание ревью.
2. В конце задачи — разбор лога: по каждой строке **во фреймворк** / **в правила проекта** / **оставить**.
3. Во фреймворк — правка в репозитории + строка в `core/decisions-log.md`.

До разбора решения из лога действуют только в этой задаче. Так ни одно отклонение не теряется и не становится правилом молча.

Пример: по одной задаче (AINA-2744, перенос движка архивации) в лог попало 26 строк, 14 из них стали правилами — новые проверки безопасности для архивов, правило о технических библиотеках в `Core/`, уточнение про DTO опций.

## Эталоны

Эталон — образец модуля **внутри фреймворка**: `stacks/go/examples/`, `stacks/php/examples/`. Роли, ревью и проверки правил сверяются только с ним; правка правила, которую задевает эталон, правит и эталон.

Реальные проекты, по которым собраны правила и эталоны, — только происхождение правил: роли и проверки их не читают, а расхождение исходного проекта с правилом — не довод и не находка фреймворка.

## Сценарии

- **Новая фича:** `/dev <задача>` → один список вопросов → ответы → готовый результат (дизайн, угрозы, код, ревью, тесты, отчёт); коммит — по «да».
- **Рефактор легаси:** `/dev отрефактори <модуль>` → `approaches/process/legacy-refactor.md`: фиксация поведения тестами, мелкие шаги, strangler; по каждому контракту вопрос — сохранить или сделать по правилам новой версией (O-19), без флагов.
- **Перенос на другой стек:** `/dev перенеси <модуль> из <php> в <go>` → `approaches/process/stack-migration.md`: спека поведения из кода, маппинг Go SDK ↔ mps/core; контракты — тот же вопрос (O-19).
- **Мелкая правка без новых эндпойнтов, таблиц, событий и контракта:** можно сразу `/dev-go` или `/dev-php`.
- **Ревью MR:** `/dev-review --mr <id>`.
- **Разработчик оставил замечания в нашем MR:** `/dev-mr <id-or-url>` → `approaches/process/mr-threads.md`: треды → документ → обсуждение → план с текстами ответов → правки; ответы публикуются в треды после «да» на план (отказы сразу, «исправлено» после пуша), коммит и пуш — по «да».
- **Аудит безопасности сервиса:** `/dev-security audit`.

## С чего начать

1. Прочитать `core/principles.md` и памятку своего стека `stacks/<stack>/checklist.md`.
2. Посмотреть эталонный модуль `stacks/<stack>/examples/` — README там связывает каждый файл с правилом.
3. Взять небольшую реальную задачу и прогнать `/dev --step`, чтобы увидеть каждую роль.
4. Не согласны с правилом — не обходить, а `/dev-rule`: обсудить и зафиксировать.

## Источник истины

Фреймворк правится **только в этом репозитории** (где бы он ни был склонирован; у автора — `~/AIProjects/dev-framework`). `~/.claude/dev-framework`, `<проект>/.claude/skills/dev-*`, `<проект>/.claude/agents/df-*` и копии в проектах — производные, обновляются из него (`install.sh`). Подробно — `core/rules-evolution.md`, «Где правится фреймворк».

```bash
./install.sh ~/GoProjects/<сервис>      # в каждый рабочий проект, где нужен /dev
```

`install.sh <папка проекта>` ставит **симлинки** на репозиторий, ничего не копирует и не удаляет. Скиллы и агенты —
**только в проект**: в `~/.claude` их описания грузились бы в каждую сессию любого проекта.

| Ссылка | На что |
|---|---|
| `~/.claude/dev-framework` | весь репозиторий (правила читаются отсюда; токенов не стоит) |
| `<проект>/.claude/skills/dev`, `dev-*` | `skills/*` — команды `/dev`, `/dev-go`, … |
| `<проект>/.claude/agents/df-*.md` | `agents/*` — агенты, которых запускает `/dev` |

Симлинки проекта записываются в его `.git/info/exclude` — в репозиторий проекта не попадают.

Переход со старой установки (скиллы и агенты в `~/.claude`): `rm ~/.claude/skills/dev ~/.claude/skills/dev-* ~/.claude/agents/df-*.md` (это симлинки) и убрать строки про `/dev*` из `~/.claude/CLAUDE.md` — иначе скиллы задвоятся и их описания так и будут грузиться в каждую сессию.

Если путь уже занят не нашей ссылкой, скрипт пишет `skip` и не трогает его — разберитесь вручную (обычно это старая копия: удалить её и запустить `install.sh` ещё раз). Повторный запуск безопасен.

### 2. Триггеры команд

Не нужны: Claude Code запускает скилл по `/dev…` сам. В `~/.claude/CLAUDE.md` строк про `/dev` не добавлять.

### 3. Перезапустить Claude Code и проверить

Скиллы и агенты загружаются при старте сессии.

- `/dev` и `/dev-*` есть в списке команд;
- `/agents` показывает `df-analyst`, `df-architect`, `df-security`, `df-qa`, `df-go`, `df-php`, `df-review`;
- `readlink ~/.claude/dev-framework` указывает на склонированный репозиторий.

### 4. Настройка проекта (по желанию)

- **Правила проекта** — `.claude/dev-rules.md` в корне проекта: особенности сервиса, которые главнее фреймворка (`core/rules-evolution.md`). Не создаётся заранее — появляется при разборе лога отклонений после задачи.
- **Справочник SDK/ядра под версию проекта** — если версии в проекте отличаются от тех, по которым собран `reference/` (указаны в шапке файлов); роли сами предложат пересобрать — команды в разделе «Справочники SDK».
- **Копия фреймворка в проекте** (`<project>/.claude/dev-framework`) — только если проект должен жить с зафиксированной версией правил; она главнее `~/.claude/dev-framework` и не правится на месте.

### 5. IDE для навигации по коду (по желанию)

Агенты ищут объявления и сигнатуры через индекс IDE, если проект открыт в IDEA (`approaches/process/code-navigation.md`); нет IDE — grep, как раньше, ничего не ломается.

1. В IDE: **Settings → Tools → MCP Server → Enable MCP Server** (порт по умолчанию `64342`).
2. Подключить сервер к Claude Code **под именем `idea`** — агентам `df-*` выданы инструменты `mcp__idea__*`, с другим именем они их не увидят:
   ```bash
   claude mcp add --transport http --scope user idea http://127.0.0.1:64342/stream
   ```
3. Разрешить без вопросов четыре инструмента только на чтение — в `~/.claude/settings.json`:
   ```json
   "permissions": { "allow": [
     "mcp__idea__search_symbol", "mcp__idea__get_symbol_info",
     "mcp__idea__search_structural", "mcp__idea__lint_files"
   ] }
   ```
   Остальные инструменты сервера (правка, терминал, SQL, отладчик) не разрешать: агентам они не выданы.
4. Проект задачи держать открытым в IDE (можно отдельным окном) и запускать Claude Code после IDE — сессия подключается к серверу при старте; иначе `/mcp` → переподключить `idea`.

`/dev` и роли, запущенные напрямую, сами проверяют доступ при старте и, если IDE недоступна или проект в ней не открыт, предлагают включить — работа при этом идёт дальше через grep.

Проверка: `/mcp` показывает `idea` как подключённый. В итоге каждого агента — строка `навигация: IDE` или `навигация: grep (<причина>)`.

### Первый запуск

```
/dev <задача или номер из трекера>
```
`/dev` изучит проект, задаст все вопросы одним списком и после ответов доведёт до результата. Коммит, пуш, миграции и действия с БД — только по вашему «да».

### Обновление

```bash
cd ~/AIProjects/dev-framework && git pull && ./install.sh <папка проекта>
```
Правки существующих файлов видны сразу (симлинки); `install.sh <проект>` нужен, когда появились новые скиллы или агенты — после него перезапустить Claude Code.

### Удаление

```bash
./install.sh --remove <папка проекта>      # из проекта; совсем — ещё rm ~/.claude/dev-framework
```
Удаляются только ссылки. IDE: `claude mcp remove idea --scope user` и строки `mcp__idea__*` из `permissions.allow` в `~/.claude/settings.json`.

### Где править

Фреймворк правится только в репозитории; `~/.claude/*` — ссылки на него. Подробно — раздел «Источник истины» выше и `core/rules-evolution.md`.

## Справочники SDK

`stacks/go/go-sdk/reference/{gitlab,github}/` (два источника Go SDK — версии у них разные) и `stacks/php/mps-core/reference/` генерируются из исходников и не правятся руками:

```bash
tools/sdk-ref/go.sh  stacks/go/go-sdk/reference/gitlab --gomod stacks/go/examples/tariff/go.mod  # GitLab — версии эталона
tools/sdk-ref/go.sh  stacks/go/go-sdk/reference/github --latest github.com/exgamer           # GitHub — свежие из module cache
tools/sdk-ref/go.sh  <dir> --gomod <project>/go.mod                       # версии конкретного проекта
tools/sdk-ref/php.sh stacks/php/mps-core/reference <project-dir>          # mps/core + mps/utils из vendor проекта
```

Официальная документация (`official/`) копируется из пакетов той же версии (`docs/`, README).

После обновления справочника — пройтись по `capabilities.md` (что появилось/устарело) и по примерам `examples/`.

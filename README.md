# dev-framework

Правила, роли и агенты Claude Code для бэкенда на Go и PHP: код пишется по регламентам `backend-regulation`, архитектуре Go SDK и mps/core и стилю автора, собранному в эталоны. Существует отдельно от `claude-skills`.

Задача идёт как в команде: требования → дизайн → код с тестами → независимое ревью. Спорное модель не решает сама: все вопросы — одним списком в начале, дальше работа без остановок. Каждое отклонение от правил разбирается в конце задачи и, если нужно, становится правилом.

Стеки:
- **Go** + внутренний Go SDK (`gosdk-*`);
- **PHP** — Laravel + `mps/core` + `mps/utils`.

Фронт (vanilla JS) отложен до проекта-образца (`stacks/vanilla-js/README.md`).

*Термины Claude Code:* **скилл** — команда вида `/dev`, загружающая инструкцию роли; **субагент** — отдельный экземпляр модели с чистым контекстом, которому оркестратор поручает одну роль.

## Какие проблемы решает

| Проблема | Что делает фреймворк |
|---|---|
| Код «в среднем по интернету», а не как в команде | эталонные модули (`stacks/*/examples/`), стиль автора, памятка стека |
| Выдуманные API библиотек | справочники SDK/ядра из исходников: нет в справочнике — нет в SDK |
| Молча принятые спорные решения | пробел или спор — вопрос пользователю с вариантами и рекомендацией |
| Вопросы по одному весь день | один список вопросов в начале |
| Сломано то, чего модель не видела | карта связей до кода, ревью проверяет по ней |
| Модель проверяет сама себя | ревью — отдельный агент без контекста разработки |
| Правила теряются в длинной сессии или контекст переполняется | каждая роль — свежий субагент; задачи плана маленькие, у каждой — список того, что читать; при сжатии контекста `/dev` просит перезапустить сессию и продолжает с записанного шага |
| Целые файлы читаются ради одной сигнатуры | индекс IDE через MCP, без IDE — grep (`approaches/process/code-navigation.md`) |
| Механические правила проверяются глазами | анализаторы с конфигом фреймворка (`tools/lint/`) |
| Опасные действия | миграции, правки и очистка БД, коммит, пуш — только по явному «да» на каждое |
| Правила устаревают | лог отклонений по задаче → разбор → правка правил |

## Как выглядит работа

```
/dev <задача или номер из трекера>
/dev --step <задача>      # то же, со стопом после каждой роли
```

1. **Разведка.** Субагенты по очереди: требования (`requirements.md`) → дизайн, карта связей, план волнами (`design.md`, `plan.md`) → модель угроз при чувствительных зонах (`threats.md`) → тест-кейсы до кода (`qa.md`). Что можно выяснить из кода и правил, выясняется без вопросов.
2. **Один список вопросов** с вариантами и рекомендацией. Можно ответить «1 — да, 2 — Б, остальное по рекомендации».
3. **Разработка** маленькими задачами, до 3 разработчиков параллельно (рефактор и перенос — до 5), каждый пишет код с unit-тестами и прогоняет анализаторы по своему диффу.
4. **QA:** интеграционные и e2e тесты по кейсам, регрессия по связям.
5. **Независимое ревью** → исправления → повторное ревью по дельте, не больше 3 кругов.
6. **Результат:** что сделано, как проверено и что не проверено, выкатка и откат, сообщения коммитов. Коммит — по «да».
7. **Разбор лога отклонений:** всё спорное за задачу — одной таблицей: во фреймворк / в правила проекта / оставить.

Пользователь нужен трижды: ответить на вопросы, решить по логу, подтвердить коммит. Порядок ролей и что каждая читает — `approaches/process/role-chain.md`.

Артефакты задачи — в проекте, `docs/tasks/<ключ>/`; статусы задач в `plan.md`, поэтому работу можно продолжить в новой сессии: после `/clear` или в новом окне хватит «дальше» — хук, который ставит `install.sh`, напомнит сессии незаконченную команду (`tools/resume/resume.py`). Там же `usage.md` — расход агентов и токенов (`tools/usage/usage.py`, по транскриптам Claude Code).

### Пример

Задача AINA-2744 — перенести легаси-движок архивации (PHP) в новый подпроект. После разведки `/dev` прислал один список (фрагмент, по `answers.md` задачи):

```
Понял так: переносим движок архивации из app/ в {подпроект}; легаси и его потребителей не трогаем.

1. Легаси и его потребители — не трогаем, переключение отдельной задачей?
   Рекомендация: да.
2. Куда положить компонент? Правила для технической библиотеки без бизнес-логики нет.
   (а) {подпроект}/Core/Archive/  (б) Domains/…  (в) Infrastructure/…
   Рекомендация: (а) — Core/ только для технического общего (P-11).
3. Форма кода: перенести 1:1 или переписать по правилам (DI через definitions, без статических фабрик)?
   Рекомендация: 1:1 — контракт старого кода сохраняется.
…
```

Ответ — одной фразой: «1 да, легаси не трогаем. По остальным — это полный перенос, можно переписать, чтобы было удобно, контракт сохранять не обязательно». Дальше — дизайн, модель угроз, код с тестами и два круга ревью без вопросов. Спорное за это время попало в `rules-log.md` — 26 строк, 14 стали правилами фреймворка: место технических библиотек в `Core/`, проверки безопасности для архивов (zip-slip, zip-бомба, симлинки).

## Роли

| Команда | Роль |
|---|---|
| `/dev` | главная точка входа: вся цепочка от задачи до результата; `--step` — пошагово |
| `/dev-fix` | баг-фикс: падающий тест → причина → исправление → ревью; миграция или новый контракт — в `/dev` |
| `/dev-analyst` | требования из задачи, в т.ч. бизнесовой |
| `/dev-architect` | тех. дизайн и план с волнами; режимы feature / refactor / migrate |
| `/dev-go` | разработчик Go + Go SDK |
| `/dev-php` | разработчик Laravel + mps/core + mps/utils |
| `/dev-security` | модель угроз до кода (`design`) и аудит сервиса (`audit`) |
| `/dev-review` | ревью Go/PHP по тем же правилам; `--mr <id>` — MR через glab |
| `/dev-qa` | тест-кейсы, тесты стека, UI-автотесты (Playwright) |
| `/dev-rule` | обсудить пробел или спор и записать правило; разбор лога задачи (`/dev-rule <rules-log.md>`); полная сверка (`/dev-rule audit`) |
| `/dev-mr` | замечания ревьюеров в нашем MR: треды → документ → обсуждение → правки → ответы в треды |

Что делает каждая — `skills/<команда>/SKILL.md`. В цепочке `/dev` роли выполняют агенты `df-*` (`agents/`, общие правила — `approaches/process/subagent.md`): у каждого свежий контекст и ограниченный набор инструментов, модель — как у основной сессии (`/model` переключает все роли). Вызывать их напрямую не нужно.

Сценарии:
- **Новая фича:** `/dev <задача>`.
- **Рефактор легаси:** `/dev отрефактори <модуль>` — `approaches/process/legacy-refactor.md`.
- **Перенос на другой стек:** `/dev перенеси <модуль> из php в go` — `approaches/process/stack-migration.md`.
- **Баг:** `/dev-fix <баг или ключ>` — `approaches/process/bugfix.md`; `--hotfix` — ветка от `production`.
- **Мелкая правка без новых эндпойнтов, таблиц, событий и контрактов:** сразу `/dev-go` или `/dev-php`.
- **Ревью MR:** `/dev-review --mr <id>`.
- **Замечания ревьюеров в нашем MR:** `/dev-mr <id или url>` — `approaches/process/mr-threads.md`.
- **Аудит безопасности сервиса:** `/dev-security audit`.

## Как устроены правила

Главное — `core/principles.md`; короткий список ключевых решений и открытых споров — `core/decisions.md`.

```
core/            принципы, стиль автора (style.md), развитие правил (rules-evolution.md), decisions.md, decisions-log.md, backlog.md
regulations/     выжимки регламентов про код: REST, git, code review, сущности, контракты, согласования, требования к сервису
architecture/    слои, связи доменов, интеграции — без привязки к стеку
approaches/
  patterns/      транзакции, outbox, кэш, идемпотентность, асинхронность, миграции, производительность, конкурентность, платежи
  process/       цепочка ролей, анализ, карта связей, навигация по коду, планирование, рефактор, перенос, тесты, самопроверка, ревью, безопасность, MR
stacks/
  go/            памятка (checklist.md), структура, соглашения, стиль, ревью, безопасность, эталон examples/; go-sdk/ — SDK
  php/           то же для Laravel + mps/core; карта файлов — stacks/php/README.md; mps-core/ — ядро
  qa-playwright/ UI-автотесты
  vanilla-js/    отложен
skills/          роли — команды /dev*
agents/          агенты df-* для цепочки /dev
tools/           анализаторы на проекте, проверки фреймворка, справочники, граф правил, учёт токенов
install.sh       установка в проект
```

- **Приоритет:** правила проекта (`.claude/dev-rules.md` в корне проекта) > стек > архитектура > core.
- **Памятка стека** (`stacks/<stack>/checklist.md`) — жёсткие правила одной строкой со ссылкой на подробности; по ней работают и разработчик, и ревьюер.
- **Уровень находки ревью** ([ОШИБКА]/[ВНИМАНИЕ]/[ИНФО]) задаётся только в каталогах тегов: `approaches/process/review-tags.md`, `stacks/<stack>/review-tags.md`, теги безопасности — `approaches/process/security.md`.
- **Одно правило — одно место**, в остальных файлах — ссылка. Роли загружают правила по задетым слоям, а не всё сразу.
- **Справочники SDK/ядра** (`capabilities.md` — что есть, `reference/` — полный API, `official/` — документация пакетов) — в `stacks/go/go-sdk/` и `stacks/php/mps-core/`.

### Эталоны

Эталон — образец модуля внутри фреймворка: `stacks/go/examples/tariff/`, `stacks/php/examples/`; README эталона связывает каждый файл с правилом. Роли, ревью и проверки сверяются только с ним; правка правила, которую задевает эталон, правит и эталон.

Реальные проекты, по которым собраны правила, — только их происхождение: роли и проверки их не читают, а расхождение проекта с правилом — не довод и не находка фреймворка.

## Как меняются правила

1. Во время задачи всё спорное пишется в `docs/tasks/<ключ>/rules-log.md`: спор, пробел, противоречие, решение по ходу, правка стиля, новое замечание ревью. До разбора эти решения действуют только в этой задаче.
2. В конце задачи — `/dev-rule <rules-log.md>`: по каждой строке во фреймворк / в правила проекта / оставить.
3. Не согласны с правилом — не обходить, а `/dev-rule`: обсудить и записать.

Правка во фреймворк — в этом репозитории, строкой в `core/decisions-log.md` (полная история с причинами) и пунктом в `CHANGELOG.md` (что изменилось для пользователя); задела установку, команды, инструменты или порядок работы — ещё `README.md`. Порядок — `core/rules-evolution.md`.

После правки `/dev-rule` прогоняет все проверки разом (`skills/dev-rule/SKILL.md`, Шаг 3а):
- `tools/check/` — битые ссылки и орфаны, ссылки на пункты и разделы, формат журнала и бэклога, синтаксис блоков кода, кандидаты в дубли, теги ревью, цепочки загрузки ролей, правила анализаторов (таблица — `tools/check/lint-proof/RULES.md`); запуск — `python3 tools/check/<скрипт>.py` из корня репозитория;
- оба эталона: Go — сборка, тесты и `tools/lint/lint.py go`; PHP — `tools/php-check/run.sh` (phpunit + phpstan в docker);
- граф правил (`tools/graph/`) — поиск того же правила другими словами и кандидатов в противоречия;
- независимое ревью диффа.

`/dev-rule audit` — то же по всему репозиторию; находки — в `core/backlog.md`.

### Источник истины

Фреймворк правится только в этом репозитории (у автора — `~/AIProjects/dev-framework`). `~/.claude/dev-framework`, `<проект>/.claude/skills/dev-*`, `<проект>/.claude/agents/df-*` — симлинки на него. Подробно — `core/rules-evolution.md`, «Где правится фреймворк».

## Установка и настройка

### Что нужно

| Что | Зачем | Когда |
|---|---|---|
| Claude Code | всё работает внутри него | всегда |
| `git`, `bash`, `python3` | клонирование, `install.sh`, скрипты `tools/` | всегда |
| Go + доступ к `git.mpinnovations.kz/mps/go-packages` (`GOPRIVATE`, ключ или токен) | сборка и тесты, справочник SDK | Go |
| `golangci-lint` v2 | правила фреймворка на Go-проекте (`tools/lint/lint.py go`); `install.sh` предложит поставить через brew | Go |
| Docker с PHP-контейнером проекта | тесты, `phpstan`, правила фреймворка на PHP-проекте (`tools/lint/lint.py php`) | PHP |
| Docker-контейнер с PHP >= 8.3 + `gitlab-token` для `mps/*` | прогон PHP-эталона (`tools/php-check/run.sh`) | правка правил |
| `graphify` (`pip install graphifyy`) | граф правил | правка правил |
| `glab` (авторизованный) | `/dev-review --mr`, `/dev-mr` | работа с MR |
| IntelliJ IDEA / GoLand / PhpStorm со встроенным MCP-сервером (проверено на IDEA 2026.2) | навигация по индексу IDE (шаг 5) | по желанию, без IDE — grep |

### 1. Скачать и установить

```bash
git clone https://github.com/exgamer/claude-dev-framework.git ~/AIProjects/dev-framework
cd ~/AIProjects/dev-framework
./install.sh ~/GoProjects/<сервис>      # в каждый проект, где нужен /dev
```

`install.sh <папка проекта>` ставит симлинки и хук продолжения, ничего не копирует и не удаляет:

| Ссылка | На что |
|---|---|
| `~/.claude/dev-framework` | весь репозиторий — отсюда роли читают правила |
| `<проект>/.claude/skills/dev`, `dev-*` | `skills/*` — команды `/dev`, `/dev-go`, … |
| `<проект>/.claude/agents/df-*.md` | `agents/*` |

И хук `SessionStart` в `<проект>/.claude/settings.local.json` (личные настройки, в репозиторий не попадают): после `/clear` или в новом окне напоминает сессии незаконченную команду фреймворка — продолжить можно словом «дальше» (`tools/resume/resume.py`).

Скиллы и агенты — только в проект: в `~/.claude` их описания грузились бы в каждую сессию любого проекта. Симлинки проекта пишутся в его `.git/info/exclude` и в репозиторий не попадают. Занятый чужим файлом или ссылкой путь скрипт пропускает с `skip` — разберитесь вручную (обычно это старая копия: удалить и запустить ещё раз). Повторный запуск безопасен.

Ещё `install.sh` проверяет анализаторы для `tools/lint/`: в Go-проекте — `golangci-lint` v2, в PHP-проекте — выбирает PHP-контейнер (ниже), и печатает правила `ask` для `~/.claude/settings.json` — подтверждение перед коммитом, пушем и разрушающим SQL. Их нужно добавить вручную.

Переход со старой установки (скиллы и агенты в `~/.claude`): `rm ~/.claude/skills/dev ~/.claude/skills/dev-* ~/.claude/agents/df-*.md` и убрать строки про `/dev*` из `~/.claude/CLAUDE.md`, иначе скиллы задвоятся.

### 2. PHP-контейнер

Имя контейнера у каждого разработчика своё, во фреймворке оно не зашито. Для проекта берётся по порядку: `--container`, `PHP_CONTAINER`, запомненный для проекта, единственный запущенный контейнер с php, в который смонтирован проект; иначе спросит в терминале и запомнит. Для PHP-эталона (`tools/php-check/run.sh`) — так же, но без монтирования. Запомненное — `tools/lint/.php-containers.json`, локально, в git не попадает; сменить — `PHP_CONTAINER` или удалить строку из файла. Подробности — `tools/lint/README.md`.

### 3. Перезапустить Claude Code и проверить

- `/dev` и `/dev-*` есть в списке команд (триггеры в `~/.claude/CLAUDE.md` не нужны);
- `/agents` показывает `df-analyst`, `df-architect`, `df-security`, `df-qa`, `df-go`, `df-php`, `df-review`;
- `readlink ~/.claude/dev-framework` указывает на склонированный репозиторий.

### 4. Настройка проекта (по желанию)

- **Правила проекта** — `.claude/dev-rules.md`: особенности сервиса, которые главнее фреймворка. Заранее не создаётся — появляется при разборе лога отклонений.
- **Справочник SDK/ядра под версию проекта** — роли сами предложат пересобрать, если версии проекта отличаются от тех, по которым собран `reference/` (раздел «Справочники SDK»).
- **Копия фреймворка в проекте** (`<проект>/.claude/dev-framework`) — если проект должен жить с зафиксированной версией правил; она главнее `~/.claude/dev-framework` и не правится на месте.

### 5. IDE для навигации по коду (по желанию)

Если проект открыт в IDE, агенты ищут объявления и сигнатуры через её индекс, иначе — grep (`approaches/process/code-navigation.md`).

1. В IDE: **Settings → Tools → MCP Server → Enable MCP Server** (порт по умолчанию `64342`).
2. Подключить сервер под именем `idea` — агентам выданы инструменты `mcp__idea__*`, с другим именем они их не увидят:
   ```bash
   claude mcp add --transport http --scope user idea http://127.0.0.1:64342/stream
   ```
3. Разрешить без вопросов четыре инструмента только на чтение — в `~/.claude/settings.json`:
   ```json
   "permissions": { "allow": [
     "mcp__idea__search_symbol", "mcp__idea__get_symbol_info",
     "mcp__idea__search_structural", "mcp__idea__lint_files"
   ] }
   ```
   Остальные инструменты сервера (правка, терминал, SQL, отладчик) не разрешать: агентам они не выданы.
4. Держать проект открытым в IDE и запускать Claude Code после неё; иначе `/mcp` → переподключить `idea`.

Проверка: `/mcp` показывает `idea` подключённым; в итоге каждого агента — `навигация: IDE` или `навигация: grep (<причина>)`.

### Обновление

```bash
cd ~/AIProjects/dev-framework && git pull && ./install.sh <папка проекта>
```
Правки существующих файлов видны сразу; `install.sh` нужен, когда появились новые скиллы, агенты или хук, — после него перезапустить Claude Code. Что изменилось — `CHANGELOG.md`.

### Удаление

```bash
./install.sh --remove <папка проекта>      # совсем — ещё rm ~/.claude/dev-framework
```
Удаляются ссылки и хук продолжения. IDE: `claude mcp remove idea --scope user` и строки `mcp__idea__*` из `permissions.allow` в `~/.claude/settings.json`.

## Инструменты

| Где | Что |
|---|---|
| `tools/lint/` | правила фреймворка анализаторами на проекте, своим конфигом, без файлов в проекте: `python3 tools/lint/lint.py go <проект> [--base <rev>]`, `python3 tools/lint/lint.py php <проект> --sub <подпроект> [--container <имя>] [--base <rev>]`. Запускают разработчик и ревьюер; что анализатор не ловит — печатает списком «проверить глазами». Подробно — `tools/lint/README.md` |
| `tools/check/` | проверки самого фреймворка после правки правил (раздел «Как меняются правила») |
| `tools/php-check/` | прогон PHP-эталона в docker (`run.sh`) |
| `tools/sdk-ref/` | генераторы справочников SDK/ядра (`go.sh`, `php.sh`) |
| `tools/graph/` | граф правил для `/dev-rule` |
| `tools/ab/` | A/B фреймворка на написании кода: та же задача на версии до правки и после, разработчик → ревью → слепой судья (`ab.py`, поручения — `prompts.md`, задача — `task/`); в Шаге 3а `/dev-rule` при правке ролей, памяток, эталонов |
| `tools/resume/resume.py` | продолжение команды после `/clear` и в новой сессии: метка незаконченной команды (`set`/`done`/`list`), хук `SessionStart` (`install`/`uninstall` — делает `install.sh`) |
| `tools/usage/usage.py` | расход агентов и токенов: `--task <ключ> [--write]` — по задаче, без `--task` — список задач проекта, `--session <ID>` — агенты одной сессии без ключа задачи, `--context` — контекст текущей сессии (по нему `/dev` перезапускает сессию); в отчёте — стоимость в единицах цены входа и перезапись кэша после пауз |

## Справочники SDK

`stacks/go/go-sdk/reference/{gitlab,github}/` (два источника Go SDK, версии разные) и `stacks/php/mps-core/reference/` генерируются из исходников и руками не правятся:

```bash
tools/sdk-ref/go.sh  stacks/go/go-sdk/reference/gitlab --gomod stacks/go/examples/tariff/go.mod  # GitLab — версии эталона
tools/sdk-ref/go.sh  stacks/go/go-sdk/reference/github --latest github.com/exgamer           # GitHub — свежие из module cache
tools/sdk-ref/go.sh  <dir> --gomod <проект>/go.mod                        # версии проекта
tools/sdk-ref/php.sh stacks/php/mps-core/reference <проект>               # mps/core + mps/utils из vendor проекта
```

`official/` копируется из пакетов той же версии. После обновления справочника — сверить `capabilities.md` (что появилось и устарело) и эталоны `examples/`.

## С чего начать

1. Прочитать `core/principles.md` и памятку своего стека `stacks/<stack>/checklist.md`.
2. Посмотреть эталон `stacks/<stack>/examples/`.
3. Прогнать небольшую задачу через `/dev --step`, чтобы увидеть каждую роль.

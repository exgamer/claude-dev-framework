# Безопасность: роль `/dev-security`

Две работы, которые ревью диффа не закрывает: **модель угроз до кода** (режим `design`) и **глубокий аудит всего сервиса** (режим `audit`). Правила одни для всех ролей — чеклисты `stacks/<stack>/security.md` (с тегами); эта роль их не дублирует, а применяет в другой момент.

| Кто | Когда | Что делает с безопасностью |
|---|---|---|
| `/dev-architect` | дизайн | отмечает в `design.md` чувствительные зоны задачи |
| **`/dev-security design`** | после архитектора, если есть чувствительные зоны | модель угроз → `docs/tasks/<ключ>/threats.md`: угрозы, меры, где в коде, что тестировать |
| `/dev-go`, `/dev-php` | код | реализуют меры из `threats.md`; самопроверка по `security.md` |
| `/dev-qa` | тесты | негативные кейсы из `threats.md` |
| `/dev-review` | каждый дифф | `security.md` стека + реализованы ли меры из `threats.md` |
| **`/dev-security audit`** | периодически, перед комплаенсом | многоагентный аудит репозитория/пути |

## Каталог тегов безопасности

Общий для стеков: тег — суть уязвимости. Признаки в коде — `stacks/<stack>/security.md`, строка с тем же тегом; колонка «Признаки» ниже — в каком стеке они уже описаны (у тега без признаков стека — искать по сути). Уровень — только в колонке «Уровень» (O-24; остальные теги — `review-tags.md`): подтверждённая находка — [БЕЗОПАСНОСТЬ], всегда КРИТИЧНО, и в новом, и в унаследованном коде (`review.md`, «Порядок», п. 3a); не подтверждено однозначно (нет пользовательского ввода в опасном месте) — [ВНИМАНИЕ] с пояснением риска.

| `soft-deleted-membership-grants-access` | [БЕЗОПАСНОСТЬ] | мягко удалённое членство продолжает давать доступ | PHP |

| `user-enumeration` | [БЕЗОПАСНОСТЬ] | логин, сброс пароля или регистрация отвечают по-разному (текст, код, размер, порядок времени) на существующий и несуществующий аккаунт | Go, PHP |
| `spoofable-rate-limit` | [БЕЗОПАСНОСТЬ] | лимит обходится подменой IP или не считает попытки | Go, PHP |
| `unverified-webhook` | [БЕЗОПАСНОСТЬ] | колбэк внешней системы меняет состояние без проверки подлинности | Go, PHP |
| `hardcoded-secret` | [БЕЗОПАСНОСТЬ] | секрет литералом в коде или конфиге вместо env/vault | Go, PHP |
| `secret-in-build-artifact` | [БЕЗОПАСНОСТЬ] | CI запекает секрет в артефакт или слой образа | Go, PHP |
| `weak-crypto` | [БЕЗОПАСНОСТЬ] | слабый хеш паролей или предсказуемый генератор токенов | Go, PHP |
| `sensitive-data-in-logs` | [БЕЗОПАСНОСТЬ] | ПДн и секреты в логах, трейсах, таблицах логов | Go, PHP |
| `internal-details-leak` | [БЕЗОПАСНОСТЬ]; Go: техническая ошибка (драйвер Postgres/Redis) текстом в `message` через `ErrorResponse` SDK — [ВНИМАНИЕ] (сверка 2026-10-20) | клиенту уходят внутренние детали: текст технической ошибки, trace, пути | Go, PHP |
| `insecure-file-upload` | [БЕЗОПАСНОСТЬ] | файл сохраняется под клиентским именем или расширением без проверки; тип не сверен с содержимым; принимается HTML, JS или XML; SVG отдаётся inline с домена приложения (Stored XSS) | Go, PHP |
| `api-docs-exposed` | [БЕЗОПАСНОСТЬ] | Swagger UI или схема OpenAPI доступны на проде без аутентификации | Go, PHP |

| `symlink-following` | [БЕЗОПАСНОСТЬ] | упаковка или распаковка следует симлинкам | PHP |

## Чувствительные зоны (когда нужен режим `design`)

Задача задевает хотя бы одно:
- аутентификацию/авторизацию: новые роуты, права, роли, middleware, JWT, сессии, OTP;
- доступ к данным с владельцем/тенантом (парковка, организация, здание, компания…): списки, поиск, дашборды, `show/update/delete` по ID;
- деньги: оплата, возврат, списание, автоплатёж, фискализация, баланс;
- входящие интеграции: вебхуки, колбэки шлюзов, железо (ЛПМ, СКУД), партнёрские API;
- исходящие интеграции с секретами, ключами, подписями;
- персональные данные: телефон, ИИН, госномер, фото/биометрия, карты;
- файлы: загрузка, скачивание, пути;
- конфиг, секреты, CI/Dockerfile, деплой, публикация документации API.

Ни одной — `design` не нужен, безопасность закрывают самопроверка разработчика и ревью.

Баг-фикс `/dev-fix` в пределах контракта — без `design`, даже в чувствительной зоне: разработчик и ревью проверяют исправление по `stacks/<stack>/security.md` (`bugfix.md`, «Границы»). Вернуть проверку, которую контракт уже подразумевает (принадлежность записи, скоуп владельца, существующее право — `broken-access-control`, `tenant-scope-missing`), — баг-фикс; новые или другие права, роли, middleware, новое правило видимости — изменение контракта: `/dev` с `design`.

## Режим `design` — модель угроз

**Вход:** `docs/tasks/<ключ>/design.md`. Прочитать: `stacks/<stack>/security.md` (чеклист с тегами и «Меры по слоям»; `review-findings.md` в этом режиме не читается — O-15, он нужен только аудиту), `architecture/integrations.md`, `approaches/patterns/idempotency.md`, `outbox.md`, `stacks/<stack>/…/capabilities.md` (готовые механизмы: подпись HMAC, JWT, rate limit…). Посмотреть, как в проекте уже решено то же самое у соседнего модуля/шлюза — меры повторяют его форму.

**Проход по каждому эндпойнту / консьюмеру / сценарию задачи:**

| Вопрос | Угрозы (теги `security.md`) | Типичная мера |
|---|---|---|
| Кто может вызвать? Какой middleware? | `missing-auth-middleware`, `fail-open-authorization` | middleware соседних ручек; право существует для имени роута (проверить генератор прав) |
| Чем ограничен актор? Скоуп выводится сервером или приходит параметром? | `broken-access-control`, `tenant-scope-missing` | скоуп из прав актора обязателен в `list/search` **и** в `show/update/delete` (у `update/delete` — в чтении перед записью, запись после него — по `id`; или в условии самой записи без чтения); чужой ID → 404 |
| Входящий колбэк: чем подтверждается подлинность? | `unverified-webhook` | подпись по протоколу провайдера (как у соседнего шлюза), постоянное время сравнения (PHP utils ≥ 2.8 — `HmacHelper::verify`) |
| Деньги и лимиты: повтор, гонка, чья сумма? | двойное списание, обход оплаты/лимита (`stacks/<stack>/security.md`, «Меры по слоям»; `approaches/patterns/concurrency.md`, `approaches/patterns/idempotency.md`) | идемпотентность по внешнему ID + уникальный индекс; сумма с сервера, не из запроса; переход статуса с проверкой текущего |
| Вход ссылается на другие записи или ресурсы по id (связанный объект, вложения, файлы)? | `cross-scope-reference` | каждый id — поиск в скоупе актора, у списка — одним запросом на набор; нет или чужой — 422 по полю, один текст для «нет» и «чужой»; id владельца скоупа (`parking_id`, `building_id`) — не здесь: 403 в middleware (`architecture/layers.md`, «Принадлежность записи скоупу») |
| Что пишется в БД из запроса? | `mass-assignment`, `dynamic-mass-assignment` | DTO из `validated()` по всей цепочке записи (P-18), явный список колонок в репозитории |
| Что попадает в логи, ответы, Sentry? | `sensitive-data-in-logs`, `internal-details-leak` | маскирование ПДн и секретов; клиенту — общее сообщение |
| Ввод в SQL / команду / путь / URL? | `sql-injection`, `command-injection`, `path-traversal`, `ssrf`, `open-redirect` | плейсхолдеры, allowlist, `filepath.Clean`/базовая директория, проверка схемы/домена |
| Перебор угадываемого (логин, OTP, сброс, промокод, купон, код подтверждения, инвайт)? | `missing-rate-limiting`, `spoofable-rate-limit` | лимит по пользователю/номеру и IP, неудачные попытки в счёт; числа — в `design.md`; доверенные прокси ограничены |
| Ответ раскрывает, есть ли аккаунт (логин, сброс, регистрация)? | `user-enumeration` | один ответ, код и порядок времени для «есть» и «нет»: «код или письмо отправлены», владельцу существующего аккаунта — уведомление; продукт осознанно раскрывает «занят» — решение в «Решения, которые нужны» |
| Секреты и сборка? | `hardcoded-secret`, `secret-in-build-artifact`, `test-auth-backdoor` | env/vault; `.dockerignore`; тестовые обходы только в `local/testing` |
| Файлы? | `insecure-file-upload`, `path-traversal` | allowlist типов по содержимому (магические байты) + сверка с расширением, HTML/JS/XML не принимаются; своё имя файла; отдача — `X-Content-Type-Options: nosniff` и `Content-Disposition: attachment` или с отдельного домена/хранилища; SVG — только так, иначе не принимается |
| Документация API на проде? | `api-docs-exposed` | маршрут UI и схемы включается явной настройкой (переменная, конфиг), не заданная или нераспознанная — выключен; проверка «окружение не прод» не подходит: пустое или новое окружение открывает маршрут; на проде не включается; нужна на проде — за аутентификацией |

**Выход — `docs/tasks/<ключ>/threats.md`:**

```markdown
# Угрозы и меры — <ключ>

Зоны: <из списка выше>

| # | Где (эндпойнт/сценарий) | Угроза | Тег | Мера (что именно сделать в коде) | Слой и где в коде | Тест |
|---|---|---|---|---|---|---|
| Th1 | PUT /admin/tariffs/{id} | чужой тариф по ID | broken-access-control | скоуп по parking_ids актора в findById | репозиторий: TariffRepository::getByIdInParkings | 404 на тариф чужой парковки |

## Решения, которые нужны от пользователя/продукта
- …
```

- Угрозы нумеруются `Th1…` — `S*` заняты сценариями `requirements.md`, `T*` — задачами `plan.md`.
- Мера — конкретная и проверяемая («скоуп по `parking_ids` актора в `findById`»), не «обеспечить безопасность».
- Слой меры — по `stacks/<stack>/security.md`, «Меры по слоям» (Request — только формат, без SQL; существование — сервис/workflow; уникальность — индекс + сервис). Мера легаси не переносится как есть (`legacy-refactor.md`, «Что переносится»); то же — для мер «к следующим задачам».
- Мера, которой нет в правилах/SDK и которую надо придумать, — пробел: вопрос пользователю (`core/principles.md`); в авто-режиме `/dev` — в общий список вопросов Фазы 2.
- Часть угроз — продуктовые (например, политика повторной оплаты) — выносить в «Решения, которые нужны», а не решать кодом молча.
- Меры попадают в `plan.md` как часть задач (или отдельной задачей волны 0, если это общий механизм — middleware, проверка подписи).

## Новые классы уязвимостей

Нашлась угроза, которой нет в каталоге выше или в `security.md` стека (в дизайне или аудите), — строка в `rules-log.md` (тип `пробел`, предложение «фреймворк»: тег и суть — каталог выше, признаки — `security.md` стека, при необходимости `review-findings.md`). После решения на разборе её начинает ловить и обычное ревью.

## Режим `audit` — глубокий аудит безопасности (`/dev-security audit [path]`)

Отдельный режим, не diff-ревью одного PR/MR. Ищет накопленные проблемы безопасности по всему репозиторию
(или указанному пути) параллельным многоагентным проходом — не читать всё самому последовательно, а
раздать периметр нескольким параллельным subagent'ам с прицельными брифами и свести их находки. Дороже
обычного ревью — не гонять на каждый MR: применять периодически (раз в квартал/релиз) или перед
комплаенс-проверкой/security-аудитом сервиса.

**Когда предлагать:** пользователь просит «проверить сервис на дыры/уязвимости», аудит для комплаенса/
безопасников — а не ревью конкретного диффа или MR.

### A — Периметр

- Без пути → весь код сервиса: Go — `internal/` (`domains`, `entrypoints`, `infrastructure`, `workflows`); PHP — подпроект (`{subproject}/`) или `app/`.
- С путём → ограничить им.
- Собери список доменов/модулей верхнего уровня (`find internal -maxdepth 3 -type d`) — единицы
  распределения между агентами. Для сервисов с несколькими платёжными шлюзами
  — каждый шлюз отдельная единица: шлюзы, скопированные друг с друга, расходятся по реализации (см. `review-findings.md` стека).

### B — Подгрузи контекст перед тем, как раздавать задания

Прочитай `stacks/<stack>/review-findings.md` целиком (особенно «Безопасность»; Go — ещё «Платёжные хендлеры») и
`stacks/<stack>/security.md`. Бриф каждого агента должен явно перечислять нужные паттерны текстом — агент
стартует без контекста этих файлов и без них даст поверхностный проход.

### C — Распредели домены/классы уязвимостей между параллельными агентами

Не читай репозиторий целиком сам. Раздели периметр на 4–8 параллельных заданий (`Agent`,
`subagent_type: "Explore"`, без `isolation` — только чтение), запущенных **одним сообщением** (параллельно,
не по очереди). Группируй по одной из двух осей — какая даёт более ровную нагрузку на агента при этом
периметре:
- **по доменам/модулям** (2–4 на агента), если их много и они разнородны;
- **по классу уязвимости** — broken-access-control/IDOR по каждому handler'у ресурса отдельно, проверка
  подписи вебхуков по каждому платёжному шлюзу отдельно, секреты/конфиг/деплой, JWT/auth-middleware,
  fail-open в авторизации — если периметр меньше и нужен сфокусированный проход сразу по всем модулям.

Каждый бриф обязан:
- перечислять конкретные паттерны из `review-findings.md` и `security.md` стека текстом (не «найди
  уязвимости», а «проверь каждый handler ресурса X по отдельности: list/get корректно скоупят по
  владельцу/тенанту, а update/cancel/delete — тоже, а не только валидный ID»);
- явно требовать **трассировку через смежные файлы**, а не чтение изолированного файла: handler → auth
  middleware → генератор/сидер прав (совпадает ли реальное имя/путь роута с его конвенцией); платёжный
  шлюз → сравнить с соседним шлюзом проекта (эвристика — `review-findings.md`); конфиг → откуда берётся
  секрет и как он используется в Dockerfile/CI;
- просить находки в формате: проблема, `file:line`, сценарий эксплуатации, приоритет, предлагаемый фикс —
  тем же уровнем детализации, что Step 6 обычного ревью;
- явно перечислять, что уже покрыто другими агентами этого запуска (домены/файлы), чтобы не дублировать.

### D — Сведение находок

Не читай `output_file` агентов напрямую — только их финальный хендбек-отчёт. После того как все агенты
вернулись:
- убери дубликаты;
- классифицируй по существующим паттернам из `security.md`; если паттерна там ещё нет — заведи его и по
  итогам добавь в `security.md`/`review-findings.md`;
- присвой приоритет (Критический/Высокий/Средний/Низкий) по бизнес-импакту — двойное списание, обход
  оплаты, IDOR на чужую сессию обычно Критично; стилистические расхождения — Низкий.

### E — Отчёт

Формат — как «Отчёт» / «Сохранение» в `review.md` (таблица «🔴 Безопасность», «Итог по категориям»), но с типом файла
`security-audit`: `review_result/{datetime}_security-audit.md`. Если пользователь просит таблицу/Excel —
оформи через скилл `xlsx`, колонки № / Область / Проблема / Описание / Место в коде / Приоритет / Решение,
строки отсортированы по приоритету.

После отчёта — как «Исправления» в `review.md`, но точечно: не предлагай «исправить всё скопом» — часть находок (например
отсутствие идемпотентности платежа) требует продуктового решения, а не только правки кода.

> Агенты аудита — только чтение (`Explore`, без `isolation`), поэтому их 4–8, а не «не больше 3 (в рефакторе 5)», как у разработчиков (`planning.md`).

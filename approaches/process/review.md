# Ревью кода

Процедура для `/dev-review` (Go и PHP). Собрана из `claude-skills` — `go-reviewer` и `php-reviewer`; стековые части — в `stacks/<stack>/`:

| Что | Go | PHP |
|---|---|---|
| Памятка — жёсткие правила одной строкой; ревью проходит её первой, как и разработчик | `checklist.md` | `checklist.md` |
| Правила | `structure.md`, `conventions.md`, `style.md`, `go-sdk/*` | `structure.md`, `conventions.md`, `style.md`, `mps-core/*` |
| Безопасность (чеклист с тегами) | `security.md` | `security.md` |
| Проверки сверх правил: команды и grep для стека (общие правила — раздел «За пределами дифа» ниже, платежи — `approaches/patterns/payments.md`) | `review-checks.md` | `review-checks.md` (+ дублирование логики) |
| Реальные замечания из MR | `review-findings.md` | `review-findings.md` |
| Теги находок | `security.md` + `stacks/php/review-tags.md` для общих паттернов (раздел «Теги» ниже) | `security.md` + `review-tags.md` |
| Что уже есть в SDK/ядре (переизобретение) | `go-sdk/capabilities.md` | `mps-core/capabilities.md` |
| Производительность, конкурентность | `approaches/patterns/performance.md`, `concurrency.md` | то же |
| Эталон формы | `examples/tariff/` | `examples/` |

## Цель ревью

```
/dev-review                         # изменённые файлы (git diff HEAD)
/dev-review --staged                # только staged
/dev-review <path>                  # файл или директория
/dev-review --module <name>         # модуль
/dev-review --all                   # весь проект
/dev-review --mr <id-or-url>        # MR (glab)
/dev-review --security-audit [path] # = /dev-security audit [path] — см. approaches/process/security.md
```

Файлы стека: Go — `*.go` (без `vendor/`), PHP — `*.php` (без `vendor/`, `node_modules/`).

**`--mr <id-or-url>`:**
1. URL → числовой ID из `/merge_requests/<id>` (всё после `#` игнорировать).
2. `glab mr view <id> --output text` → `Source Branch`, `Target Branch`.
3. `git fetch origin`.
4. `git diff origin/<target>...origin/<source> --name-only -- '*.<ext>'`.
5. `glab` недоступен — сказать об этом, попросить ветку MR, `git diff origin/main...origin/<branch>`.
6. **Локальный HEAD — не обязательно MR.** Сверить `git branch --show-current` с `Source Branch` и явно сказать, что проверяется.
7. **База — `Target Branch` этого MR**, не дефолт: фичи идут в `stage`, есть `preprod`/`production`.
8. **Открытые треды:** `glab api --paginate "projects/:fullpath/merge_requests/<id>/discussions?per_page=100"`, заметки без `system=true`; префикс замечания — по `regulations/code-review.md`. Уже написанное ревьюерами не дублировать; проверить, **закрыто ли замечание в текущем HEAD** — незакрытые отдельным блоком «Открытые замечания ревьюеров» (префикс, файл, суть). Разбирать чужие треды здесь не нужно — это `/dev-mr` (`mr-threads.md`).

Нет файлов — «Нет файлов для ревью», стоп. Иначе — вывести список файлов.

## Независимость

В цепочке `/dev` ревью выполняет **отдельный субагент без контекста разработки** (только чтение) — автор кода сам себя не ревьюит. Ревьюится код **и** тесты.

## Порядок

1. Загрузить правила по `skills/dev-review/SKILL.md`, Шаг 2 (всегда — памятка, безопасность, проверки сверх правил, principles/style/decisions; остальное — по задетым слоям); есть `docs/tasks/<ключ>/design.md` — сверять код с ним, есть `threats.md` — проверить, что каждая мера реализована; сами `threats.md` и `design.md` (в т.ч. меры «к следующим задачам») — проверить на соответствие правилам слоёв (`stacks/<stack>/security.md`, «Меры по слоям», `legacy-refactor.md`, «Что переносится») в первом круге и при изменении артефакта, уровень — как у той же находки в коде, тег перенесённого из легаси — `legacy-pattern-copied`; есть чеклист ревью проекта (`docs/code-review-checklist.md` и т.п.) — он приоритетнее. Известные споры (`core/decisions.md`) — фиксировать как спор, не как находку.
2. SDK/ядро — только по затронутым слоям/пакетам (Go: `go-sdk/<слой>.md`, PHP: `mps-core/<тема>.md`).
3. Прочитать файлы; при частичном ревью — и соседние того же модуля (handler → request/response/mapper/routes; infra-репозиторий → интерфейс в домене).
3a. **Унаследованное нарушение** — то, что было в файле до задачи и задачей не написано и не переписано (нет в diff): **[ВНИМАНИЕ]** с пометкой «унаследовано» и строкой для `rules-log.md`, не [ОШИБКА] и не повод для круга ревью; попутно не исправляется. Задача переписывает этот сценарий (код в diff) — уровень по правилу. Исключение — безопасность: уровень по `security.md` всегда. Ревью без diff (`<path>`, `--module`, `--all`) — 3a не применяется, уровни по правилам.
4. Проверить расположение файла (`review-checks.md` стека, раздел 5.0 / `structure.md`).
5. **Безопасность** — `security.md` стека, независимо от типа файла.
6. Правила стека + `review-findings.md`; платёжные пути — каждый пункт `approaches/patterns/payments.md` явно, результат в отчёт даже без нарушений.
6a. **Производительность** — по `approaches/patterns/performance.md`; **конкурентность** — по `approaches/patterns/concurrency.md` (теги оттуда).
6b. **Транзакции** — по `approaches/patterns/transactions.md`: каждый workflow с записью — в одной транзакции вместе с проверками (или причина в `design.md`); Go — внутри `fn` только репозитории из аргументов; побочные эффекты — после коммита. Теги `workflow-without-transaction`, `multi-write-without-transaction`, `tx-bypassed-by-service`.
7. Переизобретение и несуществующий API — по `capabilities.md` и `reference/` версии проекта (**[ОШИБКА]**).
8. Проверки за пределами дифа (`review-checks.md`) — при ревью дифа/MR; при `--all` из них нужны только механические проверки — пункты, перечисленные для `--all` в начале раздела `review-checks.md` стека, — по всему проекту, остальные (разъезд списков, данные под миграцию, гигиена MR) без дифа смысла не имеют. **Связи:** по каждому изменённому символу/роуту/событию/таблице/enum — поиск использований; есть `design.md` — сверить с «Связи». Изменение, у которого не учтено использование, — **[ОШИБКА]** (тег `impact-unhandled-usage`).
9. Блок **«Не покрыто правилами»** — что сделано в коде, но в регламенте/фреймворке этого нет; варианты + рекомендация, не ошибка автора.

## За пределами дифа — общее для стеков

Команды и grep-паттерны — `stacks/<stack>/review-checks.md`; здесь само правило (O-12). При ревью дифа/MR — все пункты; при `--all` — только механические grep-проверки (запросы вне репозитория, повторённая обработка формата, индекс массива, константы вместо enum, копии enum и импорт чужого домена).

1. **Запросы к хранилищам вне Infrastructure** — grep по репозиторию, не глазами (`architecture/layers.md`, `service-direct-db-query`).
2. **Повторённая обработка формата** и **индекс массива без проверки** (PHP) — grep (`core/principles.md`, `duplicated-format-logic`; `stacks/php/conventions.md` п. 11b).
2a. **Копии понятий и импорт чужого домена** — новый или изменённый enum сверяется с наборами значений всех enum проекта, файлы домена — с импортами из других доменов, `Common` — с запрещёнными зависимостями; скриптом, не глазами (`architecture/layers.md`, «Общий бизнес-словарь»; `duplicated-enum`, `common-with-logic`).
3. **Разъезд захардкоженных списков.** Появился или расширился enum, статус, allowlist — grep по старому набору: другие валидации, Swagger `enum`, словари фронта, `switch`/`match`/мапперы по этому типу. Рассинхрон — **[ОШИБКА]** `enum-list-drift` с перечислением мест (`impact-analysis.md`).
4. **Новый статус без потребителя** — показать, кто обрабатывает (крон, consumer, переход); нет — **[ОШИБКА]** `status-without-consumer`.
4a. **Миграция = согласованная схема.** Каждая новая или изменённая миграция в диффе сверяется с разделом «Схема БД» `design.md` (таблицы, поля, типы, NULL, default, индексы, FK, уникальность) и с «да» в `answers.md`. Изменение структуры БД, которого нет в «Схеме БД», или нет согласования — **[ОШИБКА]** `schema-not-approved`; без `design.md` (ревью MR без артефактов) — **[ВНИМАНИЕ]** «проверить согласование схемы» (`regulations/technical-approval.md`).
5. **Данные под миграцию поведения.** Новый `NOT NULL`, новое значение enum, новый каст/тип, новый FK — сначала посмотреть, что лежит в колонке (запрос в БД локально — команда в стековом файле). Значение вне enum ломает **чтение**, не только запись. Локальная база не равна проду: если грязь возможна только там — написать это явно и поручить проверку автору, а не выдавать «локально чисто» за проверку.
6. **Инструменты стека** прогнаны по файлам дифа (сборка, линтер, статанализ, тесты); охват инструмента смотреть в его конфиге — диф вне охвата так и назвать. CI без гейтов — локальный прогон единственный гейт, результат в отчёт явно. Падение e2e без окружения — не сигнал, но и не зелёный.
7. **Гигиена MR** (каждый пункт **[ВНИМАНИЕ]**, деплойный риск — **[ОШИБКА]**):
   - lock-файл обновлён вместе с манифестом (`go.sum`/`composer.lock`), нет неиспользуемых импортов и конфликт-маркеров; сгенерированные файлы не уезжают посторонней правкой (`mr-hygiene-lockfile-drift`);
   - менялись роуты/DTO → Swagger перегенерирован (`regulations/rest-api.md`);
   - новый роут без auth-middleware — вопрос «осознанно?» с ответом в MR; административное действие в контексте без auth — сразу [БЕЗОПАСНОСТЬ] (`security.md`);
   - название MR = тикет + суть; коммиты — `regulations/git.md`;
   - **раскомментированный крон, включённый флаг, снятый `if (false)`** — деплойный риск, не мелочь: первый прогон на проде пройдёт по всем накопленным данным; отдельный MR и `--dry-run` (`deploy-risk-flag-enabled`);
   - рефактор/перенос с переключателем или новый контракт под старым адресом без версии — **[ОШИБКА]** `refactor-toggle` (O-19);
   - комментарии-пересказы и «ИИ-вода» в текстах — снять до ревью (`core/style.md`);
   - сценарий без теста при живых тестах в проекте — законное замечание; тесты в проекте не запускаются — сказать об этом, не предлагать их как проверку (`testing.md`).

Уровни: **[БЕЗОПАСНОСТЬ]** — всегда КРИТИЧНО; **[ОШИБКА]** — исправить до мержа; **[ВНИМАНИЕ]** — желательно; **[ИНФО]** — предложение. Не подтверждено однозначно (нет пользовательского ввода в опасном месте) — не [БЕЗОПАСНОСТЬ], а [ВНИМАНИЕ] с пояснением риска. Соответствие префиксам регламента (`blocking:`/`suggestion:`/`nit:`/`question:`) — `regulations/code-review.md`, «Соответствие уровням фреймворка».

## Теги

Колонка «Категория»/«Уязвимость» в сохранённом отчёте — **kebab-case тег паттерна**, а не слой: по нему считаются повторяющиеся ошибки автора MR.

Правила:
- kebab-case, 2–5 английских слов, называет **паттерн**, а не файл/слой (`service-direct-db-query`, не `Service` и не «прямой запрос к БД в SessionService»);
- **переиспользуй** тег из таблицы ниже (или уже использованный в этом же ревью), если находка — тот же паттерн;
- новый тег заводи только если ни один известный не подходит — коротко, конкретно, без деталей конкретного MR (детали — в `Описание`, не в теге).

Теги безопасности — колонка «Тег» в `security.md` стека (общие для Go и PHP); остальные PHP — `stacks/php/review-tags.md`; теги паттернов — в своих файлах `approaches/patterns/*.md` (транзакции, платежи, конкурентность, производительность) и в шагах ревью выше (`impact-unhandled-usage`); для Go — те же теги, если паттерн тот же (`service-direct-db-query`, `n-plus-one-query`, `enum-list-drift`, `deploy-risk-flag-enabled`, `ai-style-comment`, `duplicated-enum`, `common-with-logic`…), новый — в том же формате.

## Отчёт

Один формат — файл из раздела «Сохранение» ниже (таблицы с тегами). В чат — только итог: путь к файлу, вердикт, число находок по уровням (в цепочке `/dev` — не длиннее 15 строк, `subagent.md`). Для каждой находки в таблице: файл, строка, тег, описание с тем, как исправить (код-фрагмент — только если без него не понять); текст описания — `core/style.md`, «Любой текст для людей»: что не так и как исправить, без вступлений и пересказа кода. Текст комментариев, docblock, Swagger, сообщений ошибок в проверяемом коде — по тому же разделу, тег `ai-style-text` (комментарии — `ai-style-comment`).

Отчёт — самое дорогое сверху: безопасность → двойное списание / потеря платежа → тупиковый статус → деплойный риск → архитектура → стиль.

Вердикт:
- **ПРОЙДЕНО** — 0 ошибок и 0 находок [БЕЗОПАСНОСТЬ]
- **НУЖНЫ ПРАВКИ** — 1–3 ошибки, 0 находок [БЕЗОПАСНОСТЬ]
- **КРИТИЧНО** — хотя бы 1 находка [БЕЗОПАСНОСТЬ], ИЛИ 4+ ошибок, ИЛИ запрещённая зависимость между слоями

## Сохранение


Создай файл `review_result/{datetime}_{type}.md` в корне проекта.

**Имя файла:**
- `datetime` — текущие дата и время в формате `YYYY-MM-DD_HH-MM`
- `type` — тип ревью: `all`, `staged`, `diff`, `path`, `module`, `mr-<iid>`, `security-audit`

## Аудит безопасности

Глубокий аудит всего репозитория — роль `/dev-security`, режим `audit` (`approaches/process/security.md`). `/dev-review --security-audit` — синоним, перенаправляет туда. В обычном ревью безопасность проверяется по `security.md` стека для каждого дифа.

# Рефакторинг легаси

Цель — привести существующий код к правилам фреймворка без поломки поведения.

## Порядок

1. **Инвентаризация** (`/dev-architect`, режим refactor): что есть — модули, слои, где нарушения правил (по `stacks/*/conventions.md` и `review-findings.md`), кто вызывает (HTTP, очереди, крон, другие сервисы), какие внешние контракты (URL, формат ответа, события, схема БД) трогать нельзя.
2. **Зафиксировать поведение до изменений:** есть тесты — прогнать; нет — написать характеризующие тесты на публичный контракт (HTTP-ответы, события, записи в БД) хотя бы для затрагиваемых сценариев.
3. **План — маленькими шагами**, каждый шаг сам по себе рабочий и сливаемый: перенос слоя, выделение интерфейса, вынос логики из контроллера в сервис, workflow вместо прямой связи доменов. Не «переписать модуль целиком одним MR».
4. **Strangler:** новый код пишется сразу по целевой структуре рядом со старым; старое переключается на новое и удаляется, когда на него не осталось ссылок. Как `superapp-api`: `app/` (легаси) → `parking_app/`, `super_app/` (целевая структура).
5. **Внешний контракт не меняется** в рамках рефакторинга. Нужно поменять API/схему — это отдельная задача с согласованием (`regulations/technical-approval.md`).
6. После каждого шага — сборка, линтер, тесты, сравнение с зафиксированным поведением.

## Правила

- Рефакторинг и новая функциональность — разные задачи/MR.
- Массово переписывать старое без задачи не надо: в новом коде — по правилам, старое — когда его трогает задача (правило бойскаута в пределах затрагиваемого модуля).
- Найденное в легаси «так сделано, но в правилах этого нет» — не копировать как образец и не исправлять молча: это тема для обсуждения (`core/principles.md`).
- Мёртвый код удаляется только после проверки, что на него нет ссылок (grep по проекту, маршрутам, конфигам очередей и крона).

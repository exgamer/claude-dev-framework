# Рефакторинг легаси

Цель — привести существующий код к правилам фреймворка без поломки поведения.

## Что переносится из легаси (O-17)

**Из легаси переносятся только контракты и бизнес-правила; реализация — не образец** (**[ОШИБКА]** на ревью, тег `legacy-pattern-copied`).

- **Контракты** — URL, формат ответа, таблицы и значения в БД, morph-типы, теги и ключи кэша, события, очереди — сохраняются или делаются по правилам (новой версией) — по ответу пользователя, вопрос обязателен (раздел «Контракт: сохранить или по правилам»).
- **Бизнес-правила** — как требования: *что* должно происходить («организация пользователя должна существовать»), без механизма легаси (`exists:users,id` в Request).
- **Реализация** — слой проверки, форма классов, фильтры, валидация, приёмы — только по правилам стека (`stacks/<stack>/*`; слой меры — `stacks/<stack>/security.md`, «Меры по слоям»). Соседний код проекта — образец, только если совпадает с правилами; расходится — пишем по правилам и называем расхождение в итоге и в `rules-log.md`.
- Инвентаризация (аналитик — в `requirements.md`, архитектор — в `design.md`) делит найденное на «контракт» и «реализация (не переносится)»; у каждой меры и проверки в `design.md`/`threats.md` указан слой.
- Отличие нового кода от легаси вне контракта — **вопрос пользователю, только если меняется видимое поведение** (результаты поиска, кто что видит и может сделать); иначе — строка в `design.md` («было / стало / почему») без вопроса.

Почему: мера `exists:` в Request, перенесённая из легаси в `threats.md`, противоречила P-17 и ушла бы в следующую задачу как требование (AINA-2978).

```
плохо (threats.md): «user_id — exists:users,id в Request, как в легаси»
хорошо:            «user_id — integer|gt:0 в Request; существование — workflow через репозиторий домена User → ValidationAppException по полю»
```

## Контракт: сохранить или по правилам — всегда вопрос (O-19)

**Перед дизайном рефактора/переноса — всегда вопрос пользователю** по каждому найденному контракту (раздел «Контракты»): сохраняем его или делаем по правилам. Не решается по умолчанию и не выводится из кода.

- **(а) сохранить контракт** — те же URL, поля, форматы, коды ошибок, события; меняется только реализация — шагами на месте или новым кодом рядом (strangler, «Порядок» п. 4), на который маршрут/обработчик переводится целиком одним деплоем. Неизменность доказывают характеризующие тесты. Версия не нужна.
- **(б) по правилам** — контракт приводится к правилам фреймворка (`regulations/rest-api.md`, формат ответа и ошибок стека) и выходит **новой версией**: HTTP — `/v2` (`rest-api.md`, «Версионирование»), событие — новая версия. Старая версия остаётся без изменений, потребители переходят сами, старая удаляется отдельной задачей, когда на неё не осталось вызовов.

**Переключателей нет ни в (а), ни в (б)** (**[ОШИБКА]** на ревью, тег `refactor-toggle`): ни feature-флага в конфиге/env/БД (`if (config('…use_new'))` / `if cfg.UseNew`), ни выбора реализации в DI по настройке, ни процента трафика, ни переключения по заголовку или параметру, ни shadow-трафика/dual-write. Новый контракт под старым URL/событием без версии — тоже нет: это (б), значит `/v2`.

Почему: флаг — две живые реализации за одним адресом, непонятно, какая отвечает, старую забывают удалить. Версия видна в URL и логах, у каждой версии один код.

```
плохо:  if (config('archive.use_new_engine')) { $this->newEngine->run(); } else { $this->legacy->run(); }
плохо:  POST /api/admin/v1/archive теперь отвечает в новом формате
хорошо (а): POST /api/admin/v1/archive — тот же контракт, реализация переписана, характеризующие тесты зелёные
хорошо (б): v1 — легаси без изменений; POST /api/admin/v2/archive — новый код по правилам; v1 удаляется отдельной задачей
```

- Таблицы, которые читают другие сервисы, версией не разводятся — схема меняется обратно совместимо (expand/contract, `approaches/patterns/migrations.md`).
- Контракт без внешних потребителей (технический компонент ниже) — вопрос всё равно задаётся, но (б) там без версии.

## Порядок

1. **Инвентаризация и карта связей** (`/dev-architect`, режим refactor; `impact-analysis.md` — обязательно, включая неявные связи и другие репозитории): что есть — модули, слои, где нарушения правил (по `stacks/*/conventions.md` и `review-findings.md`), кто вызывает (HTTP, очереди, крон, другие сервисы), какие внешние контракты есть (URL, формат ответа, события, схема БД) и их потребители — для вопроса «сохранить или по правилам» (O-19).
2. **Зафиксировать поведение до изменений:** есть тесты — прогнать; нет — написать характеризующие тесты на публичный контракт (HTTP-ответы, события, записи в БД) хотя бы для затрагиваемых сценариев. Неизменность ожиданий должна быть доказуема: тесты фиксируются до правок кода — отдельным коммитом (с подтверждения пользователя) или хэшем файлов тестов в `plan.md`; в конце — сверка хэша / `git diff` по тестам или прогон тех же тестов на дереве базовой ветки (AINA-2978: без этого «ожидания не правили» не проверить).
3. **План — маленькими шагами**, каждый шаг сам по себе рабочий и сливаемый: перенос слоя, выделение интерфейса, вынос логики из контроллера в сервис, workflow вместо прямой связи доменов. Не «переписать модуль целиком одним MR».
4. **Strangler:** новый код пишется сразу по целевой структуре рядом со старым; контракт — сохранён или новая версия по ответу пользователя, без флагов (раздел «Контракт: сохранить или по правилам»); старое удаляется, когда на него не осталось ссылок. Как `superapp-api`: `app/` (легаси) → `parking_app/`, `super_app/` (целевая структура).
5. **Контракты — по ответу пользователя** (раздел «Контракты» ниже). Без ответа контракт не трогается.
6. После каждого шага — сборка, линтер, тесты, сравнение с зафиксированным поведением.

Технический компонент без внешнего контракта (библиотека над ФС/расширением, потребители только внутри проекта и не переключаются в этой задаче) — по ответу пользователя можно **переписать** по правилам стека: соответствие — по функциональности (те же возможности, сценарии легаси — тестами нового кода), не по API; дефекты легаси исправляются; характеризующие тесты на легаси не пишутся, тесты нового кода легаси не импортируют (AINA-2744).

## Контракты

**Сохраняем контракт или делаем по правилам — всегда вопрос пользователю (O-19)** (как версия SDK, не решается по умолчанию). До вопроса — инвентаризация контрактов из кода (не из документации):

| Контракт | Что выписать |
|---|---|
| HTTP API | метод, URL, контекст, параметры, тело запроса, формат ответа (обёртка `success/data`, пагинация), коды и формат ошибок, заголовки (подписи, токены) |
| События | exchange/очередь, routing key, payload, кто публикует и кто потребляет |
| Данные для других | таблицы/колонки, которые читают или пишут другие сервисы; общие кэш-ключи |
| Консоль/крон | команды и расписания, на которые завязан деплой или эксплуатация |
| Потребители | кто вызывает: фронт, мобильные приложения (старые версии!), другие сервисы, партнёры, железо |

Вопрос — со списком найденного и вариантами:
- **(а) сохранить контракт** — тот же URL и формат, меняется только реализация, без версии;
- **(б) по правилам** — контракт по правилам фреймворка, новой версией (`/v2`, новая версия события); старая работает до отключения, срок — уточнить;
- можно по-разному для разных контрактов (например, HTTP — (а), события — (б)).

Рекомендация — (а), если в потребителях есть мобильные приложения, партнёры или железо; иначе — по ситуации, с обоснованием. Ответ записывается в `design.md` (раздел «Контракты»); характеризующие тесты пишутся на то, что сохраняется, и на старую версию при (б). Изменение контракта для других сервисов — ещё и согласование (`regulations/technical-approval.md`).

## Правила

- Рефакторинг и новая функциональность — разные задачи/MR.
- Массово переписывать старое без задачи не надо: в новом коде — по правилам, старое — когда его трогает задача (правило бойскаута в пределах затрагиваемого модуля).
- Найденное в легаси «так сделано, но в правилах этого нет» — не копировать как образец (раздел «Что переносится»); если правила тему не покрывают — это тема для обсуждения (`core/principles.md`).
- Мёртвый код удаляется только после проверки, что на него нет ссылок (grep по проекту, маршрутам, конфигам очередей и крона).

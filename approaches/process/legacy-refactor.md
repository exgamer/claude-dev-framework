# Рефакторинг легаси

Цель — привести существующий код к правилам фреймворка без поломки поведения.

## Порядок

1. **Инвентаризация и карта связей** (`/dev-architect`, режим refactor; `impact-analysis.md` — обязательно, включая неявные связи и другие репозитории): что есть — модули, слои, где нарушения правил (по `stacks/*/conventions.md` и `review-findings.md`), кто вызывает (HTTP, очереди, крон, другие сервисы), какие внешние контракты (URL, формат ответа, события, схема БД) трогать нельзя.
2. **Зафиксировать поведение до изменений:** есть тесты — прогнать; нет — написать характеризующие тесты на публичный контракт (HTTP-ответы, события, записи в БД) хотя бы для затрагиваемых сценариев.
3. **План — маленькими шагами**, каждый шаг сам по себе рабочий и сливаемый: перенос слоя, выделение интерфейса, вынос логики из контроллера в сервис, workflow вместо прямой связи доменов. Не «переписать модуль целиком одним MR».
4. **Strangler:** новый код пишется сразу по целевой структуре рядом со старым; старое переключается на новое и удаляется, когда на него не осталось ссылок. Как `superapp-api`: `app/` (легаси) → `parking_app/`, `super_app/` (целевая структура).
5. **Контракты — по ответу пользователя** (раздел «Контракты» ниже). Без ответа контракт не трогается.
6. После каждого шага — сборка, линтер, тесты, сравнение с зафиксированным поведением.

## Контракты

**Сохраняем ли контракты старого проекта — всегда вопрос пользователю** (как версия SDK, не решается по умолчанию). До вопроса — инвентаризация контрактов из кода (не из документации):

| Контракт | Что выписать |
|---|---|
| HTTP API | метод, URL, контекст, параметры, тело запроса, формат ответа (обёртка `success/data`, пагинация), коды и формат ошибок, заголовки (подписи, токены) |
| События | exchange/очередь, routing key, payload, кто публикует и кто потребляет |
| Данные для других | таблицы/колонки, которые читают или пишут другие сервисы; общие кэш-ключи |
| Консоль/крон | команды и расписания, на которые завязан деплой или эксплуатация |
| Потребители | кто вызывает: фронт, мобильные приложения (старые версии!), другие сервисы, партнёры, железо |

Вопрос — со списком найденного и вариантами:
- **(а) сохранить 1:1** — те же URL, поля, форматы, коды ошибок, события, схема для внешних читателей; внутри — по новым правилам;
- **(б) новая версия рядом** — новый контракт (`/v2`, новое событие), старый работает до отключения; срок совместимости — уточнить;
- **(в) менять свободно** — потребителей нет или все обновляются одновременно с этой задачей;
- можно по-разному для разных контрактов (например, HTTP — (а), события — (б)).

Рекомендация по умолчанию — (а), если в потребителях есть мобильные приложения, партнёры или железо; ответ записывается в `design.md` (раздел «Контракты»), характеризующие тесты пишутся на то, что сохраняется. Изменение контракта для других сервисов — ещё и согласование (`regulations/technical-approval.md`).

## Правила

- Рефакторинг и новая функциональность — разные задачи/MR.
- Массово переписывать старое без задачи не надо: в новом коде — по правилам, старое — когда его трогает задача (правило бойскаута в пределах затрагиваемого модуля).
- Найденное в легаси «так сделано, но в правилах этого нет» — не копировать как образец и не исправлять молча: это тема для обсуждения (`core/principles.md`).
- Мёртвый код удаляется только после проверки, что на него нет ссылок (grep по проекту, маршрутам, конфигам очередей и крона).

# Разбор замечаний ревьюеров в MR

Процедура для `/dev-mr`. Сторона — **автор MR**: код написан (нами или человеком), ревьюеры оставили треды, нужно по регламенту (`regulations/code-review.md`) на каждое замечание ответить — исправить или обосновать отказ — и при этом ничего не решить молча: все решения принимает пользователь на обсуждении, правки идут по плану, спорное попадает в `rules-log.md`.

Ревью кода нами (мы — ревьюер) — `review.md`. Там же `--mr` и блок «Открытые замечания ревьюеров» — это только *не дублировать* чужие треды; разбирать их — здесь.

```
/dev-mr <id-or-url>            # открытые треды ревьюеров
/dev-mr <id-or-url> --all      # и закрытые (resolved) тоже — для ретроспективы и правил
/dev-mr <id-or-url> --no-post  # ответы в треды не публиковать, только черновики в документе
```

## Принципы

- **Ни одно замечание не теряется и не решается молча.** Каждый тред — строка в документе с решением пользователя.
- **Ревьюер — не правило.** Замечание сверяется с правилами фреймворка и проекта. Совпало — исправляем по правилу. Противоречит — это спор, показываем обе стороны, решает пользователь; принятое — в правила через `/dev-rule`, отклонённое — обоснованный ответ в тред со ссылкой на правило. «Ревьюер сказал» само по себе правилом не становится, как и «в проекте так сделано» (`core/principles.md`).
- **`blocking:` без ссылки на правило** — ищем правило сами (памятка, `security.md`, `review-findings.md`, регламенты, `.claude/dev-rules.md`). Нашли — это ссылка для ответа. Нет — замечание всё равно разбирается по существу (баг и безопасность — исправляются), а отсутствие правила — строка `пробел`/`ревью` в `rules-log.md`.
- **Две остановки**: после документа (обсуждение замечаний) и после плана (обсуждение плана и текстов ответов). Коммит и пуш — по отдельному «да» на каждый.
- **Ответы в треды публикуются**, потому что регламент требует ответа автора на каждое замечание, — но только тексты, которые пользователь видел в плане и подтвердил, и в правильный момент: отказ и ответ на вопрос — сразу после «да» на план; «исправлено» — после пуша правок, с хэшем коммита (ответ без кода в ветке ревьюера только путает). `--no-post` — только черновики. Треды не резолвятся: закрывает открывший. Правила фреймворка не правятся до разбора лога.

## Шаг 1 — MR и ветка

1. URL → числовой IID из `/merge_requests/<iid>` (всё после `#` отбросить).
2. `glab mr view <iid> -F json` → `source_branch`, `target_branch`, `author.username`, `sha`, `web_url`, `title`. `glab` нет или не авторизован — сказать и остановиться: без тредов разбирать нечего.
3. `git fetch origin`. Правки нужны в ветке MR: `git branch --show-current` ≠ `source_branch` → дерево чистое (`git status --porcelain` пуст) — `git switch <source_branch>`; грязное — остановиться и спросить, `stash` не делать. Явно сказать, на какой ветке и каком коммите идёт разбор; локальный HEAD отстаёт от `sha` MR — `git pull --ff-only`.
4. Ключ задачи = имя ветки (`git.md`: ветка = `PROJECTKEY-номер`). Артефакты — `docs/tasks/<ключ>/`: есть `design.md`, `requirements.md`, `threats.md`, `review.md`, `rules-log.md` — читать, замечания сверяются и с ними.
5. Стек: `go.mod` с `gosdk-*` → Go, `composer.json` с `mps/core` → PHP.

## Шаг 2 — Треды

```
glab api --paginate "projects/:fullpath/merge_requests/<iid>/discussions?per_page=100"
```

Из каждой discussion: `notes[]` без `system: true`. Первая заметка — корень треда (замечание), остальные — ответы. Берём треды, где автор корня ≠ `author.username` MR; треды автора MR (вопросы к ревьюерам) — отдельной короткой строкой «автор спрашивает». Поля корня: `author.username`, `body`, `position.new_path` / `position.new_line` (DiffNote; у `DiscussionNote` позиции нет — замечание ко всему MR), `resolvable`, `resolved`, `created_at`, `id` discussion (нужен для ответа).

Без `--all` — только `resolved: false` (нерезолвабельные общие комментарии — всегда). Закрытые — одной цифрой в сводке.

**Префикс** — по `regulations/code-review.md`: регулярка по началу `body` без markdown-обёртки (`**blocking:**`, `blocking (security):`, `Blocking:` — одно и то же): `blocking`, `suggestion`, `nit`, `question`, `praise`; прочие Conventional Comments (`issue`→`blocking`, `todo`/`chore`→`suggestion`, `thought`→`question`) приводятся к пяти регламентным. **Без префикса** — определить по содержанию и записать `— → blocking` (стрелка = выведено нами, не поставлено ревьюером); в обсуждении это отдельно видно, в ответ ревьюеру про это не пишем.

**Состояние треда**: прочитать ответы — автор уже ответил / ревьюер согласился / спор идёт; и **закрыто ли в текущем HEAD**: найти место по `new_path`+`new_line`, строка уехала — по фрагменту кода из цитаты/контекста. Статусы: `открыто`, `исправлено в HEAD, тред открыт` (нужен только ответ), `спор в треде`.

Нет тредов ревьюеров — сказать «Открытых замечаний ревьюеров нет» (и сколько закрытых), стоп.

## Шаг 3 — Анализ каждого замечания

Для каждого треда:

1. **Суть** одной строкой — что ревьюер хочет изменить и почему (своими словами, без цитаты целиком).
2. **Правило**: grep по `{DF}/stacks/<stack>/{checklist,conventions,style,security,review-findings,review-tags}.md`, `{DF}/regulations/`, `{DF}/architecture/`, `{DF}/core/decisions.md`, `.claude/dev-rules.md` проекта. Записать ссылку (файл, пункт/тег) или «правила нет».
3. **Отношение к правилам** — одно из:
   - **по правилу** — замечание совпадает с правилом фреймворка/проекта (значит, код правило нарушил; если код писали мы — это ещё и строка в `rules-log.md`: почему пропустили — пробел в памятке, ревью не поймало);
   - **верно, правила нет** — баг, безопасность, потеря данных, читаемость по существу; исправлять, кандидат в правила (`review-findings.md` стека или регламент);
   - **противоречит правилу** — ревьюер просит то, что правило запрещает, или наоборот; спор: показать пользователю правило и аргумент ревьюера, рекомендация — с чьей стороны и почему;
   - **вкус** — `nit`/`suggestion` без правила и без ущерба; рекомендация по стоимости (пара строк — принять, перестройка — отклонить с обоснованием);
   - **вопрос** — ответ из кода, `design.md`, `requirements.md`; вопрос, вскрывший баг, переводится в «верно, правила нет»;
   - **уже сделано** — закрыто в HEAD, нужен только ответ в тред.
4. **Объём правки**: файлы, слои, нужны ли миграция/контракт/`design.md`. Правка выходит за мелкую (`approaches/process/security.md` — чувствительные зоны; новые эндпойнты, таблицы, события, контракт) — так и записать: это пойдёт не правкой на месте, а в `/dev` или `/dev-architect`.
5. **Рекомендация**: `исправить` / `отклонить (обоснование)` / `ответить` / `спор — решает пользователь` / `в /dev`.

Правил по теме нет и замечание повторяется (2+ треда одного класса или уже было в `review.md`/прошлых логах) — пометить «повторяющееся»: сильный кандидат во фреймворк.

В чат — та же таблица без колонок «Правило» и «Решение» (чтобы читалась), и после неё — вопросы по спорным строкам текстом: по каждому спору варианты и рекомендация, одним списком (`core/principles.md`, «Пробелы и споры»). Пользователь отвечает по строкам или «всё по рекомендации». Не переходить к плану, пока решений нет. Решения — в колонку «Решение» и раздел «Решения» (кто решил: пользователь / по рекомендации).

Решение «ревьюер прав, правило неверное» — не править правило сейчас: строка `противоречие` в `rules-log.md`, правило меняется на разборе лога (`/dev-rule`); правка кода в этой задаче — по решению пользователя.

## Шаг 5 — План правок и обсуждение (остановка 2)

Из решений `исправить` — раздел «План правок»:

- порядок: безопасность → `blocking` → принятые `suggestion`/`nit`; зависимые правки — вместе;
- на каждую: тред(ы), файлы, что меняется, какие тесты добавить/поправить, затрагивает ли `design.md`/`threats.md`/Swagger/миграции (тогда обновить и их);
- что не правится здесь: правки «в /dev» — отдельным списком с причиной;
- проверки после: тесты пакетов/модулей задетых файлов, линтер/статанализ стека, самопроверка `self-check.md`;
- **тексты ответов** на каждый тред (раздел «Ответы в треды», ниже) и момент публикации: «после „да“» для отказов, вопросов и уже сделанного в HEAD; «после пуша» для исправлений.

Показать план вместе с текстами ответов, обсудить, получить «да». «Да» на план = разрешение опубликовать эти тексты в указанные моменты (без `--no-post`). План меняется — документ меняется.

## Шаг 6 — Выполнение

- Правки — по правилам разработчика стека: `skills/dev-<stack>/SKILL.md`, Шаги 1, 3–5 (памятка, `capabilities.md`, эталон, unit-тесты вместе с кодом). Только файлы из плана. Соседний код с тем же нарушением вне тредов — не править молча: отметить в «Итог» как находку.
- После каждой правки — тесты задетого пакета; в конце — полный прогон тестов и линтера стека.
- **Ответы в треды** — текст на каждый тред в разделе «Ответы в треды», по правилам «Как писать ответ» ниже. Публикация: `glab api -X POST "projects/:fullpath/merge_requests/<iid>/discussions/<discussion_id>/notes" -f body=…`.
  - Сразу после «да» на план: отказы, ответы на вопросы, «уже сделано в HEAD».
  - После пуша исправлений (пуш — по своему «да»): ответы «исправлено» с хэшем. Пуша в этой сессии не было — эти ответы остаются черновиками, перечислить в «Итог».
  - Текст изменился относительно плана (например, правка пошла иначе) — показать новый текст и получить «да» на него отдельно.
  - `--no-post` — ничего не публиковать. Треды не резолвим — закрывает открывший (`code-review.md`). Каждую публикацию отметить в документе: тред, время, `id` заметки.
- `rules-log.md` задачи — строки по каждому замечанию, которое задело правила: `ревью` (класс, которого нет в `review-findings.md`), `противоречие` (ревьюер против правила), `пробел` (правила нет), `спор` (задет `core/decisions.md`); колонка «Предложение» — куда. Формат — `core/rules-evolution.md`.
- Коммит — по `git.md`, одной логической правкой, **только по «да»**. Напомнить: после значимых правок апрувы сбрасываются, ревьюер с `blocking:` должен перепроверить.

### Как писать ответ

Ответ читает живой разработчик под аккаунтом пользователя. Общее правило текста — `core/style.md`, «Любой текст для людей» (суть первой фразой, без благодарностей, канцелярита, пересказа и упоминания фреймворка). Ниже — что важно именно для тредов.

- 1–3 предложения, суть первой фразой: что сделал / почему нет / ответ. Обращение как принято в треде (на «ты», если ревьюер на «ты»).
- Исправлено: что именно и где — файл/класс, хэш коммита. Не пересказывать диф.
- Отклонено: причина одной фразой и ссылка на правило или регламент (пункт/тег), если есть. Не спорить о вкусе — если правила нет, так и сказать: «оставил как есть, причина …».
- Вопрос: ответ по существу, при необходимости — где это в коде/дизайне.
- Не форматировать списками, если ответ в одну мысль.

```
плохо:  Спасибо за замечание! Вы абсолютно правы, проверка exists: в Request действительно
        выполняет запрос в БД. В рамках исправления данная проверка была перенесена в сервис,
        где осуществляется поиск через репозиторий. Надеюсь, теперь всё корректно 🙂
хорошо: Перенёс проверку из StoreRequest в BuildingService через репозиторий, в Request осталась
        только валидация формата — 3f9a2c1.

плохо:  Благодарю за предложение. Однако согласно принятым в проекте правилам передача данных
        между слоями осуществляется через DTO, поэтому было принято решение оставить текущую реализацию.
хорошо: Оставил DTO: массивы между слоями у нас не передаём (регламент, п. про DTO по всей цепочке), иначе
        затирается типизация сеттеров.
```

## Шаг 7 — Итог

Раздел «Итог» в документе и в чат, не длиннее 15 строк:

- исправлено (треды, файлы), отклонено с обоснованием (треды), отвечено (треды), ушло в `/dev`;
- тесты/линтер — результат словами и выводом при падении;
- опубликовано ответов / осталось черновиками (и почему — нет пуша, `--no-post`);
- строк в `rules-log.md` и предложение `/dev-rule <путь>`;
- что ждёт подтверждения: коммит, пуш, ответы «исправлено».

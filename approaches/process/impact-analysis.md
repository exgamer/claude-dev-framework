# Карта связей: что затронет изменение

Перед любым изменением существующего кода — рефактор, доработка, новая фича, которая встраивается в существующее, — нужно знать **всё, что зависит от изменяемого, и всё, от чего зависит оно само**. Иначе что-то забудем или сломаем там, где не смотрели.

Карту делает архитектор в Фазе 1 (раздел «Связи» в `design.md`), разработчик сверяется с ней при каждом изменении символа, ревью и QA проверяют по ней, что ничего не сломано.

---

## Что искать

### Входящие — кто зависит от изменяемого

| Связь | Как найти |
|---|---|
| Вызовы функций/методов/сервисов | поиск по имени символа (Go: `grep -rn 'Name(' internal`; PHP: по имени метода и по FQCN/интерфейсу, в режиме IDE — ещё `search_structural`); объявления и сигнатуры — через IDE, если доступна (`code-navigation.md`) |
| Реализации интерфейса и его потребители | поиск по имени интерфейса; DI — `*_factory.go`, `app.go` / `definitions.php`, провайдеры |
| HTTP-клиенты эндпойнта | фронт, мобильные приложения (в т.ч. старые версии), другие сервисы, партнёры, железо — по URL и имени роута в доступных репозиториях; остальное — вопрос |
| Имя роута | генератор/сидер прав (fail-open, если имя перестанет попадать под конвенцию), `route()`-вызовы, ссылки во фронте |
| Потребители событий | кто слушает exchange/routing key; payload как контракт |
| Читатели/писатели данных | кто ещё читает и пишет таблицу/колонку (другие модули, сервисы, отчёты, BI, views, триггеры); кэш-ключи, которые читают другие |
| Консоль, крон, очереди | команды и расписания, обработчики очередей (`config/queue.php`, consumers_factory), feature-флаги |
| Тесты, Swagger, конфиг | тесты на изменяемое, аннотации, env-переменные |

### Исходящие — от чего зависит изменяемое

Репозитории и сервисы других модулей/доменов, внешние интеграции, события, которые потребляет, конфиг и секреты, кэш, транзакции.

### Неявные — то, что не находится по имени символа

- **Строковые значения**: статусы, типы, enum — `switch`/`match`/`map`, `Rule::in`/`in:`, swagger `enum:`, словари фронта, SQL-литералы, `const`-блоки.
- **Новый кейс enum** — поиск по имени enum (не только по старым значениям): мапперы, allowlist, `match`/`switch` по нему — «источники истины» набора (`MediaCollectionMapper::MAP[тип модели]`). Каждый — связь «меняется вместе»; пропущенный — разъезд, на ревью `enum-list-drift` (AINA-2978).
- **Новый статус/значение без потребителя** — у каждого нового значения статуса есть тот, кто его обрабатывает дальше (крон, consumer, переход в workflow, фильтр списка; для терминального статуса ошибки — ручной разбор, если описано, чем он выражается: выборка или алерт, `approaches/patterns/outbox.md`, «Форма», п. 3); показать его в `design.md`/MR. Статус без потребителя — тупик навсегда, на ревью `status-without-consumer` (уровень — `review-tags.md`; прод-инцидент `parking-session-service`).
- **Имена по строке**: DI по алиасу, рефлексия, имена очередей/exchange в конфиге, имена роутов, имена прав, ключи кэша, имена колонок в raw SQL.
- **Данные**: что лежит в колонках на stage/prod (новый NOT NULL, новое значение enum, смена типа).
- **Другие репозитории**: сервисы-потребители, которых нет в текущем проекте.

## Как собрать

1. Список изменяемого: символы (типы, функции, методы, интерфейсы), URL/роуты, события, таблицы/колонки, кэш-ключи, конфиг, значения enum.
2. По каждому пункту — поиск входящих, исходящих и неявных связей по таблице выше. Поиск — по имени **и** по строковому литералу.
3. Другие репозитории: доступны локально — поиск в них (только чтение); недоступны или неизвестно, кто потребляет, — **вопрос пользователю** в общий список («кто ещё вызывает `POST /…` / слушает `promocode.redeemed` / читает таблицу `…`?»).
4. Каждую найденную связь классифицировать:
   - **меняется вместе** — правка входит в план (своей задачей или в задачу изменения);
   - **сохраняется** — контракт не трогаем, нужен тест, что не сломано;
   - **проверено, не затронута** — с указанием, как проверено. Проверяется разово на ревью (`git diff` по путям), не постоянным автотестом: тест «легаси-потребитель по-прежнему вызывает легаси» упадёт в задаче, которая его переключает (ревью AINA-2744).

## Формат — раздел «Связи» в `design.md`

```markdown
## Связи

Изменяется: `TariffService.Update`, `PUT /admin/tariffs/{id}`, колонка `tariffs.grace_minutes`, enum `TariffStatus` (+`archived`).

| # | Связь | Тип | Где | Что делаем | Тест/проверка |
|---|---|---|---|---|---|
| C1 | `TariffService.Update` ← `UpdateTariffWorkflow` | вызов | internal/workflows/billing/tariff/… | меняется вместе (новая сигнатура) | unit workflow |
| C2 | `TariffStatus` → `switch` в `CalculateSessionDebt` | неявная (enum) | internal/workflows/… | меняется вместе: обработать `archived` | unit на `archived` |
| C3 | `PUT /admin/tariffs/{id}` ← админка (фронт) | HTTP | другой репозиторий | сохраняется: поля и ответ те же | регрессия API |
| C4 | `tariffs.grace_minutes` ← отчёт BI | данные | неизвестно | **вопрос пользователю** | — |

Не затронуто (проверено): события тарифа — не публикуются; кэш `tariff:*` — формат не меняется.
```

## Обратная совместимость — вопрос пользователю (O-29)

Правка существующего — доработка, фича, задевающая существующее, рефактор, перенос — до кода выясняет у пользователя, нужна ли обратная совместимость. Архитектор её сам не решает.

- **Контракт** — то, на что опирается код вне сервиса: HTTP API (URL, вход, поля и коды ответа, формат ошибок), события и сообщения брокера (очередь, routing key, payload), таблицы, колонки и формат кэша, которые читают или пишут другие. Что выписать по каждому — таблица `legacy-refactor.md`, «Контракты». Изменение контракта — **всегда вопрос**, даже если карта потребителей не нашла: потребитель контракта может быть неизвестен (старая версия мобильного приложения, партнёр, отчёт BI). Изменение — то, что ломает прежнего потребителя: удалено или переименовано поле, сменились тип, обязательность входа, код ответа, URL, payload, формат. Ломающее добавление — тоже изменение: новое обязательное поле входа, новое значение enum или новый код ошибки в ответе или событии, колонка `NOT NULL` без default в таблице, куда пишут другие. Добавление, которое старых не ломает (новое поле ответа, необязательный параметр, новый эндпойнт или событие), — без вопроса, строкой «сохраняется» в «Связях».
- Вопрос — списком затронутых контрактов (что меняется, известные потребители или «не найдены») с вариантами: (а) сохранить совместимость — новое рядом, старое не удаляется: новые поля без удаления старых, таблицы — expand/contract (`approaches/patterns/migrations.md`), API и события — новой версией (`regulations/rest-api.md`, «Версионирование»); (б) ломать — с согласованием (`regulations/technical-approval.md`) и порядком выкатки потребителей. Рекомендация — (а), если потребители неизвестны или среди них мобильные приложения, партнёры, железо.
- **Остальное существующее** (сигнатуры, методы, типы, env и конфиг) — вопрос только при найденном потребителе вне сервиса: другой сервис, общий пакет (публичный метод пакета SDK или библиотеки), манифест деплоя, задающий переименованную или удалённую переменную. Такого нет — вызовы правятся вместе с правкой (связь «меняется вместе»), без вопроса.
- Рефактор и перенос задают этот вопрос в своей форме — «сохранить контракт / по правилам новой версией» (`legacy-refactor.md`, «Контракт: сохранить или по правилам», O-19); второй не задаётся. Баг-фикс контракт не меняет — это граница `/dev-fix` (`bugfix.md`, «Границы»).
- Ответ — в `design.md`, раздел «Контракты» (контракт → решение); связь в «Связях» — «сохраняется» или «меняется вместе» по ответу.

Почему: о потребителе, которого нет в репозитории, знает пользователь, а не код; молча сломанный контракт находят уже на проде.

```
плохо:  поле `amount` ответа `GET /v1/orders/{id}` переименовано в `total`, потребителей поиск не нашёл — вопроса нет
хорошо: «Контракты: `GET /v1/orders/{id}` — `amount` → `total`; потребители не найдены. (а) отдавать оба поля, `amount` удалить отдельной задачей — рекомендация; (б) переименовать с согласованием»
```

## Кто и как использует

| Роль | Что делает с картой |
|---|---|
| Архитектор | строит её в Фазе 1; связи «меняется вместе» — задачи в `plan.md`; неизвестные потребители и изменение контракта — вопросы («Обратная совместимость») |
| Безопасник | проверяет связи с auth, правами, деньгами, внешними системами |
| Разработчик | перед изменением символа — ищет использования ещё раз (карта могла устареть); нашлась связь, которой нет в карте, — дописать её в «Связи» `design.md` и упомянуть в итоге; после изменений — повторный поиск по изменённым символам и литералам |
| Ревью | каждая связь «меняется вместе» — изменена, «сохраняется» — не сломана; изменённый символ, использование которого не учтено в карте, — `impact-unhandled-usage`; контракт изменён без ответа пользователя в «Контрактах» `design.md` — `contract-change-unasked` |
| QA | на связи «сохраняется» — регрессионные кейсы/тесты; на «меняется вместе» — кейсы на новое поведение |

Карта не нужна только для изменения, у которого нет внешних использований (новый файл, который ещё никто не вызывает) — и это тоже пишется одной строкой: «связей с существующим кодом нет, проверено поиском по …».

# Цепочка ролей

```
задача → /dev-architect (тех. дизайн + план) → [/dev-security design — если есть чувствительные зоны]
       → /dev-go | /dev-php | /dev-front (код)
       → /dev-review (ревью тем же сводом правил) → /dev-qa (тест-кейсы, тесты)
```

`/dev` — роутер: определяет стек, тип задачи (новая фича / рефактор легаси / перенос на другой стек), ведёт цепочку и останавливается после каждого шага на подтверждение пользователя. Любой шаг можно запустить отдельно по готовому артефакту.

## Авто-режим

```
Фаза 0  контекст: стек, тип задачи, ключ, артефакты прошлой сессии
Фаза 1  разведка без вопросов: дизайн + план, модель угроз, предпроверка окружения, чеклист ниже
Фаза 2  ОДИН список вопросов пользователю (варианты + рекомендация) + политика новых вопросов
Фаза 3  ответы → design/threats/plan; решения уровня правил → /dev-rule
Фаза 4  разработка по волнам (до 3 параллельно), сборка/тесты после каждой волны
Фаза 5  ревью → исправления → ревью (до 3 кругов)
Фаза 6  QA: кейсы + автотесты, прогон
Фаза 7  результат: что сделано, как проверено, что нет, решения, отложено, готовый коммит (без коммита)
```

Пользователь нужен дважды: ответить на вопросы и подтвердить коммит. Если вопросов нет — один раз.

### Что выяснить до старта

Каждый пункт — закрыть по коду/правилам (записать в `design.md`, откуда взято) или вынести в вопрос. Не спрашивать то, что можно выяснить самому.

| # | Что | Где искать до вопроса |
|---|---|---|
| 1 | Что считается «готово»: критерии приёмки, граничные случаи | задача, трекер, соседний функционал |
| 2 | Срез: что делаем сейчас, что откладываем | задача; по умолчанию — минимальный рабочий срез (`core/principles.md`) |
| 3 | Контракт API: URL, контекст, поля, коды ошибок, совместимость со старыми клиентами | `regulations/rest-api.md`, соседние эндпойнты, swagger |
| 4 | Данные: новые таблицы/поля, NOT NULL, значения enum, что лежит в колонках на stage/prod | миграции проекта, модели; prod-данные — только вопрос |
| 5 | Версия Go SDK (всегда вопрос, O-4); версия mps/core — из `composer.lock` | `go.mod`, `composer.lock` |
| 6 | Открытые споры `core/decisions.md`, которые задевает задача | журнал решений |
| 7 | Пробелы: нужен тип компонента/слой/интеграция без правила и без образца | `stacks/*`, `architecture/*`, эталоны |
| 8 | «Сделано в проекте, но нет в регламенте» в затрагиваемой области | соседний код vs правила |
| 9 | Что требует согласования до кода (новая технология, внешняя система, изменение схемы для других сервисов) | `regulations/technical-approval.md` |
| 10 | Продуктовые решения из модели угроз (повтор оплаты, политика доступа) | `threats.md` → «Решения, которые нужны» |
| 11 | Окружение: чем собрать и прогнать тесты, общие контейнеры БД/Redis | `docker ps`, `composer.json`/`Makefile`, CI |
| 12 | Рефактор/перенос: какой внешний контракт обязан сохраниться | `legacy-refactor.md`, `stack-migration.md` |
| 13 | Ветка и номер задачи для коммитов | `regulations/git.md`, запрос |

### Новые вопросы по ходу

Политику выбирает пользователь в Фазе 2: **(а) по умолчанию** — решить по рекомендации, записать в правила (`/dev-rule`) и вынести в отчёт; (б) отложить затронутый кусок, остальное доделать, вопрос — в результат. Работа целиком из-за нового вопроса не останавливается. Исключение — то, что требует согласования до кода (п. 9) или меняет внешний контракт: такой кусок всегда откладывается до ответа.

## Артефакты

Лежат в проекте: `docs/tasks/<ключ-задачи>/` (ключ — номер задачи из трекера или короткий slug).

| Файл | Кто пишет | Что внутри |
|---|---|---|
| `design.md` | архитектор | что делаем, домены/модули/слои, API (URL, запрос/ответ), сущности и миграции, что требует согласования, открытые вопросы |
| `threats.md` | безопасник | угрозы по эндпойнтам/сценариям, теги, конкретные меры, где в коде, тесты; продуктовые решения |
| `plan.md` | архитектор | задачи, зависимости между ними, волны параллельной работы (`planning.md`) |
| `review.md` | ревьюер | находки по уровням, вердикт |
| `qa.md` | QA | тест-кейсы по критериям приёмки, что покрыто автотестами |
| `result.md` | `/dev` | итог: сделано, как проверено, не проверено, решения по ходу, отложено, готовый коммит |

Артефакт — источник правды для следующей роли. Если по ходу работы дизайн меняется — меняется `design.md`, а не только код.

## Правила для всех ролей

- Перед работой — `core/principles.md` и правила своего стека.
- Пробел или спор — стоп на этом месте и обсуждение (`core/principles.md`, «Пробелы и споры»), после решения — `/dev-rule`. В авто-режиме `/dev`: на разведке — в общий список вопросов; по ходу работы — по политике новых вопросов (см. выше).
- Вопросы пользователю — обычным текстом: что не ясно, 2–3 варианта, рекомендация. Не опросником с кнопками.
- Коммит/пуш — только по явному подтверждению на каждый раз.

# Цепочка ролей

```
задача → /dev-analyst (требования) → /dev-architect (дизайн + связи + план) → [/dev-security design]
       → /dev-qa cases (тест-кейсы по требованиям, до кода)
       → /dev-go | /dev-php (код + unit-тесты, волнами)
       → /dev-qa tests (интеграционные/e2e, регрессия по связям)
       → /dev-review (независимое ревью кода и тестов) ⇄ исправления (до 3 кругов)
       → результат (Definition of Done) → разбор rules-log
```

`/dev` — главная точка входа. По умолчанию **авто-режим**: разведка → один список вопросов → результат без остановок (ниже). `/dev --step` — пошагово, со стопом после каждой роли. Любой шаг можно запустить отдельно по готовому артефакту.

## Авто-режим

```
Фаза 0  контекст: стек, тип задачи, ключ, артефакты прошлой сессии
Фаза 1  разведка без вопросов: требования, дизайн + карта связей + план, модель угроз, тест-кейсы, предпроверка окружения, чеклист ниже
Фаза 2  ОДИН список вопросов пользователю (варианты + рекомендация) + политика новых вопросов
Фаза 3  ответы → design/threats/plan; всё, что касается правил, → rules-log.md
Фаза 4  рабочая ветка; разработка по волнам (до 3 параллельно) с unit-тестами; сборка/тесты после каждой волны; статусы в plan.md
Фаза 5  QA: интеграционные/e2e тесты по qa.md, регрессия по связям, прогон
Фаза 6  независимое ревью (отдельный субагент) → исправления → тесты → ревью (до 3 кругов)
Фаза 7  результат: что сделано, как проверено, что нет, решения, отложено, готовый коммит (без коммита)
Фаза 8  разбор rules-log.md: по каждой строке — во фреймворк / в проект / оставить
```

Пользователь нужен: ответить на вопросы, решить по логу отклонений и подтвердить коммит.

### Контекст ролей

Правил на роль — 15–40 тыс. токенов при загрузке по задетым слоям (замер 2026-10-09: оркестратор ~15k, разработчик ~35k, архитектор ~55k; ревьюер «всё сразу» был ~100k — поэтому грузит по слоям, `skills/dev-review`, Шаг 2). Если одна сессия выполняет все роли подряд, контекст переполняется и при сжатии первыми теряются детали правил. Поэтому:

- `/dev` только координирует: каждая роль и каждая задача разработки — отдельный агент со свежим контекстом. Оркестратор читает лишь `core/principles.md` и этот файл.
- Агенты — `agents/df-*.md` (ставятся `install.sh` в `~/.claude/agents/`); общие правила субагента — `subagent.md`:

  | Роль | Агент | Имя | Инструменты |
  |---|---|---|---|
  | аналитик | `df-analyst` | Алан | чтение, Bash, запись артефактов |
  | архитектор | `df-architect` | Олжас | то же |
  | безопасник (`design`) | `df-security` | Дима | то же |
  | QA (`cases` / `tests`) | `df-qa` | Асель / Асыл | то же + тесты |
  | разработчик | `df-go` / `df-php` | Адиль / Рома / Асхат / Даулет / Берик / Саша | чтение, Bash, правка кода |
  | ревьюер | `df-review` | Илюха | чтение, Bash, только запись `review.md` (без `Edit`) |

  **Имена — только чтобы пользователь видел в консоли, кто работает.** Оркестратор ставит подпись запуска (`description` у Agent) «Роль Имя: задача» — `Разработчик Даулет: T3 TariffRepository`, `Ревьюер Илюха: круг 2`.
  - QA и разработчик — случайное свободное имя из пула. QA — одно на задачу (`cases` и `tests` делает один). Разработчик — имя закрепляется за задачей `plan.md` до конца, включая исправления после ревью; среди одновременно работающих имена не повторяются. Имя пишется в статус `plan.md` (`в работе — Даулет`) и в шапку `qa.md` (`QA: Асель`) — чтобы продолжить в новой сессии с теми же именами.
  - Тем же именем роль подписана в итоге `/dev`, в колонке «Кто решил» `rules-log.md` и в заголовке круга `review.md`.
  - Имя не меняет роль: в поручение агенту оно не идёт («ты — Рома» не пишется), правила, инструменты и модель — из типа агента.
  - Имени нет в коде и git: ни в комментариях, ни в `@author`, ни в коммитах и MR — только консоль и `docs/tasks/<ключ>/`.

  Ни у одного агента нет `Agent` — субагенты своих субагентов не запускают. Модель у всех — `inherit` (как у основной сессии): переключение `/model` действует на все роли сразу. Если нужно развести расход по квотам (на Max у Fable отдельная недельная квота), можно поставить `model:` отдельной роли в файле агента — например, `df-review` как самому тяжёлому и независимому.
- Между ролями передаются **артефакты** (`docs/tasks/<ключ>/*.md`), а не пересказ: всё, что нужно следующей роли, должно быть записано в файл.
- Поручение агенту (что читать и как себя вести, агент знает сам):
  ```
  Задача: <ключ>; артефакты: docs/tasks/<ключ>/{requirements,design,plan,threats,qa}.md (какие есть).
  Режим: <feature/refactor/migrate | cases/tests> (если есть у роли).
  Твоя задача из plan.md: <id>, файлы: <список> (разработчику). Базовая ветка: <release> (ревьюеру).
  Ответы пользователя: <…>. Политика новых вопросов: <а/б>.
  ```
- Роль, запущенная пользователем напрямую (`/dev-go`, `/dev-review`…), работает в текущей сессии как обычно.

### Что выяснить до старта

Каждый пункт — закрыть по коду/правилам (записать в `design.md`, откуда взято) или вынести в вопрос. Не спрашивать то, что можно выяснить самому.

| # | Что | Где искать до вопроса |
|---|---|---|
| 1 | Что считается «готово»: критерии приёмки, граничные случаи (делает аналитик → `requirements.md`) | задача, трекер, соседний функционал |
| 2 | Срез: что делаем сейчас, что откладываем | задача; по умолчанию — минимальный рабочий срез (`core/principles.md`) |
| 3 | Контракт API: URL, контекст, поля, коды ошибок, совместимость со старыми клиентами | `regulations/rest-api.md`, соседние эндпойнты, swagger |
| 4 | Данные: новые таблицы/поля, NOT NULL, значения enum, что лежит в колонках на stage/prod | миграции проекта, модели; prod-данные — только вопрос |
| 5 | Версия Go SDK (всегда вопрос, O-4); версия mps/core — из `composer.lock` | `go.mod`, `composer.lock` |
| 6 | Открытые споры `core/decisions.md`, которые задевает задача | журнал решений |
| 7 | Пробелы: нужен тип компонента/слой/интеграция без правила и без образца | `stacks/*`, `architecture/*`, эталоны |
| 8 | «Сделано в проекте, но нет в регламенте» в затрагиваемой области | соседний код vs правила |
| 9 | Что требует согласования до кода (новая технология, внешняя система, изменение схемы для других сервисов) | `regulations/technical-approval.md` |
| 10 | Продуктовые решения из модели угроз (повтор оплаты, политика доступа) | `threats.md` → «Решения, которые нужны» |
| 11 | Окружение: чем собрать и прогнать тесты, общие контейнеры БД/Redis | `docker ps`, `composer.json`/`Makefile`, CI |
| 11a | Нужно ли по ходу трогать БД: прогон миграций, тесты с пересозданием схемы, сиды, массовые правки данных — какая БД и разрешено ли (`core/principles.md`, «Действия с БД») | всегда вопрос пользователю |
| 12 | Рефактор/перенос: **сохранить контракт или делать по правилам** (HTTP API, события, данные для других, консоль) — всегда вопрос (O-19), со списком найденных контрактов и вариантами «сохранить / по правилам новой версией» | инвентаризация по `legacy-refactor.md`, «Контракты» |
| 13 | Ветка и номер задачи для коммитов | `regulations/git.md`, запрос |
| 14 | Новый сервис с нуля: основа (шаблон или с нуля), имя модуля/пакета, какие kernels нужны (HTTP, Postgres, Redis, Rabbit, консоль) | `regulations/service-requirements.md`, `stacks/<stack>/structure.md`, задача |
| 15 | Кто ещё зависит от изменяемого и не виден в проекте: другие сервисы, фронт, мобильные приложения, отчёты/BI, партнёры (карта связей) | `impact-analysis.md`; доступные локально репозитории |

### Новые вопросы по ходу

Политику выбирает пользователь в Фазе 2: **(а) по умолчанию** — решить по рекомендации, записать в `rules-log.md` и вынести в отчёт; (б) отложить затронутый кусок, остальное доделать, вопрос — в результат. Работа целиком из-за нового вопроса не останавливается. Исключение — то, что требует согласования до кода (п. 9) или меняет внешний контракт: такой кусок всегда откладывается до ответа.

## Артефакты

Лежат в проекте: `docs/tasks/<ключ-задачи>/` (ключ — номер задачи из трекера или короткий slug).

| Файл | Кто пишет | Что внутри |
|---|---|---|
| `requirements.md` | аналитик | участники и права, сценарии (с негативными), бизнес-правила R*, критерии приёмки AC*, нефункциональное, границы, термины, неясности |
| `design.md` | архитектор | что делаем, домены/модули/слои, API (URL, запрос/ответ), сущности и миграции, что требует согласования, открытые вопросы |
| `threats.md` | безопасник | угрозы по эндпойнтам/сценариям, теги, конкретные меры, где в коде, тесты; продуктовые решения |
| `plan.md` | архитектор | задачи, зависимости между ними, волны параллельной работы (`planning.md`) |
| `qa.md` | QA: кейсы — до кода, покрытие — после | кейсы по AC*/R*/S*/T*/C* с уровнем unit / интеграционный / e2e; после `tests` — что покрыто автотестами |
| `review.md` | ревьюер | находки по уровням, вердикт; повторные круги — разделами «Круг N» |
| `rules-log.md` | все роли (субагенты — через оркестратора) | споры, пробелы, отступления, решения по ходу, расхождения проекта, правки стиля — с предложением «фреймворк / проект / оставить»; после разбора — статус |
| `result.md` | `/dev` | итог: сделано, как проверено, не проверено, решения по ходу, отложено, готовый коммит |

Артефакт — источник правды для следующей роли. Если по ходу работы дизайн меняется — меняется `design.md`, а не только код.

## Definition of Done

Задача «готова», когда выполнено всё (что не выполнено — в результате с причиной):

- [ ] Каждый критерий приёмки AC* из `requirements.md` покрыт тестом (unit / интеграционный / e2e — по `qa.md`) и тест зелёный.
- [ ] Новая логика покрыта unit-тестами её автора; регрессия по связям «сохраняется» — зелёная.
- [ ] Сборка, линтер/статанализ, все тесты — зелёные, вывод приложен; проверка зависимостей на уязвимости (Go — `govulncheck ./...`, PHP — `composer audit`), если инструмент доступен.
- [ ] Меры из `threats.md` реализованы; связи из «Связи» учтены; требования к производительности (`approaches/patterns/performance.md`) и конкурентности (`concurrency.md`: решения из «Конкурентность» реализованы и покрыты тестами с параллельными запросами; Go — `go test -race` чистый) соблюдены.
- [ ] Независимое ревью — ПРОЙДЕНО (0 [ОШИБКА], 0 [БЕЗОПАСНОСТЬ]).
- [ ] Документация: Swagger перегенерирован при изменении API; новые env/конфиг описаны (`.env.example`/README); миграции обратно совместимы, порядок выкатки и откат описаны в «Выкатка».
- [ ] Нет отладочного кода, закомментированных блоков, ИИ-шных комментариев, посторонних изменений вне задачи.
- [ ] `rules-log.md` заполнен; результат (`result.md`) с ветками/коммитами по регламенту — готов к подтверждению пользователя.

## Правила для всех ролей

- Перед работой — `core/principles.md` и правила своего стека.
- Пробел или спор — стоп на этом месте и обсуждение (`core/principles.md`, «Пробелы и споры»), случай и решение — в `rules-log.md`; в правила — после разбора лога. В авто-режиме `/dev`: на разведке — в общий список вопросов; по ходу работы — по политике новых вопросов (см. выше).
- Вопросы пользователю — обычным текстом: что не ясно, 2–3 варианта, рекомендация. Не опросником с кнопками.
- Действия с БД и коммиты/пуш — только по явному «да» на каждое (`core/principles.md`).

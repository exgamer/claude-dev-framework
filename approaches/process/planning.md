# Планирование и параллельная работа

Архитектор раскладывает задачу так, чтобы независимые части делались одновременно несколькими разработчиками (субагентами), а зависимые — по порядку. Вторая цель — **маленькие задачи**: каждый разработчик — свежий контекст, и задача должна в него помещаться вместе с правилами (~35k токенов на правила, `role-chain.md`, «Контекст ролей»); иначе при сжатии первыми теряются детали правил.

## Как резать

- Задача плана = законченный кусок, который можно проверить отдельно. **Законченный** = собирается, свои unit-тесты зелёные, закрывает названные в плане R*/AC*/кейсы `qa.md`. Работающая целиком фича — результат сборки (регистрация) и QA, не каждой задачи.
- Для каждой задачи в `plan.md`: id, что сделать, **файлы/директории, которые она трогает**, **контекст** (какие разделы `design.md` и какие файлы правил сверх базы стека ей нужны; меры безопасности задачи — `threats: Th…`, вписывает безопасник, `skills/dev-security/SKILL.md`, Шаг 2a), от каких задач зависит, критерий готовности (какие AC*/кейсы `qa.md` закрывает), **статус** (`ожидает` / `в работе` / `готово` / `отложено`) — обновляется по ходу, чтобы работу можно было продолжить в новой сессии.
- Сначала — минимальный рабочий срез с точками расширения; остальное — в раздел «Отложено», явно, чтобы не потерялось.

## Размер задачи

Каждая задача плана сверяется с пределом:
- один модуль одного домена;
- не больше двух соседних слоёв (сервис + валидатор; контроллер + requests/responses);
- ориентир — до 8–10 создаваемых/изменяемых файлов без тестов;
- отдельная сложность (транзакции с блокировкой, конкурентность, внешняя интеграция, перенос легаси) — отдельной задачей.

В пределе — одна задача, как есть: маленькая фича и не режется. Больше предела — режется **по слоям** (схема ниже). Предел — ориентир: задачу из 12 однотипных файлов одного слоя (DTO, enum) можно не резать, причину — одной строкой в `plan.md`.

Предел проверяется и по факту: разработчик, которому на задачу понадобилось больше ~120 шагов (вызовов инструментов), не дотягивает её — доделывает законченную часть (собирается, свои тесты зелёные) и возвращает предложение разреза остатка (`subagent.md`). Почему: каждый шаг заново читает весь накопленный контекст, стоимость агента растёт быстрее числа шагов — на mobile-api-rewrite агенты со 100+ шагами (23% запусков) дали две трети расхода токенов (`usage.md`).

Мельче «модуль × слой» не резать: у каждого агента ~35k токенов правил на старте, экономия на задаче съедается повторной загрузкой.

## Волны

```
Волна 0  (один исполнитель): контракты — миграции, сущности, DTO, enum, интерфейсы репозиториев
         (+ заглушки для unit-тестов), в PHP — интерфейсы сервисов; общие хелперы; каркас нового сервиса
Волна 1  (параллельно): реализации, которые опираются только на контракты волны 0 —
         репозитории (Infrastructure) ∥ сервисы и Command домена (на заглушках репозиториев);
         в PHP — и workflow/точки входа, которые вызывают только сервисы через ServiceInterface
Волна 2  (параллельно): то, что вызывает конкретные типы волны 1 — workflow и точки входа в Go;
         в PHP — точки входа, которые вызывают Workflow/Command (у них нет интерфейса)
Волна 3  (один исполнитель): регистрация — bootstrap/фабрики/провайдеры/definitions, маршруты
Волна 4  (последовательно): QA — интеграционные/e2e тесты по qa.md и регрессия по связям
Волна 5  (последовательно): независимое ревью кода и тестов ⇄ исправления (до 3 кругов)
```

Маленькая фича проходит те же волны, но её задача в пределе может закрыть несколько слоёв сразу; пустые волны пропускаются. Слои, где кода мало (workflow — тонкая обёртка над одним Command), объединяются в одну задачу.

Почему так: задача «модуль × слой» грузит правила только своего слоя (`go-sdk/infra/*`, `domain.md`, `workflow.md`, `entrypoint/*` / их аналоги в PHP), её файлы — отдельная директория и сами не пересекаются с соседними, а слои пишутся параллельно, потому что опираются на скомпилированные контракты волны 0, а не друг на друга. В Go сервис домена — конкретный тип без интерфейса (эталон `stacks/go/examples/tariff/`), поэтому workflow и обработчики ждут домен (волна 2); в PHP у сервиса есть `ServiceInterface` (`regulations/contracts.md`), и вызывающий его код идёт в волне 1. Тесты при этом — по `regulations/contracts.md`, «Моки в тестах»: в Go workflow тестируется на настоящих сервисах с фейками репозиториев (поэтому и ждёт домен), в PHP сервис мокается только в тестах workflow/Command; у точки входа unit-тестов обычно нет — её «законченность» = сборка/статанализ, сценарий через HTTP проверяет QA.

Волну 0 можно разделить по модулям (0a, 0b…), если контрактов много и файлы не пересекаются. Режимы `refactor`/`migrate` — всегда по слоям; первая задача волны 0 — характеризующие тесты (`legacy-refactor.md`, п. 2). Задача, в которой в проекте впервые появляется `Common`, — в волне 0 ещё и тест его границ (`testing.md`, «Архитектурный тест границ `Common`»).

Тест-кейсы (`qa.md`) пишутся до волны 0 — это разведка (`role-chain.md`, Фаза 1), не задача плана. Ревью идёт после QA, потому что проверяет и тесты; параллельно их не ставить.

Две задачи могут идти одновременно, только если:
- их **множества файлов не пересекаются** (включая общие: `app.go`, `definitions.php`, `routes.php`, `composer.json`, `go.mod`, файлы миграций с одинаковой датой, общая база тестов);
- ни одна не читает результат другой;
- контракты, на которые они опираются, уже готовы (волна 0).

Правки общих файлов регистрации (`app.go`, `*_factory.go`, `ServiceProvider.php`, `definitions.php`, `routes.php`) собираются в одну задачу волны 3, а не размазываются по параллельным.

## Контракты слоёв

Когда план режется по слоям, `design.md` обязательно содержит раздел **«Контракты слоёв»**: по каждому модулю — методы интерфейса репозитория (имя, параметры, фильтры, сортировка, что возвращает), методы сервиса/Command (вход/выход DTO, ошибки), DTO между слоями. Волна 0 переносит это в код как есть; нижний слой не добавляет методов «на всякий случай», верхний не придумывает недостающие. Не хватает метода в контракте — вопрос оркестратору (`subagent.md`), а не правка чужого слоя.

## Команда

- **Не больше 3 разработчиков одновременно** (+ 1 QA на волне 4 и 1 ревьюер на волне 5); **в режимах `refactor`/`migrate` — до 5**, если нарезка «модуль × слой» без пересечений файлов (замер mobile-api-rewrite, волны 7–8: 5 исполнителей в одном дереве без конфликтов, решение пользователя 2026-10-15). Задач больше — ждут свободного места или следующей волны; **не объединяются ради лимита** (объединять можно только правки в пару строк одного слоя). Почему 3: одно рабочее дерево, нарезка без пересечений, контекст оркестратора с итогами агентов, расход квоты; последовательные волны всё равно ограничивают выигрыш (решение 2026-10-07, `core/decisions-log.md`). Поднимать — по замеру времени ожидания на реальных фичах.
- **Запуск по готовности, а не по волне.** Задача стартует, как только готовы все её зависимости из `plan.md`, — не ждёт конца всей волны (лимит одновременных исполнителей сохраняется). Номер волны — порядок для чтения плана, а не барьер; барьеры — только волна 3 (регистрация: ждёт все задачи реализации) и волны 4–5.
- **Каждая задача — свежий агент.** Продолжать закончившегося агента (`SendMessage`) новой задачей или правками ревью нельзя: он тянет весь прошлый контекст, и каждый его шаг стоит 150–400 тыс. токенов против ~35 тыс. правил у свежего; всё нужное свежему агенту — в артефактах. Исключение — доводка в 1–3 шага того же агента сразу после его итога (комментарий, строка документа, ответ на уточнение) — не позже 5 минут после итога: кэш агента живёт 5 минут, после паузы продолжение записывает весь его контекст заново по цене записи (замер D-3, 2026-10-22: 28–48% записи кэша агентов — такие перезаписи); позже — свежий агент с точным поручением (файл, строка, что сделать); в `/dev-fix` — ещё продолжение разработчика после «ок» на причину и при одном возврате к тесту (`bugfix.md`, «Тот же разработчик»).
- Каждый параллельный разработчик — субагент, получает: задачу из `plan.md`, `design.md` (читает разделы из колонки «контекст» и «Контракты слоёв»), список правил стека и **список файлов, за которые он отвечает** (за пределы не выходит).
- Параллельные разработчики работают **в одном рабочем дереве**, не в `git worktree`: коммит — только с «да» пользователя на каждый коммит (`core/principles.md`, «Git»), обычно в конце задачи; характеризующие тесты до правок — отдельным коммитом тоже только по «да», иначе хэшем в `plan.md` (`legacy-refactor.md`, «Порядок», п. 2), поэтому worktree от ветки не увидел бы незакоммиченные предыдущие волны. Отсюда правила: файлы задач не пересекаются, общие файлы (база тестов, регистрация) не трогаются параллельными задачами, каждый гоняет только свой тест (AINA-2744).
- **Проверка после каждой задачи** (оркестратор, без коммитов): файлы задачи — только из её списка (`git status`), сборка и тесты **её пакетов/её тестов** (полная сборка дерева, пока работают другие агенты, может упасть на их недописанных файлах). **Полный прогон** сборки/линтера/всех тестов — когда никто не работает: перед регистрацией (волна 3) и после неё. Красное — чинить до задач, которые от этого зависят.
- Пробел или спор, найденный субагентом, — по политике новых вопросов из поручения (`subagent.md`): (а) решение по рекомендации и строка для `rules-log.md`, (б) затронутый кусок откладывается и вопрос возвращается оркестратору; согласования до кода и изменение внешнего контракта — всегда откладываются. Так же — задача по факту больше предела: разработчик не дотягивает её, а возвращает предложение разреза (`subagent.md`).

## Формат `design.md`

Состав и содержание разделов — `skills/dev-architect/SKILL.md`, Шаг 3. Заголовки — **дословно** как ниже: роли читают `design.md` по именам разделов (колонка «контекст» `plan.md`, ссылки в skills и агентах), заголовок, написанный иначе, не найдётся. Раздел, не нужный задаче, не пишется; «Конкурентность» — всегда (хотя бы «конкурентных мест нет»).

```markdown
# Дизайн — <ключ>

## Что и зачем            — цель и критерии приёмки (ссылки на AC*)
## Связи                  — карта связей (`impact-analysis.md`)
## Домены и слои          — модули, слой каждой части, нужен ли workflow
## API                    — метод, URL, запрос, ответ, коды ошибок
## Данные                 — сущности, миграции, индексы, кэш, очереди/outbox
## Схема БД               — таблица по `regulations/technical-approval.md`, «Схема БД»
## Границы транзакций
## Конкурентность
## Производительность
## Требует согласования   — `regulations/technical-approval.md`
## Выкатка и эксплуатация
## Чувствительные зоны
## SDK                    — Go
## Список                 — PHP, новый пагинируемый список
## Новый сервис
## Контракты              — изменённые контракты и ответ о совместимости (O-29); `refactor` / `migrate` — инвентаризация
## Контракты слоёв        — план режется по слоям
## Открытые вопросы
```

В колонке «контекст» `plan.md` и в ссылках — те же имена (`design: Границы транзакций`, не `design: Транзакции`).

# Планирование и параллельная работа

Архитектор раскладывает задачу так, чтобы независимые части делались одновременно несколькими разработчиками (субагентами), а зависимые — по порядку.

## Как резать

- Задача плана = законченный вертикальный кусок, который можно проверить отдельно (модуль целиком; эндпойнт; миграция + репозиторий; workflow).
- Для каждой задачи в `plan.md`: id, что сделать, **файлы/директории, которые она трогает**, от каких задач зависит, критерий готовности.
- Сначала — минимальный рабочий срез с точками расширения; остальное — в раздел «Отложено», явно, чтобы не потерялось.

## Волны

```
Волна 0  (последовательно, один исполнитель): общее, от чего зависят все — миграции, интерфейсы/контракты, DTO, enum, общие хелперы
Волна 1  (параллельно): независимые модули/эндпойнты/инфра-реализации поверх контрактов волны 0
Волна 2  (последовательно): сборка — bootstrap/провайдеры/definitions, маршруты, workflow поверх модулей волны 1
Волна 3  (параллельно): ревью + QA
```

Две задачи можно ставить в одну волну, только если:
- их **множества файлов не пересекаются** (включая общие: `app.go`, `definitions.php`, `routes.php`, `composer.json`, `go.mod`, файлы миграций с одинаковой датой);
- ни одна не читает результат другой;
- контракты, на которые они опираются, уже готовы (волна 0).

Правки общих файлов регистрации (`app.go`, `*_factory.go`, `ServiceProvider.php`, `definitions.php`, `routes.php`) собираются в одну задачу последовательной волны, а не размазываются по параллельным.

## Команда

- **Не больше 3 разработчиков одновременно** (+ 1 ревьюер и 1 QA на волне 3). Если параллельных задач больше — объединить мелкие или разбить на несколько волн. Больше людей = больше конфликтов и дороже, выигрыш падает.
- Параллелить имеет смысл, когда в волне ≥2 задачи заметного объёма. Мелочь (1–3 файла) — делает один исполнитель последовательно.
- Каждый параллельный разработчик — субагент в своей изоляции (`git worktree`), получает: задачу из `plan.md`, `design.md`, список правил стека и **список файлов, за которые он отвечает** (за пределы не выходит).
- После волны — оркестратор сводит изменения, прогоняет сборку/линтер/тесты стека и только потом запускает следующую волну.
- Пробел или спор, найденный субагентом, — не решается им самим: он останавливает свою задачу и возвращает вопрос оркестратору, тот выносит его пользователю.

## Пример `plan.md`

```markdown
| id | задача | файлы | зависит от | волна |
|----|--------|-------|-----------|-------|
| T1 | миграция tariffs + модель + RepositoryInterface + DTO | Infrastructure/Postgres/Billing/..., Domains/Billing/Modules/Tariffs/{DTO,Repositories} | — | 0 |
| T2 | TariffCrudService + валидатор | Domains/Billing/Modules/Tariffs/{Services,Validators} | T1 | 1 |
| T3 | Admin HTTP: контроллер, requests, responses | Entrypoints/Admin/Billing/Tariffs/** | T1 | 1 |
| T4 | definitions.php + routes.php + CreateTariffCommand | Domains/Billing/definitions.php, Infrastructure/.../definitions.php, Entrypoints/Admin/Billing/routes.php, Workflows/Billing/Tariffs/** | T2, T3 | 2 |
| T5 | ревью + тест-кейсы | — | T4 | 3 |

Отложено: планирование тарифа по дате (scheduled_at) — отдельной задачей.
```

# Перенос с одного стека на другой

Например, модуль из Laravel (`parking_app`) в Go-сервис на Go SDK (`parking-session-service`), или обратно.

## Порядок

1. **Спека поведения и карта связей исходника** (`impact-analysis.md`: кто вызывает, кто слушает, кто читает данные — всё это переезжает или сохраняется) (`/dev-architect`, режим migrate): эндпойнты (URL, методы, запрос/ответ, коды ошибок), события и очереди, схема БД, крон/консоль, бизнес-правила и валидации (из сервисов, валидаторов, FormRequest), интеграции. Это и есть `design.md`. Читать код, а не документацию — документация бывает устаревшей.
2. **Маппинг на целевой стек** по таблице «Go SDK ↔ mps/core» (`stacks/php/structure.md`): какой класс во что превращается. Всё, что в таблицу не ложится (своя магия Laravel, трейт, middleware с побочной логикой), — открытый вопрос к пользователю.
3. **Структура — по правилам целевого стека**, не копией исходного. Перенос — повод не тащить нарушения: в `design.md` отдельный список «в исходнике нарушает правила, в новом делаем по правилам».
4. **Контракты — по ответу пользователя** (раздел «Контракты» в `legacy-refactor.md`: инвентаризация + обязательный вопрос «сохранить контракт / по правилам», O-19). (а) — те же URL, формат ответа и события на новом сервисе; (б) — контракт по правилам целевого стека новой версией (`/v2`), старая версия работает в исходнике до отключения. Схема БД для внешних читателей — совместимая. Расхождения форматов ядер (обёртка ответа `ApiResponseMiddleware` vs `response.*` Go SDK, формат ошибок, пагинация) — выписать и решить с пользователем до кода.
5. **Тесты-эталоны:** характеризующие тесты на контракт исходника; при (а) — те же сценарии на новый сервис, при (б) — тесты новой версии по критериям приёмки, исходник остаётся под своими тестами.
6. **Без переключателей** (`legacy-refactor.md`, «Контракт: сохранить или по правилам», O-19): ни флагов, ни shadow/dual-write, ни процента трафика. (а) — маршрут переводится на новый сервис целиком одним деплоем; (б) — потребители переходят на новую версию сами. Старый код удаляется отдельной задачей, когда на него не осталось вызовов.

## Правила

- Не переносить построчно. Переносится поведение, а форма — по правилам целевого стека.
- Бизнес-правила переносятся полностью; каждое — с указанием, откуда взято (файл:метод исходника) в `design.md`.
- Планирование и параллелизм — как обычно (`planning.md`): модули с готовыми контрактами переносятся параллельно.

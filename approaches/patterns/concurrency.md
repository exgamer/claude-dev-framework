# Конкурентность: data race и race condition

Два разных класса ошибок:
- **Data race** — два потока одного процесса одновременно обращаются к одной памяти, хотя бы один пишет. В основном Go (горутины); в PHP — только общее состояние между запросами под Octane.
- **Race condition** — логическая гонка: результат зависит от порядка операций **разных** запросов, инстансов, воркеров, крона. Касается обоих стеков: двойное погашение, потерянное обновление, двойная обработка сообщения, два одновременных запуска крона.

Учитываются **при необходимости**: архитектор в `design.md` (раздел «Конкурентность») отмечает, где в задаче есть одновременность, — для этих мест правила ниже обязательны. Нет одновременности — одна строка «конкурентных мест нет: …».

---

## Где искать одновременность

| Признак в задаче | Типичная гонка |
|---|---|
| Счётчик, лимит, остаток, баланс («не больше N раз», «списать») | превышение лимита, отрицательный остаток |
| Проверка уникальности перед вставкой («код уникален», «одна активная запись») | два одинаковых при параллельных запросах |
| Смена статуса («оплачен → возврат», «активен → отключён») | двойной переход, переход из неверного статуса |
| Повторная доставка: вебхуки, колбэки, сообщения очереди, ретраи клиента | двойная обработка |
| Чтение — изменение — запись одной сущности из двух мест (админка + фон) | потерянное обновление |
| Проверка состояния связанной записи до транзакции («парковка активна», «не удалена мягко») | запись создана под связанной записью, которую параллельно деактивировали/удалили |
| Крон/консоль, несколько инстансов сервиса | два одновременных прогона |
| Outbox / очередь задач с несколькими воркерами | одну запись берут двое |
| Кэш горячего ключа | одновременный промах → лавина запросов в БД (stampede) |
| Горутины, фоновые воркеры, общие map/слайсы/поля (Go) | data race |

## Race condition — решения (от простого к сложному)

| Ситуация | Решение | Тег при нарушении |
|---|---|---|
| Счётчик/лимит | атомарный `UPDATE … SET used = used + 1 WHERE id = ? AND used < limit` + проверка числа затронутых строк; не «прочитать — проверить в коде — записать» | `race-on-counter` |
| Уникальность | **уникальный индекс** в БД + обработка ошибки нарушения как бизнес-ошибки; проверка в коде — только для понятного сообщения, не как защита | `race-on-uniqueness` |
| Смена статуса | условный апдейт `UPDATE … SET status = :new WHERE id = ? AND status = :expected` (0 строк — уже изменено) или `SELECT … FOR UPDATE` в транзакции | `race-on-status` |
| Состояние связанной записи (активна ли, не удалена ли) | внешний ключ закрывает только существование, не состояние. Проверка — до транзакции; гонка между проверкой и записью — решение в «Конкурентность» `design.md`, одно из двух: **(а) принять** — с указанием, чем закрывается последствие (например, consumer события деактивации снимает связанные записи, сверка по крону), или **(б) `SELECT … FOR SHARE`** на связанную запись внутри транзакции записи. Вариант (а) — **всегда вопрос пользователю** (ниже, «Принятие риска») | `race-on-related-state` |
| Повторная доставка | **идемпотентность**: ключ (внешний ID события, `order_id`) + уникальный индекс; повтор возвращает прежний результат (`idempotency.md`) | `missing-idempotency` |
| Конкурентное редактирование | оптимистическая блокировка: колонка `version`, `UPDATE … WHERE id = ? AND version = :v` → 0 строк = конфликт (409) | `lost-update` |
| Несколько воркеров на одну очередь записей (outbox, задачи) | `SELECT … FOR UPDATE SKIP LOCKED` с лимитом пачки; статус «в обработке» с таймаутом возврата | `double-processing` |
| Крон на нескольких инстансах | блокировка запуска: Laravel `withoutOverlapping()` / `onOneServer()`; Go — advisory lock Postgres (`pg_try_advisory_lock`) или Redis `SET key token NX PX ttl` с проверкой токена при снятии | `cron-overlap` |
| Распределённая блокировка вокруг операции | только если всё выше не подходит; Redis `SET NX PX` с уникальным токеном и TTL больше времени операции, снятие — только своим токеном; Laravel — `Cache::lock()->block()` | `unsafe-distributed-lock` |
| Stampede кэша | короткая блокировка на перезаполнение ключа или отдача устаревшего значения на время перезаполнения — только для действительно горячих ключей | `cache-stampede` |

Порядок предпочтения: **ограничение БД (уникальный индекс, условный UPDATE) → транзакция с `FOR UPDATE` → оптимистическая версия → распределённая блокировка**. Блокировка в памяти процесса (mutex) от гонок между запросами/инстансами **не защищает** — `in-process-lock-for-distributed`.

### Принятие риска

«Гонка допустима, принимаем» — решение не архитектора и не разработчика: архитектор выносит его в «Открытые вопросы» `design.md` с вариантами (принять — чем закрывается последствие / защитить — чем) и рекомендацией, решает пользователь. Пока ответа нет — место считается незакрытым. Комментарий «принятый риск» в эталоне — решение «Конкурентность» эталона, не разрешение принимать риск в задаче без вопроса. Принятый без ответа пользователя риск на ревью — тег `race-risk-accepted-silently`.

Внутри транзакции с блокировкой — только короткая работа: никаких внешних вызовов (держат блокировку), `transactions.md`.

## Data race — Go

| Правило | Тег |
|---|---|
| Общая изменяемая память между горутинами (map, слайс, поле структуры, счётчик) — под `sync.Mutex`/`RWMutex`, через `sync/atomic` или владение одной горутиной с передачей через канал; обычная `map` при конкурентной записи — паника | `data-race` |
| Переменная цикла и замыкание в горутине: передавать значение параметром, не захватывать изменяемую переменную (до Go 1.22 — обязательно) | `goroutine-loop-capture` |
| Структуры, разделяемые между запросами (сервисы, репозитории, кэши в памяти), — без изменяемого состояния после конструктора; состояние запроса — в параметрах и `ctx` | `shared-mutable-state` |
| Горутина: кто ждёт (`sync.WaitGroup`/`errgroup`), как останавливается (`ctx`), куда уходят ошибка и паника (`errorreporter`, не только лог); работа, которая переживает запрос, — на `context.WithoutCancel(ctx)`; ограничение параллелизма. Побочный эффект после записи, который должен дойти, — outbox, не горутина (`outbox.md`) | `unbounded-goroutines` |
| Канал: кто закрывает (только отправитель, один раз), нет отправки в закрытый, нет вечной блокировки без `ctx.Done()` | `channel-misuse` |
| Тесты пакета с горутинами/общим состоянием — `go test -race ./...`; гонка, найденная детектором, — `data-race` | `data-race` |

## Data race — PHP

PHP-FPM — изоляция запросов, data race нет. Под **Octane/Swoole** (долгоживущий воркер): никакого статического/синглтон-состояния, зависящего от запроса (`LogContext::clear()` в middleware, без `static` кэшей с данными пользователя) — `octane-state-leak`.

## Кто и как

| Роль | Что делает |
|---|---|
| Аналитик | сценарии «одновременно» и «повтор» в `requirements.md` (S*.a): два покупателя, два клика, повторный колбэк |
| Архитектор | раздел «Конкурентность» в `design.md`: места одновременности из таблицы выше и выбранное решение для каждого; «принять риск» — только вопросом пользователю в «Открытые вопросы» («Принятие риска») |
| Безопасник | гонки на деньгах/лимитах/статусах — угрозы в `threats.md` (двойное списание, обход лимита) |
| Разработчик | реализует выбранные решения; Go-код с горутинами/общим состоянием — `go test -race` |
| QA | для каждого конкурентного места — тест с параллельными запросами/повторной доставкой (интеграционный, на реальной БД) |
| Ревью | по таблицам выше, теги оттуда; уровни — каталоги тегов (`approaches/process/review-tags.md`, Go — `stacks/go/review-tags.md`, PHP — `stacks/php/review-tags.md`) |

# Производительность: код и запросы

Не оптимизировать «на всякий случай», но и **не писать заведомо медленное**. Горячие пути и объёмы — из `requirements.md` («Нефункциональное»); бюджеты для них — в `design.md`. Нарушения ниже — находки ревью с тегами (колонка «Тег»).

---

## Горячие пути и бюджеты

- Аналитик фиксирует в `requirements.md`: какие операции частые/массовые (проверка промокода при каждом заказе, список на главной), ожидаемые объёмы (строк в таблицах, запросов в секунду, размер выгрузок) и допустимое время ответа, если оно задано бизнесом.
- Архитектор в `design.md` для горячих путей: сколько запросов к БД/внешним системам на операцию, какие индексы, что кэшируется, что уходит в асинхрон.
- Нет данных об объёмах — это вопрос, а не «сделаем как получится».

## База данных

| Правило | Тег |
|---|---|
| **Нет N+1**: связанные данные — одним запросом по набору id (`WHERE id IN (…)`), а не запросом в цикле | `n-plus-one-query` |
| Каждый запрос списка — с **пагинацией** и верхней границей `per_page` (≤ 100); выборка «всего» без лимита — только для заведомо маленьких справочников | `unbounded-query` |
| **Индекс под запрос**: фильтры, сортировки, JOIN, внешние ключи, условия уникальности — индекс в той же миграции, что и запрос; составной — в порядке селективности и условий | `missing-index` |
| Новый тяжёлый запрос (JOIN нескольких таблиц, агрегат, полнотекст, большой `IN`) — проверен `EXPLAIN` на реалистичных данных; seq scan по большой таблице — находка | `query-not-explained` |
| Агрегаты, фильтры, сортировки — в БД, а не загрузкой всего в память | `aggregation-in-memory` |
| Только нужные колонки для больших таблиц и списков (`SELECT *` с тяжёлыми JSON/text-полями в списке — нет) | `select-heavy-columns` |
| Массовые операции — батчами (`chunk`/`cursor`/`LIMIT … OFFSET`→keyset), вставка/обновление пачкой (`upsert`, batch insert), не по одной строке в цикле | `bulk-operation-not-chunked` |
| `COUNT(*)` по большой таблице на каждый запрос списка — осознанно (кэш, приблизительный счётчик, keyset без общего числа) | `expensive-count` |
| Глубокая пагинация (`OFFSET` десятков тысяч) на частом эндпойнте — keyset (`WHERE id < :last ORDER BY id DESC LIMIT n`) | `deep-offset-pagination` |
| Каждый запрос — с **таймаутом** (Go: `context.WithTimeout`, 10s по умолчанию; PHP — таймауты соединения/запроса в конфиге) | `query-without-timeout` |
| **Транзакция короткая**: без внешних HTTP, публикаций, файлов, `sleep` внутри (`transactions.md`) | `long-transaction` |
| Конкурентные счётчики, уникальность, статусы, повторы — по `concurrency.md` | `race-on-counter` и др. |

## Кэш

| Правило | Тег |
|---|---|
| Горячее чтение — cache-aside по `cache.md`; кэш **только с инвалидацией** при записи и TTL | `cache-without-invalidation` |
| Ключ — с префиксом сервиса и всеми параметрами, от которых зависит значение (магазин, язык, версия формата) | `cache-key-incomplete` |
| Ошибки внешней системы не кэшируются; «не найдено» кэшируется только осознанно и с коротким TTL | `cache-stores-errors` |
| Кэш не заменяет индекс: медленный запрос сначала чинится в БД | — |

## Внешние вызовы и асинхронность

| Правило | Тег |
|---|---|
| Внешний вызов в цикле по одному — батч-метод API или параллельно с ограничением (Go: ограниченный пул горутин; PHP: `HttpConcurrentBuilder` / `ConcurrentRequestManager`) | `external-call-in-loop` |
| Каждый внешний вызов — с таймаутом; ретраи только для идемпотентных и только временных ошибок (`idempotency.md`) | `external-call-without-timeout` |
| Тяжёлое (выгрузка, массовая рассылка, пересчёт) не выполняется синхронно в HTTP-запросе — очередь/фоновая задача, ответ сразу | `heavy-sync-in-request` |
| Consumer: `prefetch` по нагрузке, обработка пачкой там, где возможно, идемпотентно | `consumer-unbounded` |

## Память и CPU

| Правило | Тег |
|---|---|
| Большие выборки и файлы — потоком/по частям, не целиком в память (экспорт, импорт, отчёты) | `load-all-into-memory` |
| Повторная тяжёлая работа в цикле (парсинг, регулярка, запрос конфига, рефлексия) — вынести из цикла / посчитать один раз | `repeated-work-in-loop` |
| Состояние в памяти процесса как кэш/счётчик — ломается при 2+ инстансах и утекает (Octane) | `in-memory-state-not-shared` |
| Логирование больших payload в горячем пути — нет (и это ещё риск ПДн) | `heavy-logging-hot-path` |

## Go

- Слайсы известного размера — `make([]T, 0, n)`; строки в цикле — `strings.Builder`.
- Большие структуры — по указателю; не копировать в `range` по значению, если они тяжёлые.
- Горутины — только с ограничением параллелизма (пул/семафор) и отменой по `ctx`; неограниченный `go` в цикле по входным данным — `unbounded-goroutines`.
- Пагинация — `NewGormPaginatedHelper` (SDK), медленные запросы — `SlowSqlSentryMiddleware` (`go-sdk/capabilities.md`).
- Горячий путь под нагрузкой — бенчмарк (`go test -bench`) или профиль (`pprof`), если есть сомнение.

## PHP (Laravel + mps/core)

- Связанные данные — **через репозитории пачкой** (`whereIn` по id), Eloquent-связей и eager loading нет (`stacks/php/conventions.md`).
- Большие выборки — `chunk()` / `chunkById()` / `cursor()` / `lazy()`; не `->get()->toArray()` по большой таблице.
- Фильтры — `QueryFilters\V2`; пагинация — `PaginatedQueryHelper`; медленные запросы — `SlowQueryDetector` (`mps-core/capabilities.md`).
- Octane: никакого статического/синглтон-состояния между запросами (`LogContext::clear()` и т.п.).
- Локально для поиска N+1 и тяжёлых запросов — Debugbar/Telescope.

## Как проверять

- Разработчик: самопроверка — пункты выше по своему коду; для новых тяжёлых запросов — `EXPLAIN`.
- Ревью: по таблицам выше; находка — [ОШИБКА] (N+1, отсутствие пагинации/индекса/таймаута, гонка счётчика, тяжёлое в запросе) или [ВНИМАНИЕ] (остальное).
- QA: для горячих путей с бюджетом — проверка на объёме данных, близком к реальному; нагрузочный тест — если требование есть в `requirements.md`.
